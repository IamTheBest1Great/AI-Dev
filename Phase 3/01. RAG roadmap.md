## Course Overview

This curriculum takes a learner from core RAG concepts through the architecture patterns that define production systems in 2026: contextual retrieval, hybrid search, GraphRAG, agentic RAG with tool-using agents, agentic memory, multimodal retrieval, and evaluation/observability at scale. It closes with a deployable capstone.

**What changed since the last edition:** RAG did not die in the face of long-context models — it specialized. Chunking got smarter (late chunking, contextual retrieval), hybrid retrieval became the industry default rather than an advanced technique, GraphRAG moved from research curiosity to a standard tool for multi-hop questions, agents now call retrieval as one tool among many (often via MCP), and a parallel discipline — agentic/long-term memory — emerged alongside RAG rather than replacing it. Evaluation also matured from a single "faithfulness score" into multi-layer, trajectory-aware observability.

- **1.1.1 What is RAG and the Problems It Solves**

- **1.1.2 Core Components**
  - Knowledge Base → Retriever → Generator
- **1.1.3 RAG Data Flow**
  - End-to-end flow from user query through retrieval to generation

### 1.2 RAG vs Fine-Tuning vs Prompt Engineering vs Long Context
- Comparison matrix: cost, latency, accuracy, maintenance
- **New: RAG vs. long-context models.** Frontier models now accept 200K–2M+ tokens, which sparked "RAG is dead" claims in 2025–2026. In practice, cost and latency scale with context length, and independent research (e.g., Chroma's "context rot" study) shows retrieval quality degrades as context grows — even in models built for long windows. The 2026 consensus: use chunked retrieval to control cost/latency/faithfulness, and treat long context as a fallback for hard queries or corpora under roughly 200K tokens rather than a universal replacement.
- Decision framework: when to use each approach, and when to combine them

## Module 2: Document Processing and Chunking

### 2.1 Document Loaders in LangChain
- PDF loaders: `PyPDFLoader`, `PDFMiner`, `PDFPlumber`, `Unstructured`
- Web loaders: `WebBaseLoader`, `RecursiveUrlLoader`
- Structured data: CSV, JSON
- Text documents: `TextLoader`
- **Hands-on:** Load documents from 5 different sources

### 2.2 Text Splitting Strategies
- `RecursiveCharacterTextSplitter` (still the strongest default — benchmarks put recursive 512-token splitting near the top of end-to-end accuracy comparisons)
- `CharacterTextSplitter` and `TokenTextSplitter`
- Semantic chunking with `SemanticChunker` (breakpoint thresholds: percentile, standard_deviation, gradient) — strong on precision, but can over-fragment (sub-50-token chunks) if thresholds are too aggressive
- `MarkdownTextSplitter` for structured documents
- Code splitters for Python, JavaScript, etc.
- LLM-based text splitting and agentic/context-aware partitioning
- **New: Late Chunking.** Embed the *entire document* first with a long-context embedding model to capture global context, then pool token-level embeddings into chunk vectors. Preserves cross-chunk relationships that naive splitting destroys; most effective on long, cohesive documents; requires a long-context embedding model.
- **New: Contextual Retrieval (Anthropic).** Before embedding, prepend a short (50–100 token) LLM-generated description of where a chunk sits in the document. Reported to cut top-20 retrieval failures substantially when combined with BM25 and reranking — one of the most widely adopted 2026 techniques because it's a preprocessing step, not an architecture change.
- **Hands-on:** Compare recursive, semantic, and late-chunking strategies on the same document; measure recall@k and MRR

### 2.3 Chunking Best Practices
- Optimal chunk sizes by use case (starting points, always validate on your own corpus):
  - Factoid / short Q&A: 128–256 tokens
  - General RAG: 256–512 tokens (512 tokens is the most common production default in 2026)
  - Complex analysis / legal / technical: 512–1024 tokens
- Overlap strategies: 10–20% is the traditional rule of thumb, but recent studies (Jan 2026, SPLADE + sparse retrieval) found **no measurable benefit from overlap in some hybrid setups** — treat overlap as a tunable, not a given
- The "context cliff": research identifies a quality drop-off around ~2,500 tokens of retrieved context regardless of model size — a reason to keep chunks tight and rely on reranking rather than dumping large context windows
- How chunk size affects retrieval quality; chunking can swing recall by up to ~9 points on identical corpora depending on strategy alone
- Handling tables and structured data; preserving context across chunks
- **Lab:** Optimize chunking for a PDF technical document; A/B test contextual retrieval vs. plain chunking

### 2.4 Metadata Management
- Adding metadata to documents; metadata filtering in retrieval
- Source tracking and document lineage; document versioning strategies
- **Hands-on:** Build a metadata-enriched document pipeline

## Module 3: Embeddings and Vector Representations

### 3.1 How Embeddings Work
- Vector representations of text; semantic similarity in embedding space
- Distance metrics: cosine similarity, Euclidean, dot product
- Embedding dimensions and trade-offs; Matryoshka Representation Learning (MRL) for adjustable dimensions

### 3.2 The 2026 Embedding Model Landscape
- **Closed/API models**
  - `Gemini Embedding 2` (Google) — natively multimodal (text, image, video, audio, PDF), 100+ languages, MRL down to 256 dims, current multilingual MTEB leader
  - `voyage-3-large` / `voyage-4` family (Voyage AI) — strong English retrieval, long-context variants
  - `Cohere embed-v4` — multimodal, handles up to 128K tokens without chunking, strong for visual documents (PDFs, catalogs, slides)
  - `text-embedding-3-small` / `text-embedding-3-large` (OpenAI) — still reasonable defaults but no longer state-of-the-art
- **Open-weight models**
  - `Qwen3-Embedding` family (0.6B–8B) — Apache 2.0, the 8B variant now outperforms several API models on MTEB; strong multilingual support
  - `BGE-M3` — dense + sparse + multi-vector retrieval from one model; underrated pragmatic choice for hybrid search
  - `Jina v5-omni` — universal embeddings spanning text, image, video, and audio
  - Domain-specialized embeddings (legal, medical, finance, code) reliably outperform generic models by 10–15% in-domain
- **Decision framework:** accuracy needs, language support, cost, latency, multimodal requirements, self-hosting vs. managed API. Public MTEB scores don't always transfer to your domain — benchmark on your own data before committing.
- **Hands-on:** Compare 3–4 embedding models (one API, one open-weight, one multimodal) on sample queries from your own corpus

### 3.3 Choosing the Right Embedding Model
- MTEB / MMTEB leaderboards and their limitations (benchmark overfitting, English-centric test sets)
- Dimension trade-offs: 256 (MRL-compressed) → 768 → 1536 → 3072
- Cost vs. quality decision framework; self-hosting economics for high-volume pipelines
- **Hands-on:** Build a small internal eval set and re-rank candidate embedding models against it

### 3.4 LangChain Embeddings Implementation
- `Embeddings` class usage; `embed_documents` vs `embed_query`
- Working with multimodal embedding APIs in LangChain

## Module 12: Evaluating and Observing RAG Systems

### 12.1 RAG Evaluation Fundamentals
- Three layers to evaluate separately: retrieval (did the right chunks come back), generation (did the model use them well), end-to-end (was the final answer correct and grounded)
- Key metrics: faithfulness, answer relevance, context precision, context recall, noise sensitivity
- Retrieval-specific metrics: Recall@K, Precision@K, NDCG@K, MRR, Hit Rate

### 12.2 The 2026 Evaluation Toolchain
- **RAGAS** — reference-free, LLM-as-judge claim verification; still the fastest way to get started, but a metrics library with no dashboard or production monitoring
- **DeepEval** — pytest-native, broadest metric library (50+ metrics spanning RAG, agents, multi-turn, MCP tool use, multimodal); fits teams whose stack has grown past a single RAG pipeline
- **TruLens**, **Arize Phoenix**, **LangSmith** — tracing and observability-first tools, useful once a system is in production
- Full-lifecycle platforms (e.g., FutureAGI, Maxim AI) connecting pre-deployment evaluation to production monitoring with shared eval configs
- **Important limitation:** inference-layer eval tools measure whether outputs are grounded in *what was retrieved* — they can't tell you if the retrieved content itself was stale or wrong. A well-governed, freshness-monitored index is a precondition for any of these scores to mean anything.

### 12.3 Agentic and Trajectory Evaluation
- When retrieval is a tool an agent calls (sometimes multiple times with refined queries), evaluation has to score the *retrieval strategy*, not just one retrieve-and-answer step — this blends RAG eval with agent trajectory eval
- Retrieval drift detection: as corpora age and embedding models get updated, retrieval quality drifts — track rolling precision per retrieval route, and gate re-indexing behind eval pass rates
- **Lab:** Build an evaluation dataset with RAGAS, then extend it into a CI/CD quality gate with DeepEval

## What's Actually Used in Production Right Now (Quick Reference)

- **Chunking default:** recursive character splitting, ~512 tokens, contextual retrieval preprocessing layered on top when quality matters more than cost
- **Embeddings:** managed API (Gemini Embedding 2, Voyage, Cohere embed-v4) for teams without GPU infra; Qwen3-Embedding or BGE-M3 for teams that want open-weight/self-hosted
- **Vector store:** pgvector for most teams already on Postgres; Pinecone/Qdrant when you need managed ops or heavy filtering at scale
- **Retrieval architecture:** hybrid (dense + BM25) with a reranking stage — now the consensus default, not an "advanced" option
- **Agent orchestration:** LangGraph, CrewAI, or Microsoft Agent Framework/AutoGen, with retrieval and other tools increasingly exposed via MCP
- **Evaluation:** RAGAS for fast iteration during development, DeepEval or an observability platform (LangSmith/Phoenix) once in production
- **Multi-hop or relationship-heavy domains:** GraphRAG layered on top of vector retrieval rather than replacing it
