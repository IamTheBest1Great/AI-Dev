# M04.1.1.3 — Inference Behavior

This topic is about **what happens when you actually use a trained LLM**.

A useful way to think about it is:

```text
Training
→ model learns its parameters

Inference
→ model uses those learned parameters to answer you
```

Your earlier notes describe inference as the stage where only the prompt is available initially, tokens are generated one by one, and the model uses a KV cache so previous Keys and Values do not need to be recomputed each time. 

---

# 1. Context Window

## What is a context window?

The **context window is the amount of token-based information the model can consider at one time**.

Imagine you are talking to the model:

```text
You:
"Explain Transformers."

Model:
"Sure..."

You:
"What about attention?"

Model needs to use:
- your latest question
- earlier conversation
- previous generated text
```

All of that occupies the model's available context.

### Simple analogy

Think of a person's **desk**.

```text
Context window
=
How much information can fit on the desk
```

You can put:

```text
Prompt
+ conversation
+ document
+ generated text
```

on the desk.

But the desk has a maximum size.

---

## Example

Imagine a model has a context limit of:

```text
100,000 tokens
```

and your conversation currently uses:

```text
70,000 tokens
```

There is only about:

```text
30,000 tokens
```

of remaining capacity for whatever else the particular system allows in that context.

The exact behavior depends on the model/API.

---

## What counts toward context?

Conceptually:

```text
Context
├── System instructions
├── User prompt
├── Previous conversation
├── Retrieved/document content
└── Generated tokens already in the conversation
```

So a very long conversation can eventually consume a lot of context.

### Easy mental model

> **Context window = the model's working area for the current request.**

---

## Cross-question: What happens when the context limit is reached?

The system cannot keep treating an arbitrarily long sequence as if it were still within the same context window. Depending on the application, older information may be removed, truncated, summarized, or the request may be rejected.

---

## Important distinction

**Context window is not model memory in the human sense.**

A context window is the information available to the model **for that computation**.

---

# 2. KV Cache

This is one of the most important concepts in inference.

First remember what you learned about attention:

```text
Each token
 ↓
Q, K, V
 ↓
Attention
```

During generation, the model keeps generating new tokens.

Suppose it has:

```text
The cat is
```

and generates:

```text
sleeping
```

Then it needs to generate the next token.

A naive implementation might recompute attention information for:

```text
The
cat
is
sleeping
```

again.

And then again when another token is generated.

That would waste computation.

---

## What does KV cache do?

The model **saves the Keys and Values from earlier tokens**.

So instead of throwing them away:

```text
Previous tokens
 ↓
K, V
 ↓
SAVE
```

the next step can reuse them.

Conceptually:

```text
"The cat is"
     ↓
Transformer
     ↓
K₁ K₂ K₃, V₁ V₂ V₃
     ↓
KV Cache
```

Then a new token arrives:

```text
"sleeping"
```

The model creates its new Q/K/V and uses:

```text
Old K,V from cache
+
New K,V
```

to perform attention.

Your uploaded notes explicitly describe this as saving past Keys and Values so the model does not have to recompute that work for every new token. 

---

## Why is it called KV cache?

Because it stores:

```text
K = Keys
V = Values
```

It does **not** normally mean storing the Queries in the same cache.

---

## Simple analogy

Imagine you're reading a book and taking notes.

Without KV cache:

```text
Read pages 1–10
→ throw notes away

Page 11
→ read pages 1–11 again

Page 12
→ read pages 1–12 again
```

With KV cache:

```text
Read pages 1–10
→ keep notes

Page 11
→ reuse old notes + process page 11

Page 12
→ reuse old notes + process page 12
```

---

## Why does this matter?

Because LLM generation is **token by token**.

Without caching, repeated recomputation would make generation much more expensive.

---

# 3. Prefill vs Decode

This is probably the most confusing part initially.

The key is:

> **Prefill processes the prompt. Decode generates the answer.**

---

# 3.1 Prefill

Suppose your prompt is:

```text
"The capital of France is"
```

The model first processes the **whole prompt**.

Conceptually:

```text
Prompt
 ↓
Tokenization
 ↓
Embeddings
 ↓
RoPE / position
 ↓
Transformer blocks
 ↓
KV Cache created
 ↓
Logits
```

This first phase is called **prefill**.

### Why process the whole prompt?

Because the model needs to understand the prompt/context before producing the first new token.

---

## Important intuition

During prefill, the prompt is already known:

```text
The
capital
of
France
is
```

So the model can process many token positions in parallel during the forward pass, subject to the causal attention mask.

Your source explicitly contrasts this with generation: during training/full-sequence processing, many next-token predictions can be handled in one pass, while inference generation proceeds one token at a time. 

---

# 3.2 Decode

Now suppose the model chooses:

```text
Paris
```

The answer is not finished.

It needs to predict the next token.

This is the **decode phase**.

```text
Existing context
      +
New token
      ↓
Use KV Cache
      ↓
Transformer
      ↓
New logits
      ↓
Next token
```

Then:

```text
new token
 ↓
append
 ↓
decode again
```

---

## The easiest analogy

Imagine a teacher reading your question.

### Prefill

Teacher reads the **whole question first**.

```text
"What is the capital of France?"
```

### Decode

Teacher starts answering:

```text
"Paris..."
```

then continues:

```text
"Paris is..."
```

then:

```text
"Paris is the..."
```

and keeps going.

---

# 3.3 One-line distinction

```text
Prefill = process the prompt

Decode = generate new tokens
```

---

# 4. Logits

Now we need to understand what happens after the Transformer processes the current sequence.

Suppose the prompt is:

```text
"The capital of France is"
```

The model needs to decide what comes next.

It produces a **score for every token in its vocabulary**.

These raw scores are called **logits**. Your uploaded notes define logits as raw scores for the possible next tokens. 

For example:

```text
Paris      → 8.7
London     → 3.1
Berlin     → 2.5
Rome       → 1.8
...
```

These numbers are **not probabilities yet**.

---

## Why are they called raw scores?

Because you cannot directly interpret:

```text
Paris = 8.7
London = 3.1
```

as:

```text
Paris = 87%
London = 31%
```

That would be wrong.

The logits are just relative scores.

---

# 4.1 What happens next?

The model applies **softmax**.

```text
Logits
 ↓
Softmax
 ↓
Probabilities
```

For example, conceptually:

```text
Paris      → 0.85
London     → 0.04
Berlin     → 0.03
Rome       → 0.02
...
```

The probabilities now sum to approximately:

```text
1.0
```

Your source describes the same flow: final representation → vocabulary scores/logits → softmax → next-token choice. 

---

# 4.2 Easy analogy

Think of logits as **marks** given by a teacher:

```text
Paris   → 95
London  → 60
Rome    → 55
Berlin  → 50
```

The marks themselves aren't probabilities.

Softmax converts those scores into a probability distribution.

---

# 5. Log Probabilities

This sounds complicated, but the idea is simple.

A normal probability might be:

```text
Paris → 0.85
```

A **log probability** is simply the logarithm of that probability.

```text
log(0.85) ≈ -0.16
```

Because probabilities are between 0 and 1:

```text
0 < p ≤ 1
```

their logarithms are usually:

```text
≤ 0
```

For example:

```text
Probability     Log probability

0.9             ≈ -0.105
0.5             ≈ -0.693
0.1             ≈ -2.303
0.01            ≈ -4.605
```

---

## Why use log probabilities?

One major reason is **mathematical convenience**.

Suppose a sequence has probabilities:

```text
0.8 × 0.7 × 0.9
```

Multiplying many probabilities can become extremely small.

Using logs converts multiplication into addition:

```text
log(0.8 × 0.7 × 0.9)

=
log(0.8) + log(0.7) + log(0.9)
```

That is much easier to work with numerically.

---

## Another useful intuition

Higher probability:

```text
0.9
```

means a log probability closer to zero:

```text
≈ -0.105
```

Lower probability:

```text
0.01
```

means a much more negative log probability:

```text
≈ -4.605
```

So:

```text
Better / more likely → closer to 0
Less likely         → more negative
```

---

# 5.1 Logit vs Probability vs Log Probability

Don't mix these up.

| Term                | Meaning                                      |
| ------------------- | -------------------------------------------- |
| **Logit**           | Raw score from the model                     |
| **Probability**     | Score converted into a value between 0 and 1 |
| **Log probability** | Logarithm of that probability                |

Think:

```text
Logits
  ↓
Softmax
  ↓
Probabilities
  ↓
log()
  ↓
Log probabilities
```

---

# 6. Autoregressive Generation

You've already encountered this in the Transformer chapter, but now let's connect it to **inference**.

**Autoregressive** means:

> The model uses previously generated tokens to help generate the next token.

Suppose:

```text
The capital of France is
```

### Step 1

Predict:

```text
Paris
```

Now:

```text
The capital of France is Paris
```

### Step 2

Predict:

```text
.
```

Now:

```text
The capital of France is Paris.
```

### Step 3

Maybe predict an end token.

This is exactly the **predict → append → repeat** process described in your source. 

---

## Why can't it generate the entire answer at once?

Because the next token depends on the tokens that came before it.

For example:

```text
The cat is
```

might lead to:

```text
sleeping
```

But once `"sleeping"` is generated, it changes the context for the next prediction.

So:

```text
Step 1
The cat is → sleeping

Step 2
The cat is sleeping → ...

Step 3
The cat is sleeping ... → ...
```

Each generated token changes the input for the next step.

---

# 6.1 Training vs Generation

This distinction is extremely useful in interviews.

### Training

The complete correct sequence is already available.

```text
The cat is sleeping
```

The model can learn:

```text
The → cat
The cat → is
The cat is → sleeping
```

at the same time using causal masking.

### Generation

The future answer is unknown.

```text
The cat is
       ↓
predict next token
       ↓
append it
       ↓
predict next
```

Your source explicitly makes this distinction: **training can predict many positions in parallel, while generation is one token per step**. 

---

# 7. Stop Sequences

The model needs to know:

> **"When should I stop generating?"**

One way is an **EOS token**.

EOS means:

> **End of Sequence**

Conceptually:

```text
Generate
 ↓
Generate
 ↓
Generate
 ↓
<EOS>
 ↓
STOP
```

---

## What is a stop sequence?

A **stop sequence is a piece of text that tells the generation system to stop when that sequence is produced/matched.**

For example, imagine an application wants:

```text
Question
Answer
---
```

The system could use:

```text
---
```

as a stop sequence.

Once that sequence is reached, generation stops.

---

## Why are stop sequences useful?

Because sometimes you don't want the model to keep writing.

For example, suppose you ask:

```text
Give me one line of Python.
```

You may want generation to stop after the requested output rather than continue into more text.

So:

```text
Stop sequence
=
"Stop generating when this pattern is reached."
```

---

# 7.1 Stop sequence vs EOS

They are not exactly the same.

### EOS token

A **special token** produced by the model.

```text
<END>
```

### Stop sequence

A **text pattern checked by the generation system**.

```text
"\n###"
```

Both can cause generation to stop.

---

# 7.2 Other stopping conditions

A generation system may also stop when:

```text
EOS token generated
OR
Stop sequence detected
OR
Maximum output tokens reached
OR
Another application-specific stopping rule triggers
```

Your Transformer notes already introduce these stopping ideas, including an end token and maximum-length/stop conditions. 

---

# 8. Constrained Decoding

Normally, the model has many possible next tokens.

For example:

```text
Paris
London
Berlin
...
```

But sometimes we want to **restrict what the model is allowed to generate**.

That's **constrained decoding**.

---

## Simple example

Suppose you ask:

```text
Return yes or no.
```

Normal model:

```text
yes
no
maybe
certainly
probably
...
```

With a constraint:

```text
Allowed:
yes
no
```

The decoder can be restricted to those choices.

---

# 8.1 JSON Example

Suppose your application needs:

```json
{
  "name": "...",
  "age": 25
}
```

You don't want:

```text
"Sure! Here is the JSON you requested..."
```

or malformed JSON.

A constrained decoder can restrict generation according to a grammar/schema so that only structurally valid next tokens are allowed.

Conceptually:

```text
Normal decoding

Possible next tokens
      ↓
Choose one


Constrained decoding

Possible next tokens
      ↓
Remove invalid choices
      ↓
Choose from allowed choices
```

---

## Example

Suppose we're generating:

```text
{
  "age":
```

The next token should be compatible with a number.

The decoder can eliminate many invalid choices.

Conceptually:

```text
"hello"   ✗
"banana"  ✗
123       ✓
45        ✓
27        ✓
```

Then choose from the valid options.

---

# 8.2 Why do we need constrained decoding?

Because raw language generation is flexible, but applications often need **structured output**.

Examples:

```text
JSON
XML
SQL
Function/tool arguments
Programming languages
Specific formats
```

So constrained decoding means:

> **Don't just ask the model what it wants to generate; restrict what it is allowed to generate.**

---

# 8.3 Does constrained decoding change the model?

Usually, the **model weights don't change**.

Instead, the decoding process changes which next tokens are allowed.

That's an important distinction.

```text
Model
=
same trained model

Decoder
=
more restrictive selection process
```

# 🎯 One Example From Beginning to End

Suppose your prompt is:

```text
The capital of France is
```

### 1. Context Window

The prompt is placed into the model's current context.

```text
The | capital | of | France | is
```

### 2. Prefill

The model processes the prompt through its Transformer layers.

```text
Prompt
 ↓
Embeddings
 ↓
RoPE
 ↓
Transformer blocks
```

### 3. KV Cache

The Keys and Values for those existing tokens are saved.

```text
K + V
 ↓
KV Cache
```

### 4. Logits

The model creates raw scores:

```text
Paris  → 8.7
Rome   → 2.0
London → 1.8
...
```

### 5. Probabilities

Softmax converts them:

```text
Paris  → 0.85
Rome   → 0.04
London → 0.03
...
```

### 6. Choose

Suppose the decoder selects:

```text
Paris
```

### 7. Append

Now the context becomes:

```text
The capital of France is Paris
```

### 8. Decode

The model processes the new token using the **existing KV cache**.

### 9. Predict again

Maybe:

```text
.
```

### 10. Stop

Maybe an EOS token is generated.

```text
<EOS>
 ↓
STOP
```

That's inference.

### The easiest story

> **Prefill reads the prompt. KV cache remembers attention information. Decode generates the answer one token at a time. Logits are raw choices, probabilities tell us how likely those choices are, and the decoder keeps appending tokens until a stopping condition is reached.**

That is the core of **LLM inference behavior**.
