## 1. Understanding LLM Inference

### 1.1 What is inference?

Inference is the process of using a trained language model to produce an output from an input.

A language model first learns its parameters during training. During inference, it uses those learned parameters to process a prompt and generate a response.

| Training                                                                         | Inference                                                                   |
| -------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Learns model parameters from training data                                       | Uses the learned parameters to produce outputs                              |
| Computes predictions and training losses; parameters are updated during training | Computes outputs without ordinarily updating the model's learned parameters |
| Often processes training sequences in parallel                                   | Usually generates output tokens sequentially                                |
| Learns patterns from data                                                        | Applies learned patterns to the current input                               |

### 1.2 What happens during inference?

Suppose you enter:

> The capital of France is

A decoder-only LLM broadly follows this process:

```
User prompt
    ↓
Context window
    ↓
Prefill: process the prompt
    ↓
Transformer blocks
    ↓
KV cache is populated
    ↓
Calculate next-token logits
    ↓
Convert logits into probabilities
    ↓
Select a token
    ↓
Append the selected token
    ↓
Decode the next token using the KV cache
    ↓
Repeat until a stopping condition is met
```

The model might generate `Paris`, then a period, and finally an end-of-sequence token.

The exact output depends on the model, prompt and decoding configuration.

### 1.3 The central idea

LLM inference involves three closely related activities:

- Context management: Determining which information is available to the model.
- Computation: Processing the input through the Transformer and reusing cached attention information.
- Generation control: Selecting tokens, applying constraints and deciding when to stop.

The rest of this chapter explains these activities in detail.

## 2. Context Window

### 2.1 What is a context window?

The context window is the maximum amount of token-based information a model can process together in a particular context.

Imagine a desk on which you can place your current question, earlier conversation, documents and other relevant information. The desk has limited space.

Similarly, a model has a finite context capacity.

### The context window as a working area

Prompt

Current request

Conversation

Available history

Documents

Relevant supplied content

Generated tokens

Output so far

Finite capacity

All applicable content must fit within the model's supported context limits.

### 2.2 What counts toward the context window?

Depending on the model and application, the context can include:

- System and developer instructions.
- The current user prompt.
- Earlier conversation messages.
- Retrieved documents and other supplied information.
- Generated tokens already included in the ongoing sequence.

Not every system constructs the context in exactly the same way. Some applications summarize or omit older messages, for example.

### 2.3 Worked example: Context capacity

Suppose a hypothetical model supports a context window of 100,000 tokens and the current context uses 70,000 tokens.

\\[ \text{Remaining capacity} = 100{,}000-70{,}000 = 30{,}000 \\]

Context used

### 70,000

Remaining capacity

### 30,000

Illustrative example. Actual limits and accounting rules depend on the model and API.

The remaining capacity is not necessarily all available for the response. Input, output and other model-specific requirements may impose additional limits.

### 2.4 What happens when the context limit is reached?

The model or application cannot continue processing an arbitrarily long sequence beyond the supported limit.

Depending on the implementation, it may:

- Remove or truncate older information.
- Summarize some earlier conversation content.
- Reject a request that exceeds a limit.
- Limit the number of tokens generated.

This behavior is application-dependent.

### 2.5 Context window vs human-like memory

A context window is not permanent memory.

It describes the information made available for a particular model computation. An application may separately retain conversation history or stored memories and reintroduce relevant information into later prompts, but those are separate mechanisms.

Key takeaway: The context window determines how much token-based information can be considered together. It is a capacity limit, not an unlimited record of everything the model has ever encountered.

## 3. KV Cache

The KV cache is one of the most important optimizations in LLM inference.

### 3.1 Why is caching necessary?

Recall the Transformer's attention mechanism:

\\[ \operatorname{Attention}(Q,K,V) = \operatorname{softmax} \left( \frac{QK^\top}{\sqrt{d_k}} \right)V \\]

Each token representation is projected into queries, keys and values.

Now suppose the model has the sequence:

> The cat is

It generates:

> sleeping

To generate the following token, the model needs to attend to the available token history.

A naive implementation could recompute key and value representations for the entire prefix at every step. Much of that work would be redundant.

### 3.2 What does the KV cache store?

The KV cache stores previously computed key and value representations so they can be reused during subsequent decoding steps.

```
Prompt: "The cat is"
          ↓
   Transformer layers
          ↓
  Compute K and V for
  the available tokens
          ↓
        KV cache
```

When a new token is generated, the model calculates the new token's representations and reuses the cached keys and values for the preceding tokens.

```
Existing KV cache
   K₁, K₂, K₃
   V₁, V₂, V₃
          +
New token's K and V
          ↓
Updated cache
          ↓
Attention for next-token prediction
```

In a typical decoder-only Transformer, the cache holds key and value tensors for each relevant layer and sequence position.

Important: The KV cache does not normally mean caching queries. Queries are generally calculated for the current processing step, while keys and values from earlier steps can be reused.

### 3.3 Understand it with an analogy

Imagine reading a book and keeping notes about each page.

Without caching:

```
Read pages 1–10
        ↓
Discard notes
        ↓
Page 11: review pages 1–11
        ↓
Page 12: review pages 1–12 again
```

With caching:

```
Read pages 1–10
        ↓
Keep the notes
        ↓
Page 11: reuse notes + process new page
        ↓
Page 12: reuse notes + process new page
```

The analogy represents the key idea: preserve useful intermediate computations rather than repeating them unnecessarily.

### 3.4 How KV caching improves inference

Without a KV cache, generation could repeatedly recompute key and value representations for the same prefix.

With a KV cache, those past representations can be reused. This substantially reduces redundant computation during ordinary token-by-token decoding.

The model still has work to do for each new token. It must calculate the new token's representations, perform attention and produce updated output scores.

Therefore:

- KV caching reduces repeated computation.
- It does not make generation computation-free.
- It consumes memory to store cached tensors.

### 3.5 The memory trade-off

A larger context generally requires storing more cached information. Cache memory also depends on architectural details such as the number of layers, attention heads, key/value dimensions and numerical precision.

This creates a trade-off:

| Benefit                                            | Cost                                                                         |
| -------------------------------------------------- | ---------------------------------------------------------------------------- |
| Avoids repeatedly calculating past keys and values | Requires memory to store the cache                                           |
| Improves the efficiency of sequential decoding     | Longer sequences can require more cache memory                               |
| Reuses past attention information                  | Cache management becomes important for long contexts and concurrent requests |

Interview-ready answer: The KV cache stores keys and values computed for previous tokens at each relevant Transformer layer. During autoregressive decoding, the model reuses this information instead of recomputing it for the entire prefix at every step. This improves decoding efficiency at the cost of additional memory.

## 4. Prefill vs Decode

The distinction between prefill and decode explains how LLM inference progresses from a prompt to a complete answer.

The easiest definition is:

> Prefill processes the initial prompt. Decode generates new tokens.

### 4.1 Prefill: Processing the prompt

Suppose the prompt is:

> The capital of France is

Before producing the first new token, the model processes the prompt through its Transformer layers.

```
Prompt
  ↓
Tokenization
  ↓
Token embeddings
  ↓
Positional mechanism, such as RoPE
  ↓
Transformer blocks
  ↓
Populate KV cache
  ↓
Calculate next-token logits
```

This initial processing phase is called prefill.

#### Why can prefill process multiple tokens in parallel?

The prompt is already known. The model can process its token positions together in a forward pass, subject to the attention mask and the architecture's constraints.

In a decoder-only model, causal masking still prevents each position from accessing future tokens. Parallel computation does not mean the model is allowed to use future-token information.

#### What does prefill produce?

Prefill typically produces:

- Intermediate Transformer representations.
- Keys and values that populate the KV cache.
- Logits used to determine the first generated token.

The precise scheduling of cache updates and token selection depends on the implementation.

### 4.2 Decode: Generating the answer

Suppose the first selected token is `Paris`.

The model may now need to generate a period or continue the answer.

During decoding, the model processes the newly available token using the existing cached key/value representations. It then calculates the next-token logits.

```
Existing KV cache + new token
                ↓
       Transformer layers
                ↓
         Updated cache
                ↓
          Next-token logits
                ↓
          Select next token
                ↓
             Append it
                ↓
                Repeat
```

The next token changes the context for the following prediction.

### 4.3 Prefill vs decode: Comparison

| Property        | Prefill                                                         | Decode                                            |
| --------------- | --------------------------------------------------------------- | ------------------------------------------------- |
| Primary purpose | Process the input prompt                                        | Generate the continuation                         |
| Input           | The available prompt sequence                                   | Newly generated token(s) and cached history       |
| Computation     | Processes the prompt's token positions together where supported | Typically advances generation one token at a time |
| KV cache        | Computes and populates cached representations                   | Reuses past representations and adds new ones     |
| Main output     | Context representations and initial next-token scores           | New next-token scores at each generation step     |

### 4.4 A simple analogy

Imagine a teacher answering a question.

Prefill: The teacher reads the whole question and considers the context.

Decode: The teacher begins answering, producing one part at a time and using what has already been said to continue.

This analogy captures the distinction between understanding the prompt and producing the continuation.

### 4.5 Why this distinction matters

Inference involves two different performance concerns:

- Time to first token: How long it takes to process the prompt and produce the first generated token.
- Subsequent token generation: How quickly the model continues producing tokens.

Prefill and decode have different computational patterns, so improving one does not necessarily improve the other by the same amount.

Key takeaway: Prefill processes the input; decode generates the continuation. The KV cache connects these phases by preserving reusable attention information.

## 5. Logits

### 5.1 What are logits?

Logits are the raw, unnormalized scores a model produces for possible next tokens.

After the Transformer processes the current context, its final prediction-position representation is mapped to a vector containing a score for each token in the output vocabulary.

Suppose the vocabulary contains possible candidates such as:

| Candidate token | Illustrative logit |
| --------------- | ------------------ |
| Paris           | 8.7                |
| London          | 3.1                |
| Berlin          | 2.5                |
| Rome            | 1.8                |

These are illustrative scores, not values from a real model run.

A higher logit generally means the token is favored relative to lower-logit alternatives before considering subsequent decoding transformations.

### 5.2 Why are logits not probabilities?

A logit of `8.7` does not mean an 87% probability.

Likewise, a logit of `3.1` does not mean a 31% probability.

Logits can be positive, negative or zero, and their raw magnitudes do not directly express probabilities.

The model must transform them into a probability distribution before interpreting them as next-token probabilities.

### 5.3 From logits to probabilities

A common transformation is softmax:

\\[ P_i=\frac{e^{z_i}}{\sum\_{j=1}^{V}e^{z_j}} \\]

Where:

- \\(z_i\\) = logit for candidate token \\(i\\).
- \\(e^{z_i}\\) = exponential of that logit.
- \\(V\\) = vocabulary size.
- \\(P_i\\) = resulting probability for token \\(i\\).

Softmax turns a vector of logits into probabilities between zero and one, with the probabilities summing to one, subject to numerical precision.

```
Vocabulary logits
       ↓
     Softmax
       ↓
Probability distribution
       ↓
Token selection
```

The probabilities depend on all the logits, not just one token's score.

### 5.4 An important distinction about the example

The following numbers are only illustrative:

```
Paris → 0.85
London → 0.04
Berlin → 0.03
```

Do not assume that these exact probabilities follow from the example logits above. A proper probability calculation must apply softmax across the complete set of logits.

### 5.5 Why logits matter

Logits provide the scores used by decoding methods to determine which tokens can or should be selected.

For example, decoding can involve:

- Choosing the highest-scoring token.
- Sampling a token according to a probability distribution.
- Modifying scores or masking invalid choices before selection.

Therefore, the model's logits are an important intermediate output rather than the final text response.

Key takeaway: Logits are raw token scores; softmax converts them into probabilities; a decoding method then selects the next token.

## 6. Log Probabilities

### 6.1 What is a log probability?

A log probability is the logarithm of a probability.

If a token has probability \\(p\\), its natural log probability is:

\\[ \log p \\]

For example:

\\[ \log(0.85)\approx -0.163 \\]

The logarithm is taken after a probability has been calculated or obtained.

### 6.2 Why are log probabilities usually non-positive?

A valid probability \\(p\\) satisfies:

\\[ 0\le p\le 1 \\]

For a strictly positive probability:

\\[ 0\<p\le 1 \\]

Taking the natural logarithm gives:

- \\(\log(1)=0\\).
- \\(\log(p)<0\\) when \\(0\<p<1\\).
- As \\(p\\) approaches zero, \\(\log(p)\\) becomes increasingly negative.

A probability of exactly zero has a mathematical log of negative infinity, although practical implementations handle numerical representations carefully.

### 6.3 Worked example

| Probability | Natural log probability |
| ----------- | ----------------------- |
| 0.90        | \\(-0.105\\)            |
| 0.50        | \\(-0.693\\)            |
| 0.10        | \\(-2.303\\)            |
| 0.01        | \\(-4.605\\)            |

The more likely token has a log probability closer to zero.

The less likely token has a more negative log probability.

This is a useful intuition, but the score is still relative to the probability distribution produced by the model.

### 6.4 Why use logarithms?

Suppose a sequence has successive conditional token probabilities of:

\\[ 0.8,\quad 0.7,\quad 0.9 \\]

The sequence's probability under that factorization is:

\\[ P=0.8\times 0.7\times 0.9=0.504 \\]

The log probability becomes:

\\[ \log P = \log(0.8)+\log(0.7)+\log(0.9) \\]

Instead of multiplying many small values, we can add their logarithms.

This is useful when calculating sequence likelihoods and training objectives because products of many probabilities can become extremely small.

### 6.5 Sequence log probability

For an autoregressive sequence:

\\[ P(x_1,\ldots,x_T) = \prod\_{t=1}^{T}P(x_t\mid x_1,\ldots,x\_{t-1}) \\]

Taking logarithms:

\\[ \log P(x_1,\ldots,x_T) = \sum\_{t=1}^{T} \log P(x_t\mid x_1,\ldots,x\_{t-1}) \\]

This turns the product of conditional probabilities into a sum of conditional log probabilities.

### 6.6 Logit vs probability vs log probability

| Term            | Meaning                                     | Can it be positive?                                     |
| --------------- | ------------------------------------------- | ------------------------------------------------------- |
| Logit           | Raw model score                             | Yes                                                     |
| Probability     | Normalized likelihood value for a candidate | No; it lies between 0 and 1                             |
| Log probability | Logarithm of a probability                  | No, for valid probabilities using the natural logarithm |

The last column assumes a finite log probability for a nonzero probability. A log probability is zero only for probability one, and otherwise negative.

Key takeaway: Log probabilities express probability on a logarithmic scale and are useful for comparing sequences and calculating probabilistic objectives.

## 7. Autoregressive Generation

### 7.1 What does autoregressive mean?

Autoregressive generation means producing the next token using the tokens already available in the sequence, including tokens generated earlier.

For example, suppose the prompt is:

> The capital of France is

The model might generate:

```
Step 1:
The capital of France is
            ↓
          Paris

Step 2:
The capital of France is Paris
                  ↓
                  .

Step 3:
The capital of France is Paris.
                  ↓
             End token
```

Each new token becomes part of the context for later predictions.

### 7.2 Why does generation happen sequentially?

The next prediction depends on the current context. Once a token is chosen, that token changes the context used for the following prediction.

For example:

```
The cat is
    ↓
Predict "sleeping"
    ↓
The cat is sleeping
    ↓
Predict the next token
```

The model cannot know the exact future generated sequence in advance because subsequent predictions depend on the tokens selected at earlier steps.

### 7.3 The autoregressive probability formula

The probability of a next token can be written as:

\\[ P(x_t\mid x_1,x_2,\ldots,x\_{t-1}) \\]

Here:

- \\(x_t\\) is the token currently being predicted.
- \\(x_1,\ldots,x\_{t-1}\\) are the preceding tokens.

The model estimates the next-token distribution from this preceding context.

For a complete sequence, the autoregressive factorization is:

\\[ P(x_1,\ldots,x_T) = \prod\_{t=1}^{T} P(x_t\mid x_1,\ldots,x\_{t-1}) \\]

This formula describes the chain of conditional predictions that defines the sequence's probability.

### 7.4 Training vs generation

This distinction is essential.

During training, the complete correct sequence is available, so the model can calculate predictions at many positions in parallel using a causal mask.

For example:

| Input context | Target   |
| ------------- | -------- |
| The           | cat      |
| The cat       | is       |
| The cat is    | sleeping |

These predictions can be computed together in a forward pass, because the true sequence is already available and causal masking prevents future-token leakage.

During generation, the future answer is not available. The model selects a token, appends it and predicts again.

| Training                                                          | Generation                                                 |
| ----------------------------------------------------------------- | ---------------------------------------------------------- |
| Complete training target is available                             | Future output is unknown                                   |
| Multiple position-level predictions can be calculated in parallel | New tokens are normally generated sequentially             |
| Causal masking restricts visibility                               | The selected token becomes context for the next prediction |

### 7.5 Greedy decoding vs sampling

Autoregressive generation specifies how the sequence grows; it does not prescribe exactly how the next token must be selected.

Two common selection strategies are:

Greedy decoding: Select the token with the highest score or probability after the applicable decoding transformations.

Sampling: Select a token using a probability distribution. Depending on the configuration, this can produce different continuations from the same prompt.

Other decoding methods can restrict the candidates or adjust the distribution before selection.

These strategies change the selection process, not the basic autoregressive structure.

Key takeaway: Autoregressive generation follows the cycle predict → select → append → predict again.

## 8. Stop Sequences and Stopping Conditions

The generation system needs a rule that determines when to stop producing tokens.

### 8.1 End-of-Sequence (EOS) token

An End-of-Sequence (EOS) token is a special token used to mark the end of a sequence.

Conceptually:

```
Generate token
      ↓
Generate token
      ↓
Generate token
      ↓
    EOS
      ↓
    Stop
```

When the system is configured to stop on the relevant EOS token and it is generated, generation ends.

### 8.2 What is a stop sequence?

A stop sequence is a specified text pattern that the generation system detects and uses as a stopping condition.

For example, suppose an application expects output in this form:

```
Question
Answer
---
```

The application might configure `---` as a stop sequence.

When the configured pattern is detected, the system stops generating further output.

A stop sequence is a runtime stopping rule; it does not have to be a dedicated special token learned by the model.

Actual handling depends on the API or serving implementation.

### 8.3 Why are stop sequences useful?

They allow applications to control the boundaries of generated content.

For example, an application might request one line of code, a particular response section or an answer that ends before a known delimiter.

Stop sequences can help prevent the model from continuing beyond the desired output boundary.

However, they do not guarantee that everything generated before the stopping pattern is correct or well-formed.

### 8.4 Stop sequence vs EOS

| EOS token                                       | Stop sequence                                                 |
| ----------------------------------------------- | ------------------------------------------------------------- |
| A special token in the model's token vocabulary | A configured text pattern or delimiter                        |
| Can be generated as a model output token        | Detected by the generation system when the pattern is matched |
| Commonly signals the end of a sequence          | Commonly enforces an application-defined output boundary      |

Both can trigger the end of generation, but they are distinct mechanisms.

### 8.5 Other stopping conditions

A generation process can stop for several reasons:

```
Continue generating
       |
       v
  Check stopping rules
       |
       +---- EOS reached? -------- Yes → Stop
       |
       +---- Stop sequence found?  Yes → Stop
       |
       +---- Output limit reached? Yes → Stop
       |
       +---- Other rule triggered? Yes → Stop
       |
       +---- None ----------------------→ Continue
```

A maximum output-token limit may stop generation even if the answer is incomplete.

An application can also define other stopping rules appropriate to its workflow.

Key takeaway: EOS, stop sequences and token limits are separate mechanisms that can determine when the generation process ends.

## 9. Constrained Decoding

### 9.1 What is constrained decoding?

Constrained decoding restricts the tokens that the generation process is allowed to select.

Ordinary language generation can choose from a broad range of vocabulary tokens. An application may instead need output that satisfies a format, grammar or set of rules.

For example, an application might require the output to be exactly one of:

```
yes
no
```

With constrained decoding, the selection process can disallow choices that violate the specified constraint.

### 9.2 How it works

In ordinary decoding, the system uses the model's scores and the configured selection strategy to choose a token.

Constrained decoding adds an additional restriction:

```
Model logits
     ↓
Identify permitted next tokens
     ↓
Exclude disallowed choices
     ↓
Select from permitted choices
     ↓
Append token
     ↓
Repeat
```

At each step, the allowed choices depend on the constraint and the content generated so far.

This makes it possible to enforce structural rules while the output is being generated.

### 9.3 Example: Restricting output to yes or no

Suppose an application requires:

```
Allowed outputs:
- yes
- no
```

The unconstrained vocabulary contains many other possibilities, including `maybe`, `certainly` and `probably`.

The decoding mechanism can prevent choices that do not fit the allowed output.

The exact implementation depends on whether the constraint is expressed as allowed sequences, a grammar, a schema or another formal specification.

### 9.4 Example: JSON output

Suppose an application requires an object containing a name and an age.

```
{
  "name": "Asha",
  "age": 25
}
```

Ordinary generation might produce an introduction before the object or malformed JSON.

A constrained decoder can apply a grammar or schema-based constraint to enforce the required structure during generation.

For example, after the prefix:

```
{
  "age":
```

a constraint can restrict subsequent tokens to values compatible with the required field type and the grammar's current state.

The permitted values and tokens depend on the schema and the structure being generated.

### 9.5 What can constrained decoding enforce?

Depending on the supported constraint mechanism, it can help enforce:

- Valid JSON structure.
- Required field names or field types.
- Enumerated outputs such as `yes` or `no`.
- A formal grammar.
- Required function or tool argument structures.
- Other supported output-format requirements.

The constraint must be properly defined and compatible with the intended output.

### 9.6 Does constrained decoding change the model weights?

Usually, no.

The trained model can remain the same while the decoding mechanism changes the set of permitted token choices.

```
Trained model
     ↓
Same learned parameters
     ↓
Constrained decoding
     ↓
Output restricted by the selected rules
```

This distinguishes constrained decoding from retraining or fine-tuning, which can change model parameters.

### 9.7 Structural validity vs semantic correctness

This is an important limitation.

A constrained decoder can help ensure that output follows a required format, but the content can still be wrong.

For example:

```
{
  "capital": "London"
}
```

may be valid JSON but incorrect if the requested capital is Paris.

Therefore:

- Structural validity means the output conforms to a format or grammar.
- Semantic correctness means the content is accurate and fulfills the intended task.

These are different properties.

Key takeaway: Constrained decoding restricts what can be generated. It can enforce supported structural requirements, but it does not automatically guarantee factual accuracy or correct reasoning.

Now connect all the topics into one end-to-end process.

### 10.1 The complete flow

Suppose the user enters:

> The capital of France is

The following diagram illustrates a typical decoder-only inference pipeline.

The capital of France is

2\. Context window

Available instructions, prompt and context

3\. Prefill

Process prompt through Transformer blocks

4\. KV cache

5\. Logits → probabilities

Score possible next tokens

6\. Token selection

Apply decoding strategy and constraints

7\. Append the selected token

9\. Check stopping conditions

EOS, stop sequence, output limit or another rule

Return output

Continue

Predict next token

### 10.2 Step-by-step example

Step 1 — Context window

The prompt and other applicable context are supplied to the model.

Step 2 — Prefill

The model processes the prompt through the Transformer layers and prepares the information needed for next-token prediction.

Step 3 — KV cache

The model retains reusable key/value representations for the available tokens.

Step 4 — Logits

The model produces raw scores for possible next tokens.

Illustrative example:

```
Paris  → 8.7
Rome   → 2.0
London → 1.8
```

Step 5 — Probabilities

Softmax can transform logits into a probability distribution.

Remember that these probabilities must be calculated from the actual full logit vector; the numbers above are only illustrative.

Step 6 — Token selection

The decoding strategy selects an allowed token. Suppose it selects `Paris`.

Step 7 — Append

The sequence now becomes:

```
The capital of France is Paris
```

Step 8 — Decode again

The model calculates the next-token prediction, reusing cached information and processing the newly available token.

Step 9 — Repeat or stop

The system repeats generation until the configured stopping conditions are met.

## 11. Important Concept Comparisons

### 11.1 Context window vs KV cache

These concepts are related, but they solve different problems.

| Context window                                                            | KV cache                                                  |
| ------------------------------------------------------------------------- | --------------------------------------------------------- |
| Defines the information capacity available to the model for a computation | Stores intermediate key/value representations for reuse   |
| Concerns which token-based information can be processed                   | Concerns computational efficiency during decoding         |
| Includes relevant input and context under the system's accounting rules   | Contains numerical tensors derived from processing tokens |
| Is not itself a cache                                                     | Is a cache used during inference                          |

Example: A model may have a large context window but still need a KV cache to efficiently generate a long response.

### 11.2 Prefill vs decode

| Prefill                                                           | Decode                                                   |
| ----------------------------------------------------------------- | -------------------------------------------------------- |
| Processes the prompt                                              | Generates continuation tokens                            |
| Processes the available prompt positions together where supported | Normally advances the output one token at a time         |
| Establishes the initial cache                                     | Reuses the cache and adds representations for new tokens |

### 11.3 Logits vs probabilities vs log probabilities

| Logits                                          | Probabilities                 | Log probabilities                                            |
| ----------------------------------------------- | ----------------------------- | ------------------------------------------------------------ |
| Raw scores                                      | Normalized probability values | Logarithms of probability values                             |
| Not bounded between 0 and 1                     | Between 0 and 1               | Non-positive for valid probabilities                         |
| Softmax can transform logits into probabilities | Can guide token selection     | Useful for likelihood calculations and numerical computation |

### 11.4 Autoregressive generation vs constrained decoding

| Autoregressive generation                                 | Constrained decoding                                                |
| --------------------------------------------------------- | ------------------------------------------------------------------- |
| Determines how tokens are generated in sequence           | Restricts the set of allowed token choices                          |
| Uses preceding context to predict subsequent tokens       | Uses rules, grammar or other constraints to exclude invalid choices |
| Does not, by itself, guarantee a particular output format | Can enforce supported output-format constraints                     |

They can be used together: an autoregressive model can generate a sequence one token at a time while constrained decoding controls which tokens are permitted.

### 11.5 EOS vs stop sequence vs maximum output length

| Stopping condition    | What triggers it?                             |
| --------------------- | --------------------------------------------- |
| EOS                   | A relevant end-of-sequence token is generated |
| Stop sequence         | The configured output pattern is matched      |
| Maximum output tokens | The generation limit is reached               |

These conditions may coexist. The first applicable stopping rule can end the generation process, depending on the system's configuration.

## 12. Common Misconceptions

| Misconception                                                                      | Correct understanding                                                                                                              |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| The model permanently remembers everything in its context window.                  | The context window is available information for a computation, not permanent memory.                                               |
| The context window and KV cache are the same thing.                                | One is a context-capacity concept; the other stores reusable attention tensors.                                                    |
| KV cache stores the entire previous conversation as plain text.                    | It stores numerical key/value representations, not simply a text transcript.                                                       |
| KV cache eliminates all computation for earlier tokens.                            | It avoids recomputing past key/value representations during cached decoding; new-token computation and attention remain necessary. |
| Prefill and decode are identical.                                                  | Prefill processes the prompt; decode produces the continuation.                                                                    |
| Prefill violates causal masking because it processes multiple positions at once.   | Multiple positions can be computed in parallel while the causal mask restricts what each position can see.                         |
| A logit of 8 means an 80% probability.                                             | Logits are raw scores, not percentages.                                                                                            |
| Softmax is the same as token selection.                                            | Softmax converts logits into probabilities; a decoding strategy selects a token.                                                   |
| Log probabilities are generally positive.                                          | Natural log probabilities are non-positive for valid probabilities.                                                                |
| Generation and training both require one separate forward pass per token position. | Training can compute many position-level predictions in parallel; generation is generally sequential.                              |
| An EOS token and stop sequence are the same mechanism.                             | EOS is a special token; a stop sequence is a configured text pattern.                                                              |
| Constrained decoding makes every answer factually correct.                         | It can enforce permitted output structures but does not guarantee semantic correctness.                                            |
| Constrained decoding necessarily changes model weights.                            | It usually changes the decoding process rather than the trained parameters.                                                        |
| Reaching the output token limit guarantees a complete answer.                      | Generation can be stopped by the limit even when the answer is unfinished.                                                         |

### 15.2 The formulas to know

Softmax

\\[ P_i=\frac{e^{z_i}}{\sum\_{j=1}^{V} e^{z_j}} \\]

Converts vocabulary logits \\(z_i\\) into probabilities \\(P_i\\).

Log probability

\\[ \log P \\]

The logarithm of a probability.

Autoregressive factorization

\\[ P(x_1,\ldots,x_T) = \prod\_{t=1}^{T} P(x_t\mid x_1,\ldots,x\_{t-1}) \\]

The probability of a sequence is expressed as a product of successive conditional token probabilities.

Log sequence probability

\\[ \log P(x_1,\ldots,x_T) = \sum\_{t=1}^{T} \log P(x_t\mid x_1,\ldots,x\_{t-1}) \\]

The same sequence probability expressed as a sum of log probabilities.

### 15.4 Explain inference in 60 seconds

> Inference is the process of using a trained LLM to answer a prompt. The context window determines how much token-based information can be processed together. During prefill, the model processes the prompt through its Transformer layers and populates the KV cache. The model then produces logits for possible next tokens, which can be converted into probabilities using softmax. A decoding strategy selects an eligible token, appends it to the sequence and repeats the process. The KV cache helps avoid recomputing past key and value representations at every step. Constrained decoding can restrict allowed outputs, while EOS tokens, stop sequences and output limits can terminate generation.

### 16.3 Interview questions

1\. Why is the KV cache important for inference?

It preserves keys and values from earlier tokens so the model can reuse them during subsequent decoding steps. This avoids repeatedly computing those representations for the entire prefix, reducing redundant computation at the cost of cache memory.

2\. What is the difference between prefill and decode?

Prefill processes the prompt and populates the initial KV cache. Decode generates subsequent tokens, reusing the cached representations and adding information for new tokens.

3\. What is the difference between logits and probabilities?

Logits are unnormalized model scores. Softmax can convert them into a normalized probability distribution, which a decoding method can use for token selection.

4\. Why are log probabilities useful?

The log of a product of probabilities equals the sum of their logarithms. This makes sequence likelihood calculations more convenient and can help avoid numerical problems caused by multiplying many small probabilities.

5\. Why is generation autoregressive?

Each new token depends on the context available at that point. The selected token is appended to the sequence and becomes part of the context for later predictions.

6\. Can a model generate multiple tokens in one operation?

Some systems use techniques that propose or process multiple tokens together. However, ordinary autoregressive decoding generally produces new tokens sequentially because subsequent predictions depend on preceding generated tokens.

7\. Does the KV cache increase the context window?

No. The cache improves computational efficiency; it does not by itself increase the model's supported context capacity.

8\. What is constrained decoding, and what are its limitations?

Constrained decoding restricts token selection according to supported rules, such as a grammar or JSON schema. It can improve structural validity but does not guarantee factual correctness.

9\. What is the difference between a stop sequence and an output-token limit?

A stop sequence terminates generation when a configured pattern is matched. An output-token limit terminates generation when the configured number of output tokens is reached.

10\. How would you debug an LLM that produces malformed JSON?

First inspect the raw generated output and confirm whether the problem is malformed structure, an incorrect schema, or application-side parsing. Where supported, use schema- or grammar-constrained decoding, validate the parsed output and handle failures explicitly. Even valid JSON must be checked for semantic correctness.
