## 1. Introduction to AI Architecture Trade-offs

### 1.1 What are architecture concepts?

AI architecture concepts explain how a model is structured and how that structure affects its computational requirements and behavior.

For example, two AI models may both generate text but differ significantly in their:

- Number of parameters.
- Computation performed for each token.
- Attention mechanism.
- Supported context length.
- Memory requirements.
- Inference latency.
- Operating cost.

Understanding these differences helps engineers select and deploy AI models effectively.

### 1.2 The four concepts in this chapter

| Concept                    | Main question                                         | Primary concern                                     |
| -------------------------- | ----------------------------------------------------- | --------------------------------------------------- |
| Dense vs MoE               | How much of the model participates in computation?    | Computation and model capacity                      |
| MHA vs MQA vs GQA          | How are attention keys and values shared?             | KV-cache memory and inference efficiency            |
| Long-context trade-offs    | How does processing more tokens affect the system?    | Computation, memory, latency, and information usage |
| Model size vs latency/cost | How do model resources affect production performance? | Speed, cost, hardware, and quality                  |

These concepts are related because they influence how much computation and memory an AI application needs.

```
                   AI MODEL
                      |
         +------------+------------+
         |            |            |
         v            v            v
    Architecture   Attention     Context
      Dense/MoE    MHA/GQA/MQA   Short/Long
         |            |            |
         +------------+------------+
                      |
                      v
                Resource Usage
                      |
             +--------+--------+
             |        |        |
             v        v        v
          Memory   Latency    Cost
```

Key takeaway: AI model selection is not just about choosing a model with the highest capability. It also involves understanding how the model computes, stores information, and uses hardware.

## 2. Dense vs Mixture-of-Experts (MoE)

### 2.1 Understanding model parameters

A parameter is a learned numerical value inside a neural network.

Parameters are adjusted during training so that the model learns patterns in its training data.

Models can have different numbers of parameters, such as:

```
7 billion parameters
70 billion parameters
400 billion parameters
```

Here, `B` means billion.

A larger parameter count can provide greater model capacity, but it does not automatically mean better performance on every task.

More importantly, total parameter count does not tell you how many parameters participate in every token computation.

That distinction leads to dense and MoE architectures.

### 2.2 Dense models

A dense model uses dense computational pathways through its network layers.

In a conventional dense Transformer, the main dense layers participate in processing each token rather than routing computation to a selected subset of experts.

A simplified representation is:

```
Input token
     |
     v
  Layer 1
     |
     v
  Layer 2
     |
     v
  Layer 3
     |
     v
  Layer 4
     |
     v
   Output
```

The mental model is that the model's dense computational pathway participates in processing each token.

For a large dense model, this can require substantial computation and memory.

### 2.3 A simple analogy

Imagine a company with 10 employees.

A customer submits a request, and the company's workflow involves all 10 employees.

```
Customer request
       |
       v
All 10 employees participate
       |
       v
Completed response
```

This illustrates the idea of a dense computation path: the network does not select a small set of experts instead of using its dense layers.

The analogy is simplified because actual neural-network layers perform numerical operations rather than human tasks.

### 2.4 Mixture-of-Experts (MoE) models

A Mixture-of-Experts (MoE) model contains multiple expert components within parts of its architecture.

A routing mechanism selects which experts process a particular token.

Instead of activating every expert for every token, an MoE model can activate only a subset.

```
Input token
     |
     v
   Router
     |
     v
Select relevant experts
     |
     v
Selected expert computations
     |
     v
Combine expert outputs
     |
     v
Continue model computation
```

The router is an important part of this architecture.

It decides which experts participate in the relevant computation.

### 2.5 What are experts?

Experts are components of the neural network that participate in processing selected inputs.

During training, different experts may learn different useful patterns or specializations.

For intuition, imagine:

```
Expert 1 -> Patterns useful for coding tasks
Expert 2 -> Patterns useful for language tasks
Expert 3 -> Patterns useful for mathematical tasks
Expert 4 -> Other learned patterns
```

These descriptions are illustrative. Experts are not necessarily explicitly programmed to perform one particular task. Their learned behavior depends on training and architecture.

### 2.6 Total parameters vs active parameters

This is one of the most important concepts in MoE models.

Suppose a hypothetical model has:

```
Total parameters = 100B
Active parameters ≈ 20B per token
```

The model has 100 billion parameters in total, but approximately 20 billion participate in the computation described by this example for a particular token.

| Term                  | Meaning                                               |
| --------------------- | ----------------------------------------------------- |
| Total parameters      | Parameters across the complete model                  |
| Active parameters     | Parameters participating in the specified computation |
| Total model capacity  | The capacity associated with the model as a whole     |
| Per-token computation | Computation performed to process an individual token  |

A simplified comparison is:

```
Dense model

100B parameters
       |
       v
Dense computation through its layers
```

```
MoE model

100B total parameters
       |
       v
Router selects experts
       |
       v
Approximately 20B active parameters
       |
       v
Token computation
```

The exact active-parameter count depends on the architecture and how the model defines active computation. Shared layers and other components may also participate.

Important: A 100B MoE model with 20B active parameters is not automatically equivalent to a dense 20B model. Their architecture, total capacity, memory requirements, and behavior can differ substantially.

### 2.7 Dense vs MoE comparison

| Feature                 | Dense model                                 | MoE model                                                       |
| ----------------------- | ------------------------------------------- | --------------------------------------------------------------- |
| Computational structure | Dense computational pathways                | Router selects experts in MoE components                        |
| Expert selection        | Not a defining feature                      | Central to the MoE architecture                                 |
| Total capacity          | Depends on total model size                 | Can be large relative to active expert computation              |
| Per-token computation   | Determined by dense layers and architecture | Only selected expert components are activated                   |
| Complexity              | No MoE-specific routing requirement         | Routing and expert-management complexity                        |
| Deployment              | Depends on model size and hardware          | May require additional memory and distributed execution support |

### 2.8 Why use MoE?

The primary attraction is:

> Large total model capacity without activating every expert for every token.

Potential benefits include greater model capacity and lower expert computation per token than an architecture that activated all experts.

However, MoE is not automatically cheaper or easier to deploy.

Important overheads include:

- Routing overhead: The model must select appropriate experts.
- Memory requirements: The complete model's parameters may still need to be stored or distributed.
- GPU-to-GPU communication: Different experts may reside on different devices.
- Distributed inference complexity: The serving system must coordinate the selected experts efficiently.

### 2.9 When should you consider MoE?

MoE may be appropriate when you need substantial model capacity while limiting the computation performed by the expert layers for each token.

Evaluate it alongside dense alternatives using actual quality, latency, memory, hardware, and serving-cost measurements.

### 2.10 Section recap

Remember:

- Dense models use dense computational pathways through their layers.
- MoE models route computation to selected experts.
- Total parameters and active parameters are different measurements.
- MoE can improve computational efficiency for some workloads, but routing, memory, and communication introduce additional costs.

Question: What is the main architectural difference between a dense model and an MoE model?

Answer: A dense model uses dense computational pathways, whereas an MoE model includes a routing mechanism that activates a subset of experts for a particular computation.

## 3. MHA vs MQA vs GQA

### 3.1 Introduction to attention

MHA, MQA, and GQA are attention designs associated with Transformer models.

To understand them, first understand the three components used in attention:

- Q — Query
- K — Key
- V — Value

Attention uses these representations to determine how information from other tokens contributes to the current token's representation.

For example:

```
"The cat sat on the mat because it was tired."
```

When processing the word `it`, the model may need to use information associated with `cat` to interpret the sentence.

Attention allows the model to compute relationships among token representations.

### 3.2 Query, Key, and Value

A useful intuitive analogy is a search operation.

- Query: What information am I looking for?
- Key: What information does this token represent for matching?
- Value: What information can this token contribute?

These are conceptual explanations, not literal database operations.

The architecture question is:

How many attention heads have their own Key and Value representations, and how much sharing takes place?

That is the fundamental distinction between MHA, MQA, and GQA.

### 3.3 MHA — Multi-Head Attention

MHA stands for Multi-Head Attention.

In the standard multi-head arrangement described in this chapter, each attention head has its own Query, Key, and Value projections.

Suppose the model has eight attention heads.

```
Head 1 -> Q1, K1, V1
Head 2 -> Q2, K2, V2
Head 3 -> Q3, K3, V3
Head 4 -> Q4, K4, V4
Head 5 -> Q5, K5, V5
Head 6 -> Q6, K6, V6
Head 7 -> Q7, K7, V7
Head 8 -> Q8, K8, V8
```

A simplified workflow is:

```
            Input
              |
              v
       Multiple attention heads
              |
              v
      Compute attention separately
              |
              v
       Combine head outputs
              |
              v
            Output
```

Each head can learn different attention patterns.

#### Advantage of MHA

MHA provides independent Key and Value representations for each head, offering flexibility in how the model represents and uses information.

#### Disadvantage of MHA

It requires more Key/Value cache memory than MQA and, for comparable head dimensions and layer counts, typically more KV-cache memory than GQA.

This difference becomes important during long-context inference.

### 3.4 MQA — Multi-Query Attention

MQA stands for Multi-Query Attention.

In MQA, multiple Query heads share a single set of Key and Value representations.

For example:

```
Q1 ─┐
Q2 ─┤
Q3 ─┤
Q4 ─┤
Q5 ─┤
Q6 ─┤
Q7 ─┤
Q8 ─┘
     |
     v
 Shared K and V
```

The essential idea is:

```
Multiple Q heads
        +
One shared K
        +
One shared V
```

The Query heads remain distinct, but the Key and Value representations are shared across them.

### 3.5 Why is MQA useful?

During inference, Transformer models often store previous Key and Value representations in a structure called the KV cache.

If multiple Query heads share Key and Value representations, the model needs fewer cached Key and Value values than a comparable MHA implementation.

This can reduce memory requirements and improve inference efficiency.

Potential benefits include:

- Lower KV-cache memory usage.
- Reduced memory traffic.
- Improved inference efficiency.
- Potentially higher serving throughput.

The exact performance improvement depends on the hardware and implementation.

#### Trade-off

Sharing Key and Value representations reduces the number of independent K/V heads.

This can reduce representational flexibility relative to MHA, although actual quality depends on the architecture and training.

### 3.6 GQA — Grouped-Query Attention

GQA stands for Grouped-Query Attention.

GQA combines ideas from MHA and MQA.

Rather than giving every Query head its own Key and Value heads, or making every Query head share one K/V set, GQA groups Query heads together.

Each group shares a corresponding Key and Value representation.

For example:

```
8 Query heads
4 Key heads
4 Value heads
```

A simplified grouping is:

```
Q1, Q2 -> K/V Group 1

Q3, Q4 -> K/V Group 2

Q5, Q6 -> K/V Group 3

Q7, Q8 -> K/V Group 4
```

Each group of two Query heads shares a Key head and a Value head.

### 3.7 Comparing the three mechanisms

Assume eight Query heads and compatible head dimensions.

| Attention design | Query heads | Key heads | Value heads |
| ---------------- | ----------- | --------- | ----------- |
| MHA              | 8           | 8         | 8           |
| GQA              | 8           | 4         | 4           |
| MQA              | 8           | 1         | 1           |

These are illustrative configurations. GQA can use different grouping ratios in real models.

The pattern is:

```
MHA -> Each head has separate K/V

GQA -> Groups of heads share K/V

MQA -> All Query heads share K/V
```

### 3.8 Attention comparison

| Feature                      | MHA                                                 | GQA                               | MQA                         |
| ---------------------------- | --------------------------------------------------- | --------------------------------- | --------------------------- |
| K/V sharing                  | No sharing across heads in the standard arrangement | Sharing within groups             | One shared K/V set          |
| KV-cache size                | Highest of the three for comparable dimensions      | Intermediate                      | Lowest                      |
| Memory efficiency            | Lower relative to MQA/GQA                           | Balanced                          | Highest in K/V storage      |
| Representational flexibility | More independent K/V heads                          | Intermediate                      | Fewer independent K/V heads |
| Main trade-off               | Memory requirements                                 | Balance of memory and flexibility | Maximum K/V sharing         |

### 3.9 Understanding the KV cache

During autoregressive generation, the model generates tokens sequentially.

Earlier tokens have already been processed. Their Key and Value representations can be cached so that the model does not have to recompute all those representations from scratch for every new token.

```
Previously processed tokens
           |
           v
       K/V values
           |
           v
         KV cache
           |
           v
New token uses cached information
           |
           v
     Generate next token
```

The cache stores useful information from earlier tokens across the model's layers.

As the sequence becomes longer, the cache generally grows because more tokens have associated Key and Value representations.

### 3.10 Why does K/V sharing matter?

Consider the relationship:

```
More K/V heads
       |
       v
More cached K/V representations
       |
       v
Higher KV-cache memory requirements
```

Compare this with:

```
Fewer K/V heads
       |
       v
Fewer cached K/V representations
       |
       v
Lower KV-cache memory requirements
```

For comparable models, MQA and GQA can reduce KV-cache memory relative to MHA.

This is particularly useful when a system must serve long conversations or many concurrent requests.

Important: The KV cache is not the same as the model's parameter memory. A system must account for both model weights and inference-state memory.

### 3.11 Practical selection

Consider MHA when its representational characteristics and measured quality justify its memory requirements.

Consider MQA or GQA when reducing KV-cache memory is important.

GQA is often an attractive middle ground because it reduces K/V duplication while retaining multiple K/V groups.

The best choice depends on model quality, cache size, hardware, context length, and serving workload.

### 3.12 Section recap

Question: What is the central difference between MHA, MQA, and GQA?

Answer: They differ in how Key and Value representations are shared across Query heads. MHA has independent K/V heads, MQA shares one K/V set across Query heads, and GQA shares K/V within groups.

Question: Why can GQA improve inference efficiency?

Answer: By using fewer K/V heads than MHA, GQA can reduce the KV cache and related memory traffic while preserving more independent K/V representations than MQA.

## 4. Long-Context Trade-offs

### 4.1 What is context?

Context is the information available to a model when processing a particular interaction or request.

It may include:

- System instructions.
- Conversation history.
- User questions.
- Documents.
- Code.
- Other supported input information represented within the model's context.

For example:

```
System instructions
        +
Conversation history
        +
Reference documents
        +
User question
        |
        v
      Context
        |
        v
       Model
```

The model's context window specifies how much input and relevant interaction content it can accommodate under its context rules.

Token counts are used to measure context length.

### 4.2 What is a long-context model?

A model supporting a larger context window can accept more tokens in one interaction than a model with a smaller window.

For example, the source material compares illustrative contexts of:

```
Shorter context: 5,000 tokens

Longer context: 100,000+ tokens
```

These values are examples, not universal limits.

### 4.3 Why is long context useful?

Long context allows a model to work with larger amounts of information within a single interaction.

Common applications include:

- Large documents.
- Long conversations.
- Large codebases.
- Research materials.
- Legal documents.
- Meeting transcripts.
- Multiple reference files.

For example, if you need to analyze a long technical document, a larger context window may allow you to supply more of the document together with your question.

### 4.4 Long context is not free

Increasing context length can increase:

- Computation.
- Memory usage.
- Inference latency.
- Operating costs.
- Serving complexity.

A larger context window is therefore not automatically better for every task.

The engineering question is whether the additional context improves the result enough to justify its resource requirements.

### 4.5 The quadratic attention problem

In standard full self-attention, the number of attention interactions can scale approximately with the square of the sequence length.

\\[ \text{Attention interaction complexity} = O(n^2) \\]

Here, \\(n\\) is the number of tokens in the sequence.

Why is the scaling quadratic?

Each token may compute attention scores against other tokens in the sequence. Therefore, when the number of tokens increases, the number of possible token-to-token interactions can increase much faster.

For example:

\\[ 100 \times 100 = 10{,}000 \\]

For a sequence of 10,000 tokens:

\\[ 10{,}000 \times 10{,}000 = 100{,}000{,}000 \\]

Under the simplified full-attention comparison, increasing the sequence from 100 tokens to 10,000 tokens increases the number of token-pair interactions by a factor of 10,000.

This is why traditional full attention can become expensive at long sequence lengths.

Technical qualification: \\(O(n^2)\\) describes the attention interaction scaling in standard full attention. Actual end-to-end costs depend on attention implementation, hardware, model dimensions, and optimizations. Other workloads, including token-by-token decoding with a KV cache, have different performance characteristics.

### 4.6 Long context increases KV-cache memory

During autoregressive inference, previously processed tokens can contribute Key and Value representations to the KV cache.

```
Longer context
      |
      v
More cached tokens
      |
      v
More K/V representations
      |
      v
Larger KV cache
      |
      v
More memory required
```

The KV-cache size generally grows approximately linearly with the number of cached tokens when the model architecture and cache representation remain fixed.

Its memory requirement also depends on the number of layers, K/V head count, head dimensions, numerical precision, and other implementation details.

This is why MHA, GQA, and MQA matter to long-context serving: their K/V sharing patterns affect cache size.

### 4.7 A practical comparison: 4K vs 128K context

Imagine two requests to the same model.

```
Request A
Context: 4K tokens

Request B
Context: 128K tokens
```

A 128K-token context contains 32 times as many tokens as a 4K-token context.

This does not mean every resource requirement increases by exactly 32 times. Different components scale differently.

However, the longer request can require substantially more attention computation and KV-cache memory.

At production scale, this matters even more because many requests may run concurrently.

### 4.8 Long context does not guarantee perfect understanding

A context window indicates how much information a model can accept. It does not guarantee that the model will use every piece of information equally effectively.

For example, imagine a critical condition hidden in the middle of a very long document.

The model may accept the entire document but fail to use that condition correctly when answering the final question.

This relates to the phenomenon often called "Lost in the Middle."

The term describes cases where models use relevant information less effectively when it appears in the middle of a long context than when similar information appears near the beginning or end.

It is a documented type of long-context challenge, not a guarantee that every model will behave this way in every situation.

### 4.9 Two different questions

When evaluating a long-context model, distinguish between:

Context capacity: How much information can the model accept?

Context utilization: How effectively can the model find, retain, and use the relevant information?

```
Large context window
        |
        v
Can accept more information
        |
        v
Does not guarantee
        |
        v
Perfect use of every detail
```

This distinction is crucial when building systems for large documents or codebases.

### 4.10 Strategies for managing long context

The source material emphasizes the trade-offs rather than prescribing a particular solution. Several practical approaches follow naturally from those trade-offs:

- Supply only the relevant sections when the task does not require the entire document.
- Use retrieval to locate important passages.
- Evaluate whether the model actually answers questions about information placed in different parts of the context.
- Consider KV-cache memory and concurrency when estimating production capacity.
- Compare shorter and longer contexts on the actual task.

These techniques help control resource usage and assess whether a larger context window provides practical value.

### 4.11 Section recap

Question: Why does long context increase computational requirements?

Answer: More tokens create more work for attention and increase the amount of information that the model may need to keep available during inference. In standard full self-attention, attention interactions scale approximately as \\(O(n^2)\\), while KV-cache memory generally grows linearly with cached token count for a fixed architecture.

Question: What is the difference between context capacity and context utilization?

Answer: Context capacity describes how much information the model can accept. Context utilization describes how effectively it uses the relevant information.

## 5. Model Size vs Latency and Cost

### 5.1 Why model size matters

Consider two hypothetical language models:

```
Model A = 7B parameters
Model B = 70B parameters
```

It may be tempting to assume that Model B is always the better choice because it is larger.

However, model size is only one factor affecting suitability for an application.

Engineers must also consider:

- Quality.
- Latency.
- Operating cost.
- Memory.
- Throughput.
- Hardware requirements.
- User experience.

### 5.2 Larger models

A larger model generally has more parameters and may have greater capacity.

A simplified relationship is:

```
Larger model
      |
      v
Potentially greater capacity
      |
      v
Potentially stronger performance
      |
      v
Often greater compute and memory requirements
```

Larger models frequently require more computational resources, which can increase deployment costs and make low-latency serving more difficult.

However, these are tendencies, not universal rules. Architecture, training, quantization, hardware, and implementation all matter.

### 5.3 Smaller models

A smaller model may need fewer computational resources.

```
Smaller model
      |
      v
Fewer parameters
      |
      v
Often lower compute requirements
      |
      v
Potentially lower cost and latency
```

Smaller models may also be easier to deploy locally or on resource-constrained infrastructure.

The trade-off is that a smaller model may perform less well on difficult reasoning tasks or other demanding workloads.

### 5.4 Latency

Latency is the time taken to process a request and produce a response.

For example:

```
Model A: 300 milliseconds
Model B: 2 seconds
```

In this hypothetical example, Model A has lower latency.

Latency matters in interactive applications such as chatbots, voice assistants, coding tools, and customer-support systems.

For language generation, it is also useful to distinguish the time until the first token is produced from the time needed to generate the full response. Both can affect the user's experience.

### 5.5 What affects latency?

Latency depends on more than parameter count.

Relevant factors include:

- Model architecture.
- Prompt and context length.
- Output length.
- Available GPU or other accelerator resources.
- Memory bandwidth.
- Batch size.
- Inference optimization.
- Network delay for remote services.
- Serving-system overhead.

Consequently, you should measure latency on the intended hardware and workload rather than estimating it from model size alone.

### 5.6 Cost

Model costs depend on how it is accessed and deployed.

For an API-based service, pricing may depend on input tokens, output tokens, or another provider-defined measure.

For a self-hosted model, costs may include:

- Hardware.
- Electricity.
- Hosting.
- Maintenance.
- Operations.
- Scaling capacity.

Consider the difference between small-scale and large-scale usage.

```
A few requests
      |
      v
Cost difference may be modest
```

```
Millions of requests
      |
      v
Small per-request differences
      |
      v
Potentially substantial total cost
```

The cheapest model per request is not necessarily the cheapest model overall if it requires more retries, provides lower-quality answers, or uses more operational resources.

### 5.7 Throughput

Throughput measures how much work a system completes in a given period.

It might be measured in requests per second or generated tokens per second.

For example:

```
Server A: 100 requests/second
Server B: 20 requests/second
```

These illustrative figures suggest that Server A has higher request throughput under the stated conditions.

Throughput and latency are related but different.

A system can improve throughput by processing requests in batches, for example, but this may change the latency experienced by an individual request.

The correct objective depends on the application.

### 5.8 Memory and hardware requirements

Model weights consume memory, and inference can require additional memory for intermediate computations and the KV cache.

```
Small model
     |
     v
Lower weight-memory requirements
     |
     v
May fit on fewer devices
```

```
Large model
     |
     v
Higher weight-memory requirements
     |
     v
May require multiple GPUs
```

The actual hardware required depends on the model, numerical precision, quantization, available memory, context length, and serving configuration.

A large model may require several GPUs not only to hold the parameters but also to support efficient inference.

### 5.9 Model size does not equal model quality

This is a fundamental principle.

Suppose:

```
Model A = 70B parameters
Model B = 14B parameters
```

You cannot conclude that Model A performs better on every task solely from those numbers.

A smaller model may outperform a larger model for a particular workload because of differences in:

- Training data.
- Architecture.
- Training quality.
- Post-training.
- Task specialization.
- Inference techniques.

Performance must be assessed against the specific task and evaluation criteria.

### 5.10 A practical comparison

| Consideration        | Larger model              | Smaller model                    |
| -------------------- | ------------------------- | -------------------------------- |
| Model capacity       | May be greater            | May be lower                     |
| Difficult tasks      | May perform better        | May have more limitations        |
| Memory requirements  | Often higher              | Often lower                      |
| Compute requirements | Often higher              | Often lower                      |
| Latency              | Can be higher             | Can be lower                     |
| Serving cost         | Can be higher             | Can be lower                     |
| Local deployment     | May require more hardware | Often easier on limited hardware |

These comparisons describe general tendencies. The specific model and workload determine the actual outcome.

### 5.11 Section recap

Question: Is a larger model always better?

Answer: No. Parameter count is only one characteristic of a model. Training, architecture, post-training, specialization, hardware, and task requirements all influence performance.

Question: What is the difference between latency and throughput?

Answer: Latency is the time taken to complete or begin responding to a request, depending on the metric. Throughput is the amount of work completed per unit of time.

## 6. How the Concepts Work Together

The four topics should not be evaluated independently.

A model's architecture, attention mechanism, context length, and parameter count all affect its overall resource requirements.

### 6.1 Combined model-design questions

When evaluating a model, consider:

```
AI model
   |
   +-- Dense or MoE?
   |
   +-- MHA, GQA, or MQA?
   |
   +-- What context length?
   |
   +-- How many total parameters?
   |
   +-- How many active parameters?
   |
   +-- What hardware is available?
```

These choices influence:

```
Model design
     |
     v
Computation and memory
     |
     v
+----------+----------+----------+
|          |          |          |
v          v          v          v
Quality  Latency     Cost    Throughput
```

The outcome is also affected by training quality, optimization, quantization, batching, and the serving implementation.

### 6.2 How the decisions interact

Dense vs MoE influences the amount and organization of model computation.

MHA vs MQA vs GQA influences Key/Value representation sharing and KV-cache requirements.

Context length influences how much information can be processed and how much memory and computation are needed.

Model size influences weight storage and usually affects inference resource requirements.

These decisions must be considered together when estimating serving performance.

### 6.3 Example: Two hypothetical models

Suppose an engineer compares the following models.

| Property         | Model A | Model B |
| ---------------- | ------- | ------- |
| Total parameters | 14B     | 100B    |
| Architecture     | Dense   | MoE     |
| Attention        | MHA     | GQA     |
| Context window   | 32K     | 128K    |

The engineer should not immediately conclude that Model B is better or more efficient.

Instead, evaluate the design differences.

Model capacity: Model B has more total parameters, but that fact alone does not establish superior task performance.

Active computation: Model B may activate a subset of experts per token.

Attention efficiency: GQA can reduce KV-cache memory compared with comparable MHA configurations.

Context capacity: Model B supports a larger context window.

Memory: Model B may still need substantial memory for its total model weights and KV cache.

Latency: Its actual latency depends on hardware, batching, context length, routing, quantization, and implementation.

Cost: Total cost depends on the resources and operational behavior needed to serve the target workload.

### 6.4 Engineering principle

The correct decision is not simply:

> Choose the model with more parameters.

Instead:

> Choose the model that meets the application's quality requirements within its latency, memory, throughput, and cost constraints.

## 7. Real-World Model Selection Case Study

### Scenario: Building a long-document AI assistant

An organization wants to build an assistant that answers questions about lengthy technical documents.

It must support many simultaneous users while keeping response times and serving costs under control.

### Step 1: Define the requirements

Suppose the system needs to:

- Answer questions using technical documents.
- Process long input contexts.
- Serve multiple concurrent requests.
- Maintain acceptable response quality.
- Operate within a fixed hardware budget.

### Step 2: Evaluate context length

A larger context window may allow more of a document to be processed in one request.

However, more context can increase attention computation, KV-cache memory, latency, and cost.

The engineer should determine whether every request genuinely needs the entire document.

### Step 3: Evaluate retrieval

For some questions, the system may retrieve only the relevant document sections rather than include the entire collection.

This can reduce unnecessary context while preserving the information relevant to a question.

The system must still verify that its retrieval process does not omit essential information.

### Step 4: Evaluate attention architecture

If KV-cache memory becomes a bottleneck, compare suitable MHA, GQA, or MQA implementations.

For comparable dimensions, GQA and MQA can reduce K/V cache requirements relative to MHA.

Measure their actual effects on response quality, throughput, and latency.

### Step 5: Evaluate dense versus MoE

If both dense and MoE candidates meet the task requirements, compare their resource and serving characteristics.

For an MoE candidate, include the total model memory requirements, active computation, expert routing, and communication overhead in the analysis.

Do not estimate the full deployment cost from active parameter count alone.

### Step 6: Measure the model

Use a representative evaluation set and workload.

Measure:

| Metric              | What to evaluate                                   |
| ------------------- | -------------------------------------------------- |
| Answer quality      | Correctness and relevance of answers               |
| Latency             | Time to first token and overall response time      |
| Throughput          | Requests or tokens processed per second            |
| Memory              | Model weight, KV-cache, and other runtime memory   |
| Cost                | Cost per request and total operational cost        |
| Context utilization | Whether important information is successfully used |
| Concurrency         | Behavior under realistic simultaneous demand       |

### Step 7: Select the best configuration

The suitable model is the configuration that meets the required answer quality and operational constraints.

This may be a smaller dense model, a larger MoE model, or another architecture entirely. The decision must follow the evidence from task-specific testing.

Lesson: Effective model selection is a multi-objective engineering problem rather than a competition over parameter count or context-window size.

## 8. Common Misconceptions

### Misconception 1: More parameters always mean better answers.

Correction: Parameters provide one measure of model size and capacity. Training quality, architecture, post-training, and task-specific performance also matter.

### Misconception 2: An MoE model with 20B active parameters is simply a 20B model.

Correction: Active parameters describe a particular computation. The full model can still contain many more parameters, with different storage and capacity characteristics.

### Misconception 3: MoE models are automatically cheaper.

Correction: They can reduce active expert computation, but routing, memory, communication, and distributed execution introduce overhead.

### Misconception 4: MHA, MQA, and GQA differ in the number of Query heads only.

Correction: Their key distinction is how Key and Value representations are shared across Query heads.

### Misconception 5: A smaller KV cache means the entire model uses proportionally less memory.

Correction: The KV cache is only one part of runtime memory. Model weights, intermediate activations, workspace, and other components also consume memory.

### Misconception 6: A larger context window guarantees better document understanding.

Correction: It allows more information to be accepted, but the model may not use every relevant detail effectively.

### Misconception 7: Standard attention complexity explains every part of inference cost.

Correction: The \\(O(n^2)\\) rule describes attention interactions for standard full self-attention. End-to-end inference cost varies with the operation, implementation, cache usage, and hardware.

### Misconception 8: The lowest-latency model is always the best production model.

Correction: The model must also meet quality, cost, memory, throughput, and reliability requirements.

## 10. Key Takeaways

### Dense vs MoE

- Dense models use dense computational pathways.
- MoE models route computation to selected experts.
- Total parameters and active parameters are different quantities.
- MoE can provide large total capacity without activating every expert for every token.
- Routing, memory, and communication may offset computational savings.

### MHA vs MQA vs GQA

- MHA gives each standard attention head its own K/V representations.
- MQA shares one K/V set across multiple Query heads.
- GQA shares K/V representations within groups of Query heads.
- Less K/V duplication can reduce KV-cache memory.
- GQA offers an intermediate design between MHA and MQA.

### Long context

- A larger context window enables more information to be supplied in a request.
- Standard full self-attention has \\(O(n^2)\\) attention interaction complexity.
- KV-cache memory generally increases with the number of cached tokens.
- More context does not guarantee perfect understanding.
- Context capacity and context utilization must be evaluated separately.

### Model size, latency, and cost

- Larger models may provide greater capacity but usually require more resources.
- Smaller models may be faster, cheaper, and easier to deploy.
- Parameter count alone does not establish model quality.
- Latency and throughput are different metrics.
- The right model is the one that meets quality and operational requirements.

## 11. Practice & Recall Pack

### 11.1 Easy — Fundamental Questions

Question 1: What is a dense model?

Answer: A dense model uses dense computational pathways through its network layers when processing tokens.

Question 2: What is an MoE model?

Answer: A Mixture-of-Experts model contains multiple expert components and uses a router to activate a subset of them for a particular computation.

Question 3: What is the difference between total and active parameters?

Answer: Total parameters count the parameters in the complete model. Active parameters count the parameters participating in a specified computation.

Question 4: What do MHA, MQA, and GQA stand for?

Answer: Multi-Head Attention, Multi-Query Attention, and Grouped-Query Attention.

Question 5: What is a KV cache?

Answer: It stores Key and Value representations from previously processed tokens so that autoregressive inference can reuse them instead of recomputing all previous representations from scratch.

Question 6: What is context length?

Answer: It describes how much tokenized information the model can accommodate in a request under its context rules.

Question 7: What is latency?

Answer: Latency is the time taken to process a request or produce a response, depending on the particular latency metric.

Question 8: What is throughput?

Answer: Throughput measures how much work, such as requests or generated tokens, a system processes per unit of time.

### 11.2 Medium — Understanding and Comparison

Question 9: Why can an MoE model have a large total parameter count but lower active parameter count per token?

Answer: The model contains many expert components, but its router selects only a subset for the relevant computation. The complete model's parameter count can therefore be much larger than the active parameter count for a token.

Question 10: Why can MQA reduce KV-cache memory relative to MHA?

Answer: MQA uses a shared Key and Value set across its Query heads. Fewer K/V heads mean fewer K/V representations need to be stored per cached token, assuming comparable dimensions and cache precision.

Question 11: How does GQA differ from MQA?

Answer: GQA uses multiple K/V groups, with each group shared by several Query heads. MQA uses one shared K/V set across all Query heads. GQA therefore offers an intermediate degree of K/V sharing.

Question 12: Why does long context increase KV-cache memory requirements?

Answer: More cached tokens require more Key and Value representations to be retained. For a fixed architecture and representation, KV-cache memory generally grows linearly with the number of cached tokens.

Question 13: Explain the significance of \\(O(n^2)\\) in standard full self-attention.

Answer: It describes quadratic scaling in the number of attention interactions with sequence length \\(n\\). Doubling the sequence length can produce approximately four times as many token-pair interactions under this simplified complexity model.

Question 14: Why does a large context window not guarantee better answers?

Answer: A large context window indicates how much information can be accepted, not whether every relevant detail will be identified and used correctly. Context utilization must be evaluated separately.

Question 15: Why might a smaller model be preferable in a high-volume application?

Answer: If it meets the quality requirements, a smaller model may reduce per-request compute, hardware requirements, latency, or cost. The final decision should be based on actual performance and operational measurements.

### 11.3 Hard — Technical Reasoning

Question 16: An MoE model has 100B total parameters and 20B active parameters per token. What does this tell you about its memory requirements?

Answer: It indicates that the model activates approximately 20B parameters in the specified token computation, but it does not mean only 20B parameters need to be stored. The full model may require memory for its larger parameter set, depending on how the model is distributed and served. The KV cache and other runtime memory must also be accounted for.

Question 17: Suppose a model's context increases from 8K to 64K tokens. What resource changes should you consider?

Answer: The sequence is eight times longer. For comparable conditions, the KV cache can require roughly eight times as much memory. Standard full-attention token-pair interactions can scale by a factor of \\(8^2=64\\), although actual compute and latency depend on the implementation. The increased context may also affect cost and concurrency.

Question 18: Why is active parameter count insufficient for predicting MoE inference latency?

Answer: Latency also depends on routing, expert placement, memory bandwidth, inter-device communication, batch size, kernel efficiency, hardware, context length, and other serving overheads. Active parameter count alone does not account for these factors.

Question 19: Could GQA improve throughput even if the generated answer quality remains approximately the same? Explain.

Answer: Yes. If GQA reduces KV-cache memory and memory traffic, the system may support more concurrent requests or use available hardware more efficiently. The actual throughput improvement must be measured because computation, batching, and other bottlenecks may still dominate.

Question 20: Why can a model with fewer parameters sometimes outperform a model with more parameters?

Answer: Parameter count does not determine performance on every task. Differences in training data, architecture, post-training, task specialization, and inference methods may allow a smaller model to achieve better results on a particular workload.

### 11.4 Hard — Scenario-Based Interview Questions

Question 21: You are serving thousands of concurrent chatbot requests. KV-cache memory has become the main bottleneck. What would you investigate?

Answer: Investigate the context-length distribution, cache precision, concurrent sequence count, attention configuration, and available hardware. Compare MHA with suitable GQA or MQA implementations because fewer K/V heads may reduce memory per cached token. Also consider whether the application unnecessarily includes large amounts of context. Validate the changes against answer quality, latency, and throughput.

Question 22: An MoE model requires several GPUs even though its active parameter count is relatively small. Why might this happen?

Answer: The complete model's parameters may still need to be stored or distributed across devices. Expert placement, memory constraints, shared layers, and runtime requirements can necessitate multiple GPUs. In addition, communication among devices can influence latency and throughput.

Question 23: A model supports a 128K context window, but it misses important instructions embedded in the middle of long documents. What should you investigate?

Answer: Investigate long-context utilization rather than only context capacity. Test whether relevant information is missed based on its position, use retrieval to surface important passages when appropriate, and evaluate how the model handles realistic document questions. A model accepting 128K tokens does not guarantee that every detail will be used correctly.

Question 24: You must choose between a 70B dense model and a 100B-total-parameter MoE model with 20B active parameters. Which is more efficient?

Answer: The provided parameter counts are insufficient to determine the answer. Evaluate task-specific quality, active computation, total weight memory, routing overhead, KV-cache requirements, hardware, latency, throughput, and operating cost. The MoE model may have lower expert computation per token, but its total deployment efficiency depends on the complete system.

Question 25: A smaller model responds quickly but fails difficult reasoning questions. A larger model is more accurate but expensive. How would you design the application?

Answer: First assess how frequently the difficult questions occur and the required accuracy. A potential design is to use the smaller model for straightforward requests and route demanding requests to the larger model. Evaluate routing accuracy, end-to-end latency, total operating cost, and answer quality. The design should be justified by workload measurements rather than assuming that a two-model strategy will always be better.

Question 26: An engineer argues that increasing context from 32K to 128K automatically improves an AI assistant. How would you evaluate that claim?

Answer: Test whether the longer context improves accuracy on realistic tasks, especially those requiring information distributed across a document. Also measure inference latency, KV-cache memory, concurrency, and cost. A larger context window is beneficial when it improves results enough to justify its resource requirements; the window size alone does not establish better performance.
