# M04.3.1.1 — Architecture Concepts Worth Knowing

These four topics are important because they help you understand **why one AI model is faster, cheaper, or better at long inputs than another**.

The four concepts are:

1. **Dense vs Mixture-of-Experts (MoE)**
2. **MHA vs MQA vs GQA**
3. **Long-context tradeoffs**
4. **Model size vs latency/cost tradeoffs**

Let's start from the basics.

---

# 1. Dense vs Mixture-of-Experts Models

First, remember what a **parameter** is.

A parameter is a learned number inside a neural network.

A model might have:

```text
7 billion parameters
70 billion parameters
400 billion parameters
```

More parameters generally mean more model capacity, but **parameter count alone does not tell you how much computation happens for every token**.

That's where Dense vs MoE becomes important.

---

## 1.1 Dense Models

A **dense model** is the simpler design.

For each input token, essentially the same full set of model layers participates.

Conceptually:

```text
Input
  ↓
Layer 1
  ↓
Layer 2
  ↓
Layer 3
  ↓
Layer 4
  ↓
Output
```

You can imagine:

```text
100% of the network participates
```

for each token, subject to the details of the architecture.

---

## Simple analogy

Imagine a company with 10 employees.

A customer asks a question.

In a dense setup:

```text
Customer question
       ↓
All 10 employees work
       ↓
Answer
```

That is simple, but potentially expensive.

---

# 1.2 Mixture-of-Experts (MoE)

MoE introduces multiple **experts** inside parts of the model.

Instead of using all experts for every token:

```text
Input
  ↓
Router
  ↓
Choose some experts
  ↓
Selected experts
  ↓
Output
```

For example:

```text
                 Input
                   ↓
                 Router
          ┌────────┼────────┐
          ↓        ↓        ↓
       Expert 1 Expert 2 Expert 3
                   ✓
                   ✓
                 Selected
```

The router decides which experts should process a token.

---

## 1.3 Why call them "experts"?

The model can learn different patterns in different expert components.

For example, conceptually:

```text
Expert 1 → coding-related patterns
Expert 2 → language patterns
Expert 3 → mathematical patterns
Expert 4 → other patterns
```

Don't take this too literally.

The experts are **not necessarily explicitly programmed** to be "the coding expert" or "the math expert."

They learn useful specializations during training.

---

# 1.4 Total Parameters vs Active Parameters

This is one of the most important things to understand about MoE.

Suppose a model has:

```text
Total parameters = 100B
```

but only some experts are activated for each token:

```text
Active parameters ≈ 20B
```

Then:

```text
Total model capacity → 100B
Per-token computation → closer to 20B
```

The exact relationship depends on the architecture, but this is the basic idea.

---

## Dense vs MoE

| Dense | MoE |
|---|---|
| Most/all parameters participate for each token | Only selected experts participate |
| Simpler architecture | More complex architecture |
| Computation scales with full network | Can have large total capacity with lower active computation |
| Easier to reason about/deploy | Routing and distributed systems are more complicated |

---

## 1.5 Why use MoE?

The main attraction is:

> **Large model capacity without using the entire model for every token.**

Imagine:

```text
Dense

100B parameters
↓
100B active for each token
```

versus:

```text
MoE

100B total parameters
↓
20B active for each token
```

The MoE model can have a much larger total capacity while reducing the computation per token compared with activating everything.

However, this does **not** mean MoE automatically makes everything cheap or easy.

There can be significant:

- Routing overhead
- Memory requirements
- GPU-to-GPU communication
- Distributed inference complexity

---

# 2. MHA vs MQA vs GQA

This topic is inside the **attention mechanism** of Transformers.

Before understanding MHA/MQA/GQA, remember that Transformer attention uses:

```text
Q = Query
K = Key
V = Value
```

For every token, attention essentially asks:

> "Which other tokens should I pay attention to?"

---

# 2.1 Why do we care about Q, K and V?

Suppose you have:

```text
"The cat sat on the mat because it was tired."
```

When processing **"it"**, the model may need to determine that "it" refers to "cat."

Attention uses Query, Key, and Value representations to determine relevant relationships.

You don't need the full math yet.

The architecture question is:

> **How many Query/Key/Value heads do we maintain?**

That's where MHA, MQA and GQA differ.

---

# 2.2 MHA — Multi-Head Attention

**MHA = Multi-Head Attention**

This is the traditional approach.

Imagine:

```text
8 attention heads
```

Each head has its own:

```text
Q
K
V
```

So:

```text
Head 1 → Q1 K1 V1
Head 2 → Q2 K2 V2
Head 3 → Q3 K3 V3
...
Head 8 → Q8 K8 V8
```

Conceptually:

```text
             Input
               ↓
    ┌──────┬──────┬──────┐
    ↓      ↓      ↓      ↓
  Head 1  Head 2 Head 3 ... Head 8
    ↓      ↓      ↓      ↓
           Combine
              ↓
            Output
```

---

## Advantage

MHA gives the model lots of flexibility because different heads can learn different attention patterns.

## Disadvantage

It requires more memory for the **Key/Value cache**, especially during inference.

This becomes important for long conversations.

---

# 2.3 MQA — Multi-Query Attention

**MQA = Multi-Query Attention**

Instead of giving every attention head its own K and V:

```text
Many Q heads
+
One shared K
+
One shared V
```

Conceptually:

```text
Q1 ─┐
Q2 ─┤
Q3 ─┤
Q4 ─┤
    ├── Shared K
    └── Shared V
```

So:

```text
Multiple Q heads
        +
Shared K/V
```

---

## Why is that useful?

During inference, the model often stores previous K and V vectors in something called the:

> **KV cache**

Sharing K/V reduces how much memory is needed.

That can improve:

- Memory efficiency
- Inference efficiency
- Throughput

---

## Tradeoff

The model has less independent K/V information than full MHA, so there can be some loss in modeling flexibility or quality depending on the implementation and model.

So:

```text
MHA
→ More K/V memory
→ More flexibility

MQA
→ Less K/V memory
→ More efficient
```

---

# 2.4 GQA — Grouped-Query Attention

GQA is essentially a middle ground.

**GQA = Grouped-Query Attention**

Instead of:

```text
Every Q gets its own K/V
```

or:

```text
All Q share one K/V
```

we group several Query heads together and let each group share K/V.

Example:

```text
8 Query heads
4 K/V heads
```

Conceptually:

```text
Q1 ─┐
Q2 ─┤ → K/V Group 1
    │

Q3 ─┐
Q4 ─┤ → K/V Group 2
    │

Q5 ─┐
Q6 ─┤ → K/V Group 3
    │

Q7 ─┐
Q8 ─┤ → K/V Group 4
    │
```

So:

```text
MHA → 8 Q / 8 K / 8 V

GQA → 8 Q / 4 K / 4 V

MQA → 8 Q / 1 K / 1 V
```

This is simplified but gives you the right intuition.

---

# 2.5 The easiest way to remember MHA/MQA/GQA

Think about K/V sharing:

```text
MHA
Q Q Q Q
K K K K
V V V V

MQA
Q Q Q Q
   K
   V

GQA
Q Q Q Q
K K
V V
```

Or:

```text
MHA → No sharing
GQA → Some sharing
MQA → Maximum sharing
```

---

# 2.6 Why does this matter in real systems?

Because of the **KV cache**.

Suppose you are chatting with an AI:

```text
You:
Hello

AI:
Hi

You:
Explain...

AI:
...
```

As the conversation gets longer, the model needs to work with previous tokens.

During generation, the system can cache previous **K and V values** rather than recomputing them from scratch.

A rough conceptual picture:

```text
Previous tokens
      ↓
K/V Cache
      ↓
New token generation
```

The larger the context, the larger this cache can become.

Therefore:

```text
Smaller K/V representation
        ↓
Smaller KV cache
        ↓
Lower memory pressure
        ↓
Potentially better inference efficiency
```

That's why MQA and GQA are particularly interesting for modern LLM serving.

# 3. Long-Context Tradeoffs

Now let's discuss **context length**.

Context is the information the model can consider during a single interaction.

For example:

```text
Short context:

5,000 tokens
```

versus:

```text
Long context:

100,000+ tokens
```

The exact limits depend on the model.

---

## 3.1 What is context?

Suppose you ask:

```text
Here is a 300-page document.

Summarize chapter 7.
```

The model needs access to some or all of that document.

The document becomes part of the model's context.

Conceptually:

```text
System instructions
+
Conversation
+
Documents
+
User question
        ↓
     Context
        ↓
      Model
```

---

# 3.2 Why is long context useful?

It allows you to work with larger amounts of information in one interaction.

Useful for:

- Large documents
- Long conversations
- Large codebases
- Research materials
- Legal documents
- Meeting transcripts
- Multiple files

---

# 3.3 But longer context is NOT free

This is important.

Many beginners think:

> "If a model supports 1 million tokens, that's automatically better."

Not necessarily.

Longer context can increase:

- Memory usage
- Computation
- Latency
- Cost
- Serving complexity

---

# 3.4 The quadratic attention problem

In standard self-attention, attention interactions can scale approximately with:

\[
O(n^2)
\]

where:

```text
n = number of tokens
```

Why?

Because tokens may need to interact with many other tokens.

For example:

```text
100 tokens
≈ 100 × 100 interactions

10,000 tokens
≈ 10,000 × 10,000 interactions
```

That's a huge difference.

You don't need to memorize the exact calculation yet.

Just remember:

> **Traditional attention becomes increasingly expensive as context grows.**

Modern models use many techniques to make long-context processing more practical, so real-world scaling is more nuanced than simply applying an \(n^2\) rule everywhere.

---

# 3.5 Long context also increases KV cache size

During inference:

```text
Longer context
      ↓
More previous tokens
      ↓
More K/V information
      ↓
Larger KV cache
      ↓
More memory usage
```

And this is exactly where:

```text
MHA
GQA
MQA
```

become relevant.

---

# 3.6 Example

Imagine:

```text
Context = 4K tokens
```

The KV cache might be manageable.

Now:

```text
Context = 128K tokens
```

There are dramatically more tokens to account for.

If you have millions of requests running across a serving fleet, KV-cache memory becomes a major systems concern.

---

# 3.7 Long context doesn't mean perfect understanding

Another important point:

> A model being able to accept a large context window does not guarantee that it will use every piece of information equally well.

For example, a model might technically accept:

```text
500,000 tokens
```

but information buried deep inside that context may be harder for the model to use effectively.

This is sometimes discussed through ideas such as:

> **"Lost in the middle"**

Meaning relevant information placed in the middle of a very long context can sometimes be used less effectively than information near the beginning or end.

So there are two different questions:

```text
How much can the model accept?
```

and:

```text
How well can the model use it?
```

These are not the same thing.

---

# 4. Model Size vs Latency/Cost Tradeoffs

This is probably the most practical concept for an AI engineer.

Suppose you have:

```text
Model A = 7B parameters
Model B = 70B parameters
```

You might assume:

> 70B must always be the better choice.

But deploying an AI system isn't just about model quality.

You also care about:

- Latency
- Cost
- Memory
- Throughput
- Hardware requirements
- User experience

---

# 4.1 Bigger model

A larger model generally has:

```text
More parameters
      ↓
More capacity
      ↓
Potentially stronger performance
      ↓
But usually more compute/memory
```

So:

```text
Large model
→ potentially better capability
→ more expensive
→ potentially slower
→ more hardware
```

Again, this is a general tendency, not a law. Model architecture and optimization matter.

---

# 4.2 Smaller model

A smaller model may provide:

```text
Fewer parameters
      ↓
Less computation
      ↓
Lower hardware requirements
      ↓
Lower cost
      ↓
Potentially faster response
```

But potentially:

```text
Lower capability on difficult tasks
```

So there is a tradeoff.

---

# 4.3 Latency

**Latency** means:

> How long it takes to get a response.

For example:

```text
Model A → 300 ms
Model B → 2 seconds
```

The first model has lower latency in this example.

For a chatbot, latency strongly affects user experience.

---

# 4.4 Cost

Suppose an API charges based on tokens.

A larger model may cost more per input/output token.

Then:

```text
1 request
     ↓
Large model
     ↓
Higher cost
```

At:

```text
1 user
```

you may not care much.

At:

```text
10 million requests
```

it becomes a major business issue.

---

# 4.5 Throughput

**Throughput** means:

> How many requests/tokens your system can process over a period of time.

For example:

```text
Server A
→ 100 requests/sec

Server B
→ 20 requests/sec
```

Even if Server B gives better answers, Server A may be more suitable for a massive application depending on requirements.

---

# 4.6 Memory requirements

Large models require more memory.

For example, conceptually:

```text
Small model
↓
Fits on one GPU

Large model
↓
May require multiple GPUs
```

And that affects:

- Infrastructure cost
- Deployment complexity
- Scaling
- Power consumption
- Operational complexity

---

# 5. Model Size Isn't the Same as Model Quality

This is very important.

Suppose:

```text
Model A = 70B parameters
Model B = 14B parameters
```

You cannot conclude:

```text
70B > 14B
```

in every task.

A smaller model can outperform a larger one if it has:

- Better training data
- Better architecture
- Better post-training
- Better reasoning techniques
- Better task specialization
- Better inference methods

So:

> **Parameter count is one characteristic, not a complete measure of model quality.**

---

# 6. Putting Everything Together

Now you can see how these concepts interact.

Suppose you are building an AI application.

You select:

```text
Model
│
├── Dense or MoE?
│
├── MHA / GQA / MQA?
│
├── Context length?
│
├── Number of parameters?
│
└── Deployment hardware?
```

These architectural decisions affect:

```text
Performance
    │
    ├── Quality
    ├── Latency
    ├── Cost
    ├── Memory
    └── Throughput
```

---

# 7. A Realistic Example

Imagine you have two models:

```text
Model A
14B parameters
Dense
MHA
32K context

Model B
100B total parameters
MoE
GQA
128K context
```

You should not simply say:

> "Model B is better."

Instead, ask:

### Model capacity

Model B has larger total capacity.

### Active computation

Because it's MoE, it may use only a subset of experts per token.

### Attention efficiency

GQA can reduce KV-cache memory compared with full MHA.

### Context

Model B supports a much larger context.

### Cost

Model B may still be more expensive to operate because total memory and system complexity can be substantial.

### Latency

It depends on hardware, batch size, serving stack, routing, quantization, and many other factors.

This is why **model selection is an engineering tradeoff**, not simply a parameter-count competition.

# 10. Interview Notes

### Q: What is a dense model?

A dense model is one where essentially the full model participates in processing each token.

### Q: What is an MoE model?

An MoE model contains multiple experts and uses a routing mechanism to activate only a subset of experts for a given input.

### Q: What is the difference between total and active parameters in MoE?

**Total parameters** represent the complete model capacity, while **active parameters** refer roughly to the parameters participating in processing a particular token.

### Q: What is MHA?

Multi-Head Attention, where each attention head has its own Q, K and V projections.

### Q: What is MQA?

Multi-Query Attention, where multiple Query heads share Key and Value representations.

### Q: What is GQA?

Grouped-Query Attention, where groups of Query heads share Key/Value representations.

### Q: Why is GQA useful?

It reduces KV-cache memory compared with standard MHA while retaining more flexibility than MQA.

### Q: Why is long context expensive?

Because more tokens require more attention computation and larger inference-state memory such as the KV cache.

### Q: Is a bigger model always better?

No. Model architecture, training, data, post-training, task, latency, cost, and deployment constraints all matter.
