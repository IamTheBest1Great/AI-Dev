# M04.3.1 — Modern Model Families and Capabilities

This topic is about understanding **different kinds of AI models and what each one is designed to do**.

A common beginner mistake is to think:

> “AI model = chatbot.”

That is not true.

A chatbot is only **one possible application** of AI models.

Different models are specialized for different jobs:

```text
                    AI MODELS
                        │
      ┌─────────────────┼─────────────────┐
      │                 │                 │
   Text              Vision             Audio
      │                 │                 │
      │                 │                 └── Speech / Audio models
      │                 │
      │                 └── Vision-Language
      │
      ├── General-purpose language
      └── Reasoning-oriented

      Retrieval
      ├── Embedding models
      └── Rerankers

      Generation
      ├── Image generation
      └── Video generation

      Deployment / Architecture
      ├── Small / Local models
      └── Mixture-of-Experts
```

Let's understand each one from the beginning.

---

# 1. General-Purpose Language Models

## What are they?

A **general-purpose language model** is an AI model designed primarily to understand and generate text.

It can perform many language-related tasks instead of being built for only one specific task.

### Examples of tasks

A general language model can:

- Answer questions
- Write emails
- Summarize text
- Translate languages
- Generate code
- Explain concepts
- Extract information
- Rewrite content
- Have conversations

For example:

```text
User:
Explain Docker in simple terms.

Model:
Docker is a way to package an application...
```

---

## Basic idea

The model receives text:

```text
"What is React?"
```

and generates text:

```text
"React is a JavaScript library used to build user interfaces..."
```

Internally, language models work with **tokens**.

You already learned:

```text
Text
  ↓
Tokenization
  ↓
Tokens
  ↓
Transformer model
  ↓
Next-token prediction
  ↓
Generated text
```

---

## Why are they called "general-purpose"?

Because one model can do many things.

For example:

```text
               One Model
                  │
       ┌──────────┼───────────┐
       ↓          ↓           ↓
     Coding    Writing     Translation
       │          │           │
       ↓          ↓           ↓
   Debug code   Email       English → Hindi
```

Instead of having:

```text
Model A → only translation
Model B → only summarization
Model C → only coding
```

you can have a general model capable of several tasks.

---

## When would you use one?

Use a general-purpose language model when you need:

> **A broad AI assistant capable of many text tasks.**

---

# 2. Reasoning-Oriented Models

This is one of the most important distinctions.

A **reasoning-oriented model** is designed to perform better on problems requiring **multiple steps of logical processing**.

Think:

```text
Normal language task

Question
   ↓
Answer
```

versus:

```text
Complex reasoning task

Question
   ↓
Understand problem
   ↓
Break into steps
   ↓
Evaluate possibilities
   ↓
Solve
   ↓
Answer
```

---

## Example

Suppose you ask:

```text
A train travels 120 km in 2 hours.
Another train travels 180 km in 3 hours.
Which is faster?
```

This is easy.

But consider:

```text
You have 5 constraints,
3 possible schedules,
different dependencies,
and some conditions conflict.

Find a valid schedule.
```

Now the model needs more involved reasoning.

---

## Where are reasoning models useful?

Especially:

- Mathematics
- Complex coding
- Algorithms
- Planning
- Multi-step logic
- Scientific reasoning
- Difficult problem solving
- Tasks involving many constraints

---

## Important distinction

A reasoning model is **not necessarily a completely different species of model**.

It is better to think:

```text
Language model
     +
More emphasis on reasoning/problem solving
     ↓
Reasoning-oriented model
```

Modern model families can have both:

- general language capabilities
- stronger reasoning capabilities

---

## Simple analogy

Imagine two students.

### Student A

Good at:

- Speaking
- Writing
- General knowledge

### Student B

Also good at those things, but spends more time carefully solving:

- Mathematics
- Logic
- Complex programming

Student B is similar to the idea of a **reasoning-oriented model**.

# 5. Embedding Models

This concept is extremely important when you start building **RAG applications, semantic search, recommendation systems, and vector databases**.

An **embedding model converts information into a numerical vector**.

Don't let the word "vector" scare you.

Think of it as:

> Turning text into a list of numbers that represents its meaning.

---

## Example

Suppose you have:

```text
"The cat is sleeping."
```

An embedding model might conceptually produce:

```text
[0.12, -0.43, 0.87, 0.19, ...]
```

Maybe hundreds or thousands of numbers.

The exact numbers aren't important to you.

The important thing is:

> Similar meanings tend to produce vectors that are close to each other in vector space.

---

## Example

These sentences are semantically similar:

```text
"I love dogs."

"I really like puppies."
```

Their embeddings may be relatively close.

But:

```text
"The database connection failed."
```

would be much farther away.

---

## Why do we need embeddings?

Because computers need a way to compare **meaning**.

Imagine a database containing:

```text
Document 1:
How to reset your password

Document 2:
How to change your email

Document 3:
How to restart your server
```

User asks:

```text
"I forgot my password. How can I get access again?"
```

Keyword matching might struggle.

Embedding-based search can recognize that:

```text
forgot password
```

is semantically related to:

```text
reset password
```

---

## Embeddings are heavily used in RAG

A typical RAG system:

```text
Documents
    ↓
Embedding Model
    ↓
Vectors
    ↓
Vector Database
```

Then:

```text
User Question
      ↓
Embedding Model
      ↓
Query Vector
      ↓
Similarity Search
      ↓
Relevant Documents
      ↓
LLM
      ↓
Answer
```

---

## Important

An embedding model normally does **not** generate a long conversational answer.

Its job is mainly:

> **Represent meaning numerically.**

---

# 6. Rerankers

Rerankers are closely related to search.

Suppose you search:

```text
"How do I reset my password?"
```

Your search system retrieves 20 documents.

Something needs to determine:

> Which of these 20 documents are actually the most relevant?

That's where a **reranker** can help.

---

## Typical pipeline

```text
User Query
    ↓
Embedding Model
    ↓
Retrieve 20 documents
    ↓
Reranker
    ↓
Best 5 documents
    ↓
LLM
```

---

## Why not let embeddings do everything?

Embedding search is usually optimized for **fast retrieval from a large collection**.

A reranker can perform a more detailed comparison between:

```text
Query
   +
Document
```

and assign a relevance score.

Conceptually:

```text
Query:
"How do I reset my password?"

Document A → 0.95
Document B → 0.81
Document C → 0.23
Document D → 0.12
```

Then you keep the highest-ranked results.

---

## Simple analogy

Imagine searching Google.

### Embedding model

Finds:

> "These 100 pages seem related."

### Reranker

Then says:

> "Among these 100, these 5 are the most relevant to the exact question."

---

## Embedding vs Reranker

| Embedding Model | Reranker |
|---|---|
| Converts text to vectors | Scores query-document relevance |
| Used for retrieval | Used after retrieval |
| Very useful for semantic search | Improves ranking of retrieved results |
| Fast comparison | More detailed comparison |
| Can search huge datasets | Usually works on a smaller candidate set |

Remember:

```text
Embedding = Retrieve
Reranker = Refine the ranking
```

That's a very useful mental model.




```text

      ↓

      ↓
Broader audio + language understanding
```

There can be significant overlap between these categories.

# 10. Small / Local Models

Now we're moving from **what a model can do** to **where/how it can run**.

A **small model** generally has fewer parameters and computational requirements than a very large model.

For example, conceptually:

```text
Large model
100B+ parameters

        vs

Small model
1B–10B parameters
```

The exact size boundaries vary, so don't treat these numbers as strict definitions.

---

## Why use a smaller model?

Because it can be:

- Faster
- Cheaper
- Easier to deploy
- Easier to run on local hardware
- More private
- Suitable for edge devices

---

## Local model

A local model runs on your own machine or infrastructure instead of sending every request to a remote API.

For example:

```text
Your Laptop
    ↓
Local AI Model
    ↓
Response
```

Instead of:

```text
Your Laptop
    ↓
Internet
    ↓
Cloud AI API
    ↓
Response
```

---

## Why would someone run a model locally?

### Privacy

Sensitive information can potentially remain inside your environment.

### Cost

You may avoid paying per API request.

### Offline usage

Some models can run without an internet connection once downloaded.

### Latency

For certain workloads, local inference can be fast.

---

## But there is a tradeoff

Small models generally have fewer resources available than huge models.

Conceptually:

```text
Bigger model
   ↑
Potentially stronger capabilities
   ↓
More compute / memory / cost

Smaller model
   ↑
Cheaper / easier to run
   ↓
Potentially weaker on difficult tasks
```

This is not an absolute rule—model architecture, training, quantization, and task all matter.

# 11. Mixture-of-Experts (MoE) Models

This sounds complicated, but the basic idea is actually simple.

**Mixture-of-Experts** means a model contains multiple specialized components called **experts**.

Instead of sending every input through every expert, the model can route the input to a subset of them.

---

## Simple analogy

Imagine a company:

```text
                 Manager
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   Engineer      Designer     Accountant
```

A customer asks:

> "Fix this database problem."

The manager sends the problem mainly to:

```text
Engineer
```

rather than making:

```text
Engineer + Designer + Accountant
```

all work on it.

An MoE model uses a similar routing idea.

---

# 12. How MoE works

A simplified view:

```text
Input
  ↓
Router
  ↓
Choose relevant experts
  ↓
Expert 2 + Expert 5
  ↓
Combine results
  ↓
Output
```

For example:

```text
                 Input
                   ↓
                 Router
              /    |    \
             /     |     \
         Expert1 Expert2 Expert3
                   ✓
                   ✓
                 Active
```

Only some experts may be activated for a particular token/input.

---

## Why is this useful?

It can provide:

> **A very large total model capacity without requiring all parameters to be used for every token.**

That's the key concept.

---

## "Total parameters" vs "active parameters"

This is very important when reading modern AI model specifications.

Suppose an MoE model has:

```text
Total parameters = 100B
```

but for a given token it activates only:

```text
Active parameters = 20B
```

Then the model has:

```text
100B total capacity
```

but doesn't necessarily compute with all 100B parameters for every token.

---

# 13. Why Use MoE?

Potential advantages include:

- Greater model capacity
- More efficient computation for some workloads
- Specialized experts
- Scaling model size without activating everything every time

But MoE also introduces additional engineering complexity, such as:

- Routing
- Load balancing
- Distributed inference/training
- Communication overhead

So MoE isn't simply "better." It is an **architecture/design choice**.

# 15. The Most Important Differences

Let's put everything together.

| Model Type | Main Input | Main Output | Main Purpose |
|---|---|---|---|
| General-purpose language model | Text | Text | General language tasks |
| Reasoning-oriented model | Text / multimodal | Text / actions | Complex multi-step reasoning |
| Vision-language model | Image + text | Text | Understand visual information |
| Audio-language model | Audio + text | Text / other outputs | Understand audio |
| Embedding model | Text/images/etc. | Vector | Represent meaning |
| Reranker | Query + candidates | Relevance scores/ranking | Improve search results |
| Speech model | Speech/text | Text/audio | Speech recognition or synthesis |
| Image generation model | Text/image | Image | Create or edit images |
| Video generation model | Text/image/video | Video | Create video |
| Small/local model | Depends | Depends | Efficient/private/local deployment |
| MoE model | Depends | Depends | Architecture using routed experts |

# 27. What Should You Remember for Interviews?

You don't need to memorize every model name.

Understand these **core concepts**:

### General-purpose language model

> A broad model for understanding and generating language.

### Reasoning model

> A model optimized for difficult multi-step problem solving.

### Vision-language model

> A model that understands images together with language.

### Audio-language model

> A model that understands audio together with language.

### Embedding model

> Converts information into vectors representing semantic meaning.

### Reranker

> Reorders retrieved candidates according to their relevance to a query.

### Speech model

> Handles speech tasks such as speech recognition and speech synthesis.

### Image generation model

> Generates or edits images.

### Video generation model

> Generates or edits video.

### Small/local model

> A relatively lightweight model that can be efficiently deployed, including on local hardware.

### MoE model

> A model containing multiple experts where a routing mechanism activates only a subset for a given input.
