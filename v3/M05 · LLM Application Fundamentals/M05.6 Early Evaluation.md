# 1. M05.6 Early Evaluation

## Simple Definition

**Early evaluation** means testing an AI system **soon after the first model integration**, before investing heavily in prompts, application logic, infrastructure, or production rollout.

The goal is to answer:

> **"Does this model and implementation work well enough for our actual task?"**

A simple lifecycle is:

```text id="xv5b1v"
First Model Integration
        ↓
Small Representative Dataset
        ↓
Run Evaluation
        ↓
Measure
 ┌──────┼──────────┐
 ↓      ↓          ↓
Correctness       Latency     Cost
 └──────┬──────────┘
        ↓
Record Failures
        ↓
Improve
        ↓
Evaluate Again
```

---

## Why Evaluate Early?

Suppose you spend two weeks building:

```text id="2n3itb"
Complex prompts
+
Agent workflow
+
Database integration
+
Frontend
+
Caching
+
Production infrastructure
```

and later discover that the selected model performs poorly on the actual task.

Much of that work may need to be redesigned.

Early evaluation reduces this risk.

### Core principle

> **Validate the model-task fit before optimizing the surrounding system.**

---

# 1.1 M05.6.1 First Model Integration

The first model integration should be treated as an **experiment**, not as the final production implementation.

At this stage, focus on obtaining a reliable baseline.

```text id="a7xg6p"
Simple Integration
       ↓
Representative Dataset
       ↓
Measure Performance
       ↓
Understand Failures
       ↓
Decide Next Direction
```

The three core activities are:

1. Version a small representative dataset.
2. Measure correctness, latency and cost.
3. Record failure cases from the first implementation.

---

# 1.1.1 Version a Small Representative Dataset

## Definition

A **representative dataset** is a collection of test inputs that reflects the kinds of inputs the real system is expected to receive.

The dataset should be:

- Small enough to run quickly
- Large enough to reveal meaningful patterns
- Representative of real use cases
- Versioned so results can be reproduced

---

## Why Not Test One Example?

Suppose you test:

```text id="q13d7p"
Input:
"What is React?"
```

The model gives an excellent answer.

You might conclude:

```text id="s0nvh3"
Model = Good
```

But one example tells you almost nothing about general performance.

A better dataset contains different types of cases:

```text id="w8cyn5"
Normal cases
+
Difficult cases
+
Edge cases
+
Representative real-world cases
```

---

## Example Dataset

Suppose you are building an **AI assessment generator**.

Your evaluation dataset might contain:

```text id="8k2p0l"
Easy topic
Medium topic
Hard topic
Different subject areas
Different question types
Ambiguous requirements
Long context
Short context
Boundary cases
```

Instead of:

```text id="2wf7az"
10 identical questions
```

you want diversity.

---

## Dataset Size

Early evaluation does not require thousands of examples.

A small dataset might contain:

```text id="mf3jmq"
20–100 carefully selected cases
```

The exact number depends on the task.

The important factor is **representativeness**, not an arbitrary number.

A small but carefully designed test set can be more useful than a large set of repetitive examples.

---

## Dataset Versioning

Treat the dataset as a versioned artifact.

Example:

```text id="ocdck1"
evaluation-dataset/
├── v1
├── v2
└── v3
```

Or:

```text id="phbz0d"
dataset_version = "assessment_eval_v1"
```

### Why version it?

Because the evaluation set itself can change.

Suppose:

```text id="n5b2aw"
Model A
Dataset v1 → 92%
```

Later:

```text id="vn5an7"
Model A
Dataset v2 → 86%
```

The results are not directly comparable unless you understand what changed in the dataset.

---

## What Should a Dataset Entry Contain?

A test case might contain:

```json id="pdg3jg"
{
  "id": "case_001",
  "input": "...",
  "expected_output": "...",
  "category": "easy",
  "tags": ["structured-output", "normal"]
}
```

For generative tasks, `expected_output` may instead be an evaluation criterion or reference answer.

---

## Dataset Categories

A useful early dataset can contain:

| Category | Purpose |
|---|---|
| Normal | Typical production inputs |
| Edge | Unusual but valid inputs |
| Difficult | Challenging cases |
| Adversarial | Designed to expose weaknesses |
| Regression | Previously failed cases |
| Boundary | Inputs near limits |

This helps prevent overfitting to easy examples.

---

# 1.1.2 Measure Correctness, Latency and Cost

These are the three core measurements in the initial evaluation.

```text id="kzq53q"
                 AI Evaluation
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
      Correctness   Latency     Cost
```

A model should not be evaluated only on answer quality.

A model could be:

```text id="xemzdo"
Very accurate
+
Too slow
+
Too expensive
```

and therefore unsuitable for your application's requirements.

---

# Correctness

## Definition

**Correctness** measures whether the model produces an acceptable result for the task.

The exact metric depends on what the model is doing.

### Classification

Use metrics such as:

- Accuracy
- Precision
- Recall
- F1 score

Example:

```text id="z5r18g"
100 test cases
93 correct
=
93% accuracy
```

---

## Structured Output

For structured outputs, correctness can include:

```text id="8j9ekf"
Schema compliance
+
Required fields
+
Allowed values
+
Business rules
```

Example:

```text id="05t0sm"
100 responses

Schema valid = 98
Business valid = 95
```

This tells you more than simply saying "the model returned JSON."

---

## Generative Tasks

For open-ended responses, correctness may require:

- Human evaluation
- Reference answers
- Rubrics
- LLM-based evaluation with safeguards
- Task-specific checks
- Ground-truth verification

Example rubric:

```text id="hw7v0d"
Score each answer from 0–4:

0 → Incorrect
1 → Mostly incorrect
2 → Partially correct
3 → Mostly correct
4 → Fully correct
```

---

## Important

Correctness should be defined **before** evaluating whenever possible.

Otherwise, you may unconsciously move the goalposts after seeing the results.

---

# Latency

## Definition

**Latency** is the time taken for the system to produce a response.

For AI systems, useful latency measurements can include:

### Time to First Token (TTFT)

How long before the first streamed output arrives.

```text id="snz21w"
Request
 ↓
2.1 sec
 ↓
First token
```

### Total Response Time

How long until the complete response is available.

```text id="x5k6g9"
Request
 ↓
8.4 sec
 ↓
Complete
```

For non-streaming systems, total response time is often the main metric.

For streaming systems, **TTFT** can be especially important for user experience.

---

## Average Is Not Enough

Suppose:

```text id="yj3jqj"
Request 1 → 1 sec
Request 2 → 1 sec
Request 3 → 15 sec
```

Average:

```text id="7z62v5"
5.67 sec
```

The average hides the long tail.

Therefore, production-oriented evaluation should also consider **percentiles**, such as:

- P50
- P95
- P99

### Example

```text id="14b5j1"
P50 = 2 sec
P95 = 8 sec
P99 = 15 sec
```

This tells you how slower requests behave.

---

# Cost

## Definition

**Cost** measures the financial resources required to perform the model operation.

A simplified view is:

```text id="l5x3rb"
Cost
≈
Input token usage
+
Output token usage
+
Provider-specific charges
+
Relevant infrastructure costs
```

The exact calculation depends on the provider/model.

---

## Cost per Request

A useful metric is:

```text id="h48xmj"
Cost per request
```

Example:

```text id="5l7h2a"
1,000 requests
Total AI cost = $5

Cost/request = $0.005
```

---

## Cost at Scale

A small cost difference becomes significant at high volume.

```text id="gpr5o1"
$0.01/request
×
1,000,000 requests
=
$10,000
```

So early evaluation should consider:

```text id="tf6q5r"
Quality
+
Latency
+
Unit cost
```

rather than quality alone.

---

# Measuring All Three Together

A useful evaluation table is:

| Model / Version | Correctness | P50 Latency | P95 Latency | Cost / Request |
|---|---:|---:|---:|---:|
| Model A | 91% | 1.8s | 4.2s | $0.004 |
| Model B | 95% | 2.4s | 5.1s | $0.010 |
| Model C | 93% | 1.2s | 3.0s | $0.006 |

Now you can see the trade-offs.

For example:

```text id="51cuqv"
Model B
→ Highest correctness
→ Highest cost
→ Higher latency
```

Model A might be sufficient if its quality meets the product requirement.

# 1.1.3 Record Failure Cases from the First Implementation

## Definition

A **failure case** is an input where the first implementation behaves incorrectly, incompletely, inconsistently, or inefficiently.

Do not simply record:

```text id="c4zj88"
Test failed
```

Record enough information to understand **why** it failed.

---

## Failure Record

A useful failure record can include:

```text id="iq1sd2"
Case ID
Input
Expected behavior
Actual output
Failure type
Model
Prompt version
Schema version
Latency
Cost
Notes
```

Example:

```json id="zpxzbd"
{
  "case_id": "case_017",
  "failure_type": "invalid_schema",
  "model": "model-x",
  "prompt_version": "v1",
  "expected": "4 options",
  "actual": "3 options",
  "notes": "Model omitted one option"
}
```

---

## Why Record Failures?

Because the failure cases become your most valuable improvement dataset.

```text id="keu1tv"
First Evaluation
      ↓
Failure Cases
      ↓
Analyze Patterns
      ↓
Improve Prompt / Model / Logic
      ↓
Regression Dataset
      ↓
Retest
```

This creates a continuous learning loop for the engineering team.

---

# Failure Taxonomy

Instead of keeping one generic "failed" category, classify failures.

Possible categories:

```text id="y0n4f4"
Schema failure
Factual error
Incomplete output
Refusal
Hallucination
Wrong classification
Instruction following failure
Tool failure
Timeout
Rate limit
High cost
Latency issue
```

This allows you to identify patterns.

---

# Example Failure Analysis

Suppose your first evaluation has:

```text id="la1y1j"
100 cases
```

Results:

```text id="n8ga3t"
90 passed
5 schema failures
3 factual errors
2 timeouts
```

You can now say:

```text id="3uqn8z"
Correctness = 90%
Schema failure rate = 5%
Factual error rate = 3%
Timeout rate = 2%
```

More importantly, you know **where the problems are**.

---

# Failure Cases Become Regression Tests

Suppose case 17 fails:

```text id="hft6rg"
Case 017
→ Invalid schema
```

You fix the prompt.

The next evaluation must include Case 017.

```text id="0bz5uj"
v1 → Case 017 FAIL
        ↓
Fix prompt
        ↓
v2 → Case 017 PASS
```

From then on:

> **Never allow a previously important failure to disappear from the evaluation set.**

This is called **regression testing**.

---

# 1.1.4 Early Evaluation Workflow

A practical first-model workflow is:

```text id="ed0e39"
             Define Task
                 ↓
        Select First Model
                 ↓
        Create Dataset v1
                 ↓
      Build Minimal Integration
                 ↓
           Run Evaluation
                 ↓
      ┌──────────┼──────────┐
      ↓          ↓          ↓
 Correctness  Latency     Cost
      │          │          │
      └──────────┼──────────┘
                 ↓
           Analyze Failures
                 ↓
         Record Failure Cases
                 ↓
          Improve System
                 ↓
        Dataset v2 / Regression
                 ↓
            Evaluate Again
```

---

# Minimal First Integration

The first implementation should usually remain small.

Avoid immediately adding:

```text id="57nqkf"
Complex agent orchestration
+
Multiple models
+
Large retrieval system
+
Complex caching
+
Fine-tuning
+
Heavy infrastructure
```

Instead:

```text id="3nk5vk"
Simple request
+
Simple prompt
+
One model
+
Small dataset
```

Then evaluate.

This isolates the model's behavior.

---

# Why "Small" Matters

A small evaluation loop lets you iterate quickly:

```text id="of1p4y"
Change
 ↓
Test
 ↓
Measure
 ↓
Learn
```

rather than:

```text id="3h1e6d"
Change
 ↓
Large deployment
 ↓
Large test
 ↓
Weeks later
 ↓
Discover problem
```

Early evaluation is therefore closely related to **rapid experimentation**.

# 1.1.5 Baseline and Decision Making

The first model evaluation creates a **baseline**.

Example:

```text id="m5qg53"
Dataset: eval_v1
Prompt: v1
Model: Model A

Correctness: 91%
P95 latency: 4.2 sec
Cost/request: $0.004
```

This becomes the reference point.

Now suppose you test Model B:

```text id="fnje7k"
Correctness: 95%
P95 latency: 6.0 sec
Cost/request: $0.010
```

You can make a deliberate trade-off.

---

## Decision Matrix

```text id="7q4zyp"
                  Quality
                     ↑
                     │
             B       │
                     │
                     │      A
                     │
                     └────────────→ Cost
```

The best choice depends on product requirements.

For example:

### Interactive chatbot

Latency may be highly important.

### Compliance system

Correctness may dominate cost.

### Massive batch processing

Cost may be more important than real-time latency.

## Failure recording

Example:

```text id="4t1l5e"

correct_option pointed to a non-existing option.

Add business validation rule.

```

Notice that the solution may not even require changing the AI model.

It could be:

```text id="lrbigq"
Model change
OR
Prompt change
OR
Validation change
OR
Application logic change
```

Early evaluation helps identify **where** the problem actually belongs.

# Common Mistakes

## 1. Evaluating only one or two examples

A handful of successful responses does not establish reliability.

---

## 2. Using unrealistic test inputs

If the evaluation dataset doesn't resemble production traffic, the evaluation can be misleading.

---

## 3. Measuring only correctness

A very accurate model can still be unusable if it is too slow or expensive.

---

## 4. Measuring only average latency

Long-tail latency matters.

Use percentiles such as P95/P99 when appropriate.

---

## 5. Not versioning the dataset

Without dataset versions, comparing experiments becomes difficult.

---

## 6. Not saving failure cases

You lose valuable information for improving the system.
