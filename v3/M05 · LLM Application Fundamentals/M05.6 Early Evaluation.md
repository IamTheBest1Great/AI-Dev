# 1. M05.6 Early Evaluation

## Simple Definition

**Early evaluation** means testing an AI system **soon after the first model integration**, before heavily investing in prompts, application logic, infrastructure, or production rollout. Pasted text

The main question is:

> **Does this model and this implementation work well enough for our actual task?** Pasted text

---

## Basic Lifecycle

```text
First Model Integration
        ↓
Small Representative Dataset
        ↓
Run Evaluation
        ↓
Measure
 ┌──────────┼──────────┐
 ↓          ↓          ↓
Correctness Latency    Cost
 └──────────┼──────────┘
            ↓
      Record Failures
            ↓
          Improve
            ↓
      Evaluate Again
```

Pasted text

### The three core activities

1. Version a small representative dataset.
2. Measure correctness, latency, and cost.
3. Record failure cases from the first implementation. Pasted text

# 1.1.1 Version a Small Representative Dataset

## What is a representative dataset?

A **representative dataset** is a collection of test inputs reflecting the kinds of inputs the real system is expected to receive. Pasted text

It should be:

- Small enough to run quickly
- Large enough to reveal useful patterns
- Representative of real use cases
- Versioned so results can be reproduced

---

## Why one example is not enough

Suppose you test:

```text
"What is React?"
```

and the model gives an excellent answer.

You might conclude:

```text
Model = Good
```

But one example tells you almost nothing about general performance. Pasted text

A stronger dataset contains:

```text
Normal cases
+
Difficult cases
+
Edge cases
+
Representative real-world cases
```

---



# Dataset Versioning

Treat the evaluation dataset as a versioned artifact.

Example:

```text
evaluation-dataset/
├── v1
├── v2
└── v3
```

or:

```text
dataset_version = "assessment_eval_v1"
```

Pasted text

### Why version it?

Because the dataset itself can change.

For example:

```text
Model A
Dataset v1 → 92%
```

Later:

```text
Model A
Dataset v2 → 86%
```

That does **not** automatically mean the model got worse. The test set may have become harder or changed in other ways. Pasted text

---

# What Should a Dataset Entry Contain?

A test case could contain:

```json

  "category": "easy",
  "tags": ["structured-output", "normal"]
}
```

For generative tasks, `expected_output` may instead be an evaluation criterion or reference answer. Pasted text

---

# Dataset Categories

A useful early evaluation set can contain:

| Category | Purpose |
|---|---|
| **Normal** | Typical production inputs |
| **Edge** | Unusual but valid inputs |
| **Difficult** | Challenging cases |
| **Adversarial** | Designed to expose weaknesses |
| **Regression** | Previously failed cases |
| **Boundary** | Inputs near limits |

Pasted text

### Why these categories matter

They prevent the model from looking good merely because the evaluation contains easy examples.

# Latency

## Definition

**Latency** is the time taken for the system to produce a response. Pasted text

Two especially useful measurements are:

### Time to First Token — TTFT

Time until the first streamed output arrives.

```text
Request
  ↓
2.1 sec
  ↓
First Token
```

### Total Response Time

Time until the complete response is available.

```text
Request
  ↓
8.4 sec
  ↓
Complete
```

Pasted text

---

## TTFT vs Total Response Time

| Metric | Measures | Especially useful for |
|---|---|---|
| **TTFT** | Time until first output | Streaming UX |
| **Total response time** | Time until response completes | Overall task completion |

For streaming applications, TTFT can be particularly important for perceived responsiveness. Pasted text

---

# Average Latency Is Not Enough

Suppose:

```text
Request 1 → 1 sec
Request 2 → 1 sec
Request 3 → 15 sec
```

Average:

```text
5.67 seconds
```

But the average hides the slow request. Pasted text

Therefore consider percentiles:

```text
P50
P95
P99
```

Example:

```text
P50 = 2 sec
P95 = 8 sec
P99 = 15 sec
```

This shows the **tail latency**. Pasted text

### Mental model

```text
Average
→ "What is typical overall?"

P95
→ "How slow are the slower 5%?"

P99
→ "How slow are the slowest 1%?"
```

# 1.1.3 Record Failure Cases from the First Implementation

## Definition

A **failure case** is an input where the first implementation behaves incorrectly, incompletely, inconsistently, or inefficiently. Pasted text

Don't record only:

```text
Test failed
```

Record enough information to determine **why** it failed.

---

# Failure Record

A useful failure record can contain:

```text
Case ID
Input
Expected behavior
Actual output
Failure type
Model
Prompt version
Schema version
Latency
Cost
Notes
```

Pasted text

### Example

```json
{
  "case_id": "case_017",
  "failure_type": "invalid_schema",
  "model": "model-x",
  "prompt_version": "v1",
  "expected": "4 options",
  "actual": "3 options",
  "notes": "Model omitted one option"
}
```

Pasted text

# Why Record Failures?

Because failure cases become your most valuable improvement dataset.

```text
First Evaluation
      ↓
Failure Cases
      ↓
Analyze Patterns
      ↓
Improve Prompt / Model / Logic
      ↓
Regression Dataset
      ↓
Retest
```

Pasted text

### Key insight

> **Failure cases should not be discarded after fixing them. They should become future regression tests.**

# Failure Taxonomy

Instead of one generic `failed` label, classify failures.

Possible categories:

```text
Schema failure
Factual error
Incomplete output
Refusal
Hallucination
Wrong classification
Instruction-following failure
Tool failure
Timeout
Rate limit
High cost
Latency issue
```

Pasted text

### Why classify?

Suppose:

```text
100 cases
```

Results:

```text
90 passed
5 schema failures
3 factual errors
2 timeouts
```

You can calculate:

```text
Correctness = 90%
Schema failure rate = 5%
Factual error rate = 3%
Timeout rate = 2%
```

Pasted text

Now you know **where the system is failing**, not merely that it failed.

# Failure Cases → Regression Tests

Suppose:

```text

→ Invalid schema
```

You improve the prompt.

Then:

```text

       ↓
   Fix prompt
       ↓
v2 → Case 017 PASS
```

### Key rule

> **Important historical failures should remain in the evaluation set.**

This creates a regression-testing loop.

# Minimal First Integration

The first implementation should stay relatively small.

Avoid immediately adding:

```text
Complex agent orchestration
+
Multiple models
+
Large retrieval system
+
Complex caching
+
Fine-tuning
+
Heavy infrastructure
```

Instead start with:

```text
Simple request
+
Simple prompt
+
One model
+
Small dataset
```

Then evaluate. Pasted text

### Why?

Because this isolates the model's behavior.

If the first integration contains ten complex components, a failure becomes difficult to diagnose.

# Evaluation Strategy

A good first evaluation asks four questions:

```text
1. Is the output correct enough?
2. Is it fast enough?
3. Is it cheap enough?
4. What exactly fails?
```

Then:

```text
Failure pattern
      ↓
Identify responsible layer
      ↓
Prompt?
Model?
Validation?
Application logic?
Infrastructure?
      ↓
Apply targeted fix
      ↓
Retest
```

This avoids random experimentation.

# Interview Questions

### Q1. Why should AI systems be evaluated early?

Because discovering poor model-task fit after building complex prompts, agents, integrations, and infrastructure can cause substantial rework. Early evaluation reduces that risk. Pasted text

### Q2. Why is a small representative dataset better than one example?

One example cannot establish general performance. A diverse dataset exposes behavior across normal, difficult, edge, and realistic production-like cases. Pasted text

### Q3. Why is dataset versioning important?

Because changing the evaluation dataset changes the benchmark itself. Versioning makes results reproducible and allows you to understand what changed between evaluations. Pasted text

### Q4. What three metrics should be measured during first model integration?

**Correctness, latency, and cost.** A model can be accurate but still be too slow or too expensive for the application. Pasted text

### Q5. Why isn't average latency enough?

Because averages hide slow outliers. Percentiles such as P95 and P99 expose tail latency and are therefore useful for production-oriented analysis. Pasted text

### Q6. What information should be captured for a failure case?

Track enough information to reproduce and understand the failure: case ID, input, expected/actual behavior, failure type, model, prompt/schema versions, latency, cost, and notes. Pasted text

### Q7. Why should failure cases become regression tests?

Because they represent real weaknesses that have already appeared. Keeping them in the evaluation set helps ensure fixes remain effective in later versions. Pasted text

### Q8. Why should the first integration be minimal?

A minimal implementation isolates the model's behavior and keeps the change-test-measure-learning cycle fast. Pasted text

### Q9. How do you choose between two models with different quality, latency, and cost?

Use the product's actual requirements. For interactive systems, latency may dominate; for compliance-sensitive systems, correctness may dominate; for large batch workloads, cost may dominate. Pasted text

### Remember these five rules

```text
1. Test early.
2. Use representative data.
3. Measure correctness + latency + cost.
4. Save failures as regression cases.
5. Compare every improvement against a baseline.
```

The supplied material's central engineering lesson is therefore:

> **Don't build a sophisticated AI system and hope it works. Build the smallest useful integration, test it against representative data, measure it, learn from failures, establish a baseline, and only then invest in optimization and scale.** Pasted text
