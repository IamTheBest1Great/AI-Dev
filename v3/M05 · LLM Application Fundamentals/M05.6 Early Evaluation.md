# 1. Early Evaluation Fundamentals

## What Is Early Evaluation?

**Early evaluation** means testing an AI system soon after the first model integration, before investing heavily in prompts, agents, application logic, infrastructure, caching, or production rollout.

The central question is:

> Does this model and this implementation work well enough for our actual task?

Instead of assuming that a model will perform well and building a sophisticated system around it, test the basic model–task combination first.

### Basic early-evaluation lifecycle

```text
First Model Integration
          |
          v
Small Representative Dataset
          |
          v
Run Evaluation
          |
          v
Measure Performance
    +-----+-----+
    |     |     |
    v     v     v
Correctness Latency Cost
    |     |     |
    +-----+-----+
          |
          v
Record Failure Cases
          |
          v
Analyze Problems
          |
          v
Improve the System
          |
          v
Evaluate Again
```

## The Three Core Activities

Early evaluation focuses on three essential activities.

**1. Create a small, representative evaluation dataset.**

Choose examples that reflect the inputs the application is expected to receive in real use.

**2. Measure correctness, latency, and cost.**

Determine whether the system produces acceptable results, responds quickly enough, and operates within the required budget.

**3. Record failure cases from the first implementation.**

Capture unsuccessful or problematic examples so the team can identify patterns, fix the correct component, and test future improvements.

These three activities establish an evidence-based starting point for AI engineering.

## Why Early Evaluation Matters

Imagine spending two weeks building:

```text
Complex prompts
       +
Agent workflow
       +
Database integration
       +
Frontend
       +
Caching
       +
Production infrastructure
```

Only after all that work do you discover that the selected model performs poorly on the actual task.

The team may need to redesign prompts, change models, modify validation logic, or rebuild parts of the application.

Early evaluation helps identify such problems before substantial engineering effort is committed.

### Core principle

**Validate model–task fit before optimizing the surrounding system.**

Model–task fit means how well a particular model, with a particular implementation, performs the task the application actually needs.

A model may perform impressively in a general demonstration but still be unsuitable for your task because it is inaccurate, too slow, too expensive, or unreliable with your required output format.

# 2. Building a Representative Evaluation Dataset

## What Is a Representative Dataset?

A **representative dataset** is a collection of test inputs that reflects the kinds of inputs the real system is expected to receive.

The dataset allows developers to evaluate the system using more than a few handpicked examples.

A useful early-evaluation dataset should be:

- Small enough to run quickly.
- Large enough to reveal useful patterns.
- Representative of realistic use cases.
- Versioned so that evaluations can be reproduced.
- Diverse enough to expose different types of failures.

## Why One or Two Examples Are Not Enough

Suppose you test an AI model using only this question:

> What is React?

The model provides an excellent explanation.

You might conclude that the model is good. However, one successful example tells you very little about its general performance.

The model might perform well on simple technical questions but poorly on complex questions, ambiguous inputs, long context, or structured output.

A more useful evaluation set contains:

```text
Normal cases
     +
Difficult cases
     +
Edge cases
     +
Representative real-world cases
```

**The goal is to evaluate diversity of behavior, not merely to accumulate test cases.**

## Example: AI Assessment Generator

Suppose you are developing an AI system that generates multiple-choice assessments from course material.

A representative test dataset could include:

```text
Different subject areas
Different difficulty levels
Different question types
Short source material
Long source material
Ambiguous requirements
Boundary cases
Previously failed examples
```

For example, an evaluation set could contain questions based on easy, medium, and difficult maritime safety topics, using both short and long course excerpts.

### Poor dataset

```text
10 nearly identical questions
```

### Better dataset

```text
Easy questions
Medium questions
Hard questions
Different topics
Different input sizes
Different question types
Edge cases
```

The second dataset is more likely to reveal weaknesses across the actual range of tasks.

## How Large Should the Dataset Be?

Early evaluation does not necessarily require thousands of examples.

The supplied material gives **20–100 carefully selected cases** as an example of a small early-evaluation dataset. The appropriate size depends on the task, its complexity, and the confidence required from the evaluation.

A small dataset can help identify early problems, but it should not automatically be considered sufficient evidence for production readiness.

### Important lesson

**Representativeness matters more than an arbitrary dataset size.**

A small, diverse dataset may reveal more useful problems than a much larger dataset containing repetitive examples.

## Dataset Versioning

Treat an evaluation dataset as a versioned artifact, similar to source code or a prompt.

For example:

```text
evaluation-dataset/
    |
    +---- v1
    |
    +---- v2
    |
    +---- v3
```

Or track a version identifier:

```text
dataset_version = "assessment_eval_v1"
```

### Why version the dataset?

Because the dataset itself can change over time.

Suppose the results are:

```text
Model A
Dataset v1 -> 92% accuracy
```

Later:

```text
Model A
Dataset v2 -> 86% accuracy
```

This does not automatically mean Model A became worse. Dataset v2 might contain harder questions, more edge cases, or a different mix of tasks.

To interpret evaluation results correctly, you must know which dataset version produced them.

### What should a dataset entry contain?

A test case can be represented using a structure such as:

```json
{
  "id": "case_001",
  "input": "...",
  "expected_output": "...",
  "category": "easy",
  "tags": [
    "structured-output",
    "normal"
  ]
}
```

For generative tasks, an exact `expected_output` may not always be appropriate. You can instead store reference answers, correctness criteria, or an evaluation rubric.

The structure is illustrative; the fields should match the needs of the task.

## Dataset Categories

A well-designed evaluation dataset can use several categories.

| Category | Purpose |
|---|---|
| **Normal** | Tests typical production inputs |
| **Edge** | Tests unusual but valid inputs |
| **Difficult** | Tests challenging cases |
| **Adversarial** | Tests whether the system handles deliberately challenging or misleading inputs |
| **Regression** | Retains previously failed examples to check that fixes remain effective |
| **Boundary** | Tests inputs near limits or constraints |

### Why these categories matter

If your evaluation contains only easy examples, a model may appear highly accurate even though it fails on difficult real-world requests.

Including multiple categories gives you a more informative picture of system behavior.

# 3. Measuring Model Performance

## The Three Core Evaluation Dimensions

The initial evaluation should measure:

```text
                 AI Evaluation
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
     Correctness    Latency      Cost
```

These dimensions must be considered together.

A model may be highly accurate but too slow or expensive for the product. Another model may respond quickly and cheaply but produce too many incorrect results.

Neither model is automatically suitable just because it performs well on one metric.

## Correctness

### Definition

**Correctness** measures whether a model produces an acceptable result for the task.

The specific metric depends on what the application does.

### Classification tasks

For classification, useful metrics include:

- Accuracy
- Precision
- Recall
- F1 score

Suppose a classifier is tested on 100 cases and correctly classifies 93.

\[
\text{Accuracy}
=
\frac{\text{Correct predictions}}{\text{Total cases}}
\times 100
\]

\[
\text{Accuracy}
=
\frac{93}{100}\times 100
=
93\%
\]

Accuracy is informative when considered alongside the task's requirements and the distribution of examples. For imbalanced classification tasks, precision, recall, and F1 may be more revealing.

### Structured-output correctness

For structured responses, correctness can include:

```text
Schema compliance
       +
Required fields
       +
Allowed values
       +
Business rules
```

Suppose a model generates 100 structured responses.

```text
Schema-valid responses   = 98
Business-valid responses = 95
```

These are different measurements. A response can have valid JSON and the required fields but still violate business rules.

For example, a generated assessment question might contain four options but specify a correct-answer index that points outside the options array.

The JSON structure may parse, but the result is not usable.

### Generative-task correctness

Open-ended generation often requires more than exact string matching.

Possible evaluation approaches include:

- Human evaluation
- Reference answers
- Scoring rubrics
- Task-specific checks
- Ground-truth verification
- LLM-based evaluation with appropriate safeguards

The evaluation method should match the task.

### Example evaluation rubric

| Score | Meaning |
|---:|---|
| 0 | Incorrect |
| 1 | Mostly incorrect |
| 2 | Partially correct |
| 3 | Mostly correct |
| 4 | Fully correct |

A rubric helps evaluators apply consistent criteria when assessing open-ended responses.

### Define correctness before evaluating

Whenever possible, establish the evaluation criteria before reviewing the results.

Otherwise, there is a risk of changing what counts as a good answer after seeing how the model performs.

**Interview phrase:** Define the evaluation criteria before looking at the results.

## Latency

### Definition

**Latency** is the time taken for the system to produce a response.

Two particularly useful measurements are Time to First Token and total response time.

### Time to First Token (TTFT)

**TTFT** measures how long it takes for the first streamed output to arrive after a request is made.

Example:

```text
Request sent
      |
      v
   2.1 seconds
      |
      v
First token arrives
```

TTFT is particularly useful for evaluating streaming user experiences.

### Total response time

Total response time measures how long it takes for the complete response to become available.

Example:

```text
Request sent
      |
      v
   8.4 seconds
      |
      v
Complete response available
```

### TTFT vs. total response time

| Metric | Measures | Particularly useful for |
|---|---|---|
| **TTFT** | Time until first streamed output | Streaming responsiveness |
| **Total response time** | Time until the response is complete | Overall task completion |

A system can have a low TTFT but a high total response time if it starts generating quickly and then generates slowly.

For non-streaming applications, TTFT may be less relevant than the time to the complete response.

## Why Average Latency Is Not Enough

Consider these response times:

```text
Request 1 -> 1 second
Request 2 -> 1 second
Request 3 -> 15 seconds
```

The average is:

\[
\frac{1+1+15}{3}
\approx 5.67\text{ seconds}
\]

However, the average does not adequately communicate how slow the third request was.

This is why latency percentiles are useful.

## P50, P95, and P99 Latency

A percentile describes the response time below which a given proportion of measured requests complete.

| Metric | Interpretation |
|---|---|
| **P50** | Median response time; approximately half of observations are at or below this value |
| **P95** | Approximately 95% of observations are at or below this value |
| **P99** | Approximately 99% of observations are at or below this value |

Consider this example:

```text
P50 = 2 seconds
P95 = 8 seconds
P99 = 15 seconds
```

The median request completes in approximately two seconds, but the slowest portion of requests takes considerably longer.

P95 and P99 help expose **tail latency** that the average may hide.

### Mental model

```text
Average -> Typical overall performance

P50     -> Median request

P95     -> Slow tail affecting roughly 5% of requests

P99     -> Slowest tail affecting roughly 1% of requests
```

The precise interpretation depends on the percentile calculation method and the sample being measured.

## Cost

### Definition

**Cost** measures the financial resources required to perform an AI operation.

A simplified model is:

```text
Total Cost
    ≈
Input token cost
    +
Output token cost
    +
Provider-specific charges
    +
Relevant infrastructure costs
```

Actual costs depend on the provider, model, pricing rules, and service configuration.

### Cost per request

Cost per request is a useful unit-economics metric.

Suppose an evaluation runs 1,000 requests at a total cost of $5.

\[
\text{Cost per request}
=
\frac{\$5}{1{,}000}
=
\$0.005
\]

### Why cost matters at scale

Suppose an operation costs $0.01 per request.

For one million requests:

\[
\$0.01\times 1{,}000{,}000
=
\$10{,}000
\]

A small difference in per-request cost can become significant at high volume.

Early evaluation should therefore measure correctness, latency, and cost together rather than evaluating correctness alone.

## Comparing Models Across All Three Dimensions

Consider the following illustrative results.

| Model | Correctness | P50 Latency | P95 Latency | Cost per request |
|---|---:|---:|---:|---:|
| Model A | 91% | 1.8 s | 4.2 s | $0.004 |
| Model B | 95% | 2.4 s | 5.1 s | $0.010 |
| Model C | 93% | 1.2 s | 3.0 s | $0.006 |

Model B has the highest correctness, but it also has the highest cost and a slower response time than the alternatives in this example.

That does not automatically make it the best model.

Model A may be preferable if 91% correctness satisfies the product requirement and lower cost is important.

Model B may be preferable if its additional correctness is necessary for a high-stakes or accuracy-sensitive workflow.

Model C may be attractive when responsiveness matters and its accuracy is sufficient.

**The winner depends on the application's requirements.**

# 4. Recording and Analyzing Failure Cases

## What Is a Failure Case?

A **failure case** is an input for which the initial implementation behaves incorrectly, incompletely, inconsistently, or inefficiently.

Early evaluation should not simply record that a test failed. It should preserve enough information to investigate why the failure occurred.

## What Should a Failure Record Contain?

A useful failure record can include:

```text
Case ID
    +
Input
    +
Expected behavior
    +
Actual output
    +
Failure type
    +
Model identifier
    +
Prompt version
    +
Schema version
    +
Latency
    +
Cost
    +
Notes
```

Example:

```json
{
  "case_id": "case_017",
  "failure_type": "invalid_schema",
  "model": "model-x",
  "prompt_version": "v1",
  "expected": "4 options",
  "actual": "3 options",
  "notes": "Model omitted one option"
}
```

The identifiers and values are illustrative.

A well-structured failure record makes it easier to reproduce the case, identify a pattern, and determine which part of the system needs improvement.

## Why Record Failures?

Failure cases provide evidence about the actual weaknesses of the implementation.

```text
First Evaluation
       |
       v
Record Failure Cases
       |
       v
Analyze Patterns
       |
       v
Improve Prompt / Model / Logic
       |
       v
Add Cases to Regression Dataset
       |
       v
Retest
```

Without recorded failures, developers may repeatedly encounter the same problems and make fixes that cannot be evaluated systematically.

### Key insight

**Failure cases should not be discarded after fixing them. They should become future regression tests.**

## Failure Taxonomy

A **failure taxonomy** classifies failures into meaningful categories rather than assigning every problem a generic `failed` label.

Possible categories include:

```text
Schema failure
Factual error
Incomplete output
Refusal
Hallucination
Wrong classification
Instruction-following failure
Tool failure
Timeout
Rate limit
High cost
Latency issue
```

Not every category represents the same type of problem. Some are output-quality failures, while others relate to infrastructure, performance, or cost.

## Example: Classifying Failures

Suppose the evaluation contains 100 cases:

```text
90 passed
5 schema failures
3 factual errors
2 timeouts
```

You can calculate:

| Metric | Result |
|---|---:|
| Passing rate | 90% |
| Schema-failure rate | 5% |
| Factual-error rate | 3% |
| Timeout rate | 2% |

The measurements use 100 cases as the denominator in this illustration.

This breakdown is more informative than a single pass/fail total because it shows where the system is failing.

## Turning Failures into Regression Tests

Suppose case `case_017` fails because the generated assessment contains three options when four are required.

The team modifies the prompt or validation logic.

```text
Prompt v1
    |
    v
Case 017 fails
    |
    v
Apply targeted fix
    |
    v
Prompt v2
    |
    v
Case 017 passes
```

The case should remain in the evaluation set so that later changes can be checked against it.

A **regression test** is a previously known case retained to ensure that a fixed problem does not reappear.

## Why Regression Testing Matters

A change that fixes one failure can unintentionally introduce another.

For example, modifying an assessment-generation prompt to ensure four options may cause the model to produce repetitive questions.

Keeping historical failures allows the team to verify that improvements do not repeatedly break previously working behavior.

### Core rule

**Important historical failures should remain in the evaluation set.**

# 5. Early Evaluation Workflow and Baselines

## The Complete Early Evaluation Workflow

A practical first-model workflow is:

```text
Define the Task
       |
       v
Select the First Model
       |
       v
Create Evaluation Dataset v1
       |
       v
Build Minimal Integration
       |
       v
Run Evaluation
       |
       v
Measure
  +----+----+
  |    |    |
  v    v    v
Quality Latency Cost
  |    |    |
  +----+----+
       |
       v
Analyze and Record Failures
       |
       v
Identify Root Causes
       |
       v
Apply Targeted Improvements
       |
       v
Update Regression Dataset
       |
       v
Evaluate Again
       |
       v
Compare Against Baseline
```

The purpose is to create a short feedback loop between implementation, testing, measurement, and improvement.

## Minimal First Integration

The initial implementation should remain relatively simple.

Avoid immediately introducing:

```text
Complex agent orchestration
Multiple models
Large retrieval system
Complex caching
Fine-tuning
Heavy production infrastructure
```

Instead begin with:

```text
Simple request
      +
Simple prompt
      +
One model
      +
Small representative dataset
```

Then evaluate the results.

### Why keep the first integration small?

A minimal integration helps isolate model behavior.

If the initial system contains ten complex components, it becomes difficult to determine whether a failure originates from the model, prompt, retrieval system, tools, validation, or infrastructure.

A smaller system makes debugging and experimentation easier.

## Short Feedback Loops

The goal is to repeat this cycle quickly:

```text
Change
  |
  v
Test
  |
  v
Measure
  |
  v
Learn
```

This is preferable to making major changes, deploying a large system, and discovering weeks later that the basic model–task combination is unsuitable.

**Core lesson: Short feedback loops accelerate AI engineering.**

## Baseline and Decision Making

The first evaluation establishes an initial **baseline**: the measured performance of the existing model, prompt, dataset, and configuration.

For example:

```text
Dataset: eval_v1
Prompt: v1
Model: Model A

Correctness: 91%
P95 latency: 4.2 seconds
Cost/request: $0.004
```

Now consider another model:

```text
Correctness: 95%
P95 latency: 6.0 seconds
Cost/request: $0.010
```

The second model is more accurate, but it is slower and more expensive.

The correct choice depends on the product requirements.

A baseline provides the reference needed to make that decision.

## Choosing Models by Use Case

Different applications prioritize different metrics.

### Interactive chatbot

Typical priorities:

```text
Low latency
      +
Good-enough quality
```

An extremely slow model may create a poor user experience even if its answers are slightly more accurate.

### Compliance-sensitive system

Typical priorities:

```text
Correctness
      +
Reliability
```

A more expensive model or additional validation may be justified when mistakes are costly.

### Large batch workload

Typical priorities:

```text
Cost
      +
Throughput
```

If results do not need to be returned immediately, real-time latency may be less important than the total cost and processing capacity.

### Important distinction

These priorities are examples, not universal rules. A system may require all three dimensions to meet minimum thresholds before any model is acceptable.

# 6. Worked Example: AI Assessment Generator

Suppose you are building an AI assessment generator that creates 10 multiple-choice questions from course material.

## Step 1: Create the evaluation dataset

The dataset could contain examples covering:

```text
20 course topics
      ×
Different difficulty levels
      ×
Different content types
```

It should include a mixture of typical questions, difficult topics, longer source material, and edge cases.

The exact size and composition should be appropriate for the application.

## Step 2: Define correctness checks

Each generated question should satisfy requirements such as:

```text
Valid question
Correct answer exists
Exactly 4 options
Exactly 1 correct answer
Relevant explanation
```

These checks define what an acceptable assessment item means for the system.

## Step 3: Measure latency

Measure the time required to generate the requested set of 10 questions.

Where appropriate, also record:

- Time to first output if streaming is used
- P50 latency
- P95 latency
- P99 latency
- Total generation time

## Step 4: Measure cost

Estimate the cost associated with the request using the relevant usage and pricing information.

At minimum, the model-token usage generally needs to be considered:

```text
Input tokens
      +
Output tokens
      |
      v
Request usage and cost
```

Provider-specific charges and relevant infrastructure costs may also apply.

## Step 5: Record a failure

Suppose one test case produces a correct-answer index that points to a nonexistent option.

Failure record:

```text
Case: navigation-hard-07

Failure:
correct_option points to a nonexistent option.

Prompt: v1
Model: Model A

Action:
Add a business-validation rule.
Retain case in the regression dataset.
```

This example illustrates an important engineering principle:

**The model may not be the problem.**

The fix might instead involve:

```text
Model change
     OR
Prompt change
     OR
Validation change
     OR
Application logic change
```

If a correct-answer index is invalid, an application-level validation rule may be the most direct solution.

Changing the model without diagnosing the failure could add cost without solving the actual problem.

## Step 6: Improve and retest

After implementing a targeted fix:

```text
Failure detected
       |
       v
Record failure details
       |
       v
Identify responsible layer
       |
       v
Apply targeted fix
       |
       v
Retest the original case
       |
       v
Run regression dataset
       |
       v
Measure correctness, latency, and cost
```

This approach verifies both that the original issue was resolved and that other behavior did not regress.

## Evaluation Strategy

A good initial evaluation answers four questions:

```text
1. Is the output correct enough?
2. Is the response fast enough?
3. Is the cost acceptable?
4. What exactly is failing?
```

Then identify the responsible layer:

```text
Failure pattern
       |
       v
Root-cause analysis
       |
       +---- Prompt?
       |
       +---- Model?
       |
       +---- Validation?
       |
       +---- Application logic?
       |
       +---- Infrastructure?
       |
       v
Targeted fix
       |
       v
Retest
```

This is more effective than randomly changing prompts, switching models, or increasing infrastructure capacity without knowing what caused the failure.

# 7. Common Mistakes and Best Practices

## Mistake 1: Evaluating only one or two examples

**Problem:** A few successful cases do not establish that the system is reliable across realistic inputs.

**Better approach:** Use a small but diverse and representative dataset.

## Mistake 2: Using unrealistic test inputs

**Problem:** The evaluation does not reflect the actual inputs the system will receive in production.

**Better approach:** Include representative normal, difficult, edge, boundary, and historical failure cases.

## Mistake 3: Measuring only correctness

**Problem:** The model may be accurate but too slow or expensive.

**Better approach:** Measure correctness, latency, and cost together.

## Mistake 4: Measuring only average latency

**Problem:** The average can hide extremely slow requests.

**Better approach:** Use P50, P95, and P99 latency where appropriate, along with total response time.

## Mistake 5: Failing to version the dataset

**Problem:** Changes in evaluation results become difficult to interpret because the test set itself may have changed.

**Better approach:** Store dataset versions and track which version was used for each experiment.

## Mistake 6: Not saving failure cases

**Problem:** Valuable evidence about the system's weaknesses is lost.

**Better approach:** Record each important failure and retain it as a regression test after fixing it.

## Mistake 7: Changing the test set without controlling the change

The supplied material ends abruptly after introducing this mistake with the phrase **“Changing the test set after…”**. The intended continuation is unavailable, so its exact wording and further explanation cannot be established from the source.

The broader lesson supported by the surrounding material is that evaluation datasets should be versioned and changes to the dataset should be tracked. Comparisons must account for dataset changes rather than automatically attributing all performance differences to the model.

## Mistake 8: Assuming every AI failure requires a model change

**Problem:** The actual cause may be incorrect prompt instructions, missing validation, application logic, or infrastructure.

**Better approach:** Classify the failure and identify the responsible layer before choosing a fix.

## Mistake 9: Optimizing before establishing a baseline

**Problem:** The team cannot determine whether a change improved the system.

**Better approach:** Measure the first implementation before making major changes.

## Mistake 10: Treating the first evaluation as proof of production readiness

**Problem:** An early evaluation may reveal useful patterns without providing enough evidence for production deployment.

**Better approach:** Treat early evaluation as an initial experiment. Expand testing and validation according to task risk, expected traffic, reliability requirements, and business needs.

# 9. Practice Questions and Interview Preparation

## Question-and-Answer Recall

**Q1. What is early evaluation?**

**Answer:** Testing an AI system shortly after the first model integration, before investing heavily in surrounding infrastructure and complexity.

**Q2. What is the main goal of early evaluation?**

**Answer:** To determine whether the model and its implementation perform well enough for the actual task.

**Q3. Why use a representative dataset?**

**Answer:** It reveals how the system behaves across realistic inputs, instead of relying on a few simple examples.

**Q4. Why should evaluation datasets be versioned?**

**Answer:** To make evaluations reproducible and help explain differences between experiments when the test set changes.

**Q5. What are the three core evaluation dimensions?**

**Answer:** Correctness, latency, and cost.

**Q6. What is TTFT?**

**Answer:** Time to First Token—the time between sending a request and receiving the first streamed output.

**Q7. Why are P95 and P99 latency useful?**

**Answer:** They reveal slow-tail behavior that an average can hide.

**Q8. What should a failure record contain?**

**Answer:** Details such as case ID, input, expected behavior, actual output, failure type, model identifier, prompt and schema versions, latency, cost, and notes.

**Q9. Why turn failures into regression tests?**

**Answer:** To ensure previously fixed problems do not reappear after later changes.

**Q10. Does every failure require a model change?**

**Answer:** No. The cause may be the prompt, validation rules, application logic, or infrastructure.

**Q11. What is a baseline?**

**Answer:** A measured reference configuration and performance level used to compare future changes.

**Q12. Why should an initial integration be minimal?**

**Answer:** It isolates model behavior and keeps the testing and learning cycle fast.

**Q13. Why is correctness alone insufficient for model selection?**

**Answer:** A model may be accurate but too slow or expensive for the application's needs.

**Q14. Why define evaluation criteria before running an evaluation?**

**Answer:** To reduce subjective or inconsistent judgments and avoid changing the definition of a good answer after seeing the results.

**Q15. How can a failure help improve the system?**

**Answer:** By providing a concrete example to reproduce, classify, analyze, fix, and retain as a regression test.

## Scenario-Based Interview Questions

### Scenario 1: Choosing a model before building the full application

**Question:** You are developing an AI-powered application and are considering investing several weeks in agent workflows, retrieval, caching, and frontend integration. What should you do first?

**Answer:** Build a minimal model integration and evaluate it against a small representative dataset. Measure correctness, latency, and cost, and record failure cases. This establishes whether the model-task combination is suitable before investing heavily in the surrounding architecture.

### Scenario 2: A model looks good in a demonstration

**Question:** Your model produces an excellent response in a demo, but you do not have an evaluation dataset. Can you conclude that it is suitable for production?

**Answer:** No. A single successful example does not establish reliability across real inputs. Build a representative dataset containing normal, difficult, edge, and relevant boundary cases, then measure performance against predefined criteria.

### Scenario 3: Accuracy is high, but the system is slow

**Question:** A model achieves 96% correctness, but its P95 latency is eight seconds. The application is an interactive chatbot. How would you make a decision?

**Answer:** Compare the latency with the product's responsiveness requirements and evaluate alternatives. A model with slightly lower accuracy may be preferable if it still meets the required quality threshold while providing significantly better response times. Measure correctness and latency together rather than optimizing one metric in isolation.

### Scenario 4: Failure patterns repeat

**Question:** Your evaluation repeatedly finds that generated assessment questions contain only three options instead of four. What would you do?

**Answer:** Record the failure details, classify the problem, and investigate the prompt, model behavior, and output-validation logic. Add a specific check for the required option count, apply a targeted fix, and retain the failure as a regression test. Retest the broader dataset to ensure the fix does not introduce new problems.

### Scenario 5: A model becomes less accurate after a dataset change

**Question:** A model's measured accuracy falls from 92% to 86% after the team adds difficult questions to the evaluation dataset. What should you investigate?

**Answer:** Verify the dataset version and compare its composition with the previous version. The lower score may reflect a harder evaluation set rather than degraded model performance. To compare model versions fairly, use a consistent evaluation set and document any dataset changes.

### Scenario 6: Debugging an invalid correct-answer index

**Question:** An assessment generator produces valid JSON, but the correct-answer index sometimes points to a nonexistent option. Is switching to a different model the only solution?

**Answer:** No. The failure could be handled with application-level business validation, a prompt change, or a model change, depending on the root cause. Validate that the index falls within the options array and retain failed cases for regression testing.

### Scenario 7: Cost increases substantially

**Question:** A new model improves correctness from 91% to 95%, but it costs more than twice as much per request. How would you decide whether to deploy it?

**Answer:** Compare the quality improvement with the additional cost and latency. Determine whether the new accuracy is necessary for the task, evaluate the alternatives against the same dataset, and select the configuration that satisfies the product requirements at an acceptable cost.

### Scenario 8: The average latency looks acceptable

**Question:** Your average model latency is three seconds, but some requests take 15 seconds. What additional metrics would help?

**Answer:** Measure P50, P95, and P99 latency, as appropriate. These percentiles expose the slower portion of requests and provide a clearer view of tail latency than the average alone. For streaming applications, also measure TTFT.

### Scenario 9: A fixed failure reappears

**Question:** Your team corrected a schema failure in one prompt version. Two releases later, the same failure returns. How could the evaluation process help prevent this?

**Answer:** Keep the original failed example in a regression dataset and run it as part of subsequent evaluations. The test should verify not only that the original problem remains fixed, but also that the broader changes do not introduce related failures.

### Scenario 10: Deciding which layer to improve

**Question:** Your initial evaluation shows three failures: invalid schema, incorrect facts, and timeouts. Should you change the model to solve all three?

**Answer:** No. Classify and investigate each failure separately. Schema failures may require prompt or validation changes; factual errors may require better context, model selection, or verification; timeouts may require investigation of the provider, network, retry policy, or infrastructure. A targeted fix is more effective than assuming every problem originates in the model.

### Remember these five rules

```text
1. Test early.
2. Use representative data.
3. Measure correctness + latency + cost.
4. Save failures as regression cases.
```

**Central lesson:** Do not build a sophisticated AI system and hope it works. Start with the smallest useful integration, test it against representative data, measure its performance, learn from failures, establish a baseline, and only then invest in optimization and scale.
