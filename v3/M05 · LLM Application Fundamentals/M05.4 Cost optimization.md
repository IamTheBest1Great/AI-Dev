# 1. M05.4 Usage and Efficiency

## Simple Definition

**Usage and efficiency** in AI systems means achieving the required quality and functionality while minimizing unnecessary:

- Token consumption
- API requests
- Compute
- Latency
- Storage
- Cost Pasted text

### Mental model

```text
AI Efficiency
     │
     ├── Use fewer tokens
     ├── Make fewer requests
     ├── Avoid duplicate work
     ├── Reuse previous results
     ├── Use cheaper suitable models
     └── Process work efficiently
```

Pasted text

### Core principle

> **Efficiency does not mean minimizing AI usage at any cost. It means removing unnecessary usage while preserving the required quality.**

For example:

```text
10,000-token prompt
        ↓
Only 500 tokens are relevant
        ↓
Reduce irrelevant content
```

That is useful.

But:

```text
10,000 tokens
        ↓
Remove important context
        ↓
Poor answer
        ↓
Retry / human correction
```

can actually make the system **more expensive overall**. Pasted text

---

# 1.1 M05.4.1 Cost Optimization

## Definition

**Cost optimization** means designing an AI system so it performs the required work at the **lowest practical cost without reducing quality below an acceptable level**. Pasted text

A simplified model:

```text
Total AI Cost
   ≈
Input Token Cost
+
Output Token Cost
+
Other API / Infrastructure Costs
```

Exact pricing varies by provider and model. Pasted text

### Goal

Not:

```text
Minimum possible AI usage
```

But:

```text
Minimum unnecessary AI usage
+
Required quality
```

---

# 1.1.1 Token Budgeting

## Definition

**Token budgeting** means deliberately controlling how many tokens an AI request consumes. Pasted text

A token is a unit models use to represent text. It is **not exactly the same as a word**.

### Basic formula

```text
Input Tokens
      +
Output Tokens
      =
Total Token Usage
```

---

## Why Token Budgeting Matters

Large systems may make thousands or millions of requests.

Even a small saving per request can become significant.

Example:

```text
1,000 tokens saved/request
×
100,000 requests
=
100,000,000 fewer input tokens
```

Pasted text

### Important lesson

> **Small per-request optimizations become large at scale.**

---

## Token Budget Components

A request may contain:

```text
Request Budget
      │
      ├── System instructions
      ├── User input
      ├── Retrieved context
      ├── Tool results
      └── Expected output
```

Pasted text

### Worked example

Suppose:

```text
System prompt      = 500 tokens
User message       = 200 tokens
Retrieved context  = 3,000 tokens
Expected response  = 500 tokens
```

Total:

```text
500 + 200 + 3,000 + 500
= 4,200 tokens
```

Now reduce retrieved context:

```text
System prompt      = 500
User message       = 200
Retrieved context  = 1,000
Expected response  = 500

Total = 2,200 tokens
```

That is a **2,000-token reduction per request** without changing the user's actual question. Pasted text

---

## Token Budgeting Strategies

### 1. Set maximum output size

Prevent unnecessary long generations.

### 2. Limit retrieved context

Send only relevant information.

### 3. Avoid repeating instructions

Do not resend large identical content unnecessarily.

### 4. Summarize long conversation history

Instead of forwarding the entire conversation forever, maintain a compact summary when appropriate.

### 5. Choose appropriate models

Do not use an expensive model for a trivial task when a cheaper suitable model can do it. Pasted text

---

## Token Budget Trade-off

### Too little context

```text
Low cost
   ↓
Insufficient information
   ↓
Poor answer
```

### Too much context

```text
More information
   ↓
Higher cost
+
Potentially higher latency
```

### Correct target

```text
Enough context
      +
Enough output
      ↓
Required quality
```

Pasted text

# 1.1.2 Prompt Caching

## Definition

**Prompt caching** means reusing processing for prompt content that appears repeatedly rather than treating repeated content as entirely new work every time. Pasted text

This is especially useful when many requests share a large common prompt.

### Example

Every request contains:

```text
Large system instructions
+
Company policy
+
Tool definitions
+
User question
```

Only the user question changes.

```text
Request 1:
[Common Prompt] + Question A

Request 2:
[Common Prompt] + Question B

Request 3:
[Common Prompt] + Question C
```

A provider's caching mechanism may reduce the cost or latency of repeatedly processing the cacheable section. Pasted text

---

## Mental Model

```text
First Request
     ↓
Process Common Prompt
     ↓
   Cache
     ↓
Later Request
     ↓
Reuse Cached Portion
     +
New Input
```

---

## Good Candidates for Prompt Caching

- Large system instructions
- Stable policy documents
- Repeated tool definitions
- Shared domain context
- Long static examples Pasted text

### Poor candidates

Frequently changing content:

```text
Current timestamp
Latest user message
Temporary state
```

Pasted text

---

## Important limitation

Prompt caching is generally **provider/model-specific**.

Rules can differ for:

- Cache lifetime
- Pricing
- Minimum cache size
- Cacheable content
- Cache rules
- API mechanism Pasted text

Therefore:

> Treat prompt caching as a provider-specific optimization, not a universal behavior.

---

# 1.1.3 Response Caching

## Definition

**Response caching** stores the result of an AI request and returns the stored result when the **same request** occurs again. Pasted text

### Example

User asks:

> "What is HTTP?"

First request:

```text
Question
   ↓
AI Model
   ↓
Answer
   ↓
Store in Cache
```

Next identical request:

```text
Same Question
   ↓
Cache Lookup
   ↓
Cached Answer
```

The AI model does not need to be called again. Pasted text

---

## Response Cache Flow

```text
Request
   ↓
Cache Lookup
   ↓
Found?
 ┌───────┴───────┐
Yes              No
 ↓                 ↓
Return          AI Model
Result              ↓
                 Save Result
                     ↓
                  Return
```

### Benefits

- Lower API cost
- Lower latency
- Fewer requests
- Reduced provider load Pasted text

---

## When Response Caching Works Well

Especially useful for relatively stable requests:

- FAQ responses
- Product descriptions
- Repeated calculations
- Static documentation questions
- Common classification requests Pasted text

### Main problem: staleness

If the underlying information changes, the cache may contain an outdated answer.

Possible controls:

```text
TTL
Cache invalidation
Versioned keys
Freshness rules
```

Pasted text

---

# 1.1.4 Semantic Caching

## Definition

**Semantic caching** goes beyond exact string matching.

It attempts to reuse an existing answer when a new question has the **same or sufficiently similar meaning** as a previous question. Pasted text

---

## Exact Cache vs Semantic Cache

### Exact caching

```text
"What is PostgreSQL?"
        ↓
matches only the same request/key
```

It may not match:

```text
"Explain PostgreSQL."
```

### Semantic caching

The system compares meaning:

```text
"What is PostgreSQL?"
        ≈
"Explain PostgreSQL."
        ≈
"Can you tell me what PostgreSQL is?"
```

If sufficiently similar, the previous answer may be reused. Pasted text

---

## How Semantic Caching Works

A common architecture:

```text
User Question
      ↓
Embedding / Semantic Representation
      ↓
Similarity Search
      ↓
Similar Cached Request?
 ┌────────────┴────────────┐
Yes                        No
 ↓                           ↓
Cached Answer             AI Model
                              ↓
                           Answer
                              ↓
                         Cache Result
```

An **embedding** is a numerical representation used to compare meaning/similarity. Pasted text

---

## Example

Cached question:

> "How do I reset my account password?"

New question:

> "What's the process for changing a forgotten password?"

Different words, potentially the same intent.

The system may reuse the cached answer if similarity and freshness requirements are satisfied. Pasted text

---

## Advantages

- More cache hits than exact-match caching
- Lower AI usage
- Lower latency
- Useful for FAQs and support systems

## Risks

### 1. False matches

Similar questions may still require different answers.

### 2. Stale responses

The cached answer may no longer be correct.

### 3. Similarity threshold problems

```text
Low threshold
 → More cache hits
 → Greater false-match risk

High threshold
 → Fewer cache hits
 → Safer but less efficient
```

Pasted text

---

# Response Cache vs Semantic Cache

| Feature | Response Cache | Semantic Cache |
|---|---|---|
| Match | Usually exact key/request | Meaning/similarity |
| Same wording | Usually required | Not required |
| Complexity | Lower | Higher |
| Hit potential | Lower | Higher |
| Main risk | Staleness | Staleness + wrong semantic match |
| Common implementation | Key-value cache | Vector/embedding lookup |

Pasted text

### Memory trick

> **Response cache = same request.**  
> **Semantic cache = same meaning.**

# 1.1.5 Batch Processing

## Definition

**Batch processing** means grouping multiple independent AI tasks and processing them together instead of handling each one as a separate real-time operation. Pasted text

### Real-time

```text
Item 1 → API
Item 2 → API
Item 3 → API
Item 4 → API
```

### Batch

```text
Items 1–4
   ↓
 Batch
   ↓
Batch Processing
   ↓
 Results
```

---

## Example

Suppose you need to classify **50,000 customer reviews**.

### Real-time approach

```text
50,000 separate immediate requests
```

### Batch approach

```text
50,000 reviews
      ↓
   Batch Job
      ↓
Process asynchronously
      ↓
Store results
```

Batch processing is appropriate when the application doesn't require each result immediately. Pasted text

---

## Good Batch Use Cases

- Large-scale classification
- Embedding generation
- Document processing
- Data enrichment
- Offline analysis
- Dataset evaluation
- Content transformation Pasted text

---

## Batch vs Real-Time

| Factor | Real-Time | Batch |
|---|---|---|
| Immediate response | Required | Not required |
| Best for | Interactive apps | Offline workloads |
| Scheduling | Immediate | Queued |
| Per-request latency | Low | Higher overall |
| Bulk efficiency | Can be lower | Often better |

Pasted text

# 1.1.6 Model Routing

## Definition

**Model routing** means selecting the most appropriate AI model for each request rather than sending every request to one model. Pasted text

### Basic architecture

```text
                    Request
                       ↓
                  Model Router
              ┌────────┼────────┐
              ↓        ↓        ↓
        Small Model  Mid Model  Large Model
              ↓        ↓        ↓
           Simple   Moderate   Complex
            Tasks     Tasks     Tasks
```

---

## Example

### Simple task

> "Is this email spam?"

Use a cheaper suitable model if quality is sufficient.

### Moderate task

> "Summarize this 10-page report."

Choose a model with appropriate context and quality.

### Complex task

> "Analyze this architecture and identify design trade-offs."

Use a more capable model when necessary. Pasted text

---

## Routing Criteria

A router can consider:

```text
Task type
Input size
Required quality
Latency requirement
Cost target
Tool requirements
Multimodal requirements
Provider availability
```

Pasted text

### Example policy

```text
Classification
      ↓
Cheaper model

Summarization
      ↓
Medium model

Complex reasoning
      ↓
Advanced model
```

---

## Why Model Routing Saves Money

Suppose:

```text
90% requests → Simple
10% requests → Complex
```

Using an expensive model for every request wastes resources.

Instead:

```text
90% → Cheaper suitable model
10% → Expensive capable model
```

This is often called **right-sizing the model**. Pasted text

### Critical rule

> **Use the cheapest model that reliably meets the task's quality requirements.**

Not:

> Always use the cheapest model.

# 1.1.7 Output Limits

## Definition

**Output limits** control the maximum amount of content a model can generate. Pasted text

They can reduce:

- Token cost
- Latency

### Example

A classifier does not need a 1,000-word explanation.

Instead:

```text
Return:
{
  "label": "...",
  "reason": "one sentence"
}
```

---

## Output Limiting Strategies

### Limit generated tokens

Set a realistic maximum when supported.

### Define concise formats

```text
Return exactly 3 bullets.
```

### Use structured output

```json
{
  "category": "...",
  "confidence": 0.95
}
```

### Avoid unnecessary explanations

If the application only needs a label:

```text
Don't ask for a long explanation.
```

Pasted text

---

## Output Limit Trade-off

### Too high

```text
More tokens
   +
Higher cost
   +
Higher latency
```

### Too low

```text
Incomplete response
```

### Correct target

```text
Realistic maximum
       ↓
Enough room for correct answer
       ↓
Avoid excessive generation
```

Pasted text

# 1.1.8 Context Reduction

## Definition

**Context reduction** means removing irrelevant or redundant information before sending the request to the model. Pasted text

This is one of the strongest cost-optimization techniques.

---

## The Problem

A request might accidentally contain:

```text
Entire conversation
+
Entire document
+
All search results
+
All tool output
+
Repeated instructions
```

Most of this may be irrelevant.

---

## Context Reduction Strategies

### 1. Summarization

```text
100 pages
   ↓
Relevant summary
   ↓
AI
```

### 2. Retrieval

Instead of sending 1,000 documents:

```text
1,000 documents
      ↓
Retrieve relevant documents
      ↓
5 documents
```

### 3. Remove duplication

If the same information occurs three times, keep it once.

### 4. Conversation compaction

For long conversations:

```text
Old conversation
      ↓
Compact summary
      ↓
Recent messages
      ↓
New request
```

Pasted text

---

## Context Reduction Flow

```text
Raw Context
    ↓
Remove irrelevant data
    ↓
Remove duplicate data
    ↓
Retrieve relevant content
    ↓
Summarize where appropriate
    ↓
Final Context
    ↓
AI Model
```

Pasted text

---

## Context Reduction vs Token Budgeting

These are closely related but not identical.

| Concept | Meaning |
|---|---|
| **Token budgeting** | Defines how much usage you want |
| **Context reduction** | Removes unnecessary input to fit that budget |

Pasted text

### Memory trick

> **Budget = target.**  
> **Reduction = optimization method.**

# 1.1.9 Request Deduplication

## Definition

**Request deduplication** detects duplicate or nearly duplicate requests so expensive work isn't performed repeatedly. Pasted text

### Example

Three processes request:

```text
"Summarize this document."
```

with the same document.

### Without deduplication

```text
Request A → AI
Request B → AI
Request C → AI
```

### With deduplication

```text
A ─┐
B ─┼→ Same request detected
C ─┘
          ↓
      One AI call
          ↓
     Shared result
```

---

## Why Duplicates Happen

Common causes:

- Double-clicks
- Frontend retries
- Network retries
- Multiple workers
- Queue duplication
- Repeated page loads
- Multiple users requesting the same computation Pasted text

---

# Request Fingerprints

Create a stable identifier from relevant request information:

```text
hash(
    model
    +
    prompt
    +
    relevant input
    +
    parameters
)
```

Same fingerprint:

```text
Same fingerprint
      ↓
Potential duplicate
```

Pasted text

---

# In-Flight Deduplication

This is particularly useful when duplicate requests arrive **while the first request is still running**.

```text
Request A
   ↓
AI Call Starts

Request B arrives
   ↓
Same fingerprint
   ↓
Attach B to A
```

Instead of:

```text
A ─────→ AI
B ─────→ AI
```

you get:

```text
A ─────→ AI
B ─────→ Same in-flight result
```

Pasted text

---

# Request Deduplication vs Response Caching

| Feature | Request Deduplication | Response Caching |
|---|---|---|
| Main goal | Avoid duplicate work | Reuse completed result |
| Existing result required? | No | Usually yes |
| In-flight requests | Can combine | Usually not |
| Main benefit | Avoid duplicate computation | Avoid future computation |
| Example | Same request arrives simultaneously | Same question asked later |

Pasted text

### Combined flow

```text
Request
   ↓
Deduplication Check
   ↓
Cache Check
   ↓
Cached?
 ┌──────┴──────┐
Yes            No
 ↓              ↓
Return        Start AI
                ↓
            Save Result
```

Pasted text

# 3. Real-World Case Study: Customer Support AI

## Naive architecture

```text
Every Request
    ↓
Send Entire Knowledge Base
    ↓
Use Expensive Model
    ↓
Allow Long Output
    ↓
Return Response
```

This may generate unnecessary cost.

---

## Optimization 1 — Context Reduction

Instead of:

```text
10,000 documents
```

send only:

```text
5 relevant documents
```

using retrieval. Pasted text

Users may ask:

```text
"How do I reset my password?"

"How can I change a forgotten password?"

"I forgot my password. What do I do?"
```

These could represent the same intent.

Semantic caching may allow reuse of the previous answer when similarity and freshness rules permit it. Pasted text

Instead of:

```text

```

Suppose 10 identical document-analysis requests arrive simultaneously:

        ↓

Pasted text

# Quality vs Cost

A dangerous mistake is assuming:

```text
Lower cost = Always better
```

The real objective is:

```text
Required Quality
       ↓
Find lowest practical cost
       ↓
Without causing unacceptable failures
```

### Why?

A cheap model that produces poor results may cause:

```text
Cheap model
   ↓
Poor answer
   ↓
Retry
   ↓
Human correction
   ↓
More processing
   ↓
Higher actual cost
```

Therefore the goal is to find the **best quality/cost point for the application's requirements**. Pasted text

---

# Important Trade-offs

## Context

```text
Less context
→ Lower cost
→ Higher risk of missing information

More context
→ Higher cost
→ More information
→ Potentially higher latency
```

## Model

```text
Cheaper model
→ Lower cost
→ Potentially lower capability

More capable model
→ Higher cost
→ Better for complex tasks
```

## Semantic caching

```text
Lower similarity threshold
→ More cache hits
→ More false matches

Higher threshold
→ Fewer cache hits
→ Better precision
```

## Output limits

```text
Higher limit
→ Safer against truncation
→ Higher possible cost

Lower limit
→ Lower possible cost
→ Higher truncation risk
```

# Common Mistakes

## 1. Sending the entire conversation every time

Better:

```text
Recent messages
+
Compact history
+
Relevant context
```

Pasted text

---

## 2. Using the most powerful model for every task

Use model routing when appropriate.

---

## 3. Generating unnecessarily long responses

Request only what the application actually needs.

---

## 4. Caching without freshness rules

Cached results can become stale.

Use:

```text
TTL
+
Invalidation
+
Versioning
+
Freshness checks
```

Pasted text

---

## 5. Using unsafe semantic-cache thresholds

Semantic similarity does not guarantee identical intent.

A false cache hit can be worse than making a fresh request.

---

## 6. Ignoring duplicate requests

Retries, multiple workers, and repeated page loads can multiply AI calls.

---

## 7. Cutting context too aggressively

This is a critical trap:

```text
Context reduction
      ≠
Minimum possible context
```

The goal is:

```text
Relevant context
```

Pasted text

---

## 8. Optimizing before measuring

First determine:

```text
Which requests cost the most?
Which prompts are largest?
Which models are used?
How often are calls duplicated?
Which requests can be cached?
```

Then optimize the largest sources of waste. Pasted text

# Glossary

| Term | Meaning |
|---|---|
| **Token** | Unit used by a model to represent text |

| **Semantic Cache** | Reuses a result for a sufficiently similar request |
| **Embedding** | Numerical representation useful for semantic similarity |
| **Batch Processing** | Processing many independent tasks together |
| **Model Routing** | Selecting a suitable model per task |
| **Output Limit** | Maximum amount of generated content |

| **Cache Invalidation** | Removing/refreshing stale cached data |
| **Right-Sizing** | Using the least expensive model that reliably meets requirements |

# 7. Final Revision Sheet

## The 9 optimization techniques

### 1. Token Budgeting

> Control token consumption.

### 2. Prompt Caching

> Reuse repeated prompt processing.

### 3. Response Caching

> Reuse identical completed answers.

### 4. Semantic Caching

> Reuse answers for semantically similar requests.

### 5. Batch Processing

> Process large offline workloads together.

### 6. Model Routing

# Interview Preparation

### Q1. What is the difference between response caching and semantic caching?

Response caching normally matches the same request or cache key. Semantic caching attempts to match requests based on meaning or similarity. Pasted text

### Q2. How does context reduction reduce AI cost?

It removes irrelevant, redundant, or unnecessarily broad input, reducing the number of input tokens sent to the model and potentially lowering latency. Pasted text

### Q3. What is model routing?

It dynamically selects an appropriate model based on factors such as task complexity, required quality, input size, latency, cost, and capabilities. Pasted text

### Q4. When should batch processing be preferred?

When many independent tasks can be processed asynchronously and the application does not require immediate results. Pasted text

### Q5. What is request deduplication?

It detects duplicate or equivalent work so the application does not execute the same expensive operation multiple times. Pasted text

### Q6. What is in-flight deduplication?

It detects that a duplicate request matches an operation that is already running and attaches the new consumer to the existing operation rather than starting another AI call. Pasted text

### Q7. Why can overly aggressive context reduction increase cost?

Removing important information can reduce answer quality, which may cause retries, human intervention, or additional processing. Therefore, the goal is **relevant context**, not the minimum possible context. Pasted text

### Q8. Why isn't "always use the cheapest model" a good strategy?

Because the cheapest model may not reliably meet quality requirements. The objective is to choose the **cheapest suitable model**, not simply the cheapest model. Pasted text

### Q9. Why does caching require freshness controls?

Cached answers can become stale when the underlying information changes. TTL, invalidation, versioned keys, and freshness rules can help manage this risk. Pasted text

### Q10. What metrics would you monitor for AI efficiency?

At minimum: input/output tokens, total tokens, cost per request, cache hit rate, deduplication rate, model distribution, latency, retry/error rate, and context size. Pasted text
