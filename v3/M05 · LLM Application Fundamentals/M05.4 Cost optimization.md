# 1. M05.4 Usage and Efficiency

## Simple Definition

**Usage and efficiency** in AI systems means getting the required quality and functionality while minimizing unnecessary:

- Token consumption
- API requests
- Compute
- Latency
- Storage
- Cost

A useful mental model is:

```text
AI Cost / Efficiency
        │
        ├── Use fewer tokens
        ├── Make fewer requests
        ├── Avoid duplicate work
        ├── Reuse previous results
        ├── Use cheaper suitable models
        └── Process work efficiently
```

---

# 1.1 M05.4.1 Cost Optimization

## What is AI Cost Optimization?

**Cost optimization** means designing an AI system so that it performs the required work at the lowest practical cost without reducing quality below an acceptable level.

A simplified model is:

```text
Total AI Cost
≈
Input Token Cost
+
Output Token Cost
+
Other API / infrastructure costs
```

The exact pricing model varies by provider and model.

### Important principle

> The goal is not to minimize AI usage at all costs. The goal is to eliminate **unnecessary** usage.

For example, reducing a prompt from 10,000 tokens to 500 tokens is useful when the extra content is irrelevant. But removing important context just to save tokens can reduce answer quality and increase rework.

---

# 1.1.1 Token Budgeting

## Definition

**Token budgeting** means deliberately controlling how many tokens an AI request consumes.

A token is a unit used by language models to represent text. It is not exactly the same as a word.

For example:

```text
Input tokens
+
Output tokens
=
Total token usage
```

### Why token budgeting matters

A large application may make thousands or millions of model requests.

Even a small saving per request can become significant:

```text
1,000 tokens saved/request
×
100,000 requests
=
100 million fewer input tokens
```

---

## Token Budget Components

When planning a request, think about:

```text
Request Budget
   │
   ├── System instructions
   ├── User input
   ├── Retrieved context
   ├── Tool results
   └── Expected output
```

### Example

Suppose each request contains:

```text
System prompt      = 500 tokens
User message       = 200 tokens
Retrieved context  = 3,000 tokens
Expected response  = 500 tokens
```

Approximate total:

```text
500 + 200 + 3,000 + 500
= 4,200 tokens
```

If the retrieved context can be reduced to 1,000 tokens:

```text
500 + 200 + 1,000 + 500
= 2,200 tokens
```

That is a major reduction without changing the user's actual task.

---

## Token Budgeting Strategies

### Set maximum output size

Prevent an AI model from generating unnecessarily long answers.

### Limit retrieved context

Only provide information relevant to the current question.

### Avoid repeating instructions

Do not send the same large content unnecessarily.

### Summarize long history

Instead of forwarding an entire conversation indefinitely, maintain a compact summary when appropriate.

### Choose appropriate models

Do not use a highly expensive model for a trivial classification task.

---

## Token Budgeting Trade-off

Too little context:

```text
Low cost
   ↓
Insufficient information
   ↓
Poor answer
```

Too much context:

```text
More information
   ↓
Higher cost + potentially more latency
```

The target is:

```text
Enough context
      +
Enough output
      ↓
Required quality
```

# 1.1.2 Prompt Caching

## Definition

**Prompt caching** means reusing processing for prompt content that appears repeatedly rather than treating the same repeated prefix or content as entirely new work every time.

This is especially useful when many requests share a large common prompt.

### Example

Suppose every request contains:

```text
Large system instructions
+
Company policy
+
Tool definitions
+
User question
```

Only the user question changes.

```text
Request 1:
[Large common prompt] + Question A

Request 2:
[Large common prompt] + Question B

Request 3:
[Large common prompt] + Question C
```

A provider's prompt-caching mechanism may reduce the cost/latency of repeatedly processing the cacheable portion.

---

## Prompt Caching Mental Model

```text
First request
    ↓
Common prompt processed
    ↓
Cache

Later requests
    ↓
Reuse cached prompt portion
    +
New input
```

---

## Best Candidates for Prompt Caching

- Large system instructions
- Stable policy documents
- Repeated tool definitions
- Shared domain context
- Long static examples

### Less suitable

Frequently changing content:

```text
Current timestamp
Latest user message
Temporary state
```

---

## Important Consideration

Prompt caching is usually **provider/model-specific**.

The exact:

- Cache rules
- Cache lifetime
- Pricing
- Minimum cache size
- Cacheable content
- API mechanism

vary across providers.

Therefore, treat caching as an optimization feature rather than assuming all providers implement it identically.

---

# 1.1.3 Response Caching

## Definition

**Response caching** means storing the result of an AI request and returning that stored result when the **same request** occurs again.

### Example

User asks:

> "What is HTTP?"

First request:

```text
Question
 ↓
AI Model
 ↓
Answer
 ↓
Store in cache
```

Next identical request:

```text
Same Question
 ↓
Cache lookup
 ↓
Cached Answer
```

The AI model is not called again.

---

## Response Cache Flow

```text
Request
  ↓
Cache lookup
  ↓
Found?
 ┌──┴───────┐
Yes        No
 ↓           ↓
Return     AI Model
result       ↓
             Save
              ↓
           Return
```

### Benefits

- Lower API cost
- Lower latency
- Fewer requests
- Reduced provider load

---

## When Response Caching Works Well

Best for deterministic or relatively stable requests such as:

- FAQ responses
- Product descriptions
- Repeated calculations
- Static documentation questions
- Common classification requests

### Problem

If the underlying information changes frequently, an old cached answer may become stale.

Therefore, use:

- TTL (time-to-live)
- Cache invalidation
- Versioned keys
- Explicit freshness rules

---

# 1.1.4 Semantic Caching

## Definition

**Semantic caching** goes beyond exact string matching.

It attempts to reuse a previous answer when a **new question has the same or sufficiently similar meaning** as a previous question.

### Exact cache

```text
"What is PostgreSQL?"
```

matches:

```text
"What is PostgreSQL?"
```

But not necessarily:

```text
"Explain PostgreSQL."
```

### Semantic cache

The system compares meaning:

```text
"What is PostgreSQL?"
        ≈
"Explain PostgreSQL."
        ≈
"Can you tell me what PostgreSQL is?"
```

If the questions are sufficiently similar, a previous answer may be reused.

---

## How Semantic Caching Works

A common architecture is:

```text
User Question
      ↓
Embedding / Semantic Representation
      ↓
Similarity Search
      ↓
Similar cached request?
   ┌──┴────┐
  Yes      No
   ↓        ↓
Cached     AI Model
answer       ↓
             Answer
              ↓
          Cache result
```

An **embedding** is a numerical representation of meaning that allows similarity comparisons.

---

## Example

Cached question:

> "How do I reset my account password?"

New question:

> "What's the process for changing a forgotten password?"

The wording differs, but the intent may be highly similar.

The application can potentially return the cached response if the similarity and freshness requirements are satisfied.

---

## Advantages

- More cache hits than exact-match caching
- Lower AI usage
- Lower latency
- Useful for FAQs and support systems

## Risks

### False matches

Two semantically similar questions may require different answers.

### Stale answers

The cached result may no longer be accurate.

### Threshold selection

A very low similarity threshold can return incorrect cached results.

A very high threshold reduces cache hits.

```text
Low threshold
 → More hits, greater risk

High threshold
 → Fewer hits, safer but less efficient
```

---

# Response Cache vs Semantic Cache

| Feature | Response Cache | Semantic Cache |
|---|---|---|
| Match type | Usually exact request/key | Meaning/similarity |
| Same wording required | Usually yes | No |
| Complexity | Lower | Higher |
| Cache hit potential | Lower | Higher |
| Main risk | Staleness | Staleness + wrong semantic match |
| Common technology | Key-value cache | Vector/embedding-based lookup |

# 1.1.5 Batch Processing

## Definition

**Batch processing** means grouping multiple independent AI tasks and processing them together rather than making each request as a separate real-time operation.

### Real-time processing

```text
Item 1 → API
Item 2 → API
Item 3 → API
Item 4 → API
```

### Batch processing

```text
Items 1–4
   ↓
Batch
   ↓
Batch Processing System
   ↓
Results
```

---

## Example

Suppose you need to classify 50,000 customer reviews.

Real-time approach:

```text
50,000 separate immediate requests
```

Batch approach:

```text
50,000 reviews
      ↓
Batch job
      ↓
Process asynchronously
      ↓
Store results
```

This is useful when the application **does not require an immediate response**.

---

## Good Batch Processing Use Cases

- Large-scale classification
- Embedding generation
- Document processing
- Data enrichment
- Offline analysis
- Dataset evaluation
- Content transformation

---

## Batch vs Real-Time

| Factor | Real-Time | Batch |
|---|---|---|
| Response needed immediately | Yes | No |
| Best for | Interactive applications | Offline workloads |
| Scheduling | Immediate | Queued |
| Latency | Low per request | Higher overall |
| Operational efficiency | Can be lower | Often better for bulk work |

The exact cost benefits depend on provider-specific batch offerings.

# 1.1.6 Model Routing

## Definition

**Model routing** means selecting the most appropriate AI model for each request instead of sending every request to one model.

### Example

```text
                    Request
                       ↓
                  Model Router
             ┌─────────┼─────────┐
             ↓         ↓         ↓
         Small Model  Mid Model  Large Model
             │         │         │
          Simple      Moderate   Complex
           Tasks       Tasks      Tasks
```

---

## Example Tasks

### Simple task

> "Is this email spam?"

Use a less expensive model if it provides sufficient quality.

### Moderate task

> "Summarize this 10-page report."

Use a model suitable for the context and quality requirements.

### Complex task

> "Analyze this architecture and identify design trade-offs."

Use a more capable model when necessary.

---

## Routing Criteria

A router may consider:

```text
Task type
Input size
Required quality
Latency requirement
Cost target
Tool requirements
Multimodal requirements
Provider availability
```

### Example routing policy

```text
Classification
   ↓
Cheap model

Summarization
   ↓
Medium model

Complex reasoning
   ↓
Advanced model
```

---

## Why Model Routing Saves Money

Suppose:

```text
90% of requests → simple
10% of requests → complex
```

Using an expensive model for all requests may waste money.

Instead:

```text
90% → cheaper suitable model
10% → expensive capable model
```

This is often called **right-sizing the model**.

### Important principle

> Choose the cheapest model that reliably satisfies the task's quality requirements.

Not simply:

> Always choose the cheapest model.

---

# 1.1.7 Output Limits

## Definition

**Output limits** control the maximum amount of content an AI model can generate for a request.

This can reduce both:

- Token cost
- Latency

### Example

A classifier does not need a 1,000-word response.

Instead of:

```text
"Explain your classification in detail..."
```

use:

```text
Return:
{
  "label": "...",
  "reason": "one sentence"
}
```

---

## Output Limit Strategies

### Limit tokens

Set an appropriate maximum output token count when the provider/API supports it.

### Define concise formats

```text
Return exactly 3 bullets.
```

### Use structured output

```json
{
  "category": "...",
  "confidence": 0.95
}
```

### Avoid unnecessary explanation

If the application only needs a label, do not request a long explanation.

---

## Output Limit Trade-off

Too high:

```text
More tokens
+
Higher cost
+
Higher latency
```

Too low:

```text
Incomplete response
```

Therefore:

```text
Set a realistic maximum
        ↓
Enough room for correct answer
        ↓
Avoid excessive generation
```

---

# 1.1.8 Context Reduction

## Definition

**Context reduction** means removing irrelevant or redundant information from the input before sending it to the model.

This is one of the most powerful AI cost-optimization techniques.

### Problem

A request may accidentally contain:

```text
Entire conversation
+
Entire document
+
All search results
+
All tool output
+
Repeated instructions
```

Most of that may be irrelevant.

---

## Context Reduction Strategies

### 1. Summarization

Convert a long document into a shorter useful summary.

```text
100 pages
   ↓
Relevant summary
   ↓
AI
```

### 2. Retrieval

Send only the relevant sections of a knowledge base.

```text
1,000 documents
      ↓
Retrieve top relevant documents
      ↓
5 documents
```

### 3. Remove duplication

If the same information appears three times, keep it once.

### 4. Conversation compaction

For very long chats:

```text
Old conversation
      ↓
Compact summary
      ↓
Recent messages
      ↓
New request
```

---

## Context Reduction Flow

```text
Raw Context
    ↓
Remove irrelevant data
    ↓
Remove duplicate data
    ↓
Retrieve relevant content
    ↓
Summarize where appropriate
    ↓
Final Context
    ↓
AI Model
```

---

## Context Reduction vs Token Budgeting

These are closely related.

```text
Token budgeting
→ Defines how much you want to spend/use.

Context reduction
→ Reduces unnecessary input to fit that budget.
```

---

# 1.1.9 Request Deduplication

## Definition

**Request deduplication** means detecting duplicate or nearly duplicate requests so the same expensive operation is not executed repeatedly.

### Example

Suppose three users or application processes send:

```text
"Summarize this document."
```

with exactly the same document.

Without deduplication:

```text
Request A → AI
Request B → AI
Request C → AI
```

With deduplication:

```text
A ─┐
B ─┼→ Same request detected → One AI call → Shared result
C ─┘
```

---

## Why Duplicates Happen

Duplicates can come from:

- Double-clicks
- Frontend retries
- Network retries
- Multiple workers
- Queue duplication
- Repeated page loads
- Multiple users requesting the same computation

---

## Deduplication Approaches

### Request fingerprint

Create a stable key from the relevant request content:

```text
hash(
  model
  +
  prompt
  +
  relevant input
  +
  parameters
)
```

Then:

```text
Same fingerprint
     ↓
Potential duplicate
```

---

## In-Flight Deduplication

An especially useful technique is to deduplicate requests that are **currently running**.

Example:

```text
Request A
   ↓
AI call starts

Request B arrives before A completes
   ↓
Same fingerprint
   ↓
Attach B to A's existing operation
```

Instead of starting another model request:

```text
A ───────→ AI
B ───────→ same result
```

---

# Request Deduplication vs Response Caching

These concepts are related but different.

| Feature | Request Deduplication | Response Caching |
|---|---|---|
| Main goal | Avoid duplicate concurrent/repeated work | Reuse completed results |
| Existing result required? | No | Usually yes |
| In-flight requests | Can combine them | Usually not |
| Main benefit | Avoid duplicate computation | Avoid future computation |
| Example | Two identical requests arrive together | Same question asked tomorrow |

### Combined architecture

```text
Request
  ↓
Deduplication check
  ↓
Cache check
  ↓
Cached?
 ┌─┴───┐
Yes   No
 ↓      ↓
Return  Start AI
         ↓
      Save result
```

---

# How the Techniques Work Together

The individual optimizations become much more powerful when combined.

## Optimized AI Request Pipeline

```text
                    User Request
                         ↓
                  Request Deduplication
                         ↓
                    Response Cache
                         ↓
                   Semantic Cache
                         ↓
                  Context Reduction
                         ↓
                   Token Budgeting
                         ↓
                    Model Routing
                         ↓
                   Prompt Caching
                         ↓
                    AI Model
                         ↓
                    Output Limits
                         ↓
                      Result
                         ↓
                  Response Cache
```

Not every application needs every layer, but this shows how they can complement one another.

# Worked Example: Customer Support AI

Suppose a company receives 1 million support questions each month.

A naive implementation:

```text
Every request
    ↓
Send entire knowledge base
    ↓
Use expensive model
    ↓
Allow long output
    ↓
Return response
```

This can be very expensive.

---

## Optimization 1 — Context Reduction

Instead of sending the entire knowledge base:

```text
10,000 documents
      ↓
Retrieve 5 relevant documents
```

---

## Optimization 2 — Semantic Caching

If many users ask:

```text
"How do I reset my password?"
"How can I change a forgotten password?"
"I forgot my password. What do I do?"
```

the application can potentially reuse a previous answer when the semantic similarity and freshness rules permit it.

---

## Optimization 3 — Model Routing

```text
Simple FAQ
  ↓
Lower-cost suitable model

Complex account issue
  ↓
More capable model
```

---

## Optimization 4 — Output Limits

Instead of:

> "Provide a comprehensive explanation..."

use:

```text
Give the answer in 4 concise steps.
```

---

## Optimization 5 — Request Deduplication

If the same expensive document analysis is requested simultaneously:

```text
10 identical requests
        ↓
1 model call
        ↓
10 consumers receive result
```

---

## Result

The system can reduce:

```text
Input tokens
+
Output tokens
+
Number of AI calls
+
Use of expensive models
```

while maintaining the desired user experience.

```text
Need AI response?
      ↓

 ┌────┴─────┐
Yes         No
 ↓           ↓

             ┌────┴─────┐
            Yes         No
             ↓           ↓
         Reuse work   Reduce context
                          ↓
                     Choose model
                          ↓
                    Apply prompt cache
                          ↓
                       AI call
                          ↓
                   Limit output
                          ↓
                     Save result
```

# Common Mistakes

## 1. Sending the entire conversation every time

This gradually increases token usage.

Better:

```text
Recent messages
+
Compact history
+
Relevant context
```

---

## 2. Using the most powerful model for every task

This can unnecessarily increase cost.

Use model routing where appropriate.

---

## 3. Generating unnecessarily long answers

More output means more tokens.

Ask for only what the application actually needs.

---

## 4. Caching without considering freshness

A cached result can become incorrect if the underlying information changes.

Use:

- TTL
- Invalidation
- Versioning
- Freshness checks

---

## 5. Semantic caching with an unsafe similarity threshold

Similarity does not guarantee identical intent.

For sensitive tasks, a false cache hit may be worse than making a new AI request.

---

## 6. Ignoring duplicate requests

Frontend retries and multiple workers can unintentionally multiply AI calls.

---

## 7. Cutting context too aggressively

Reducing context can save money but destroy important information.

The objective is:

```text
Relevant context
≠
Minimum possible context
```

---

## 8. Optimizing cost before measuring usage

You should first understand:

```text
Which requests cost the most?
Which prompts are largest?
Which models are used?
How often are calls duplicated?
Which requests can be cached?
```

Then optimize the largest sources of waste.

A production AI system should monitor metrics such as:

| Metric | What it tells you |
|---|---|
| Input tokens/request | Prompt efficiency |
| Output tokens/request | Generation efficiency |
| Total tokens | Overall usage |
| Cost/request | Unit economics |
| Cache hit rate | Effectiveness of caching |
| Deduplication rate | Duplicate-work reduction |
| Model distribution | How often each model is used |
| Average latency | User experience |
| Error/retry rate | Reliability overhead |
| Context size | Retrieval/prompt efficiency |

---

# Important Relationship: Quality vs Cost

Cost optimization should not be treated as:

```text
Lower cost = Always better
```

Instead:

```text
             Quality
                ↑
                │
      High ─────┼───────
                │   ● Optimal region
                │
      Low ──────┼────────────→ Cost
```

The goal is to find the **best quality/cost point for the application's requirements**.

A cheaper model that produces unusable output may actually cost more because users require retries or human correction.

---

# Key Takeaways

- **Token budgeting** controls how much input and output the system consumes.
- **Prompt caching** reuses repeated prompt processing where supported.
- **Response caching** reuses the result of an identical request.
- **Semantic caching** reuses results for sufficiently similar requests.
- **Batch processing** groups offline work for more efficient large-scale processing.
- **Model routing** selects an appropriate model based on task requirements.
- **Output limits** prevent unnecessarily long generations.
- **Context reduction** removes irrelevant or redundant input.
- **Request deduplication** prevents duplicate work, especially for repeated or concurrent requests.
- Cost optimization should preserve the required quality level.
- Caching requires careful consideration of **freshness and invalidation**.
- Semantic caching introduces the additional risk of returning a result that is similar but not actually appropriate.
- Production systems should measure **cost, tokens, cache hit rate, duplicate requests, latency and quality** rather than optimizing blindly.

## High-value interview questions

**Q1. What is the difference between response caching and semantic caching?**  
Response caching normally matches the same request/key, while semantic caching attempts to match requests based on meaning or similarity.

**Q2. Why is context reduction important for AI cost optimization?**  
Because unnecessary input consumes tokens. Removing irrelevant, duplicated or overly broad context reduces cost and can also reduce latency.

**Q3. What is model routing?**  
Model routing dynamically selects an appropriate model for each request based on factors such as task complexity, quality requirements, latency, cost and required capabilities.

**Q4. When should batch processing be preferred?**  
When many independent tasks can be processed asynchronously and users do not need each result immediately.

**Q5. What is request deduplication?**  
It detects identical or equivalent work so the application performs the expensive AI operation once and reuses the result for multiple consumers.

**Q6. What is the main risk of semantic caching?**  
Two questions can be semantically similar but still require different answers. A cache threshold that is too permissive can therefore return an inappropriate result.

**Q7. Why can reducing tokens sometimes increase total cost?**  
Over-aggressive context or output reduction can lower answer quality, causing retries, corrections, human intervention or additional model calls.

**Q8. What is the most important principle of AI cost optimization?**  
Eliminate unnecessary computation while preserving the quality, reliability and freshness required by the application.
