# 1. Usage and Efficiency Fundamentals

## What Is Usage and Efficiency in AI?

**AI usage and efficiency** means achieving the required quality and functionality while minimizing unnecessary resource consumption.

The main resources to optimize are:

- **Tokens:** The amount of text processed and generated.
- **API requests:** The number of calls made to AI services.
- **Compute:** Processing resources used by models and supporting infrastructure.
- **Latency:** The time required to produce a response.
- **Storage:** Resources used to retain cached results and other data.
- **Cost:** The total expense of running the AI system.

### Mental model

```text
                 AI Efficiency
                      |
        +-------------+-------------+
        |             |             |
        v             v             v
    Reduce         Reuse         Right-size
    tokens         results        models
        |             |             |
        v             v             v
    Less input    Fewer calls    Suitable cost
        |
        v
    Required quality
        |
        v
    Lower practical cost
```

### Core principle

**Efficiency does not mean minimizing AI usage at any cost. It means removing unnecessary usage while preserving the required quality.**

Consider two approaches.

**Approach A: Useful optimization**

```text
10,000-token prompt
        |
        v
Only 500 tokens are relevant
        |
        v
Remove irrelevant information
        |
        v
Lower cost, same required quality
```

**Approach B: Harmful optimization**

```text
10,000-token prompt
        |
        v
Remove important information
        |
        v
Poor answer
        |
        v
Retry or human correction
        |
        v
Potentially higher total cost
```

The second approach can cost more overall because the initial savings create additional work.

## Cost Optimization

**Cost optimization** means designing an AI system to perform the required work at the lowest practical cost without reducing quality below an acceptable level.

A simplified cost model is:

\[
\text{Total Cost} \approx
\text{Input Token Cost}
+
\text{Output Token Cost}
+
\text{Other API and Infrastructure Costs}
\]

Actual pricing depends on the provider, model, service, and applicable pricing rules.

The objective is not:

```text
Minimum possible AI usage
```

It is:

```text
Minimum unnecessary AI usage
                  +
        Required quality
```

For example, a simple classification task may not need a large reasoning model or a lengthy generated explanation.

### Why small optimizations matter

Suppose an optimization saves 1,000 input tokens per request and the system handles 100,000 requests.

\[
1{,}000 \times 100{,}000
= 100{,}000{,}000
\]

That represents **100 million fewer input tokens**.

This illustrates an important principle: small per-request savings can become significant at scale.

## Token Budgeting

### Definition

**Token budgeting** means deliberately controlling how many tokens an AI request consumes.

A token is a unit a model uses to represent text. A token is not exactly the same as a word; the token count depends on the text and tokenizer.

A basic usage model is:

\[
\text{Total Tokens}
=
\text{Input Tokens}
+
\text{Output Tokens}
\]

A request may contain the following components:

```text
Request Token Budget
        |
        +---- System instructions
        |
        +---- User input
        |
        +---- Retrieved context
        |
        +---- Tool results
        |
        +---- Expected output
```

### Worked example

Suppose an AI request uses:

| Component | Tokens |
|---|---:|
| System prompt | 500 |
| User message | 200 |
| Retrieved context | 3,000 |
| Expected output | 500 |
| **Total** | **4,200** |

Now reduce the retrieved context from 3,000 tokens to 1,000 by removing irrelevant material.

| Component | Tokens |
|---|---:|
| System prompt | 500 |
| User message | 200 |
| Retrieved context | 1,000 |
| Expected output | 500 |
| **Total** | **2,200** |

The request now uses 2,000 fewer tokens while keeping the user's question and the expected output unchanged.

This is a useful optimization when the removed content is genuinely unnecessary.

### Token budgeting strategies

**Set maximum output size.** Prevent the model from generating more text than the application needs.

**Limit retrieved context.** Provide only the information relevant to the request.

**Avoid repeated instructions.** Do not repeatedly send large, identical content without a reason.

**Summarize long conversation histories.** Maintain a compact summary when appropriate instead of sending the entire conversation indefinitely.

**Choose an appropriate model.** Avoid using an expensive model for a task that a cheaper suitable model can reliably perform.

### Token budget trade-offs

Too little context:

```text
Lower token cost
       |
       v
Insufficient information
       |
       v
Poor answer
```

Too much context:

```text
More information
       |
       v
Higher token cost
       |
       v
Potentially higher latency
```

The correct target is **enough relevant context and enough output to satisfy the task**.

# 2. Caching Strategies

Caching is one of the major ways to reduce repeated work in AI applications.

The three caching strategies covered here are prompt caching, response caching, and semantic caching. They solve different problems.

## Prompt Caching

### Definition

**Prompt caching** means reusing processing for repeated prompt content when the AI provider supports that capability.

It is particularly useful when many requests share a large, relatively stable section of a prompt.

### Example

Imagine every request contains:

```text
Large system instructions
          +
Company policies
          +
Tool definitions
          +
User question
```

The first three components remain mostly unchanged, while the user question changes.

```text
Request 1 = Common prompt + Question A

Request 2 = Common prompt + Question B

Request 3 = Common prompt + Question C
```

A provider's prompt-caching mechanism may reduce the cost or latency associated with repeatedly processing the cacheable section.

### How prompt caching works

```text
First request
      |
      v
Process common prompt content
      |
      v
Cache eligible content
      |
      v
Later request
      |
      v
Reuse cached portion, where supported
      |
      v
Process new input
```

The precise implementation varies by provider and model.

### Good candidates for prompt caching

- Large system instructions
- Stable policy documents
- Repeated tool definitions
- Shared domain context
- Long, repeated examples

Frequently changing content, such as the latest user message or temporary state, is generally a poorer candidate for caching as a stable shared prefix.

### Important limitations

Prompt caching is provider- and model-specific. Rules can differ in:

- Cache lifetime
- Pricing
- Minimum cacheable content
- Eligible prompt sections
- Cache invalidation and expiration
- API configuration

**Key takeaway:** Prompt caching reuses eligible, repeated prompt processing. It does not necessarily eliminate all processing of the prompt.

## Response Caching

### Definition

**Response caching** stores the completed result of an AI request and reuses it when the same request or cache key is encountered again.

### Example

A user asks:

> What is HTTP?

On the first request:

```text
Question
   |
   v
Cache lookup: MISS
   |
   v
Call AI model
   |
   v
Generate answer
   |
   v
Store answer in cache
   |
   v
Return answer
```

The next identical request may follow this path:

```text
Same request
     |
     v
Cache lookup: HIT
     |
     v
Return cached answer
```

The model does not need to be called again for a valid cache hit.

### Response cache workflow

```text
Request
   |
   v
Cache lookup
   |
   v
Result found?
   /       \
 Yes        No
  |          |
  v          v
Return     Call model
result        |
              v
          Save result
              |
              v
          Return result
```

### Benefits

Response caching can reduce:

- AI API calls
- Response latency
- Repeated computation
- Provider load

### When response caching works well

- Frequently asked questions
- Stable documentation questions
- Product descriptions
- Repeated calculations
- Common classification requests

### The main problem: stale responses

A cached response can become outdated when the underlying information changes.

For example, caching an answer about a product's current price may be unsafe if the price changes frequently.

Possible controls include:

| Control | Purpose |
|---|---|
| TTL (Time-to-Live) | Limits how long an entry remains valid |
| Cache invalidation | Removes entries that are no longer valid |
| Versioned keys | Separates results associated with different data or prompt versions |
| Freshness rules | Determines whether a cached result can still be reused |

Cache keys must also reflect relevant request parameters. Two requests with the same user text may require different answers if they use different model settings, instructions, user permissions, or underlying data.

## Semantic Caching

### Definition

**Semantic caching** attempts to reuse an existing answer when a new request has the same or sufficiently similar meaning as a previous request, even when the wording is different.

### Exact caching vs. semantic caching

An exact cache may treat these as different requests:

```text
"What is PostgreSQL?"
"Explain PostgreSQL."
```

A semantic cache attempts to recognize that both questions may express the same intent.

Another example:

Cached request:

> How do I reset my account password?

New request:

> What's the process for changing a forgotten password?

The wording differs, but the intended information may be similar.

The system may reuse the previous answer if its similarity, freshness, and correctness requirements are satisfied.

### How semantic caching works

A common design uses embeddings and similarity search.

An **embedding** is a numerical representation used to compare semantic similarity.

```text
New user question
        |
        v
Generate embedding
        |
        v
Search cached questions
        |
        v
Compare similarity
        |
        v
Sufficiently similar?
       / \
     Yes  No
      |    |
      v    v
 Reuse    Call AI model
 cached       |
 answer       v
          Generate answer
               |
               v
          Store result
```

A real implementation also needs to check whether the cached response is appropriate for the current user, data, and context.

### Advantages

- More potential cache hits than exact-match caching
- Fewer model calls for repeated intents
- Lower latency for valid cache hits
- Useful for FAQs and support systems

### Risks of semantic caching

**1. False matches**

Two questions can use similar language but require different answers.

For example:

- “How do I close my account?”
- “How do I close my account temporarily?”

These requests may have different business requirements.

**2. Stale responses**

A semantically similar question may be asked after policies or other underlying information have changed.

**3. Similarity threshold problems**

A similarity threshold determines how closely a new question must match a cached question before the system reuses the answer.

```text
Lower threshold
      |
      v
More potential cache hits
      |
      v
Higher risk of incorrect matches
```

```text
Higher threshold
      |
      v
Fewer potential cache hits
      |
      v
Potentially safer matching
```

A similarity score alone is not proof that two requests require the same response.

## Response Cache vs. Semantic Cache

| Feature | Response Cache | Semantic Cache |
|---|---|---|
| Matching approach | Usually an exact key or request match | Meaning or similarity |
| Identical wording required | Often, depending on the key | No |
| Complexity | Relatively low | Higher |
| Potential cache hits | Primarily matching requests | Can include differently worded requests |
| Main risks | Staleness and unsuitable cache keys | Staleness and false semantic matches |
| Typical implementation | Key-value lookup | Embedding or vector similarity lookup |

**Memory trick:**

- **Response cache = same request or cache key.**
- **Semantic cache = sufficiently similar meaning.**

Prompt caching is different from both: it reuses eligible prompt processing, rather than necessarily reusing a completed answer.

# 3. Processing and Model Optimization

## Batch Processing

### Definition

**Batch processing** means grouping multiple independent AI tasks and processing them as a batch instead of treating every task as a separate real-time operation.

It is especially useful when results do not need to be returned immediately.

### Real-time approach

```text
Item 1 ---> API
Item 2 ---> API
Item 3 ---> API
Item 4 ---> API
```

### Batch approach

```text
Items 1–4
    |
    v
Batch job
    |
    v
Process tasks
    |
    v
Collect results
    |
    v
Store or deliver results
```

### Real-world example: review classification

Suppose a company needs to classify 50,000 customer reviews.

A real-time approach may send each review as an individual immediate request.

A batch approach groups the work into an asynchronous job, processes the reviews, and stores the results for later use.

The precise cost savings depend on the provider's batch capabilities, pricing, and implementation.

### Good batch-processing use cases

- Large-scale classification
- Embedding generation
- Document processing
- Data enrichment
- Offline analysis
- Dataset evaluation
- Content transformation

### Batch vs. real-time processing

| Factor | Real-Time | Batch |
|---|---|---|
| Immediate response required | Usually | No |
| Best for | Interactive applications | Offline or asynchronous workloads |
| Scheduling | Immediate execution | Queued or scheduled |
| User-facing latency | Usually prioritized | Can be higher |
| Bulk processing | May involve many individual requests | Can improve bulk efficiency |

Batch processing is not automatically the best choice for every workload. It is appropriate when the delay is acceptable and the tasks can be processed independently or grouped safely.

## Model Routing

### Definition

**Model routing** means selecting the most appropriate AI model for each request instead of sending every request to one model.

Different tasks require different levels of reasoning capability, context capacity, speed, and cost.

### Basic architecture

```text
                 Incoming request
                        |
                        v
                   Model router
                        |
             +----------+----------+
             |          |          |
             v          v          v
        Small model  Mid model  Large model
             |          |          |
             v          v          v
          Simple    Moderate    Complex
           tasks      tasks      tasks
```

The router chooses a model according to a defined policy.

### Examples

**Simple task**

> Is this email spam?

A lower-cost model may be sufficient if it meets the required accuracy.

**Moderate task**

> Summarize this 10-page report.

The router may select a model that can handle the document's context and deliver an adequate summary.

**Complex task**

> Analyze this system architecture and explain its design trade-offs.

A more capable model may be appropriate because the task requires deeper reasoning.

### Routing criteria

A router can consider:

- Task type
- Input size
- Required answer quality
- Latency requirement
- Cost target
- Tool requirements
- Multimodal requirements
- Provider or model availability

### Example routing policy

```text
Classification
      |
      v
Cheaper suitable model

Summarization
      |
      v
Model with suitable context and quality

Complex reasoning
      |
      v
More capable model, when needed
```

### Why model routing saves money

Suppose 90% of requests are simple and 10% are complex.

Using an expensive model for all requests can waste resources when simpler models would perform adequately.

A routing policy might instead use:

```text
90% simple requests
          |
          v
Cheaper suitable model

10% complex requests
          |
          v
More capable model
```

The percentages are illustrative, not a universal workload distribution.

This is often called **right-sizing the model**.

### Critical rule

**Use the cheapest model that reliably meets the task's quality requirements.**

Do not confuse that with always selecting the cheapest available model. If a cheaper model produces poor answers, retries and corrections may increase the total cost.

## Output Limits

### Definition

**Output limits** control the maximum amount of content a model can generate.

Depending on the API, this can involve a maximum output-token setting, concise instructions, or an explicitly structured response format.

### Why output limits matter

They can reduce:

- Output token consumption
- Potential cost
- Generation latency

Consider a classifier that only needs to return a category and a short reason.

Instead of requesting a long explanation, the application can define a compact output contract:

```json
{
  "label": "spam",
  "reason": "Contains suspicious promotional links."
}
```

### Output-limiting strategies

**1. Set a maximum output-token limit.**

Choose a realistic limit where the API supports it.

**2. Define a concise format.**

For example:

```text
Return exactly three concise bullet points.
```

**3. Use structured output.**

Ask for only the fields the application actually requires.

```json
{
  "category": "technical",
  "confidence": 0.95
}
```

The values above are illustrative.

**4. Avoid unnecessary explanations.**

If the application only needs a classification label, do not request an essay.

### Output-limit trade-off

Too high:

```text
More possible output tokens
          |
          v
Higher possible cost
```

Too low:

```text
Insufficient output budget
          |
          v
Incomplete or truncated response
```

The correct target is enough output capacity to produce the complete, valid answer without encouraging unnecessary generation.

# 4. Context and Request Optimization

## Context Reduction

### Definition

**Context reduction** means removing irrelevant or redundant information before sending a request to the AI model.

It is often an effective way to lower input-token consumption.

### The problem

A request may accidentally contain:

```text
Entire conversation history
          +
Entire document
          +
All search results
          +
All tool output
          +
Repeated instructions
```

Much of this material may be irrelevant to the current question.

### Context-reduction strategies

**1. Summarization**

Replace a long body of material with a summary that preserves the information needed for the task.

```text
Long document collection
          |
          v
Relevant summary
          |
          v
AI model
```

A summary must preserve relevant details; otherwise, the model may lose information needed to answer correctly.

**2. Retrieval**

Instead of sending 1,000 documents, retrieve the small set of documents relevant to the current question.

```text
1,000 documents
       |
       v
Search or retrieval
       |
       v
5 relevant documents
       |
       v
AI model
```

The numbers are illustrative.

**3. Remove duplication**

If the same information appears several times, keep it once when repetition is unnecessary.

**4. Conversation compaction**

For long conversations, maintain a compact summary alongside recent messages.

```text
Older conversation
        |
        v
Compact history summary
        |
        +---- Recent messages
                    |
                    v
                New request
```

### Context-reduction workflow

```text
Raw context
     |
     v
Remove irrelevant data
     |
     v
Remove duplicated information
     |
     v
Retrieve relevant content
     |
     v
Summarize where appropriate
     |
     v
Final context
     |
     v
AI model
```

### Context reduction vs. token budgeting

These concepts are related but different.

| Concept | Main purpose |
|---|---|
| Token budgeting | Defines the intended token-usage target |
| Context reduction | Removes unnecessary input to help meet the target |

**Memory trick:**

- **Budget = target.**
- **Reduction = optimization method.**

The objective is not to minimize context at any cost. It is to provide the smallest useful context that preserves the information required for a correct answer.

## Request Deduplication

### Definition

**Request deduplication** detects duplicate or equivalent requests so the same expensive computation does not need to be performed repeatedly.

### Example

Three processes request the same document summary:

```text
Request A: Summarize this document.
Request B: Summarize this document.
Request C: Summarize this document.
```

Assume the requests have equivalent inputs and settings.

Without deduplication:

```text
Request A ---> AI call
Request B ---> AI call
Request C ---> AI call
```

With deduplication:

```text
Request A ---+
Request B ---+---> Detect equivalent requests
Request C ---+              |
                            v
                       One AI call
                            |
                            v
                       Shared result
```

This is particularly useful for duplicate work submitted by multiple processes or users.

### Why duplicate requests happen

- Double-clicks
- Frontend retries
- Network retries
- Multiple background workers
- Duplicate queue messages
- Repeated page loads
- Multiple users requesting the same computation

The system must determine whether the requests are genuinely equivalent before sharing a result.

## Request Fingerprints

A **request fingerprint** is a stable identifier derived from the parts of a request that affect its result.

A conceptual fingerprint might be computed from:

```text
Fingerprint input
        |
        +---- Model or model policy
        |
        +---- Prompt and instructions
        |
        +---- Relevant request data
        |
        +---- Generation parameters
        |
        v
Stable hash or identifier
```

Conceptually:

```text
hash(
    model configuration
    + prompt
    + relevant input
    + parameters
)
```

If two requests have the same fingerprint, they are candidates for deduplication.

However, a fingerprint must include all result-relevant information. For example, omitting an important user permission, data version, or generation parameter could cause unrelated requests to be treated as equivalent.

A matching fingerprint should therefore be understood as a deduplication signal based on a carefully designed key, not as proof that every possible aspect of two requests is identical.

## In-Flight Deduplication

### Definition

**In-flight deduplication** combines duplicate requests while the original request is still running.

This prevents multiple identical AI calls from starting at the same time.

### Example

```text
Request A arrives
       |
       v
AI call starts
       |
       v
Request B arrives
       |
       v
Fingerprint matches A
       |
       v
Attach B to A's in-flight operation
```

Instead of:

```text
A ----------------> AI call 1
B ----------------> AI call 2
```

the system shares the running operation:

```text
A ----+
      |
      +------------> One AI call
      |                  |
B ----+                  v
                     Shared result
```

Depending on the implementation, both consumers can receive the completed result or observe the same running operation.

### Request deduplication vs. response caching

| Feature | Request Deduplication | Response Caching |
|---|---|---|
| Main goal | Prevent duplicate work | Reuse a completed result |
| Requires a completed result beforehand | No | Usually |
| In-flight requests | Can be combined | Ordinary response caching usually operates on completed entries |
| Primary benefit | Avoid duplicate computation | Avoid repeated future computation |
| Example | Two identical requests arrive simultaneously | The same request occurs again later |

### Combining deduplication and response caching

```text
Incoming request
       |
       v
Check in-flight deduplication
       |
       v
Check exact response cache
       |
       v
Valid result found?
      / \
    Yes  No
     |    |
     v    v
  Return  Start AI call
  result      |
              v
          Save result
              |
              v
          Return result
```

The exact ordering can vary by architecture, but completed-result reuse and in-flight deduplication solve different problems.

# 5. Combining the Nine Optimization Techniques

A production AI system can combine the techniques into one request-processing workflow.

## The Nine Techniques

The techniques covered in this module are:

1. Token budgeting
2. Prompt caching
3. Response caching
4. Semantic caching
5. Batch processing
6. Model routing
7. Output limits
8. Context reduction
9. Request deduplication

Each technique addresses a different source of unnecessary usage.

## An Optimized AI Request Pipeline

```text
                  Incoming request
                         |
                         v
               Request deduplication
                         |
                         v
                 Exact cache lookup
                         |
                         v
                Semantic cache lookup
                         |
                         v
                  Context reduction
                         |
                         v
                   Token budgeting
                         |
                         v
                    Model routing
                         |
                         v
                   Prompt caching
                         |
                         v
                      AI call
                         |
                         v
                    Output limits
                         |
                         v
                  Validate the result
                         |
                         v
                    Save result
                         |
                         v
                 Return to consumer
```

This is a conceptual pipeline rather than a mandatory ordering. For example, output limits are usually configured before generation begins, and prompt caching is handled according to the provider's API.

Not every application needs every layer.

- A small chatbot may need only context reduction, model selection, and output limits.
- An FAQ system may benefit substantially from response and semantic caching.
- A large asynchronous data-processing system may benefit from batch processing.
- A system receiving many duplicate simultaneous requests may need in-flight deduplication.

Choose techniques based on workload characteristics and measured costs.

## Real-World Case Study: Customer Support AI

Suppose a company handles **1 million customer support questions per month**.

### Naive architecture

```text
Every request
      |
      v
Send entire knowledge base
      |
      v
Use expensive model
      |
      v
Allow long output
      |
      v
Return response
```

This architecture can spend resources on irrelevant context, unnecessarily powerful models, repeated questions, and excessive output.

### Optimization 1: Context reduction

Instead of supplying 10,000 documents to every request, retrieve the small set of relevant documents.

```text
Knowledge base
      |
      v
Retrieve relevant information
      |
      v
Provide selected context
      |
      v
AI model
```

This can reduce input-token usage while preserving the information needed for the answer.

### Optimization 2: Semantic caching

Customers may ask:

```text
"How do I reset my password?"

"How can I change a forgotten password?"

"I forgot my password. What should I do?"
```

The system may recognize that these requests share an intent and reuse an existing answer when similarity and freshness conditions are met.

The cache must not return an answer that is inappropriate for a different account state or policy.

### Optimization 3: Model routing

```text
Simple FAQ
     |
     v
Lower-cost suitable model

Complex account issue
     |
     v
More capable model, when necessary
```

The router uses task requirements rather than sending every request to the most expensive model.

### Optimization 4: Output limits

Instead of asking for a comprehensive explanation every time, the application can request a concise answer.

```text
Give the answer in four concise steps.
```

The response still needs enough detail to be useful and correct.

### Optimization 5: Request deduplication

Suppose ten equivalent document-analysis requests arrive simultaneously.

```text
10 equivalent requests
          |
          v
Deduplication
          |
          v
One AI operation
          |
          v
Shared result
```

One operation can serve multiple consumers where the requests are genuinely equivalent and sharing is appropriate.

### Expected impact

Combining these techniques can reduce:

- Input tokens
- Output tokens
- Number of AI calls
- Unnecessary use of expensive models
- Repeated computation

The actual savings depend on how often requests are repeated, what can be cached, the workload mix, and the provider's pricing model.

The goal is to lower cost while maintaining the required answer quality.

## Cost Optimization Decision Tree

A practical decision process is:

```text
Need an AI response
        |
        v
Is a valid exact cached result available?
        |
       Yes -----------------> Return result
        |
        No
        |
        v
Is a sufficiently similar cached result
safe and fresh for this request?
        |
       Yes -----------------> Return cached result
        |
        No
        |
        v
Is equivalent work already running?
        |
       Yes -----------------> Reuse in-flight operation
        |
        No
        |
        v
Reduce irrelevant context
        |
        v
Set token and output budgets
        |
        v
Choose an appropriate model
        |
        v
Use prompt caching where supported
        |
        v
Call AI model
        |
        v
Validate and store result as appropriate
        |
        v
Return response
```

Batch processing can be selected earlier when the task is asynchronous and does not require an immediate answer.

# 6. Measuring Efficiency and Balancing Quality

## Measure Before Optimizing

AI optimization should be measured rather than guessed.

Start by determining where the system spends its resources.

| Metric | What it tells you |
|---|---|
| Input tokens per request | Prompt and context efficiency |
| Output tokens per request | Generation efficiency |
| Total tokens | Overall token usage |
| Cost per request | Unit economics of inference |
| Cache hit rate | How frequently cached results are reused |
| Deduplication rate | How much duplicate work is avoided |
| Model distribution | How often different models are used |
| Average latency | Typical response time |
| Error and retry rate | Reliability problems and repeated work |
| Context size | Retrieval and prompt efficiency |

Additional metrics may be useful for specific applications, such as p95 latency, cost per successful task, answer-quality scores, or the rate of human corrections.

The most useful metrics depend on the application's requirements.

## Quality vs. Cost

A dangerous assumption is:

```text
Lower cost = Always better
```

The actual objective is:

```text
Required answer quality
          |
          v
Find the lowest practical cost
          |
          v
Avoid unacceptable failures
```

### Why cheaper is not always better

Consider this example:

```text
Cheaper model
      |
      v
Incorrect answer
      |
      v
Retry or human correction
      |
      v
Additional processing
      |
      v
Higher total cost
```

A model with lower per-request pricing may have a higher total cost if it frequently fails to meet the application's requirements.

The best model is the one that offers the appropriate quality, capabilities, latency, and cost for the task.

# 7. Common Mistakes and Best Practices

## Sending the entire conversation every time

**Problem:** Long conversations may contain irrelevant historical context and repeated instructions.

**Better approach:** Combine recent messages, a compact history summary, and the context relevant to the current request.

## Using the most powerful model for every task

**Problem:** Simple tasks may not require an expensive model.

**Better approach:** Use model routing where appropriate, and measure the quality of cheaper alternatives before deploying them.

## Generating unnecessarily long responses

**Problem:** Excessive output consumes more tokens and may increase latency.

**Better approach:** Specify the required format, length, and fields.

## Caching without freshness rules

**Problem:** Cached information may become outdated.

**Better approach:** Establish suitable TTLs, cache invalidation, versioning, and freshness checks.

## Setting unsafe semantic-cache thresholds

**Problem:** Similar wording does not guarantee identical intent.

**Better approach:** Evaluate semantic matching thresholds and enforce appropriate access, context, and freshness checks.

## Ignoring duplicate requests

**Problem:** Retries, multiple workers, and repeated page loads may trigger unnecessary AI calls.

**Better approach:** Use request fingerprints and in-flight deduplication for equivalent concurrent work.

## Cutting context too aggressively

**Problem:** Removing important information can reduce answer quality.

**Better approach:** Preserve relevant context and measure both cost and answer quality.

Remember:

```text
Context reduction
       !=
Minimum possible context
```

The objective is relevant context.

## Optimizing before measuring

**Problem:** Optimization effort may target the wrong bottleneck.

**Better approach:** Measure token consumption, cost, latency, model distribution, cache hit rate, duplicate requests, and error rates first.

Then focus on the largest sources of avoidable cost.

## Confusing the optimization techniques

| Technique | Question it answers |
|---|---|
| Token budgeting | How much usage should be allowed? |
| Context reduction | What unnecessary input can be removed? |
| Prompt caching | Which repeated prompt processing can be reused? |
| Response caching | Is a valid answer already stored for this request? |
| Semantic caching | Is there a sufficiently similar cached answer? |
| Request deduplication | Is equivalent work already being performed? |
| Model routing | Which model is appropriate for this task? |
| Batch processing | Can this work be processed asynchronously in bulk? |
| Output limits | How much output does the task actually require? |

# 9. Practice Questions and Interview Preparation

## Question-and-Answer Recall

**Q1. What is AI cost optimization?**

**Answer:** Achieving the required quality and functionality at the lowest practical cost by reducing unnecessary token usage, API calls, computation, and other resource consumption.

**Q2. Why does token budgeting matter?**

**Answer:** It controls token consumption. Small savings per request can produce substantial savings when the system handles many requests.

**Q3. What is prompt caching?**

**Answer:** Reusing eligible processing for prompt content that appears repeatedly, when the provider and model support it.

**Q4. What is response caching?**

**Answer:** Storing a completed result and returning it again when the same request or cache key occurs and the cached result remains valid.

**Q5. What is semantic caching?**

**Answer:** Reusing a cached result for a sufficiently similar request based on meaning rather than requiring identical wording.

**Q6. What is the main risk of semantic caching?**

**Answer:** Two similar questions may still require different answers, causing a false cache hit. Stale information is another important risk.

**Q7. When is batch processing useful?**

**Answer:** When many independent tasks can be processed together and the application does not require immediate results.

**Q8. What is model routing?**

**Answer:** Selecting a suitable AI model for each request based on characteristics such as complexity, quality requirements, input size, latency, cost, and capabilities.

**Q9. What does right-sizing a model mean?**

**Answer:** Choosing the least expensive model that reliably meets the task's quality requirements.

**Q10. Why are output limits useful?**

**Answer:** They help prevent unnecessary generation, reducing potential token cost and latency while controlling response length.

**Q11. What is context reduction?**

**Answer:** Removing irrelevant or redundant information before sending an AI request.

**Q12. How is context reduction different from token budgeting?**

**Answer:** Token budgeting sets the intended usage target. Context reduction is a method for removing unnecessary input to help meet that target.

**Q13. What is request deduplication?**

**Answer:** Detecting equivalent requests so the same expensive computation is not repeated unnecessarily.

**Q14. What is a request fingerprint?**

**Answer:** A stable identifier derived from the information that affects a request's result, used to help recognize equivalent work.

**Q15. What is in-flight deduplication?**

**Answer:** Combining duplicate requests while the original operation is still running instead of starting separate AI calls.

**Q16. How does request deduplication differ from response caching?**

**Answer:** Deduplication avoids duplicate work, especially concurrent work. Response caching reuses results that have already been completed and stored.

**Q17. Why can aggressive context reduction increase overall cost?**

**Answer:** Removing important context may produce poor answers, causing retries, additional processing, or human correction.

**Q18. Why is “always use the cheapest model” a poor rule?**

**Answer:** The cheapest model may not meet the task's quality requirements. The goal is to choose the cheapest suitable model.

**Q19. Why does caching need freshness rules?**

**Answer:** Cached answers may become outdated when the underlying data, policies, or instructions change.

**Q20. What metrics should you monitor when optimizing an AI system?**

**Answer:** Input and output tokens, cost per request, cache hit rate, deduplication rate, model distribution, latency, retry/error rate, and context size.

## Scenario-Based Interview Questions

### Scenario 1: High AI cost in a customer support system

**Question:** Your application receives one million customer questions every month. Input-token usage and model-provider costs are high. How would you investigate and optimize the system?

**Answer:**

First, measure input tokens, output tokens, cost per request, model distribution, cache hit rate, retries, and context size.

Then identify the largest sources of waste. Retrieve only relevant support documents, reduce repeated conversation context, enforce suitable output limits, and route simpler questions to cheaper suitable models. Introduce exact response caching or semantic caching where answers remain valid, and use deduplication for duplicate requests.

Finally, evaluate cost and answer quality together. The goal is to reduce cost per successful response rather than merely reducing token usage.

### Scenario 2: Excessive model usage

**Question:** Your application uses a powerful model for spam classification, short summaries, and complex architecture reviews. What would you change?

**Answer:**

Introduce model routing. Use a cheaper model for tasks where it meets the required quality, a model with suitable context and summarization capabilities for summaries, and a more capable model for difficult reasoning tasks when necessary.

Evaluate candidate models using representative examples before deploying the routing policy. Monitor model distribution, latency, errors, and quality after rollout.

### Scenario 3: Repeated FAQ requests

**Question:** Many users ask “How do I reset my password?” in different ways. How could you reduce model calls?

**Answer:**

Use response caching for matching requests and consider semantic caching for differently worded questions that express the same intent. Set appropriate freshness rules, validate whether the cached answer is relevant to the current context, and avoid sharing account-specific information between users.

### Scenario 4: Duplicate concurrent requests

**Question:** A user double-clicks a button, and the backend receives two identical expensive AI requests. How do you prevent duplicate work?

**Answer:**

Generate a stable fingerprint from result-relevant request information and use in-flight deduplication to identify the duplicate request. If the same operation is already running, attach the new consumer to the existing operation where appropriate.

The implementation should also consider failure handling, cancellation, and whether the consumers genuinely have equivalent permissions and parameters.

### Scenario 5: Batch or real-time processing?

**Question:** Your system classifies 100,000 archived customer reviews. The business needs the results tomorrow, but not immediately. Which processing strategy would you consider?

**Answer:**

Batch processing is a strong candidate because the workload is large, asynchronous, and does not require immediate per-review responses. Assess the provider's batch capabilities, pricing, processing deadlines, failure handling, and result-storage requirements.

### Scenario 6: Context reduction harms answer quality

**Question:** Your team removes most retrieved context to reduce token cost. The model begins making inaccurate statements because it lacks important details. How would you fix this?

**Answer:**

Reevaluate retrieval, summarization, and context selection. Preserve the details required to answer correctly and remove only irrelevant or redundant content. Compare token usage and answer quality on a representative evaluation set, and monitor retries and human corrections.

### Scenario 7: Stale cached information

**Question:** A product-support AI returns an old policy from its semantic cache after the policy has changed. What improvements are needed?

**Answer:**

Introduce freshness rules, TTLs, invalidation, and versioning where appropriate. Review how the cache key or stored metadata represents the underlying policy version. Ensure semantic similarity cannot override important freshness or access restrictions.

### Scenario 8: Choosing output limits

**Question:** A classification API only needs a category and a one-sentence reason, but model responses are often several paragraphs long. What would you do?

**Answer:**

Define a concise response contract with the required fields and configure a suitable output-token limit where supported. Validate the output and ensure the limit does not prevent the model from returning a complete valid response.

### Scenario 9: Proving an optimization worked

**Question:** Your team introduces model routing and claims the system is more efficient because the average model cost decreased. Is that sufficient evidence?

**Answer:**

No. Measure cost per successful task, answer quality, latency, error and retry rates, human correction rates where relevant, and the distribution of work across models. A lower model cost is useful only if the system continues to meet its quality requirements without creating offsetting costs.
