# 1. M05.1.1 Provider Integration

## Simple Definition

An **AI provider** is a company or platform that gives your application access to AI models through an **API** or **SDK**. Instead of running a large model yourself, your application sends requests to the provider, which runs the model and returns the response. Pasted text

### Basic architecture

```text
Your Application
       ↓
   Provider API
       ↓
    AI Model
       ↓
    Response
       ↓
Your Application
```

The main providers covered here are **OpenAI, Anthropic, and Google**, along with several other provider/model-hosting ecosystems. Pasted text

# 1.1 Provider Options

## 1.1.1 OpenAI

### What is it?

OpenAI provides APIs for AI applications involving areas such as:

- Text
- Code
- Reasoning
- Structured output
- Images
- Audio
- Tools
- Agents
- Search/retrieval

The supplied material specifically identifies APIs and capabilities around the Responses API, tools, streaming, agents, file inputs, web search, and function calling. Pasted text

### Typical integration

```text
User
  ↓
Your Backend
  ↓
OpenAI API
  ↓
Selected Model
  ↓
Response
```

### Common applications

- Chatbots
- Coding assistants
- Document analysis
- AI agents
- Information extraction
- Structured-output generation
- Multimodal applications Pasted text

### Important architectural lesson

Do **not** scatter OpenAI-specific logic throughout your entire application.

Prefer:

```text
Application
     ↓
  AI Service
     ↓
OpenAI Adapter
     ↓
OpenAI API
```

The adapter isolates provider-specific implementation details and makes it easier to introduce another provider later. Pasted text

## 1.1.2 Anthropic

Anthropic provides the **Claude** family of models through its API platform. Pasted text

```text

     ↓

     ↓

     ↓
```

- Conversational AI
- Coding assistance


Your application talks to **your interface**, while each provider has its own adapter. Pasted text

# 1.2 Access and Usage Controls

## 1.2.1 API Key / Project Management

### What is an API key?

An **API key** is a credential that allows an application to authenticate with an AI provider. Pasted text

```text
Application
     ↓
"Who am I?"
     ↓
 API Key
     ↓
Provider verifies access
     ↓
Accepted / Rejected
```

---

## Never expose API keys in frontend code

### ❌ Bad architecture

```text
React App
   ↓
API Key
   ↓
AI Provider
```

Frontend code is delivered to the user, so a secret embedded there can potentially be inspected and extracted. Pasted text

### ✅ Better architecture

```text
React App
   ↓
Your Backend
   ↓
Secret API Key
   ↓
AI Provider
```

Keep secrets in:

- Environment variables
- Secret-management systems
- Backend-only configuration Pasted text

Example:

```text
OPENAI_API_KEY=...
ANTHROPIC_API_KEY=...
GEMINI_API_KEY=...
```

The exact variable name depends on your application/SDK setup. Pasted text

---

## Project Management

A **project** is a logical boundary for organizing things such as:

- Access
- Usage
- Billing
- Permissions
- Resources

A useful environment layout is:

```text
Company
 ├── Production Project
 │      └── Production API Key
 │
 ├── Development Project
 │      └── Development API Key
 │
 └── Testing Project
        └── Test API Key
```

Pasted text

### Why separate projects?

They help with:

- Environment separation
- Access control
- Usage monitoring
- Cost tracking
- Key rotation
- Limiting the blast radius of a leaked key Pasted text

### Important distinction

```text
Account
   ↓
Projects
   ↓
Keys / Resources
   ↓
Applications
```

A project gives you an organizational and control boundary rather than simply being another name for an API key.

---

## Key Rotation

Suppose a production key is leaked.

### Recommended sequence

```text
Old Key Leaked
      ↓
Create New Key
      ↓
Deploy New Key
      ↓
Verify Application
      ↓
Disable / Revoke Old Key
      ↓
Audit Usage
```

Pasted text

### Important security rule

Never commit secrets to Git.

```text
❌ .env committed to GitHub
❌ API key inside React source
❌ API key inside screenshots
❌ API key inside public documentation

✅ Environment variables
✅ Secret manager
✅ Backend-only configuration
```

Pasted text

# 1.2.2 Usage Limits

### Definition

A **usage limit** controls how much AI usage an account, organization, project, or workspace can consume. Pasted text

Usage can be measured in:

- Requests
- Tokens
- Storage
- Cost/spend
- Daily quota
- Monthly quota

### Why do usage limits exist?

They help protect against:

- Unexpected bills
- Abuse
- Runaway loops
- Excessive API usage
- Resource exhaustion Pasted text

### Example: runaway agent

```text
Agent
 ↓
AI Call
 ↓
Tool
 ↓
AI Call
 ↓
Tool
 ↓
AI Call
 ↓
...
```

Without controls, an accidental loop can become very expensive. Pasted text

A limit acts as a safety barrier:

```text
Normal Usage
     ↓
   Limit
     ↓
Block / Throttle / Pause
```

# 1.2.3 Rate Limits

### Definition

A **rate limit** controls how quickly requests or tokens can be consumed. Pasted text

Common metrics:

| Metric | Meaning |
|---|---|
| RPM | Requests Per Minute |
| TPM | Tokens Per Minute |
| RPD | Requests Per Day |

Some providers also distinguish input-token and output-token rates. Pasted text

### Example

Suppose your application can make:

```text
100 requests/minute
```

but suddenly sends:

```text
150 requests/minute
```

The provider may reject the excess requests.

```text
Request
   ↓
Rate-limit check
   ↓
Within limit?
 ┌───────┴───────┐
Yes              No
 ↓                ↓
Process          429
```

---

## Rate Limit vs Usage Limit vs Spend Limit vs Quota

| Concept | Meaning |
|---|---|
| **Usage limit** | How much total usage is allowed |
| **Rate limit** | How quickly usage can happen |
| **Spend limit** | How much money can be spent |
| **Quota** | Allocated amount of a particular resource |

Pasted text

### Easy example

```text
Monthly usage limit = 1,000,000 tokens
Rate limit          = 10,000 tokens/minute
```

You may eventually consume 1 million tokens, but you cannot consume all 1 million within one minute. Pasted text

### Remember

> **Usage = how much**  
> **Rate = how fast**

# 1.3 Integration Behavior

# 1.3.1 Error Handling

AI APIs are network services, so failure must be treated as a normal possibility. Pasted text

### General flow

```text
Request
   ↓
Success?
 ┌──────┴──────┐
Yes            No
 ↓              ↓
Process       Identify error
response          ↓
              Retryable?
             ┌─────┴─────┐
            Yes           No
             ↓             ↓
           Retry       Report / Recover
```

---

## Common HTTP error categories

### 400 — Bad Request

The request itself is invalid.

Examples:

- Invalid parameter
- Incorrect request structure
- Unsupported option

Usually:

```text
❌ Fix request
❌ Do not blindly retry
```

Pasted text

---

### 401 — Authentication Error

Credentials are missing or invalid.

```text
Invalid API key
      ↓
     401
      ↓
Check credentials/configuration
```

Retrying the exact same request normally will not solve the underlying problem. Pasted text

---

### 403 — Forbidden

Authentication may exist, but the caller does not have permission.

Possible causes:

- Missing permissions
- Restricted resource
- Unauthorized project/model/service Pasted text

---

### 404 — Not Found

The requested resource cannot be found.

Possible causes:

- Incorrect model ID
- Incorrect URL
- Deleted resource
- Unsupported endpoint Pasted text

---

### 429 — Too Many Requests

The application exceeded some type of limit.

Possible causes include:

```text
Rate limit
Quota limit
Usage limit
Acceleration / burst limit
```

A 429 may be retryable, but the exact underlying cause matters. Pasted text

---

### 500 — Internal Server Error

The provider encountered an unexpected server-side problem.

A retry with backoff may be appropriate when the operation is safe to retry. Pasted text

---

### 503 — Service Unavailable

The provider is temporarily unavailable or overloaded.

```text
Request
  ↓
503
  ↓
Wait
  ↓
Retry
```

Pasted text

# 1.3.2 Retry Strategy

## Never retry every error

The first question should be:

> **Is this error transient and safe to retry?**

```text
API Request
     ↓
   Error?
     ↓
 ┌───────────────┐
 │               │
Retryable    Non-retryable
 │               │
 ↓               ↓
Wait           Fix request
 ↓
Retry
```

Pasted text

---

## Exponential Backoff

Instead of:

```text
retry
retry
retry
retry
```

use increasing delays:

```text
1 sec
  ↓
2 sec
  ↓
4 sec
  ↓
8 sec
  ↓
STOP
```

Pasted text

### Why?

Repeated immediate retries can make overload worse.

Exponential backoff gives the provider time to recover and reduces pressure from the client.

---

## Jitter

**Jitter** means adding a small random variation to retry delays.

Why?

Imagine thousands of clients all receive an error and retry exactly after 1, 2, 4, and 8 seconds.

They may all hit the provider simultaneously again.

```text
Without jitter

Clients
 ↓ ↓ ↓ ↓ ↓
Retry at same moment
        ↓
Traffic spike
```

With jitter:

```text
Client A → 2.1 sec
Client B → 2.6 sec
Client C → 3.0 sec
Client D → 2.3 sec
```

The retries become distributed over time.

The supplied material identifies exponential backoff plus jitter as the appropriate strategy for suitable transient failures. Pasted text

---

# 1.3.3 Idempotency and Retries

Before retrying, ask:

> **Could performing this operation twice create a duplicate side effect?**

For a simple text-generation request, duplicate execution may be relatively harmless.

For a business operation, it can be dangerous.

### Dangerous example

```text
AI
 ↓
Create Booking
```

A retry could result in:

```text
Booking #1
Booking #2
```

Likewise:

```text
AI → Send Payment
AI → Create Database Record
```

could create duplicate side effects. Pasted text

### Therefore retry design should consider

```text
Retry Strategy
      +
Idempotency
      +
Maximum Retry Count
```

Pasted text

### Key idea

**Retryable does not automatically mean safe to retry.**

Two separate questions exist:

1. Can the provider recover?
2. Can my operation safely execute again?

# 1.3.4 Provider-Specific Capabilities

This is one of the most important concepts in multi-provider integration.

Although providers solve similar AI problems, their capabilities are **not identical**. Pasted text

Providers may differ in:

- Model families
- Context length
- Vision/multimodal support
- Audio support
- Structured output
- Function/tool calling
- Streaming
- Embeddings
- Fine-tuning
- Batch processing
- Agents
- File handling
- Caching
- Deployment options Pasted text

### Important distinction

```text
Same task
   ≠
Same API
   ≠
Same model
   ≠
Same capability
```

A capability being available from several providers does **not** mean the implementation is identical. Pasted text

---

# 1.3.5 Provider Abstraction vs Provider-Specific Features

Suppose your application has a common operation:

```text
generateText()
```

This can potentially be implemented by several providers.

Similarly:

```text
streamText()
```

may be represented through a common interface.

But a special feature may be provider-specific:

```text
provider.webSearch()
provider.computerUse()
provider.specialTool()
```

Pasted text

### Recommended architecture

```text
                  AI Interface
                       │
          ┌────────────┴────────────┐
          ↓                         ↓
    Common API              Provider Extensions
          │                         │
 generateText()              Special capabilities
 streamText()                 Provider-specific tools
```

This design avoids pretending that every provider supports exactly the same feature set. Pasted text

# 1.3.6 Best Architecture for Multi-Provider Integration

A scalable architecture can look like:

```text
                         Application
                              ↓
                          AI Service
                              ↓
                           AI Router
                       /       |       \
                      /        |        \
                     ↓         ↓         ↓
                  OpenAI   Anthropic   Google
                     ↓         ↓         ↓
                   Model     Model     Model
                      \        |        /
                       \       |       /
                              ↓
                       Normalized Result
                              ↓
                         Application
```

Pasted text

## What does the AI Router do?

The router can choose a provider/model based on:

```text
Task
 ↓
Required capability
 ↓
Cost
 ↓
Latency
 ↓
Provider availability
 ↓
Select model/provider
```

Pasted text

### Example decision

```text
User asks for task
       ↓
Does task require feature X?
       ↓
Which providers support X?
       ↓
Which is cheapest?
       ↓
Which is fast enough?
       ↓
Choose provider/model
```

This creates flexibility without coupling the application directly to a single vendor.

# 1.3.7 Provider Fallback

Suppose:

```text
Primary  = OpenAI
Fallback = Anthropic
```

The architecture could be:

```text
User Request
     ↓
   OpenAI
     ↓
 Success?
 ┌────┴─────┐
Yes         No
 ↓           ↓
Return    Retryable?
response  ┌───┴────┐
         Yes       No / still failing
          ↓              ↓
     Retry OpenAI     Anthropic
                         ↓
                    Return result
```

Pasted text

### Why use fallback?

It can improve **availability**.

But fallback introduces complexity around:

- Prompt compatibility
- Response normalization
- Cost
- Provider-specific features
- Different model behavior

So fallback is not simply:

```text
OpenAI fails → blindly use Anthropic
```

It requires an abstraction strategy.

# 1.3.8 Common Mistakes

## Mistake 1: Treating all providers as identical

They are not.

```text
Same purpose
   ≠
Same API
   ≠
Same capabilities
```

Pasted text

---

## Mistake 2: Exposing API keys

Never put provider secrets directly into browser code. Pasted text

---

## Mistake 3: Retrying every error

A:

- `401`
- `403`
- Invalid request

usually requires correction instead of repeated retries. Pasted text

---

## Mistake 4: Ignoring rate limits

High-concurrency applications can unexpectedly hit provider limits. Pasted text

---

## Mistake 5: No fallback strategy

For critical systems, dependence on one provider can create a **single point of failure**. Pasted text

---

## Mistake 6: Assuming fallback providers are drop-in replacements

A fallback may support the same task but differ in:

- Prompt format
- Tool format
- Output schema
- Model behavior
- Context limits
- Feature set Pasted text

# Important Glossary

| Term | Meaning |
|---|---|
| **AI Provider** | Company/platform exposing AI models through APIs or SDKs |
| **API** | Interface through which an application communicates with a service |
| **API Key** | Credential used to authenticate access |
| **Project** | Logical boundary for access, resources, billing, permissions, or usage |
| **Quota** | Allocated amount of a resource |
| **Usage Limit** | Restriction on total consumption |
| **Rate Limit** | Restriction on consumption speed |
| **RPM** | Requests Per Minute |
| **TPM** | Tokens Per Minute |
| **RPD** | Requests Per Day |
| **Backoff** | Waiting before retrying a failed operation |
| **Exponential Backoff** | Increasing retry delays such as 1s, 2s, 4s, 8s |
| **Jitter** | Random variation added to retry timing |
| **Idempotency** | Property where repeating an operation does not create additional unintended effects |
| **Adapter** | Code that translates your application's common interface into provider-specific API calls |
| **AI Router** | Component that selects a provider/model based on requirements |
| **Fallback** | Secondary provider used when the primary provider cannot successfully serve a request |

# Practice & Recall Pack

## Flashcards

**1. What is an AI provider?**  
A company/platform that exposes AI models to applications through APIs or SDKs.

**2. Why should API keys stay on the backend?**  
Because frontend code is visible to users and can expose secrets. Pasted text

**3. Usage limit vs rate limit?**  
Usage limit = total amount. Rate limit = speed of consumption.

**4. What does RPM mean?**  
Requests Per Minute.

**5. What does TPM mean?**  
Tokens Per Minute.

**6. What does 429 usually indicate?**  
A rate, quota, usage, or acceleration/burst limitation.

**7. Why use exponential backoff?**  
To avoid immediately repeating requests and to give a transient failure time to recover.

**8. What is jitter?**  
Random variation added to retry delays.

**9. Why is idempotency important during retries?**  
Because repeating an operation could create duplicate business side effects.

**10. Why use an adapter layer?**  
To isolate provider-specific implementation details.

**11. What is an AI router?**  
A component that chooses a provider/model based on task requirements and constraints.

**12. Why aren't providers fully interchangeable?**  
Their APIs, models, capabilities, formats, and behavior can differ.

# Interview Preparation

### Q1. Why should API keys not be stored in React frontend code?

Because frontend code is visible to users. Provider credentials should normally remain in backend-only configuration or a secret-management system. Pasted text

### Q2. What is the difference between a rate limit and a usage limit?

A **rate limit** controls the speed of consumption, while a **usage limit** controls the total amount that may be consumed. Pasted text

### Q3. Why build a provider abstraction layer?

It isolates provider-specific API details, making switching providers, testing, fallback, and routing easier. Pasted text

### Q4. Should every API error be retried?

No. Only suitable transient/retryable errors should be retried, using bounded retries and backoff. Authentication, permission, and malformed-request errors generally require correction. Pasted text

### Q5. Why are OpenAI, Anthropic, and Google not completely interchangeable?

Because their APIs, models, request/response formats, and supported capabilities differ, even where their products solve similar problems. Pasted text

### Q6. What is the purpose of an AI router?

To select an appropriate provider/model according to factors such as task, required capability, cost, latency, and provider availability. Pasted text

### Q7. What is the danger of blindly retrying a business operation?

A retry can execute the operation twice and create duplicate side effects, such as duplicate bookings, payments, or database records. Pasted text

### Q8. What are the main benefits and costs of multi-provider architecture?

**Benefits:** flexibility, routing options, and improved availability through fallback.  
**Costs:** more complexity around normalization, prompt compatibility, cost management, and differing provider capabilities. Pasted text
