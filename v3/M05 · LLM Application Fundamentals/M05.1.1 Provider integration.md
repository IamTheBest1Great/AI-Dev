# 1. M05.1.1 Provider Integration

## 1.1 Provider Options

### Simple Definition

An **AI provider** is a company or platform that gives your application access to AI models through an API or SDK.

Instead of running a large model yourself:

```text
Your Application
      ↓
Provider API
      ↓
AI Model
      ↓
Response
      ↓
Your Application
```

The major providers in this section are **OpenAI, Anthropic, and Google**, plus other providers and model-hosting platforms.

---

## OpenAI

OpenAI provides APIs for building applications involving text, code, reasoning, structured output, images, audio, tools, agents, search/retrieval and other AI capabilities. Its current developer documentation exposes areas such as the Responses API, tools, streaming, agents, file inputs, web search and function calling. [OpenAI Platform](https://platform.openai.com/docs/guides/rate-limits)

### Typical use

```text
User
 ↓
Your Backend
 ↓
OpenAI API
 ↓
Selected Model
 ↓
Response
```

### Common application examples

- Chatbots
- Coding assistants
- Document analysis
- AI agents
- Information extraction
- Structured-output generation
- Multimodal applications

### Key idea

Do not make your entire application dependent on OpenAI-specific code.

A better structure is:

```text
Application
     ↓
AI Service
     ↓
OpenAI Adapter
     ↓
OpenAI API
```

That makes it easier to introduce another provider later.

---

## Anthropic

Anthropic provides the **Claude** family of models through its API platform.

Typical integration:

```text
Application
     ↓
Anthropic API
     ↓
Claude
     ↓
Response
```

Anthropic's current platform also exposes APIs and services around messages, batches, files, managed agents, models, organization management, API keys and rate limits. [Claude Platform Docs](https://docs.anthropic.com/en/api/rate-limits?utm_source=chatgpt.com)

### Common use cases

- Conversational AI
- Coding assistance
- Long-document analysis
- Reasoning-heavy workflows
- Agentic applications

### Important point

Anthropic's API format is not necessarily identical to another provider's API.

Therefore:

```text
Your Internal Interface
        ↓
 ┌──────┼────────┐
 ↓      ↓        ↓
OpenAI Claude  Google
```

is preferable to scattering provider-specific code throughout your application.

Google's current documentation covers text generation, multimodal understanding, image generation, structured output, tools, function calling, agents and background execution. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/get-started?authuser=19\&utm_source=chatgpt.com)

### Typical integration

```text
Application
     ↓
Google AI / Gemini API
     ↓
Gemini Model
     ↓
Response
```

### Important project relationship

A Gemini API key is associated with a Google Cloud project. Google AI Studio can create or import projects and allows API keys to be managed from the platform. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/api-key?tab=marketing\&utm_source=chatgpt.com)

This means:

```text
Google Account
      ↓
Google Cloud Project
      ↓
Gemini API Key
      ↓
Gemini API
```

This project structure is important for **permissions, billing, quotas and usage tracking**.

# 1.2 Access and Usage Controls

## API Key / Project Management

### What is an API key?

An **API key** is a credential that allows an application to authenticate with an AI provider.

Think of it as:

```text
Application
    ↓
"Who am I?"
    ↓
API Key
    ↓
Provider verifies access
    ↓
Request accepted/rejected
```

### Never expose secret keys in frontend code

Bad architecture:

```text
React App
   ↓
API Key
   ↓
OpenAI / Anthropic / Google
```

A user can inspect browser-delivered JavaScript and potentially obtain the key.

Better:

```text
React App
    ↓
Your Backend
    ↓
Secret API Key
    ↓
AI Provider
```

Store secrets in environment variables or an appropriate secret-management system.

Example:

```text
OPENAI_API_KEY=...
ANTHROPIC_API_KEY=...
GEMINI_API_KEY=...
```

The exact variable name depends on the SDK/application setup.

---

## Project Management

A **project** is generally a logical boundary used to organize access, usage, billing, permissions, or resources.

For example:

```text
Company
 ├── Production Project
 │      └── Production API Key
 │
 ├── Development Project
 │      └── Development API Key
 │
 └── Testing Project
        └── Test API Key
```

This is much safer than using one credential everywhere.

### Why separate projects?

It helps with:

- Environment separation
- Access control
- Usage monitoring
- Cost tracking
- Key rotation
- Limiting blast radius if a key leaks

Google's current Gemini setup explicitly associates each API key with a Google Cloud project, where projects manage billing, collaborators and permissions. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/api-key?tab=marketing\&utm_source=chatgpt.com)

---

## Key Rotation

Suppose a production API key is accidentally exposed.

Recommended approach:

```text
Old Key Leaked
      ↓
Create New Key
      ↓
Deploy New Key
      ↓
Verify Application
      ↓
Disable/Revoke Old Key
      ↓
Audit Usage
```

Google's current key-management guidance follows this general replacement process for compromised keys. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/api-key?tab=marketing\&utm_source=chatgpt.com)

### Important rule

Do not commit API keys to Git:

```text
❌ .env committed to GitHub
❌ API key inside React source
❌ API key inside screenshots
❌ API key inside public documentation
```

Use:

```text
✅ Environment variables
✅ Secret manager
✅ Backend-only configuration
```

# Usage Limits

A **usage limit** controls how much AI usage an account, organization, project or workspace can consume.

Usage can be measured in different ways:

```text
Requests
Tokens
Storage
Cost / spend
Daily quota
Monthly quota
```

### Why limits exist

They help prevent:

- Unexpected bills
- Abuse
- Runaway loops
- Excessive API usage
- Resource exhaustion

### Example

Imagine an AI agent accidentally enters a loop:

```text
Agent
 ↓
AI call
 ↓
Tool
 ↓
AI call
 ↓
Tool
 ↓
AI call
 ↓
...
```

Without controls, this can become expensive very quickly.

A usage limit acts as a safety barrier:

```text
Normal Usage
     ↓
Limit
     ↓
Block / throttle / pause
```

Google's Gemini API currently has billing tiers and project/account-level spend controls, while usage and quota can be viewed through AI Studio. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/billing?utm_source=chatgpt.com)

Anthropic also provides organization/workspace spend limits in addition to API rate limits. [Claude Platform Docs](https://docs.anthropic.com/en/api/rate-limits?utm_source=chatgpt.com)

---

# Rate Limits

## What is a rate limit?

A **rate limit** controls how quickly requests or tokens can be consumed.

Common metrics include:

- **RPM** = Requests Per Minute
- **TPM** = Tokens Per Minute
- **RPD** = Requests Per Day
- Some providers additionally distinguish input and output token rates

Google's Gemini documentation currently describes limits including RPM, input TPM and RPD, and notes that rate limits are applied per project rather than per API key. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/rate-limits?hl=es-419\&utm_source=chatgpt.com)

Anthropic currently measures Messages API limits using RPM, input tokens per minute and output tokens per minute, with limits applied at the organization level and additional workspace controls available. [Claude Platform Docs](https://docs.anthropic.com/en/api/rate-limits?utm_source=chatgpt.com)

### Example

Suppose your application has:

```text
100 requests/minute
```

and suddenly sends:

```text
150 requests/minute
```

The provider may reject excess requests.

Typical flow:

```text
Request
  ↓
Rate-limit check
  ↓
Within limit? ── Yes → Process
       │
       No
       ↓
   429 Error
```

---

## Rate Limit vs Usage Limit

These are easy to confuse.

| Concept | Meaning |
|---|---|
| Usage limit | How much total usage is allowed |
| Rate limit | How quickly usage can happen |
| Spend limit | How much money can be spent |
| Quota | Allocated amount of a particular resource |

### Example

You could have:

```text
Monthly usage limit = 1,000,000 tokens
Rate limit = 10,000 tokens/minute
```

You can eventually consume 1M tokens, but you cannot consume all 1M in one minute.

# 1.3 Integration Behavior

## Error Handling

AI APIs are network services, so failures are normal.

Your application should expect:

```text
Request
 ↓
Success?
 ├── Yes → Process response
 └── No  → Identify error
              ↓
        Retryable?
        ├── Yes → Retry
        └── No  → Report / recover
```

---

## Common Error Categories

### 400 — Bad Request

The request itself is invalid.

Examples:

- Invalid parameter
- Incorrect request structure
- Unsupported option

Usually:

```text
❌ Fix request
❌ Don't blindly retry
```

---

### 401 — Authentication Error

The credentials are invalid or missing.

```text
Invalid API key
      ↓
401
      ↓
Check credentials/configuration
```

Usually this is **not** fixed by retrying the same request.

---

### 403 — Forbidden

Authentication may exist, but the caller does not have permission to perform the requested operation.

Possible causes:

- Missing permissions
- Restricted resource
- Unauthorized project/model/service

---

### 404 — Not Found

The requested model, resource or endpoint cannot be found.

Possible causes:

- Incorrect model ID
- Incorrect URL
- Deleted resource
- Unsupported endpoint

---

### 429 — Too Many Requests

The application exceeded a limit.

Possible causes include:

```text
Rate limit
Quota limit
Usage limit
Acceleration / burst limit
```

This error often requires **waiting and retrying**, but not every 429 represents the same underlying condition.

For example, Anthropic documents 429 responses for rate-limit violations and includes a `retry-after` header for those cases. [Claude Platform Docs](https://docs.anthropic.com/en/api/rate-limits?utm_source=chatgpt.com)

Google's Gemini documentation similarly uses 429 responses for rate-limit/quota conditions and recommends exponential backoff for retryable cases. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/troubleshooting?utm_source=chatgpt.com)

---

### 500 — Internal Server Error

The provider encountered an unexpected server-side problem.

Usually:

```text
Retry with backoff
```

provided the operation is safe to retry.

---

### 503 — Service Unavailable

The provider is temporarily unavailable or overloaded.

Typical strategy:

```text
Request
 ↓
503
 ↓
Wait
 ↓
Retry
```

Google specifically recommends exponential backoff for transient `503` and `429` errors. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/troubleshooting?utm_source=chatgpt.com)

---

# Retry Strategy

Do **not** immediately retry every error.

A sensible retry policy is:

```text
API Request
    ↓
Error?
 ┌──┴──────────────┐
 │                 │
Retryable       Non-retryable
 │                 │
 ↓                 ↓
Wait             Fix request
 ↓
Retry
```

### Exponential Backoff

Instead of:

```text
retry
retry
retry
retry
```

use increasing delays:

```text
1 sec
 ↓
2 sec
 ↓
4 sec
 ↓
8 sec
 ↓
stop
```

A small random variation called **jitter** can also be added so many clients do not retry simultaneously.

Google currently recommends exponential backoff and jitter for appropriate transient failures. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/troubleshooting?utm_source=chatgpt.com)

---

# Important: Idempotency and Retries

Before retrying an operation, ask:

> "Could performing this operation twice create a duplicate side effect?"

For simple text generation this is often less problematic.

For an operation that causes a business action:

```text
AI → Create booking
AI → Send payment
AI → Create database record
```

blind retries can be dangerous.

Therefore:

```text
Retry strategy
      +
Idempotency
      +
Maximum retry count
```

should be considered together.

# Provider-Specific Capabilities

This is one of the most important ideas in multi-provider integration.

Even though providers offer similar AI functionality, **their capabilities are not identical**.

For example, a provider may differ in:

- Model families
- Context length
- Vision/multimodal support
- Audio support
- Structured output
- Function/tool calling
- Streaming
- Embeddings
- Fine-tuning
- Batch processing
- Agents
- File handling
- Caching
- Deployment options

OpenAI's current API documentation exposes features including structured output, tools, web search, file inputs, streaming, agents and multi-agent workflows. [OpenAI Platform](https://platform.openai.com/docs/guides/rate-limits)

Google's current Gemini API documentation lists multimodal understanding, image generation, structured output, tools, function calling, agents and background execution. [Google AI for Developers](https://ai.google.dev/gemini-api/docs/get-started?authuser=19\&utm_source=chatgpt.com)

Anthropic's current platform exposes Messages, batch processing, files, managed agents, model APIs and other platform services. [Claude Platform Docs](https://docs.anthropic.com/en/api/rate-limits?utm_source=chatgpt.com)

# Capability Matrix

A useful way to think about provider capabilities is:

| Capability | Provider A | Provider B | Provider C |
|---|---|---|---|
| Text generation | ✅ | ✅ | ✅ |
| Coding | ✅ | ✅ | ✅ |
| Vision | Depends on model | Depends on model | Depends on model |
| Tool calling | Model/API dependent | Model/API dependent | Model/API dependent |
| Structured output | Model/API dependent | Model/API dependent | Model/API dependent |
| Streaming | Often available | Often available | Often available |
| Agents | Available in provider ecosystem | Available in provider ecosystem | Available in provider ecosystem |
| Embeddings | Available through provider/ecosystem | Available through provider/ecosystem | Available through provider/ecosystem |
| Batch processing | Provider-dependent | Provider-dependent | Provider-dependent |

The critical point is **"available" does not mean identical implementation**.

# Provider Abstraction vs Provider-Specific Features

Suppose your application defines:

```text
generateText()
```

All providers can potentially implement it.

But then you want:

```text
webSearch()
```

Provider A may support it directly while Provider B may require another mechanism.

So your architecture should distinguish between:

### Common capabilities

```text
generateText()
streamText()
```

and:

### Provider-specific capabilities

```text
provider.webSearch()
provider.computerUse()
provider.specialTool()
```

Conceptually:

```text
                 AI Interface
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
     Common API             Provider Extensions
          │                       │
    generateText()         Special capabilities
    streamText()            Provider-specific tools
```

This avoids pretending that every provider has exactly the same feature set.

# Example: Provider Fallback

Imagine OpenAI is your primary provider and Anthropic is your fallback.

```text
User Request
      ↓
OpenAI
      ↓
Success? ── Yes → Return response
      │
      No
      ↓
Is error retryable?
      │
      ├── Yes → Retry OpenAI
      │
      └── No / still failing
                 ↓
             Anthropic
                 ↓
            Return result
```

This can improve **availability**, but introduces additional complexity around prompt compatibility, response normalization, costs and feature differences.

# Common Mistakes

### 1. Treating all providers as identical

They are not.

```text
Same purpose ≠ Same API ≠ Same capabilities
```

### 2. Exposing API keys

Never put confidential provider credentials directly in browser code.

### 3. Retrying every error

A `401`, `403`, or invalid request generally needs correction rather than repeated retries.

### 4. Ignoring rate limits

High-concurrency applications can hit limits unexpectedly.

### 5. No fallback strategy

For critical applications, dependence on one provider can create a single point of failure.

### 6. Assuming fallback providers are drop-in replacements

A fallback may support the same *task* but not exactly the same:

- Prompt format
- Tool format
- Output schema
- Model behavior
- Context limits
- Feature set

# Key Takeaways

- **API key** = credential used to authenticate your application.
- **Project** = organizational boundary for resources, permissions, billing or usage.
- **Usage limit** = controls how much you can consume.
- **Rate limit** = controls how quickly you can consume it.
- `429` commonly indicates a limit/quota/rate-related problem.
- `5xx` errors are generally server/transient failures and may be retryable.
- Use **exponential backoff + jitter** for appropriate transient failures.
- Do not blindly retry non-retryable errors.
- Providers offer overlapping but **not identical capabilities**.
- Keep provider-specific code behind an **adapter/interface**.
- A provider router can select models based on capability, cost, latency or availability.
- Multi-provider systems improve flexibility but add architectural complexity.

### Interview questions

**Q1. Why should API keys not be stored in React frontend code?**  
Because frontend code is visible to users; secrets should normally remain on the backend.

**Q2. What is the difference between a rate limit and a usage limit?**  
A rate limit controls the **speed** of consumption, while a usage limit controls the **total allowed consumption**.

**Q3. Why use a provider abstraction layer?**  
To isolate provider-specific API details and make switching, fallback, testing and multi-provider routing easier.

**Q4. Should every API error be retried?**  
No. Retry only errors that are transient/retryable, with bounded exponential backoff and appropriate safeguards.

**Q5. Why can't OpenAI, Anthropic and Google simply be treated as interchangeable?**  
Because their APIs, models, request/response formats and supported capabilities can differ even when they solve similar problems.
