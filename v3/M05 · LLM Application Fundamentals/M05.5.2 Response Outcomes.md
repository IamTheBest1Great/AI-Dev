# 1. M05.5.2 Response Outcomes

## Simple Definition

After an AI model receives a request, the result is **not necessarily just success or failure**.

A production AI system should classify the response into meaningful outcomes. Pasted text

A useful model is:

```text
AI Request
    ↓
Model Response
    ↓
┌──────────────────────────────────────┐
│ What kind of outcome occurred?       │
└──────────────────────────────────────┘
       │
       ├── Valid
       ├── Refusal
       ├── Parse failure
       ├── Incomplete
       ├── Truncated
       ├── Schema failure
       ├── Temporary provider error
       ├── Empty response
       └── Structurally valid but factually wrong
```

### Central principle

> **A response can be structurally valid and still be incorrect.** Pasted text

---

# 1.1 Valid Output

## Definition

A **valid output** is a response that satisfies the expected **technical contract**. Pasted text

Suppose the application expects:

```json
{
  "name": "John",
  "age": 30
}
```

with:

```text
name → string
age  → integer
```

The response is **schema-valid**.

---

## Valid Output Flow

```text
AI
 ↓
Response
 ↓
Parse
 ↓
Schema Validation
 ↓
Valid?
 ↓
Yes
 ↓
Application
```

Pasted text

But there is another question:

> **Is the information actually correct?**

For example:

```json
{
  "name": "John",
  "age": 30
}
```

may satisfy the schema even if John's actual age is 27.

Therefore:

```text
Schema Validity
      ≠
Factual Correctness
```

Pasted text

### Key lesson

**Valid output means technically acceptable structure—not automatically truthful content.**

---

# 1.2 Refusal

## Definition

A **refusal** occurs when the model declines to provide the requested content or action. Pasted text

Conceptually:

```text
Request
  ↓
Model evaluates request
  ↓
Refusal
  ↓
No normal task output
```

### Important point

A refusal is **not necessarily an API failure**.

The provider may have successfully processed the request and the model may intentionally return a refusal outcome. Pasted text

---

## Refusal vs Error

These must be distinguished.

| Outcome | Meaning |
|---|---|
| **Refusal** | Model intentionally declines |
| **API error** | Request failed at service/transport/API level |
| **Validation failure** | Response arrived but doesn't satisfy the contract |

Pasted text

### Example: Refusal

```text
Request
 ↓
Provider
 ↓
Model refuses
 ↓
Controlled refusal response
```

### Example: API failure

```text
Request
 ↓
Provider
 ↓
500 / timeout / network error
```

These are fundamentally different situations.

---

## Why Refusals Need Special Handling

Suppose your application expects:

```json
{
  "answer": "...",
  "confidence": 0.9
}
```

But the model refuses.

The system shouldn't blindly try to parse that response as a normal answer.

Instead:

```text
Response
 ↓
Outcome Detection
 ├── Normal Answer
 └── Refusal
       ↓
   Handle Separately
```

Pasted text

The user interface might show:

```text
"The assistant cannot provide that response."
```

rather than:

```text
"JSON parsing failed."
```

# 1.3 Incomplete Output

## Definition

An **incomplete output** is a response that does not contain everything required to complete the task. Pasted text

Suppose the application asks:

```text
Return:
1. Summary
2. Risks
3. Recommendations
```

But the model returns:

```text
Summary: Revenue increased.
```

The text may be valid, but the **task is incomplete**.

---

# Incomplete Output vs Invalid Structure

These are different problems.

## Case 1 — Schema problem

Expected:

```json
{
  "name": "string",
  "age": "integer"
}
```

Received:

```json
{
  "name": "John"
}
```

The JSON may parse successfully, but `age` is missing. Pasted text

---

## Case 2 — Task incompleteness

Suppose the schema is technically satisfied:

```json
{
  "summary": "Revenue increased.",
  "risks": [],
  "recommendations": []
}
```

The structure is valid.

But perhaps the model failed to identify real risks or recommendations.

So:

```text
Schema Validation
      ↓
Can confirm structure
      ↓
Cannot guarantee task completeness
```

Pasted text

### Important distinction

> **A response can be schema-valid but still fail to complete the actual task.**

---

## Detecting Incomplete Output

### 1. Required-field validation

```text
Missing required field?
       ↓
Incomplete
```

### 2. Minimum-content checks

```text
summary.length < minimum?
       ↓
Potentially incomplete
```

### 3. Business rules

For an assessment generator:

```text
Expected = 10 questions
Received = 6 questions

→ Incomplete
```

### 4. Task-specific validation

Expected:

```text
question
options
correct answer
explanation
```

Received:

```text
question
options
```

Therefore:

```text
→ Incomplete
```

# 1.4 Truncation

## Definition

**Truncation** occurs when generated output is cut off before it is complete. Pasted text

Possible causes include:

- Output token limits
- Context limits
- Provider/model generation limits
- Connection interruption
- Application-side cutoff Pasted text

---

## Example

Expected:

```text
Here are the three causes:
1. Cause A
2. Cause B
3. Cause C
```

Actual:

```text
Here are the three causes:
1. Cause A
2. Cause B
```

The response stopped before completion.

---

## Truncation Flow

```text
Model starts generating
        ↓
Output limit reached
        ↓
Generation stops
        ↓
Partial response
```

Pasted text

---

# Truncation vs Incomplete Output

These concepts overlap, but they aren't identical.

| Truncation | Incomplete Output |
|---|---|
| Output was cut off | Required content is missing |
| Often caused by limits/interruption | Can result from model behavior or task failure |
| Often ends abruptly | May look completely normal |
| Example: sentence stops halfway | Example: requested section is omitted |

Pasted text

### Relationship

```text
Truncation
    ↓
Can cause
    ↓
Incomplete Output
```

But:

```text
Incomplete Output
      ≠
Always Truncation
```

The model may simply forget a required section. Pasted text

---

## Detecting Truncation

Possible signals include:

```text
Finish reason indicates length
        ↓
Potential truncation
```

Application-level checks can also identify incomplete structures.

For example:

```json
{
  "items": [
    {
      "name": "A"
```

Clearly unfinished.

# 1.5 Parsing Failure

## Definition

A **parsing failure** occurs when your application cannot convert the model response into the expected data format. Pasted text

### Expected

```json
{
  "name": "John"
}
```

### Model returns

```text
Here is the answer:

{
  "name": "John"
```

Possible problems:

- Invalid JSON
- Missing braces
- Incorrect syntax
- Unexpected text around structured output
- Malformed serialization

## Parse Failure Flow

```text
AI Response
     ↓
  Parser
     ↓

 ┌──────┴──────┐
Yes            No
 ↓               ↓
Validate     Parse Failure
```

# Parsing Failure vs Schema Validation Failure

This is a **must-know distinction**.

## Parsing failure

The application cannot interpret the response as the required format.

```text
"{ invalid json"
        ↓
Parser
        ↓
FAIL
```

## Schema validation failure

The response parses successfully but violates the schema.

```json
{
  "name": "John",
  "age": "thirty"
}
```

If the schema requires:

```text
age → integer
```

then:

```text
Parse
 ↓
SUCCESS
 ↓
Schema Validation
 ↓
FAIL
```

Pasted text

### Memory trick

> **Parsing = "Can I read the structure?"**

> **Validation = "Does the structure follow the contract?"**

# 1.6 Bounded Repair Attempts

## Definition

A **repair attempt** tries to correct an invalid or incomplete response.

**Bounded** means the number of repair attempts is limited. Pasted text

Never create an unlimited repair loop.

---

## Example

Expected:

```json
{
  "score": 0,
  "passed": false
}
```

Actual:

```json
{
  "score": "85",
  "passed": "yes"
}
```

The information may be recoverable, but the types are wrong.

Send the validation problems back:

```text
Your previous response failed validation.

Problems:
- score must be a number.
- passed must be a boolean.

Return the corrected object only.
```

Possible repaired response:

```json
{
  "score": 85,
  "passed": true
}
```

Pasted text

---

## Repair Loop

```text
Generate
   ↓
Parse
   ↓
Validate
   ↓
Valid?
 ┌──────┴─────┐
Yes           No
 ↓             ↓
Use          Repair
               ↓
            Validate
               ↓
            Valid?
           /     \
         Yes      No
          ↓        ↓
         Use    Retry / Fail
```

Pasted text

---

## Why Repair Attempts Must Be Bounded

Without a limit:

```text
Attempt 1 → Invalid
Attempt 2 → Invalid
Attempt 3 → Invalid
Attempt 4 → Invalid
...
```

This can cause:

- Increasing API costs
- Growing latency
- Infinite loops
- A permanently failing task that never terminates Pasted text

### Better

```text
Maximum repair attempts = 2 or 3
```

Then:

```text
Still invalid
      ↓
Controlled failure
```

Pasted text

---

# Repair vs Fresh Retry

## Repair

Use repair when:

```text
Underlying answer mostly correct
        +
Formatting/schema problem
        ↓
Repair
```

## Fresh generation

More appropriate when:

```text
Wrong reasoning
+
Missing information
+
Fundamentally poor answer
        ↓
New generation
```

Pasted text

### Key principle

> **Don't use a repair loop to magically fix fundamentally incorrect reasoning.**

# 1.7 Schema Validity ≠ Factual Correctness

This is arguably the **most important concept in the chapter**.

A schema can determine:

```text
Does the data have the correct shape?
```

It cannot automatically determine:

```text
Is the information actually true?
```

Pasted text

---

## Example

Suppose the schema expects:

```json
{
  "capital": "string"
}
```

The model returns:

```json
{
  "capital": "Mumbai"
}
```

Technically:

```text
Valid JSON      ✅
Schema valid    ✅
Correct fact    ❓
```

The schema itself doesn't know whether `"Mumbai"` is actually the correct capital for the country being discussed.

---

# Three Levels of Correctness

A very useful mental model is:

```text
Level 1 → Parsing
          "Can I read the output?"

Level 2 → Schema Validation
          "Does it have the expected structure?"

Level 3 → Semantic / Factual Validation
          "Is the information actually correct?"
```

Pasted text

### Complete pipeline

```text
AI Output
   ↓
Parse
   ↓
Schema Validation
   ↓
Business Validation
   ↓
Factual / Semantic Evaluation
   ↓
Accept
```

Not every system needs every level, but developers should understand the distinction.

---

# Semantic Validation

**Semantic validation** checks whether the output makes sense for the task.

Example:

```json
{
  "start_date": "2026-10-10",
  "end_date": "2026-10-05"
}
```

The schema may allow:

```text
start_date → string
end_date   → string
```

So the schema passes.

But the business rule may require:

```text
start_date < end_date
```

Therefore:

```text
Schema Valid
      ↓
Business Invalid
```

Pasted text

---

# Factual Validation

For factual tasks, additional checking may be necessary.

A conceptual approach:

```text
AI Response
    ↓
Check against trusted database
    ↓
Check authoritative source
    ↓
Cross-check another system/model
    ↓
Accept / Flag
```

For example, an AI might return:

```json
{
  "customer_id": "12345",
  "plan": "Premium"
}
```

Schema validation can confirm:

```text
customer_id → string
plan → string
```

But your backend should determine whether customer `12345` actually has a Premium plan.

Pasted text

# 4. Real-World Example: AI Assessment Generator

Suppose your LMS asks an AI model to generate:

```text
10 multiple-choice questions
4 options each
1 correct answer
explanation for each
```

Expected structure:

```text
questions[]
 ├── question
 ├── options[]
 ├── correct_answer
 └── explanation
```

---

## Outcome 1 — Valid

AI returns:

```text
10 questions
4 options each
correct answers
explanations
```

Everything passes.

```text
Parse
 ↓
Schema Validation
 ↓
Business Validation
 ↓
Accept
```

---

## Outcome 2 — Incomplete

AI returns:

```text
6 questions
```

Expected:

```text
10 questions
```

Therefore:

```text
Schema may be valid
      ↓
Business/task validation fails
      ↓
Incomplete
```

---

## Outcome 3 — Truncated

The model stops halfway through question 8:

```text
Question 8:
What is...
```

Possible cause:

```text
Output limit reached
```

The system identifies truncation and can retry using appropriate limits. Pasted text

---

## Outcome 4 — Parsing failure

AI returns:

```text
Here are your questions:

{
  "questions": [
    ...
```

Malformed JSON.

```text
Parse
 ↓
FAIL
 ↓
Repair / Retry
```

---

## Outcome 5 — Schema failure

AI returns:

```json
{
  "questions": [
    {
      "question": "What is SOLAS?",
      "correct_answer": "A"
    }
  ]
}
```

But the schema requires:

```text
options → required
explanation → required
```

So:

```text
Parse → Success
Schema → Fail
Repair
```

---

## Outcome 6 — Business failure

AI returns:

```json
{
  "question": "What is 2 + 2?",
  "options": ["3", "4", "5", "6"],
  "correct_answer": 0
}
```

The schema may be completely valid.

But business validation checks:

```text
correct_answer = 0
```

which points to `"3"` rather than `"4"`.

Therefore:

```text
Schema Valid
      ↓
Business Invalid
```

---

## Outcome 7 — Factual failure

The AI could produce:

```json
{
  "question": "...",
  "correct_answer": 1
}
```

with perfectly valid structure but an incorrect answer.

Therefore:

```text
Schema Valid
+
Business Structure Valid
≠
Factually Correct
```

This is why the chapter emphasizes that structural validation cannot establish factual correctness. Pasted text

# 5. Common Mistakes

## 1. Treating all failures as identical

Bad:

```text
if (!success) retry();
```

Different failures require different treatment.

---

## 2. Treating refusal as a parsing error

A refusal is a distinct outcome, not necessarily malformed output.

---

## 3. Assuming schema-valid means correct

```text
Schema Valid
    ≠
Factually Correct
```

---

## 4. Assuming incomplete means truncated

A response can be incomplete because:

```text
Model forgot required content
```

without being cut off.

---

## 5. Repairing fundamentally wrong reasoning

Repair is best for recoverable formatting/schema issues—not fundamentally incorrect analysis. Pasted text

---

## 6. Creating unlimited repair loops

Always define a maximum attempt count.

---

## 7. Checking only syntax

Valid JSON is not enough.

You may need:

```text
Parse
 ↓
Schema
 ↓
Business
 ↓
Factual
```

# Key Takeaways

- AI response handling is more than **success vs failure**.
- **Valid output** satisfies the technical contract.
- **Refusal** means the model intentionally declined the request.
- **Incomplete output** lacks required task content.
- **Truncation** means output was cut off before completion.
- **Parsing failure** means the application cannot interpret the response format.
- **Schema failure** means the response parses but violates the expected contract.
- **Repair attempts** can fix limited/structural problems.
- Repair must be **bounded**.
- A fundamentally incorrect answer may require a fresh generation rather than repair.
- **Schema validity does not guarantee factual correctness.**
- Business validation checks domain-specific rules.
- Factual/semantic validation checks whether information is actually correct.
- A robust system should classify outcomes explicitly and use different recovery strategies for different outcomes.

# 8. Practice & Recall Pack

## Flashcards

**Q1. Why isn't an AI response simply success or failure?**  
Because responses can be valid, refused, incomplete, truncated, unparsable, schema-invalid, temporarily failed, or structurally valid but factually wrong.

**Q2. What is valid output?**  
Output that satisfies the expected technical contract.

**Q3. What is a refusal?**  
A deliberate decision by the model to decline the requested content/action.

**Q4. What is incomplete output?**  
A response that fails to provide everything required for the task.

**Q5. What is truncation?**  
Output that was cut off before completion.

**Q6. What is parsing failure?**  
When the raw output cannot be converted into the required format.

**Q7. What is schema failure?**  
When parsed data violates the expected schema.

**Q8. What is bounded repair?**  
Attempting to correct invalid output with a fixed maximum number of attempts.

**Q9. Why can't repair always fix a bad response?**  
Because fundamentally incorrect reasoning or missing information may require fresh generation rather than formatting repair.

**Q10. Does schema validity guarantee factual correctness?**  
No.

**Q11. What does business validation check?**  
Application-specific rules.

**Q12. What does factual validation check?**  
Whether the information is actually correct.

# Interview Questions

### Q1. Why should an AI system classify response outcomes instead of using only success/failure?

Because different outcomes require different handling. A refusal is different from a timeout, and a schema violation is different from a factually incorrect but structurally valid response. Pasted text

### Q2. What is the difference between a refusal and an API error?

A refusal is the model intentionally declining a request, whereas an API error occurs at the service, transport, or infrastructure level. Pasted text

### Q3. What is the difference between incomplete output and truncation?

Truncation means generation was cut off. Incomplete output means required task content is missing. Truncation can cause incompleteness, but incompleteness doesn't always mean truncation. Pasted text

### Q4. What is the difference between parsing failure and schema validation failure?

Parsing failure means the application cannot interpret the raw response in the expected format. Schema validation failure means the response parses successfully but violates the expected schema. Pasted text

### Q5. When should a repair loop be used?

When the underlying response is mostly correct and the problem is limited to formatting, schema constraints, or similarly recoverable issues. Pasted text

### Q6. Why must repair attempts be bounded?

To prevent infinite loops, uncontrolled API costs, increasing latency, and non-terminating failures. Pasted text

### Q7. Why doesn't schema validation guarantee correctness?

Because schema validation checks structure and constraints, not whether the underlying factual information is true. Pasted text

### Q8. What is business validation?

Validation that checks domain-specific application rules—for example, whether a selected answer points to an actual option or whether a date range is logically valid. Pasted text
