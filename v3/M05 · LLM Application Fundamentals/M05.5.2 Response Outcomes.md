# 1. Response Outcomes Fundamentals

## What Are Response Outcomes?

After an AI model receives a request, the result is not necessarily just **success** or **failure**.

A production AI system must identify what actually happened and choose an appropriate handling strategy.

Possible outcomes include:

- Valid output
- Refusal
- Incomplete output
- Truncation
- Parsing failure
- Schema validation failure
- Business-rule failure
- Temporary provider error
- Empty response
- Structurally valid but factually incorrect output

These outcomes are different because each represents a different problem or result.

### A simple response lifecycle

```text id="tsq9kd"
AI Request
    |
    v
Model Response
    |
    v
Identify Outcome
    |
    +---- Valid output
    |
    +---- Refusal
    |
    +---- Parsing failure
    |
    +---- Incomplete / truncated output
    |
    +---- Schema failure
    |
    +---- Provider error
    |
    +---- Business-rule failure
    |
    +---- Factual or semantic failure
```

The handling strategy depends on the outcome. For example, a refusal should not automatically be treated as malformed JSON, and a temporary network failure should not be treated as a factual error.

## Why Success vs. Failure Is Not Enough

Suppose an AI assessment generator is asked to produce 10 multiple-choice questions.

It might return:

| Result | What happened? |
|---|---|
| 10 valid questions | Potential success |
| A refusal | The model declined the task |
| Six questions instead of 10 | Incomplete output |
| JSON cut off halfway | Truncation or parsing failure |
| Valid JSON with a missing field | Schema failure |
| Four options but an invalid correct-answer index | Business-rule failure |
| Four options with the wrong correct answer | Factual or semantic failure |
| A provider timeout | Service or transport failure |

Treating all these outcomes identically makes the application harder to debug and less reliable.

### Central principle

**A response can be structurally valid and still be incorrect.**

## Valid Output

### Definition

**Valid output** is output that satisfies the expected technical contract.

Suppose the application expects:

```json id="8l4m1z"
{
  "name": "John",
  "age": 30
}
```

The contract requires:

```text id="8v45rt"
name -> string
age  -> integer
```

If the response can be parsed and satisfies the schema, it is structurally valid.

### Valid-output workflow

```text id="6b68bv"
AI response
     |
     v
Parse response
     |
     v
Validate schema
     |
     v
Schema valid?
    / \
  Yes  No
   |    |
   v    v
Continue Repair or reject
```

However, technical validity does not establish that the information is true.

For example:

```json id="kr1kjr"
{
  "name": "John",
  "age": 30
}
```

This object can satisfy the schema even if John's actual age is 27.

Therefore:

```text id="0wwkwg"
Schema validity
      !=
Factual correctness
```

**Key takeaway:** Valid output means the response satisfies the required technical contract. It does not automatically mean the content is complete, logically consistent, or factually correct.

# 2. Refusal

## What Is a Refusal?

A **refusal** occurs when the model declines to provide the requested content or perform the requested action.

Conceptually:

```text id="u9bg2t"
Request
   |
   v
Model evaluates request
   |
   v
Refusal
   |
   v
Handle refusal outcome
```

A refusal is not necessarily an API failure. The provider may have processed the request successfully, while the model intentionally declined to fulfill it.

## Refusal vs. API Error vs. Validation Failure

| Outcome | Meaning |
|---|---|
| **Refusal** | The model intentionally declines the request |
| **API error** | The request fails at the service, API, or transport level |
| **Validation failure** | The response arrives but does not satisfy the expected contract |

### Example: Refusal

```text id="z1v39a"
Request
   |
   v
Provider processes request
   |
   v
Model refuses
   |
   v
Application handles refusal
```

### Example: API failure

```text id="f30e6o"
Request
   |
   v
Provider or network issue
   |
   v
Timeout / service error
   |
   v
Apply appropriate error handling
```

These situations need different handling strategies.

## Why Refusals Need Special Handling

Suppose the application expects:

```json id="n8eg9k"
{
  "answer": "...",
  "confidence": 0.9
}
```

If the model returns a refusal, the application should not blindly parse the result as a normal answer.

Instead:

```text id="ozw062"
Response
    |
    v
Detect outcome
    |
    +---- Normal answer
    |          |
    |          v
    |      Parse and validate
    |
    +---- Refusal
               |
               v
          Handle separately
```

The UI might communicate that the assistant cannot provide the requested response rather than displaying a JSON parsing error.

### Best practice

Recognize refusal as a separate response outcome and handle it according to the application's requirements. Do not automatically retry a refusal as though it were a transient network problem.

# 3. Incomplete Output and Truncation

## Incomplete Output

### Definition

**Incomplete output** is a response that does not contain everything required to complete the task.

Suppose the application asks for:

```text id="w7gk3o"
1. Summary
2. Risks
3. Recommendations
```

The model returns:

```text id="2dk0xu"
Summary: Revenue increased.
```

The response contains valid text, but two required sections are missing.

The task is incomplete.

## Incomplete Structure vs. Incomplete Task

These are related but different problems.

### Case 1: A required schema field is missing

Expected:

```json id="mcv5hj"
{
  "name": "John",
  "age": 30
}
```

Received:

```json id="i3x46z"
{
  "name": "John"
}
```

The JSON may parse correctly, but the required `age` field is missing.

This is a schema validation failure and also an incomplete result.

### Case 2: The structure is valid, but the task is incomplete

Received:

```json id="q2xsay"
{
  "summary": "Revenue increased.",
  "risks": [],
  "recommendations": []
}
```

Suppose the task requires identifying actual risks and making useful recommendations, but the model leaves both lists empty despite relevant information being available.

The response satisfies the basic structure, but it may not fulfill the task.

```text id="0tuvaz"
Schema validation
       |
       v
Confirms structure
       |
       v
Does not guarantee task completeness
```

**Important distinction:** A response can be schema-valid but still fail to complete the requested task.

## Detecting Incomplete Output

Several types of checks can help.

### 1. Required-field validation

```text id="14k7ma"
Required field missing?
        |
        v
Potential incomplete output
```

### 2. Minimum-content checks

An application may require a minimum amount of content for a particular task.

For example, an unexpectedly short summary may trigger a review or incompleteness check.

Content length alone does not prove that an answer is incomplete, so it should be used with task-specific criteria.

### 3. Business rules

An assessment generator may be required to produce exactly 10 questions.

```text id="4dc22l"
Expected questions = 10
Received questions = 6
             |
             v
         Incomplete
```

### 4. Task-specific checks

Suppose each assessment question requires:

```text id="lznbb4"
Question
Options
Correct answer
Explanation
```

If the model returns only the question and options, the response does not contain all the required content.

## Truncation

### Definition

**Truncation** occurs when generated output is cut off before it is complete.

Possible causes include:

- Output-token limits
- Context or generation limits
- Provider or model generation limits
- Connection interruption
- Application-side cutoff

### Example

Expected output:

```text id="o0afn4"
Here are the three causes:
1. Cause A
2. Cause B
3. Cause C
```

Actual output:

```text id="epr9md"
Here are the three causes:
1. Cause A
2. Cause B
```

The output stopped before the expected content was complete.

### Truncation lifecycle

```text id="l7ffm4"
Model starts generating
        |
        v
Output limit or interruption
        |
        v
Generation stops early
        |
        v
Partial response
```

A production application should examine available completion metadata, such as a provider's finish reason, when supported. It can also check whether the resulting response is incomplete or structurally unfinished.

## Incomplete Output vs. Truncation

| Feature | Truncation | Incomplete output |
|---|---|---|
| Meaning | Output was cut off before completion | Required task content is missing |
| Possible cause | Token limits or interruption | Model omitted required content or failed to complete the task |
| Visible pattern | May end abruptly | May appear complete and well-formed |
| Example | JSON ends before closing brackets | A requested recommendations section is absent |

The relationship is:

```text id="1x3y5y"
Truncation
    |
    v
Can cause
    |
    v
Incomplete output
```

However:

```text id="nfr1xk"
Incomplete output
       !=
Always truncation
```

A model can simply omit a required section without its generation being cut off.

## Handling Truncation

A suitable response depends on the provider's metadata and the application's requirements. Potential actions include retrying with an appropriate output limit or changing the request so the task can be completed within the available limits.

Blindly repeating the same request with the same constraints may reproduce the problem.

# 4. Parsing Failure and Schema Failure

## Parsing Failure

### Definition

A **parsing failure** occurs when the application cannot convert the raw model response into the expected data format.

Suppose the application expects JSON.

Expected:

```json id="uk3cv7"
{
  "name": "John"
}
```

But the model returns:

```text id="xj8pdg"
Here is the answer:

{
  "name": "John"
```

Potential problems include:

- Invalid JSON syntax
- Missing braces or brackets
- Incorrect serialization
- Unexpected text around a structured response
- An unfinished object caused by truncation

The parser cannot construct the required object from invalid JSON.

### Parsing workflow

```text id="g6m2kj"
AI response
    |
    v
Parser
    |
    v
Can it be parsed?
     / \
   Yes  No
    |    |
    v    v
Validate Parsing
schema  failure
```

## Schema Validation Failure

A **schema validation failure** occurs when the response can be parsed, but the resulting data violates the expected schema.

Suppose the output is:

```json id="om5pce"
{
  "name": "John",
  "age": "thirty"
}
```

The JSON is syntactically valid, but the schema requires `age` to be an integer.

The correct flow is:

```text id="7t0xar"
Raw response
     |
     v
Parse successfully
     |
     v
Validate schema
     |
     v
Schema validation fails
```

## Parsing Failure vs. Schema Failure

| Feature | Parsing failure | Schema validation failure |
|---|---|---|
| Can the response be parsed? | No | Yes |
| Is the required structure readable? | No | Yes |
| Main problem | Invalid or incompatible syntax/format | Data violates the expected contract |
| Example | Malformed JSON | A string supplied where an integer is required |
| Possible handling | Repair or retry | Repair or retry |

### Memory trick

**Parsing asks:** “Can I read the structure?”

**Validation asks:** “Does the structure follow the contract?”

### Practical example

Expected contract:

```json id="fu6q9d"
{
  "score": 0,
  "passed": false
}
```

Two different failures are possible.

Malformed response:

```text id="z6vmf1"
{ score: 85, passed: true
```

This is invalid JSON.

Schema-invalid response:

```json id="0e0a0n"
{
  "score": "85",
  "passed": "yes"
}
```

This JSON is parseable, but both values violate the required types.

These failures should be classified separately so the application can use the correct recovery strategy.

# 5. Bounded Repair Attempts

## What Is a Repair Attempt?

A **repair attempt** tries to correct an invalid or incomplete AI response.

**Bounded repair** means limiting the number of attempts so that an invalid result cannot trigger an endless sequence of additional calls.

## Example: Repairing Invalid Types

Expected output:

```json id="h6idva"
{
  "score": 0,
  "passed": false
}
```

Actual output:

```json id="3tpr0q"
{
  "score": "85",
  "passed": "yes"
}
```

The response contains potentially recoverable information, but its values have the wrong types.

The application can send a repair instruction describing the validation errors:

```text id="9br8yl"
The previous response failed validation.

Problems:
- score must be a number.
- passed must be a boolean.

Return the corrected object only.
```

A possible corrected response is:

```json id="no0r2s"
{
  "score": 85,
  "passed": true
}
```

The repaired result must still be validated.

## Repair Workflow

```text id="yq90tf"
Generate response
       |
       v
Parse response
       |
       v
Validate schema and rules
       |
       v
Valid?
   /       \
 Yes       No
  |         |
  v         v
Use       Is repair appropriate?
result         |
             Yes
              |
              v
         Repair response
              |
              v
         Revalidate
              |
        +-----+-----+
        |           |
       Valid     Still invalid
        |           |
        v           v
       Use      Bounded retry
                   or failure
```

## Why Repair Attempts Must Be Bounded

Without an attempt limit, the application may continue retrying indefinitely.

```text id="l7387d"
Attempt 1 -> Invalid
Attempt 2 -> Invalid
Attempt 3 -> Invalid
Attempt 4 -> Invalid
...
```

This can cause:

- Increasing API cost
- Higher latency
- Infinite retry loops
- Non-terminating tasks
- Repeated failures without progress

The supplied material gives two or three repair attempts as an example. The appropriate limit depends on the task, cost, latency requirements, and recovery behavior.

After the limit is reached, the application should stop the repair loop and produce a controlled failure outcome.

## Repair vs. Fresh Generation

These strategies solve different problems.

### Use repair when

- The answer is mostly correct.
- The main issue is formatting.
- A schema constraint has been violated.
- A limited, well-defined correction is possible.

### Consider fresh generation when

- The reasoning is fundamentally incorrect.
- Important information is missing.
- The response is unsuitable for the task.
- Fixing the structure would not resolve the underlying problem.

```text id="zlg50k"
Minor or structural problem
           |
           v
         Repair

Fundamentally incorrect answer
           |
           v
 Fresh generation or rejection
```

**Key principle:** Do not use a formatting repair loop as a substitute for correcting fundamentally incorrect reasoning.

A fresh generation may also fail, so its output must pass the same appropriate validation steps.

# 6. Schema Validity vs. Correctness

This is one of the most important concepts in response handling.

A schema determines whether data follows an expected structure. It does not automatically determine whether the information is true.

## Three Levels of Output Correctness

A useful mental model separates three levels.

### Level 1: Parsing

Question: Can the application read the output in the expected format?

Example:

```text id="k45uf5"
Can the raw response be parsed as JSON?
```

### Level 2: Schema validation

Question: Does the parsed data have the required structure, field types, and constraints?

Example:

```text id="u50p8v"
Is "age" an integer?
Is "name" a string?
Are required fields present?
```

### Level 3: Semantic and factual correctness

Question: Does the data make sense for the task, obey application rules, and contain correct information?

Example:

```text id="r52gcs"
Does the selected answer actually answer
the question correctly?
```

### The complete hierarchy

```text id="j62l48"
                 AI Output
                     |
                     v
              1. Can I parse it?
                     |
                     v
               Parsed output
                     |
                     v
            2. Does it match schema?
                     |
                     v
              Structurally valid
                     |
                     v
        3. Is it semantically correct?
                     |
                     v
           Business / factual checks
```

Passing one level does not guarantee that the next level will pass.

## Business Validation

**Business validation** checks whether output satisfies application-specific rules.

Consider:

```json id="h5n7sr"
{
  "start_date": "2026-10-10",
  "end_date": "2026-10-05"
}
```

The schema may allow both fields to be strings, so the output can be structurally valid.

However, suppose the application's rule requires the start date to be earlier than the end date.

```text id="gizxi5"
start_date < end_date
```

The result violates the business rule.

Therefore:

```text id="t2scx3"
Schema valid
     |
     v
Business validation fails
```

Business validation checks meaning and constraints specific to the application's domain.

### Assessment example

Suppose an AI returns:

```json id="paoa37"
{
  "question": "What is 2 + 2?",
  "options": ["3", "4", "5", "6"],
  "correct_answer": 0
}
```

The structure may be valid, but `correct_answer: 0` points to `"3"` when array indexing begins at zero.

The correct answer should point to `"4"` at index `1`.

The application can detect the incorrect answer through semantic or factual validation, but the schema alone cannot establish correctness.

## Semantic Validation

**Semantic validation** checks whether the output makes sense in the context of the task and its rules.

Examples include:

- Checking date relationships
- Ensuring a selected option exists
- Confirming that a required number of items has been produced
- Checking that generated fields are consistent with each other

A response can satisfy the schema while violating a semantic constraint.

## Factual Validation

**Factual validation** checks whether the content is actually correct.

For factual tasks, a system may need to compare model output against trusted information.

A conceptual process is:

```text id="uf1m5o"
AI Response
     |
     v
Compare with trusted database
     |
     v
Consult authoritative source
     |
     v
Cross-check where appropriate
     |
     v
Accept or flag result
```

For example, a model may return:

```json id="2n6gx6"
{
  "customer_id": "12345",
  "plan": "Premium"
}
```

Schema validation can verify that both fields are strings. It cannot prove that customer `12345` actually has a Premium plan.

The backend must verify the claim against an authoritative customer record or another appropriate source.

Not every application requires an external factual verification step, but developers must understand when structural validation is insufficient.

### The four validation questions

| Stage | Question |
|---|---|
| Parsing | Can I read the output? |
| Schema validation | Does it follow the expected structure? |
| Business validation | Does it satisfy application rules? |
| Factual validation | Is the information actually correct? |

**Golden rule:** Valid JSON is not the same as a valid business result, and a valid business result is not automatically factually correct.

# 7. Complete Response Outcome Handling

## Outcome Classification

A production application should use an outcome classification system rather than relying on one boolean success flag.

A useful conceptual flow is:

```text id="g0wgx1"
                    AI Response
                         |
             +-----------+-----------+
             |           |           |
             v           v           v
          Refusal     Response      Error
                         |
                         v
                    Can parse?
                    /         \
                  No           Yes
                  |             |
                  v             v
             Parse failure   Schema check
                              /       \
                           Invalid    Valid
                              |         |
                              v         v
                            Repair   Business checks
                                        |
                                  +-----+-----+
                                  |           |
                               Invalid       Valid
                                  |           |
                                  v           v
                                Repair   Factual checks,
                                         when required
```

The application's handling of provider errors, refusals, retries, repair, and rejection should be explicit.

## Response Outcome Decision Table

| Outcome | What happened? | Typical handling |
|---|---|---|
| **Valid output** | Response satisfies the technical contract | Continue to required downstream checks |
| **Refusal** | Model intentionally declined | Handle as a refusal |
| **Incomplete output** | Required task content is missing | Repair or retry when appropriate |
| **Truncation** | Output was cut off before completion | Investigate the cause and retry appropriately |
| **Parsing failure** | Response cannot be parsed in the expected format | Repair or retry when appropriate |
| **Schema failure** | Parsed response violates the schema | Repair or regenerate when appropriate |
| **Business failure** | Output violates application rules | Reject or attempt a suitable correction |
| **Factual failure** | Content is incorrect | Requires appropriate correctness checking and handling |
| **Provider error** | Service, API, or transport request failed | Retry if appropriate for the error |
| **Empty response** | No usable content was returned | Classify and handle according to the provider and task |

The supplied material identifies these outcomes but does not specify one universal action for every possible failure. Handling depends on the application and provider behavior.

## End-to-End Response Handling

A robust response-processing pipeline can be designed as follows:

```text id="0zxrh2"
AI Request
    |
    v
Model Call
    |
    v
Raw Response
    |
    v
Outcome Detection
    |
    +---- Refusal
    |        |
    |        v
    |   Handle separately
    |
    +---- Provider error
    |        |
    |        v
    |   Retry if appropriate
    |
    +---- Normal response
             |
             v
          Parse response
             |
             v
          Schema validation
             |
             v
          Business validation
             |
             v
          Factual / semantic checks
             |
             v
           Accept result
```

If parsing or validation fails, the application can consider repair or fresh generation when appropriate, with bounded attempts.

### Important rule

**Each stage answers a different question.**

Do not treat the outcome of one stage as proof that every subsequent stage will succeed.

## Real-World Example: AI Assessment Generator

Suppose an LMS asks the model to generate:

- 10 multiple-choice questions
- Four options per question
- One correct answer per question
- An explanation for each answer

The expected structure is:

```text id="u7f75f"
questions[]
    |
    +---- question
    |
    +---- options[]
    |
    +---- correct_answer
    |
    +---- explanation
```

### Outcome 1: Valid response

The model returns 10 questions, four options for each, correct-answer references, and explanations.

```text id="odj82s"
Parse succeeds
      |
      v
Schema validation succeeds
      |
      v
Business validation succeeds
      |
      v
Accept, subject to required checks
```

### Outcome 2: Incomplete response

The model returns only six questions when 10 are required.

```text id="7dl57r"
Expected: 10 questions
Received: 6 questions
          |
          v
     Incomplete
```

The JSON may be valid, but the task requirement is not satisfied.

### Outcome 3: Truncated response

The model stops halfway through question eight:

```text id="i8z5lh"
Question 8:
What is...
```

The application identifies an incomplete or truncated response and determines whether an appropriate retry or other recovery action is possible.

### Outcome 4: Parsing failure

The model returns malformed JSON:

```text id="5o4onn"
Here are your questions:

{
  "questions": [
    ...
```

The parser cannot read the response as the required JSON structure.

```text id="3c8y9k"
Parse fails
    |
    v
Repair or retry
```

### Outcome 5: Schema failure

The model returns:

```json id="c43vpx"
{
  "questions": [
    {
      "question": "What is SOLAS?",
      "correct_answer": "A"
    }
  ]
}
```

But the output contract requires `options` and `explanation`.

The response can parse successfully, but schema validation fails because required fields are missing.

### Outcome 6: Business-rule failure

A response contains four options, but the correct-answer index points to an invalid position.

For example:

```json id="2v2vwz"
{
  "question": "What is 2 + 2?",
  "options": ["3", "4", "5", "6"],
  "correct_answer": 9
}
```

The JSON may satisfy basic field types if the schema allows any integer, but the answer index is outside the options array.

Business validation should reject this result.

### Outcome 7: Factual failure

The model may return a fully formed question with four options and a valid answer index, yet select the wrong answer.

```text id="bu1t0j"
Parsing:              Pass
Schema validation:    Pass
Business structure:   Pass
Factual correctness:  Fail
```

This demonstrates why schema validation and basic business checks cannot replace factual evaluation.

## Common Mistakes

### 1. Treating all failures as identical

Poor approach:

```javascript
if (!success) {
  retry();
}
```

Different outcomes require different handling.

### 2. Treating refusal as a parsing error

A refusal is a distinct outcome, not necessarily malformed output.

### 3. Assuming schema validity means correctness

```text id="y9dn6s"
Schema valid
     !=
Factually correct
```

### 4. Assuming incomplete output always means truncation

A response can omit a required section without being cut off.

### 5. Repairing fundamentally incorrect reasoning

Repair is more appropriate for recoverable structural problems. Fundamentally incorrect reasoning may require fresh generation, independent verification, or rejection.

### 6. Creating unlimited repair loops

Always define a maximum number of repair attempts.

### 7. Checking only syntax

A production validation chain may need to include:

```text id="1gveac"
Parsing
   |
   v
Schema validation
   |
   v
Business validation
   |
   v
Factual validation, when required
```

### 8. Trusting the repaired response automatically

A successful repair attempt does not prove that the response is correct. The corrected response must be parsed and validated again.

# 8. Concept Map, Glossary, and Final Revision Sheet

## Glossary

| Term | Meaning |
|---|---|
| **Response outcome** | Classification of what happened after an AI request |
| **Valid output** | Output that satisfies the technical contract |
| **Refusal** | Model intentionally declines the request |
| **Incomplete output** | Required task information is missing |
| **Truncation** | Output is cut off before completion |
| **Parsing failure** | Raw output cannot be converted into the expected structure |
| **Schema failure** | Parsed output violates the expected schema |
| **Repair attempt** | Attempt to correct a problematic response |
| **Bounded repair** | Repair with a maximum number of attempts |
| **Business validation** | Checks application-specific rules |
| **Semantic validation** | Checks whether data makes sense in context |
| **Factual validation** | Checks whether information is actually correct |
| **Schema validity** | Structural compliance with an expected contract |
| **Outcome taxonomy** | Structured classification of possible response states |

# 9. Practice Questions and Interview Preparation

## Question-and-Answer Recall

**Q1. Why isn't an AI response simply success or failure?**

**Answer:** Because it can be valid, refused, incomplete, truncated, unparsable, schema-invalid, affected by a provider error, or structurally valid but factually incorrect. Each outcome may require different handling.

**Q2. What is valid output?**

**Answer:** Output that satisfies the expected technical contract, including the required structure and constraints.

**Q3. What is a refusal?**

**Answer:** A deliberate decision by the model to decline the requested content or action.

**Q4. What is incomplete output?**

**Answer:** A response that does not provide everything required to complete the task.

**Q5. What is truncation?**

**Answer:** Output that is cut off before completion, possibly because of limits or interruptions.

**Q6. What is a parsing failure?**

**Answer:** A failure to convert the raw response into the expected data format.

**Q7. What is schema validation failure?**

**Answer:** A failure that occurs when the response parses successfully but violates the expected schema.

**Q8. What is bounded repair?**

**Answer:** An attempt to correct invalid output with a fixed maximum number of attempts.

**Q9. Why can't repair always fix a bad response?**

**Answer:** Because fundamental reasoning errors or missing information may require fresh generation, independent verification, or rejection rather than formatting repair.

**Q10. Does schema validity guarantee factual correctness?**

**Answer:** No. A schema checks structure and constraints, not whether the information is true.

**Q11. What does business validation check?**

**Answer:** Application-specific rules, such as whether an answer index points to an existing option or whether a date range is valid.

**Q12. What does factual validation check?**

**Answer:** Whether the information corresponds to the relevant facts, using appropriate trusted information or verification methods when needed.

**Q13. How does truncation differ from incomplete output?**

**Answer:** Truncation means the output was cut off. Incomplete output means required content is missing. Truncation can cause incompleteness, but omission can also occur without truncation.

**Q14. Why must repair attempts be bounded?**

**Answer:** To prevent unlimited API costs, increasing latency, infinite loops, and permanently failing tasks that never terminate.

**Q15. What should happen after repairing a response?**

**Answer:** The repaired response should be parsed and validated again before acceptance.

## Scenario-Based Interview Questions

### Scenario 1: An AI assessment contains fewer questions than requested

**Question:** Your LMS requests 10 multiple-choice questions. The model returns six questions in valid JSON, and every returned question satisfies the schema. What should your backend do?

**Answer:** Validate the task-level requirement that the question count equals 10. Since only six questions were returned, classify the result as incomplete even though its structure is valid. Apply an appropriate bounded repair or regeneration strategy, and validate the complete result again.

### Scenario 2: Malformed JSON

**Question:** Your model returns a response that starts with `{` but stops before closing the JSON object. How would you handle it?

**Answer:** Attempt to identify whether the response was truncated using the provider's completion metadata, if available. Classify the response as unparsable and potentially truncated. Repair or retry when appropriate, using suitable generation limits. Validate the resulting response before acceptance.

### Scenario 3: Incorrect answer in a structurally valid assessment

**Question:** An AI generates four options and a valid integer for the correct-answer index, but the selected option is factually wrong. All schema checks pass. What validation is missing?

**Answer:** The application needs a correctness check capable of evaluating the answer's meaning. Structural validation establishes that the index and fields are correctly formed, but factual verification must establish that the chosen option actually answers the question.

### Scenario 4: Unlimited repair attempts

**Question:** Your service keeps asking the model to repair invalid JSON, but the response remains invalid. API cost and latency continue to increase. How would you fix this?

**Answer:** Introduce a maximum repair-attempt count, record the validation errors, and stop when the limit is reached. Depending on the failure, use an explicitly defined fallback, controlled rejection, or a fresh generation. Every repaired or regenerated response must be validated again.

### Scenario 5: Refusal vs. provider error

**Question:** The model declines a request in one case, while another request fails because of a provider timeout. Should the backend handle these outcomes identically?

**Answer:** No. A refusal indicates that the model declined the task, whereas a timeout indicates a service or transport failure. Handle refusals through the application's refusal path and apply retry logic to timeouts when appropriate.

### Scenario 6: Valid output but incorrect business logic

**Question:** An AI generates a JSON object with valid date strings, but the end date occurs before the start date. How should the application catch this?

**Answer:** Schema validation confirms that the dates follow the required data types. Business or semantic validation must check the relationship between the dates and reject the result if the date range violates the application's rules.

### Scenario 7: A repair produces valid JSON but changes the answer

**Question:** Your initial answer is factually correct but has a formatting problem. The repair fixes the format while changing the answer to an incorrect one. Can the repaired response be accepted?

**Answer:** No. Repair success at the structural level does not guarantee factual correctness. The repaired response must pass all required parsing, schema, business, and factual checks before acceptance.

### Scenario 8: Choosing between repair and fresh generation

**Question:** A model returns syntactically valid JSON with all required fields, but its reasoning is fundamentally wrong. Would you keep using a repair prompt?

**Answer:** Not as a substitute for correcting the underlying reasoning. Consider fresh generation, independent verification, or controlled rejection based on the task. A repair instruction is more appropriate for limited structural or formatting errors.
