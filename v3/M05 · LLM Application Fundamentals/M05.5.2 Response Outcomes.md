# 1. M05.5.2 Response Outcomes

## Simple Definition

After an AI model receives a request, the result is **not always simply "success" or "failure."**

A production AI system should classify the response into meaningful outcomes.

```text
                         AI Request
                             ↓
                        Model Response
                             ↓
                  ┌──────────┼───────────┐
                  ↓          ↓           ↓
               Valid      Invalid      No usable result
                  │          │
                  │      ┌───┴─────────────────┐
                  │      ↓                     ↓
                  │   Parse failure        Incomplete /
                  │                        Truncated
                  │
                  └──────────────────────────────→ Continue
```

Other outcomes can include:

- Refusal
- Schema validation failure
- Temporary provider error
- Empty response
- Content that is structurally valid but factually wrong

The key idea is:

> **A response can be structurally valid and still be incorrect.**

---

# 1.1 Valid Output

## Definition

A **valid output** is a response that satisfies the expected technical contract.

For example, suppose the application expects:

```json
{
  "name": "John",
  "age": 30
}
```

with this contract:

```text
name → string
age  → integer
```

The response:

```json
{
  "name": "John",
  "age": 30
}
```

is **schema-valid**.

---

## Valid Output Flow

```text
AI
 ↓
Response
 ↓
Parse
 ↓
Schema Validation
 ↓
Valid?
 ↓
Yes
 ↓
Application
```

But there is an important second question:

> Is the information itself correct?

For example:

```json
{
  "name": "John",
  "age": 30
}
```

may be perfectly valid according to the schema while the real age is actually 27.

Therefore:

```text
Schema Validity
      ≠
Factual Correctness
```

This distinction is one of the most important concepts in this section.

---

# 1.2 Refusal

## Definition

A **refusal** occurs when the model declines to provide the requested content or action.

For example, the application asks for something the model will not provide under its safety or usage policies.

Conceptually:

```text
Request
  ↓
Model evaluates request
  ↓
Refusal
  ↓
No normal task output
```

A refusal is **not necessarily an API failure**.

The provider may have successfully processed the request and intentionally returned a refusal outcome.

---

## Refusal vs Error

These should not be treated as the same thing.

| Outcome | Meaning |
|---|---|
| **Refusal** | Model intentionally declines the request |
| **API error** | Request failed at the service/transport/API level |
| **Validation failure** | Response was received but does not satisfy the expected contract |

### Example

```text
Request
 ↓
Provider
 ↓
Model refuses
 ↓
Controlled refusal response
```

versus:

```text
Request
 ↓
Provider
 ↓
500 / timeout / network error
```

The second case is an infrastructure or service problem.

---

## Why Refusals Need Special Handling

Suppose the application expects:

```json
{
  "answer": "...",
  "confidence": 0.9
}
```

but the model refuses.

The system should not blindly try to parse the refusal as if it were a normal answer.

Instead:

```text
Response
 ↓
Outcome detection
 ├── Normal answer
 └── Refusal
       ↓
   Handle separately
```

The UI might show:

```text
"The assistant cannot provide that response."
```

rather than:

```text
"JSON parsing failed."
```

---

# 1.3 Incomplete Output

## Definition

An **incomplete output** is a response that does not contain everything required to complete the task.

Example:

The application asks:

```text
Return:
1. Summary
2. Risks
3. Recommendations
```

The model returns only:

```text
Summary: Revenue increased.
```

The response may be syntactically valid text, but the task is incomplete.

---

## Incomplete Output vs Invalid Output

These are different.

### Invalid structure

Expected:

```json
{
  "name": string,
  "age": integer
}
```

Received:

```json
{
  "name": "John"
}
```

The JSON may parse, but `age` is missing.

### Incomplete task

The schema may even be satisfied:

```json
{
  "summary": "Revenue increased.",
  "risks": [],
  "recommendations": []
}
```

but the actual analysis may be insufficient because the model failed to identify important risks or recommendations.

This demonstrates:

```text
Schema validation
      ↓
Can confirm structure
      ↓
Cannot guarantee task completeness
```

---

## Detecting Incomplete Output

Possible checks include:

### Required-field validation

```text
Missing required field?
→ Incomplete
```

### Minimum content checks

```text
summary.length < minimum?
→ Potentially incomplete
```

### Business rules

For an assessment generator:

```text
Expected 10 questions
Received 6
→ Incomplete
```

### Task-specific validation

```text
Expected:
question
options
correct answer
explanation

Received:
question
options

→ Incomplete
```

---

# 1.4 Truncation

## Definition

**Truncation** occurs when the generated output is cut off before the response is complete.

This can happen because of:

- Output token limits
- Context limits
- Provider/model generation limits
- Connection interruption
- Application-side cutoff

---

## Example

Expected:

```text
Here are the three causes:
1. Cause A
2. Cause B
3. Cause C
```

Actual:

```text
Here are the three causes:
1. Cause A
2. Cause B
```

The response stopped before finishing.

---

## Truncation Flow

```text
Model starts generating
       ↓
Output limit reached
       ↓
Generation stops
       ↓
Partial response
```

---

## Truncation vs Incomplete Output

These are related but not identical.

| Truncation | Incomplete Output |
|---|---|
| Output was cut off | Required task content is missing |
| Often caused by generation/transport limits | May result from model behavior or validation |
| Often ends abruptly | May look completely normal |
| Example: sentence stops halfway | Example: one requested section is missing |

### Important relationship

```text
Truncation
    ↓
Can cause
    ↓
Incomplete Output
```

But:

```text
Incomplete Output
    ✕
does not always mean truncation
```

The model might simply forget a required section.

---

## Detecting Truncation

Possible signals include:

```text
Finish reason indicates length
        ↓
Potential truncation
```

or application-level checks:

```text
Expected closing structure missing
```

For example:

```json
{
  "items": [
    {
      "name": "A"
```

The response is clearly incomplete.

---

# 1.5 Parsing Failure

## Definition

A **parsing failure** occurs when the application cannot convert the model's response into the expected data format.

### Example

Expected JSON:

```json
{
  "name": "John"
}
```

Model returns:

```text
Here is the answer:

{
  "name": "John"
```

Problems may include:

- Invalid JSON
- Missing closing braces
- Incorrect syntax
- Unexpected text around structured output
- Malformed serialization

---

## Parse Failure Flow

```text
AI Response
    ↓
Parser
    ↓
Can parse?
 ┌──┴────┐
Yes      No
 ↓        ↓
Validate  Parse Failure
```

---

# Parsing Failure vs Schema Validation Failure

This distinction is extremely important.

### Parsing failure

The application cannot even interpret the response as the expected data format.

```text
"{ invalid json"
      ↓
Parser
      ↓
FAIL
```

### Schema validation failure

The response parses successfully, but violates the schema.

```json
{
  "name": "John",
  "age": "thirty"
}
```

```text
Parse
 ↓
SUCCESS
 ↓
Schema Validation
 ↓
FAIL
```

### Memory trick

```text
Parsing    = "Can I read the structure?"
Validation = "Does the structure follow the contract?"
```

---

# 1.6 Bounded Repair Attempts

## Definition

A **repair attempt** tries to correct an invalid or incomplete response.

**Bounded** means the number of repair attempts is limited.

Never create an unlimited loop.

---

## Example

Expected:

```json
{
  "score": 0,
  "passed": false
}
```

Actual:

```json
{
  "score": "85",
  "passed": "yes"
}
```

The structure is almost usable, but the field types are wrong.

A repair step can provide the validation errors:

```text
Your previous response failed validation.

Problems:
- score must be a number.
- passed must be a boolean.

Return the corrected object only.
```

The model may return:

```json
{
  "score": 85,
  "passed": true
}
```

---

## Repair Loop

```text
Generate
   ↓
Parse
   ↓
Validate
   ↓
Valid?
 ┌──┴─────┐
Yes      No
 ↓        ↓
Use     Repair
          ↓
       Validate
          ↓
      Valid?
      /    \
    Yes     No
    ↓        ↓
   Use    Retry / Fail
```

---

## Why Bounded Repairs?

Consider:

```text
attempt 1 → invalid
attempt 2 → invalid
attempt 3 → invalid
attempt 4 → invalid
...
```

Without a limit:

- API costs can increase
- Latency can grow
- The system can enter an infinite loop
- A permanently invalid task may never terminate

Instead:

```text
Maximum repair attempts = 2 or 3
```

Then:

```text
Still invalid
     ↓
Controlled failure
```

---

## Repair vs Fresh Retry

A repair is useful when the **underlying answer is mostly correct** but the format or small details are wrong.

Example:

```text
Correct information
+
Wrong JSON type
→ Repair
```

A fresh generation may be better when:

```text
Wrong reasoning
+
Missing information
+
Fundamentally poor answer
→ New generation
```

# 1.7 Schema Validity ≠ Factual Correctness

## The Most Important Concept

A schema can tell you:

```text
Is this data shaped correctly?
```

It cannot automatically tell you:

```text
Is this information actually true?
```

---

## Example

Suppose the schema is:

```json
{
  "capital": "string"
}
```

The model returns:

```json
{
  "capital": "Mumbai"
}
```

This is:

```text
Valid JSON        ✅
Valid schema      ✅
Correct fact      ❓
```

The schema says nothing about whether Mumbai is actually the capital of the country being discussed.

---

## Three Levels of Correctness

A useful model is:

```text
Level 1 → Parsing
           "Can I read the output?"

Level 2 → Schema Validation
           "Does it have the correct structure?"

Level 3 → Semantic / Factual Validation
           "Is the information correct?"
```

### Complete pipeline

```text
AI Output
   ↓
Parse
   ↓
Schema Validation
   ↓
Business Validation
   ↓
Factual / Semantic Evaluation
   ↓
Accept
```

Not every application needs all levels, but the distinction is essential.

---

# Semantic Validation

**Semantic validation** asks whether the output makes sense for the task.

Example:

```json
{
  "start_date": "2026-10-10",
  "end_date": "2026-10-05"
}
```

The JSON can be perfectly valid.

Schema:

```text
start_date → string
end_date   → string
```

So the schema may pass.

But business logic says:

```text
start_date < end_date
```

is required.

Therefore:

```text
Schema valid
      ↓
Business invalid
```

---

# Factual Validation

For factual tasks, additional validation may be required.

Possible approaches:

```text
AI Response
    ↓
Check against trusted database
    ↓
Check authoritative source
    ↓
Cross-check with another system/model
    ↓
Accept / Flag
```

For example, an AI-generated customer record might contain:

```json
{
  "customer_id": "12345",
  "plan": "Premium"
}
```

The schema can verify the types.

But your backend should check whether customer `12345` actually has the Premium plan.

---

# Complete Response Outcome Taxonomy

A production system can classify outcomes like this:

```text
                         AI Response
                              │
                 ┌────────────┼────────────┐
                 ↓            ↓            ↓
              Refusal      Response      Error
                              │
                    ┌─────────┼──────────┐
                    ↓         ↓          ↓
                 Parse OK   Parse Fail   Empty
                    │
              ┌─────┴─────────────┐
              ↓                   ↓
          Schema Valid        Schema Invalid
              │                   │
              ↓                   ↓
       Business Valid         Repair
              │                   │
              ↓               Revalidate
         Factual Check            │
              │               Bounded
              ↓                Attempts
          Accept                  │
                              ┌───┴───┐
                              ↓       ↓
                            Fixed   Failed
                              ↓       ↓
                           Accept   Reject
```

---

# Practical Outcome Table

| Outcome | What happened? | Typical action |
|---|---|---|
| **Valid output** | Parsed and satisfies contract | Continue |
| **Refusal** | Model declined the task | Handle as refusal |
| **Incomplete output** | Required task information is missing | Repair/retry |
| **Truncation** | Output stopped before completion | Retry with suitable limits |
| **Parsing failure** | Response cannot be parsed | Repair/retry |
| **Schema failure** | Parsed but violates schema | Repair/retry |
| **Business failure** | Violates application rules | Reject/repair |
| **Factual failure** | Struct
