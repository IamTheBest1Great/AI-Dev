## 1. Response Contracts and Structured Outputs

### Definition

A **response contract** defines the expected structure, types and rules of an AI response.

**Validation** checks whether the actual response satisfies that contract.

LLMs generate probabilistic outputs, while software applications generally require predictable, machine-readable data. Response contracts form the boundary between these two systems.

### Example: Unstructured vs. structured output

An AI model might respond with ordinary text:

```text
John is 25 years old and lives in Mumbai.
```

A backend may instead require:

```json
{
  "name": "John",
  "age": 25,
  "city": "Mumbai"
}
```

The structured response is easier for application code to process because each value has a defined field.

### Why are response contracts important?

Suppose your backend expects:

```text
user_id → string
score   → number
passed  → boolean
```

But the AI returns:

```json
{
  "user_id": "123",
  "score": "ninety",
  "passed": "yes"
}
```

Although this is valid JSON, the `score` and `passed` values have the wrong types for the expected contract.

Without validation, the application may fail or behave incorrectly when it attempts to use these values.

### The response-validation workflow

```text
Prompt
  ↓
AI Model
  ↓
Generated Output
  ↓
Parse
  ↓
Validate Against Contract
  ↓
Valid?
  ├── Yes → Use Result
  └── No  → Repair / Retry / Reject
```

### What is structured output?

**Structured output** means asking the model to produce information in a predefined, machine-readable structure.

Common forms include:

- JSON.
- JSON conforming to a schema.
- Structured objects.
- Function or tool-call arguments.

Example:

```json
{
  "sentiment": "negative",
  "issue": "late delivery"
}
```

A backend can read the `sentiment` and `issue` fields without attempting to extract them from free-form text.

### Important principle

A response can look correct to a human and still be unsafe for software to consume.

For example, a score of `"ninety"` may be understandable to a person, but it cannot necessarily be passed directly into a numeric calculation.

### Key takeaways

- A response contract defines what the application expects.
- Structured outputs make AI responses easier to process.
- Validation checks whether the response satisfies the required rules.
- Valid structure does not automatically guarantee factual correctness.

## 2. Schema Contracts

### Definition

A **schema** is a formal description of the structure and rules that valid data must follow.

A schema can specify:

- Field names.
- Data types.
- Required fields.
- Optional fields.
- Allowed values.
- Nested objects.
- Arrays.
- Minimum and maximum values.
- String patterns.
- Other structural constraints.

### Example: Customer schema

Suppose the application expects a customer object.

```text
Customer
  ├── name  → string, required
  ├── age   → integer, required
  └── email → string, optional
```

A valid response could be:

```json
{
  "name": "Shubham",
  "age": 25
}
```

An invalid response could be:

```json
{
  "name": "Shubham",
  "age": "twenty-five"
}
```

The second response violates the schema because `age` must be an integer.

### What does a schema protect against?

A schema helps detect:

- Missing required fields.
- Incorrect data types.
- Unexpected values.
- Incorrect nested structures.
- Invalid array elements.
- Values outside defined limits.

This helps protect downstream application logic from receiving data in an unexpected shape.

### Schema contract workflow

```text
Define Schema
      ↓
Generate AI Output
      ↓
Parse Output
      ↓
Validate Schema
      ↓
Accept or Reject
      ↓
Application Logic
```

### Why schemas are valuable in AI systems

Consider an application in which an AI model produces a user assessment result.

The application expects:

```text
score   → number
passed  → boolean
feedback → string
```

If the model returns the result in the wrong format, the backend may be unable to save or display it correctly.

A schema establishes an explicit contract that the model output must satisfy before processing continues.

### Key takeaway

A schema makes the expected data structure explicit, allowing the application to detect invalid responses before they enter downstream processing.

## 3. JSON Schema

### Definition

**JSON Schema** is a standard way to describe and validate the structure and constraints of JSON data.

It allows developers to define required fields, types, allowed values and other rules in a machine-readable format.

### Example: Customer JSON Schema

```json
{
  "type": "object",
  "properties": {
    "name": {
      "type": "string"
    },
    "age": {
      "type": "integer",
      "minimum": 0
    }
  },
  "required": ["name", "age"],
  "additionalProperties": false
}
```

This schema specifies that:

- The output must be an object.
- `name` must be a string.
- `age` must be an integer.
- `age` cannot be negative.
- Both fields are required.
- Additional fields are not allowed.

The `additionalProperties` rule is included here to demonstrate a strict contract. Whether extra fields should be allowed depends on the application's requirements.

### Valid response

```json
{
  "name": "Rahul",
  "age": 30
}
```

### Invalid response

```json
{
  "name": "Rahul",
  "age": "thirty"
}
```

The second response violates the integer requirement for `age`.

Another invalid example is:

```json
{
  "name": "Rahul",
  "age": -5
}
```

This value violates the `minimum: 0` constraint.

### How JSON Schema works with AI

```text
JSON Schema
     ↓
Model / Structured Output API
     ↓
Generated JSON
     ↓
JSON Schema Validator
     ↓
Valid / Invalid
```

Some providers support constrained structured-output generation based on a schema. The available features and supported schema subset depend on the provider and API.

Even when the provider constrains generation, application-side validation remains valuable.

### Why JSON Schema is useful

It provides a common, machine-readable contract that can be used across different application components.

It is particularly useful when AI output flows into:

- Databases.
- APIs.
- Frontend applications.
- Workflow engines.
- Other AI agents.
- Business logic.

### Key takeaway

JSON Schema formally describes which JSON structures are acceptable. It helps applications check structure and constraints instead of relying on the model's formatting instructions alone.

## 4. Pydantic Validation

### Definition

**Pydantic** is a Python library used to define data models, parse data and validate it against declared types and constraints.

It is especially useful in Python backends, including FastAPI applications.

### Defining a Pydantic model

```python
from pydantic import BaseModel, Field

class Customer(BaseModel):
    name: str
    age: int = Field(ge=0)
```

This defines a customer with:

- `name` as a string.
- `age` as an integer.
- `age` greater than or equal to zero.

Both fields are required because they do not have default values.

### Valid data

```python
customer_data = {
    "name": "Rahul",
    "age": 30
}

customer = Customer.model_validate(customer_data)

print(customer.name)
print(customer.age)
```

The data satisfies the declared model.

### Invalid data

```python
customer_data = {
    "name": "Rahul",
    "age": "hello"
}

customer = Customer.model_validate(customer_data)
```

The validation call raises a validation error because `"hello"` cannot be validated as the required integer.

### Important detail: Type coercion

Pydantic may convert some compatible input values depending on its validation rules and configuration.

If an application requires strict types, configure strict validation where appropriate. Do not assume that every value with the wrong original type will always be rejected under default settings.

### Pydantic with AI output

Suppose an AI assessment system must return a score, pass status and feedback.

```python
from pydantic import BaseModel, Field

class AssessmentResult(BaseModel):
    score: float = Field(ge=0, le=100)
    passed: bool
    feedback: str
```

Expected output:

```json
{
  "score": 82.5,
  "passed": true,
  "feedback": "Strong performance."
}
```

The backend can parse the JSON and validate it against `AssessmentResult` before passing the result to business logic.

### AI-to-Pydantic workflow

```text
AI Model
   ↓
Raw JSON
   ↓
Parse JSON
   ↓
Pydantic Validation
   ↓
Validated AssessmentResult
   ↓
Business Logic
```

### Why is Pydantic useful?

It supports:

- Type validation.
- Required and optional fields.
- Nested models.
- Value constraints.
- Data parsing.
- Detailed validation errors.
- Integration with Python application frameworks.

### JSON Schema vs. Pydantic

| Feature | JSON Schema | Pydantic |
|---|---|---|
| Primary purpose | Describe and validate JSON structures | Define and validate data models in Python |
| Representation | JSON-based schema document | Python classes and types |
| Main environment | Language-independent schema ecosystems | Python applications |
| Constraints | Types, properties, required fields and supported keywords | Types, field constraints, custom validators and more |
| Relationship | Can be used directly by compatible validators and APIs | Can generate JSON Schema from models |

They are complementary rather than mutually exclusive.

A Pydantic model can be used to generate a JSON Schema, and a Python application can validate parsed AI output using Pydantic.

### Key takeaway

Use JSON Schema when you need a standard schema description. Use Pydantic when your Python application needs strongly defined data models and runtime validation.

## 5. Function and Tool Schemas

### Definition

A **function or tool schema** describes the arguments a model may provide when requesting an external function or tool to be executed.

The schema informs the model about the tool's purpose and the expected argument structure.

### Example: Weather tool

Suppose the application provides a function called `get_weather`.

Its arguments are expected to contain:

```json
{
  "city": "string",
  "unit": "C or F"
}
```

A structured tool call could contain:

```json
{
  "city": "Mumbai",
  "unit": "C"
}
```

The application can validate the arguments before calling the actual weather function.

### Tool-calling workflow

```text
User Request
     ↓
Model selects a tool
     ↓
Tool call with arguments
     ↓
Validate arguments
     ↓
Check authorization and rules
     ↓
Execute tool
     ↓
Return tool result
     ↓
Model or application continues
```

The exact sequence depends on the API and application architecture. Tool execution is commonly controlled by the application rather than being performed by the model itself.

### Why tool schemas matter

Without a schema, the model might return a sentence such as:

```text
Please get the weather for Mumbai in Celsius.
```

The application would then need to interpret the sentence and extract the city and unit.

A tool schema instead provides structured arguments that can be validated and passed to the function.

### Response schema vs. function/tool schema

| Feature | Response schema | Function/tool schema |
|---|---|---|
| Purpose | Defines the model's structured result | Defines arguments for a tool invocation |
| Example | `{"score": 85, "passed": true}` | `{"city": "Mumbai", "unit": "C"}` |
| Main consumer | Application | Function or tool executor |
| Validation point | Before business logic consumes the result | Before tool execution |
| Common risk | Invalid or incorrect output data | Invalid arguments or unsafe actions |

### Important security distinction

A valid tool schema does not prove that the requested action is authorized.

For example, a tool call might have valid fields but request access to another user's account.

Therefore, the application must also enforce:

- Authentication.
- Authorization.
- Input constraints.
- Business rules.
- Safety checks for consequential actions.

### Key takeaway

Tool schemas constrain the structure of function arguments. Application-side validation and authorization determine whether those arguments should actually be executed.

## 6. Schema Evolution

### Definition

**Schema evolution** is the process of changing a data contract over time while maintaining system compatibility and reliability.

AI applications often have several connected components:

```text
Prompt
  ↓
Model
  ↓
Response Schema
  ↓
Backend
  ↓
Database
  ↓
Frontend
```

Changing the response schema can affect multiple components at once.

### Example: Adding a field

Version 1:

```json
{
  "name": "John",
  "age": 30
}
```

Version 2:

```json
{
  "name": "John",
  "age": 30,
  "city": "Mumbai"
}
```

Adding a new optional field can often be backward-compatible when existing consumers ignore unknown fields.

However, compatibility depends on the consumers' behavior and the exact contract.

### Backward-compatible vs. breaking changes

**Potentially safer change:** Add an optional field that existing consumers can ignore.

```json
{
  "name": "John",
  "city": "Mumbai"
}
```

If older consumers require only `name`, they may continue to operate.

**Riskier change:** Change the type of an existing field.

Version 1:

```json
{
  "age": 30
}
```

Version 2:

```json
{
  "age": "thirty"
}
```

A backend expecting an integer may fail when it receives a string.

Other breaking changes include:

- Removing a required field.
- Renaming a field.
- Changing a field's meaning.
- Changing allowed enum values.
- Changing a nested object structure.

### Safe schema-evolution process

```text
Current Schema
      ↓
Design New Version
      ↓
Check Consumers
      ↓
Run Compatibility Tests
      ↓
Deploy Compatible Changes
      ↓
Monitor
      ↓
Deprecate Old Version When Safe
```

### Good practices

- Prefer additive changes where possible.
- Introduce optional fields when appropriate.
- Version breaking changes.
- Test old and new consumers.
- Plan database migrations when stored data is affected.
- Do not silently change field semantics.
- Keep prompts, schemas and consuming application code synchronized.

### Key takeaway

Schema evolution is a system-wide compatibility problem, not merely a change to a JSON object.

## 7. Structured Output APIs

### Definition

**Structured Output APIs** are provider features designed to constrain model responses to a specified structure, often using a schema.

They provide stronger structural guarantees than a natural-language instruction alone.

### Plain instruction vs. schema-constrained output

Plain instruction:

```text
Please return valid JSON.
```

This requests JSON, but it does not necessarily guarantee that every response follows the required schema.

Schema-constrained output:

```text
Required schema:
{
  "score": number,
  "passed": boolean
}
```

A supported structured-output mechanism can enforce more of the specified structure during generation.

The exact guarantees and schema restrictions depend on the provider and API.

### Workflow

```text
Prompt
  +
Output Schema
      ↓
Structured Output API
      ↓
AI Model
      ↓
Structured Response
      ↓
Application-Side Validation
```

### Why use a structured-output API?

It can improve:

- Output consistency.
- Machine readability.
- Schema adherence.
- Integration with software.
- Reliability of downstream processing.

### Important limitation

Structural constraints do not necessarily guarantee factual correctness or business validity.

For example:

```json
{
  "score": 150,
  "passed": true
}
```

This is valid JSON. It may even satisfy a basic schema that declares `score` as a number and `passed` as a boolean.

But if scores must remain between 0 and 100, the response violates the business rules.

### Key takeaway

Use a provider's structured-output mechanism when appropriate, then validate the response at the application boundary before using it.

## 8. Parsing and Validation

Parsing and validation are separate operations that solve different problems.

### Parsing

**Parsing** means converting raw output into a usable data structure.

Example:

```text
Raw JSON string
      ↓
JSON parser
      ↓
Python or JavaScript object
```

### Validation

**Validation** means checking whether the parsed object satisfies the expected contract.

```text
Parsed object
      ↓
Schema validator
      ↓
Valid or invalid
```

### Example: Valid output

The model returns:

```json
{
  "score": 90,
  "passed": true
}
```

First, the application parses the JSON.

Next, it validates that:

- `score` is numeric.
- `passed` is boolean.
- Required fields exist.
- `score` falls within the allowed range, if a range is defined.

If the result satisfies the contract, the application can proceed.

### Parsing failure vs. validation failure

**Parsing failure:** The output is not syntactically valid JSON.

```text
{
  "name": "John"
```

The closing brace is missing, so a JSON parser cannot parse the complete object.

**Validation failure:** The JSON is syntactically valid, but violates the schema.

```json
{
  "name": "John",
  "age": "unknown"
}
```

The JSON can be parsed, but `age` violates an integer requirement.

### Comparison

| Question | Parsing | Validation |
|---|---|---|
| Main purpose | Read and convert the output | Check whether it follows the contract |
| Input | Raw output | Parsed data |
| Example failure | Malformed JSON | Missing required field or wrong type |
| Typical response | Reject or attempt format repair | Repair, retry or reject |

### Memory trick

**Parsing = Can I read it?**

**Validation = Does it follow the rules?**

### Recommended pipeline

```text
Raw Model Output
       ↓
Parse
       ↓
Schema Validation
       ↓
Business Validation
       ↓
Use or Store Data
```

### Key takeaway

Parsing establishes whether the output can be converted into data. Validation establishes whether that data satisfies the required rules.

## 9. Repair Loops

### Definition

A **repair loop** attempts to correct invalid model output and validate the corrected result again.

Instead of immediately abandoning a request, the application can use feedback from the validation process to request a corrected response.

### Example

Expected structure:

```json
{
  "score": 0,
  "passed": false
}
```

Suppose the intended schema requires a numeric score and a boolean pass status.

The model returns:

```json
{
  "score": "85",
  "passed": "yes"
}
```

The JSON parses, but the values violate the expected types.

A repair process can send the validation errors back to the model.

```text
Your previous output failed validation.

Problems:
- score must be a number.
- passed must be a boolean.

Return the corrected JSON object only.
```

The model may then return:

```json
{
  "score": 85,
  "passed": true
}
```

The application must validate this new response rather than assuming that the repair succeeded.

### Repair loop architecture

```text
Model
  ↓
Raw Output
  ↓
Parse + Validate
  ↓
Valid?
  ├── Yes → Continue
  └── No
       ↓
   Generate repair request
       ↓
   Corrected output
       ↓
   Validate again
```

### When does repair make sense?

Repair is useful when:

- The underlying answer is mostly correct.
- The main problem is formatting.
- Only a small number of fields violate the schema.
- The model can reasonably correct the issue.

For example, correcting a string where a number is required may be feasible if the intended value is clear.

### When might repair be insufficient?

If the response contains incorrect facts or deeply flawed reasoning, simply changing the format is not enough.

The system may need to regenerate the answer, retrieve better source information, use another validation strategy or return a controlled failure.

### Avoid infinite repair loops

A repair loop should have a maximum number of attempts.

For example:

```text
Initial generation
       ↓
Repair attempt 1
       ↓
Repair attempt 2
       ↓
Still invalid?
       ↓
Return controlled failure
```

The number of attempts should be chosen according to the application's cost, latency and reliability requirements.

### Key takeaway

A repair loop can correct invalid output, but every repaired response must be validated again and the number of attempts must be bounded.

## 10. Retry Strategies

### Definition

A **retry strategy** defines what an application does when an AI request or a subsequent processing step fails.

Different failures require different handling.

### Three broad failure categories

**Transient failures:** Temporary network issues, provider outages, overload or rate limiting. A retry may be appropriate.

**Validation failures:** The request succeeds, but the generated response fails parsing or schema validation. A repair or fresh generation may be appropriate.

**Permanent failures:** Invalid credentials, insufficient permissions or malformed requests. These normally require correction rather than repeated retries.

### Retry decision flow

```text
Request
  ↓
Failure
  ↓
Classify the problem
  ├── Transient
  │     ↓
  │   Retry if safe
  │
  ├── Validation failure
  │     ↓
  │   Repair or regenerate
  │
  └── Permanent failure
        ↓
      Log and correct
```

### Exponential backoff

**Exponential backoff** increases the wait between successive retries.

Example:

```text
Attempt 1 → wait 1 second
Attempt 2 → wait 2 seconds
Attempt 3 → wait 4 seconds
Attempt 4 → stop
```

These values are illustrative rather than universal defaults.

Exponential backoff gives temporary failures time to recover and reduces unnecessary pressure on the provider.

### Jitter

**Jitter** adds random variation to retry delays.

Without jitter, many clients may retry simultaneously after the same delay, creating another traffic spike.

Jitter helps distribute retry traffic over time.

### Bounded retries

Never use an unrestricted loop that keeps regenerating invalid output indefinitely.

Instead, set a maximum attempt count or total retry budget.

After the limit is reached, the system should return a controlled error, use an appropriate fallback or route the issue for further handling.

### Repair vs. retry

| Feature | Repair | Retry |
|---|---|---|
| Main objective | Correct an existing output problem | Attempt the operation again |
| Typical trigger | Formatting or schema violation | Temporary provider or network failure |
| Input | Often includes validation errors | Often repeats an operation or creates a new generation |
| Important consideration | Validate the repaired result | Ensure the retry is appropriate and safe |

The terms are not mutually exclusive. A system may repair an output, validate it and perform a bounded fresh generation if the repair fails.

### Combined strategy

```text
Request
   ↓
Generate response
   ↓
Parse and validate
   ├── Valid → Use result
   └── Invalid
        ↓
      Repair
        ↓
      Validate again
        ├── Valid → Use result
        └── Invalid → Bounded regeneration
                         ↓
                    Validate again
                         ↓
                    Accept or fail safely
```

### Key takeaway

Classify failures before responding. Repair schema problems, retry suitable transient failures and stop after a bounded number of attempts.

## 11. Schema Validation vs. Business Validation

This distinction is especially important in production systems.

### Schema validation

**Schema validation** checks the structure and basic constraints of the data.

For example:

```text
name  → string
score → number
passed → boolean
```

It can also check required fields, allowed values and supported value constraints.

### Business validation

**Business validation** checks whether the data makes sense according to the application's domain rules.

Examples:

```text
score must be between 0 and 100

correct_option must reference an existing option

start_date must be before end_date

user must be authorized to access this assessment
```

Some business rules can be expressed directly in a schema, but domain checks often require relationships, database lookups, application context or authorization logic.

### Comparison

| Feature | Schema validation | Business validation |
|---|---|---|
| Main purpose | Check data structure and declared constraints | Check application-specific correctness |
| Example | `score` must be numeric | `score` must not exceed 100 |
| Example | `correct_option` must be an integer | The referenced option must exist |
| Example | `name` must be a string | The user must be allowed to access the record |
| Typical location | Schema or data-validation layer | Application or domain logic |

### Example: Assessment question

Consider an AI-generated multiple-choice question.

```json
{
  "question": "What is HTTP?",
  "type": "mcq_single",
  "options": [
    "A protocol",
    "A database",
    "A programming language",
    "An operating system"
  ],
  "correct_option": 8,
  "difficulty": "easy"
}
```

This is valid JSON.

A schema might verify that:

- `question` is a string.
- `type` is an allowed value.
- `options` is an array of strings.
- `correct_option` is an integer.
- `difficulty` is an allowed value.

However, `correct_option: 8` is invalid if the list contains only four options indexed from 0 to 3.

The application must also check that the selected index refers to an actual option.

### Complete validation pipeline

```text
AI Response
     ↓
Parse
     ↓
Schema Validation
     ↓
Business Validation
     ↓
Authorization where relevant
     ↓
Database / Application
```

### Important distinction

A response can be perfectly valid JSON and still contain incorrect facts, an incorrect answer or an unauthorized operation.

Schema validation establishes structural compliance; it does not establish universal factual truth.

### Key takeaway

**Validate structure first, then verify application-specific rules before trusting or storing the data.**

## 12. Real-World Case Study: AI Assessment Generator

Suppose you are developing an AI assessment generator for a Learning Management System.

The AI must generate a question, its options, the correct answer and the difficulty level.

### Define the required output

```json
{
  "question": "What is HTTP?",
  "type": "mcq_single",
  "options": [
    "A protocol",
    "A database",
    "A programming language",
    "An operating system"
  ],
  "correct_option": 0,
  "difficulty": "easy"
}
```

### Step 1 — Define the schema

The application expects:

| Field | Required type or constraint |
|---|---|
| `question` | Non-empty string |
| `type` | Allowed assessment-type value |
| `options` | Array of strings |
| `correct_option` | Integer |
| `difficulty` | Allowed difficulty value |

Other requirements, such as a minimum option count, can also be defined.

### Step 2 — Generate the response

The model receives the task, source material and required schema.

Where supported, use a schema-constrained structured-output API rather than depending solely on the instruction "return JSON."

### Step 3 — Parse the output

The application converts the raw response into a JSON object.

If the output is malformed, parsing fails before the business logic should use it.

### Step 4 — Validate the schema

Check whether:

- All required fields are present.
- The question is a string.
- The options are an array of strings.
- The correct answer index is an integer.
- The difficulty is an allowed value.

### Step 5 — Validate business rules

Check additional domain rules such as:

- The question is not empty.
- The options meet the required count.
- The correct answer index refers to an existing option.
- The correct answer is actually correct.
- The question satisfies the intended assessment type.
- The generated question is sufficiently grounded in the relevant course material.

These checks are not all guaranteed by a basic JSON schema.

### Step 6 — Repair if appropriate

Suppose the model returns:

```json
{
  "question": "What is HTTP?",
  "type": "mcq_single",
  "options": [
    "A protocol",
    "A database",
    "A programming language",
    "An operating system"
  ],
  "correct_option": "0",
  "difficulty": "easy"
}
```

The response parses, but `correct_option` is a string instead of an integer.

The system can attempt a bounded repair and then validate the corrected result again.

### Step 7 — Store validated data

```text
AI Model
   ↓
Raw Response
   ↓
Parse JSON
   ↓
Schema Validation
   ↓
Business Validation
   ↓
Accept?
  ├── Yes → Save to database
  └── No  → Repair / Regenerate / Reject
```

### Step 8 — Monitor quality

Track:

- JSON parse failures.
- Schema violations.
- Business-rule failures.
- Repair success rate.
- Retry count.
- Cost per accepted question.
- Question correctness.
- Duplicate or low-quality questions.

### Main lesson

An AI assessment generator should not save model output directly to the database. It should parse, validate and check application-specific rules before accepting a question.

## 15. Practice and Interview Questions

### Question-and-Answer Recall

**Question 1: What is a response contract?**

**Answer:** A response contract defines the structure, data types and rules that an AI response is expected to satisfy.

**Question 2: What is structured output?**

**Answer:** Structured output is a machine-readable response that follows a predefined structure, such as JSON matching a schema.

**Question 3: What is JSON Schema?**

**Answer:** JSON Schema is a standard for describing and validating JSON structures, field types, required properties and other constraints.

**Question 4: What is Pydantic?**

**Answer:** Pydantic is a Python library used to define data models, parse input and validate data against declared types and constraints.

**Question 5: What is the difference between JSON Schema and Pydantic?**

**Answer:** JSON Schema is a language-independent schema format, while Pydantic provides Python data models and validation. A Pydantic model can generate JSON Schema, allowing both to work together.

**Question 6: What is a function/tool schema?**

**Answer:** A function/tool schema describes the arguments expected when a model requests the execution of an external function or tool.

**Question 7: What is schema evolution?**

**Answer:** Schema evolution is the controlled process of changing a data contract while maintaining compatibility with systems that consume it.

**Question 8: What is the difference between parsing and validation?**

**Answer:** Parsing converts raw output into a data structure. Validation checks whether that structure satisfies the expected contract.

**Question 9: What is a repair loop?**

**Answer:** A repair loop attempts to correct invalid output and validates the corrected response again, typically with a maximum number of attempts.

**Question 10: What is the difference between repair and retry?**

**Answer:** Repair attempts to correct an existing output problem, whereas retry attempts the operation again or requests a new generation. The appropriate approach depends on the failure type.

**Question 11: Why are bounded retries important?**

**Answer:** Bounded retries prevent endless attempts that increase cost, latency and resource consumption without guaranteeing success.

**Question 12: What is the difference between schema validation and business validation?**

**Answer:** Schema validation checks data structure and declared constraints. Business validation checks whether the data satisfies application-specific rules, such as whether a correct-answer index refers to an existing option.

#### Hard — Scenario-Based

**Question 19: An AI assessment generator returns `correct_option: 8`, but the generated question contains only four options. The field is correctly typed as an integer. Is the result valid?**

**Answer:** It may pass a basic type check, but it fails business validation because the index does not refer to an existing option. The application should reject or repair the result before storing it.

**Question 20: A model returns a string instead of a number in a score field. The JSON is syntactically valid. What should happen next?**

**Answer:** Parsing succeeds, but schema validation fails. The application can attempt a bounded repair or fresh generation, then validate the result again. It should return a controlled failure if the problem persists.

**Question 21: A new response schema adds a required field, and the old frontend cannot handle it. How should the team manage this change?**

**Answer:** The team should assess compatibility with existing consumers, consider introducing the field as optional first, or create a new version of the contract if the change is breaking. Both backend and frontend should be tested before deployment, with a migration plan where necessary.

**Question 22: An AI response is valid JSON and satisfies its schema, but contains a fabricated invoice total. Will schema validation detect this?**

**Answer:** Not necessarily. Schema validation checks structure and defined constraints, not general factual truth. The application needs additional checks, such as calculating totals from line items, comparing against source documents or using other suitable verification mechanisms.

**Question 23: Your application keeps requesting repairs until the model eventually returns valid JSON. What is the risk, and how should this be corrected?**

**Answer:** An unbounded repair loop can create excessive latency, API costs and resource consumption. Set a maximum number of repair or generation attempts, log persistent failures, and return a controlled error when the retry budget is exhausted.

**Question 24: How would you design reliable structured output for an AI-powered assessment generator?**

**Answer:** I would define a schema for fields, types and allowed values, use a structured-output API where supported, parse the returned result, validate it using JSON Schema or Pydantic, and apply business rules such as verifying the correct-answer index and option count. Invalid outputs would receive bounded repair attempts, and only validated results would be saved to the database.

### Interview Questions

**Question 25: Why is structured output preferable to simply instructing an LLM to return JSON?**

**Answer:** A natural-language instruction alone does not guarantee the required structure. A supported structured-output API can constrain generation more strongly, while application-side validation verifies that the result satisfies the contract.

**Question 26: How would you distinguish a parsing failure from a validation failure?**

**Answer:** A parsing failure occurs when raw output cannot be converted into the expected data structure, such as malformed JSON. A validation failure occurs when parsing succeeds but the resulting data violates the schema, such as using a string where an integer is required.

**Question 27: How would you decide whether to repair an invalid response or retry the request?**

**Answer:** I would classify the failure. Small formatting or schema violations may be repairable, while transient network or provider failures may justify a retry. Permanent failures require correction, and every repair or retry should be bounded and followed by the appropriate validation.

**Question 28: How do schema contracts improve production reliability?**

**Answer:** They establish explicit expectations for response structure and constraints. Combined with parsing, schema validation, business validation and controlled failure handling, they prevent malformed or invalid AI outputs from silently entering downstream processing.

## Final Summary

Response contracts and validation make AI outputs safer and more predictable for software applications.

- **Schemas** define the expected data structure.
- **JSON Schema** provides a standard way to describe JSON contracts.
- **Pydantic** validates data models in Python.
- **Tool schemas** constrain function-call arguments.
- **Structured Output APIs** help enforce response structure.
- **Parsing** converts raw output into data.
- **Schema validation** checks structural requirements.
- **Business validation** checks application-specific correctness.
- **Repair loops and retries** handle failures with bounded attempts.
- **Schema evolution** keeps changes compatible with downstream systems.

The central principle is:

> **Never pass AI-generated data directly into critical application logic without the parsing, validation and business checks required by the use case.**
