# 1. M05.2 Response Contracts and Validation

## Simple Definition

A **response contract** defines what an AI response is expected to look like.

**Validation** checks whether the actual response satisfies that contract.

Instead of accepting arbitrary model text:

```text
"John is 25 and lives in Mumbai."
```

an application may require:

```json
{
  "name": "John",
  "age": 25,
  "city": "Mumbai"
}
```

The overall idea is:

```text
AI Model
   ↓
Generated Output
   ↓
Parse
   ↓
Validate Against Schema
   ↓
Valid?
 ┌─┴──────────────┐
 Yes              No
 ↓                 ↓
Use Result      Repair / Retry / Reject
```

---

## Why Response Contracts Matter

LLMs generate probabilistic output. Software systems usually require **predictable, typed data**.

For example, your backend may expect:

```text
user_id → string
score   → number
passed  → boolean
```

If the model returns:

```text
score = "ninety"
```

your application may fail or behave incorrectly.

A response contract provides a boundary:

```text
           AI World
              │
       Unstructured /
       probabilistic
              │
              ↓
      Response Contract
              │
              ↓
        Validated Data
              │
           Software
```

### Core principle

> **Never assume that because an AI response looks correct to a human, it is automatically safe for software to consume.**

# 1.1 M05.2.1 Structured Outputs

## Definition

**Structured output** means asking the model to return information in a predefined machine-readable structure.

Common formats include:

- JSON
- JSON matching a schema
- Tool/function-call arguments
- Structured objects

### Unstructured

```text
The customer is unhappy because the delivery was late.
```

### Structured

```json
{
  "sentiment": "negative",
  "issue": "late delivery"
}
```

The second result is much easier for application code to process.

# 1.1.1 Schema Contracts

## What is a Schema?

A **schema** is a formal description of the structure and rules that valid data must follow.

For example:

```text
Customer
 ├── name     → string, required
 ├── age      → integer, required
 └── email    → string, optional
```

A schema can define:

- Field names
- Data types
- Required fields
- Optional fields
- Allowed values
- Nested objects
- Arrays
- Minimum/maximum values
- String patterns
- Additional constraints

### Contract idea

```text
Expected:
{
  "name": string,
  "age": integer
}

Actual:
{
  "name": "Shubham",
  "age": 25
}

→ VALID
```

---

# JSON Schema

## Definition

**JSON Schema** is a standard way to describe and validate the structure of JSON data.

Example:

```json
{
  "type": "object",
  "properties": {
    "name": {
      "type": "string"
    },
    "age": {
      "type": "integer",
      "minimum": 0
    }
  },
  "required": ["name", "age"]
}
```

This schema says:

- The response must be an object.
- `name` must be a string.
- `age` must be an integer.
- `age` cannot be negative.
- Both fields are required.

### Valid response

```json
{
  "name": "Rahul",
  "age": 30
}
```

### Invalid response

```json
{
  "name": "Rahul",
  "age": "thirty"
}
```

because `"thirty"` is a string, not an integer.

---

## Why JSON Schema Is Useful

It provides a common, machine-readable contract.

```text
Schema
   ↓
Provider / Model
   ↓
JSON Response
   ↓
JSON Schema Validator
   ↓
Valid / Invalid
```

This is particularly useful when AI output is passed to:

- Databases
- APIs
- Frontend applications
- Workflow engines
- Other AI agents
- Business logic

---

# Pydantic Validation

## Definition

**Pydantic** is a Python library commonly used to define data models and validate Python data.

It is especially useful with Python backends such as **FastAPI**.

Example:

```python
from pydantic import BaseModel

class Customer(BaseModel):
    name: str
    age: int
```

Now the application expects:

```text
Customer
├── name → str
└── age  → int
```

### Valid data

```python
{
    "name": "Rahul",
    "age": 30
}
```

### Invalid data

```python
{
    "name": "Rahul",
    "age": "hello"
}
```

Pydantic validates the incoming data and raises a validation error when the data does not satisfy the model.

---

## Pydantic + AI

A useful architecture is:

```text
AI Model
   ↓
JSON
   ↓
Parse
   ↓
Pydantic Model
   ↓
Validation
   ↓
Business Logic
```

Example:

```python
class AssessmentResult(BaseModel):
    score: float
    passed: bool
    feedback: str
```

The AI might return:

```json
{
  "score": 82.5,
  "passed": true,
  "feedback": "Strong performance."
}
```

Your backend converts that into a validated `AssessmentResult`.

---

## Why Pydantic Is Valuable

It gives Python applications:

- Type validation
- Required/optional field rules
- Nested models
- Value constraints
- Automatic parsing in many cases
- Clear validation errors

### Important distinction

**JSON Schema** describes the contract in a standard schema language.

**Pydantic** defines and validates data models in Python.

They can work together rather than being alternatives.

```text
Pydantic Model
      ↓
JSON Schema
      ↓
AI Structured Output
      ↓
Pydantic Validation
```

# Function / Tool Schemas

## Definition

AI models can sometimes invoke **functions/tools** rather than simply returning text.

A tool schema tells the model:

> "Here is a tool, these are its arguments, and these arguments must follow this structure."

Example:

```text
Tool: get_weather

Arguments:
{
  "city": string,
  "unit": "C" | "F"
}
```

The AI might produce a tool call such as:

```json
{
  "city": "Mumbai",
  "unit": "C"
}
```

Your application receives the structured arguments and calls the actual function:

```text
Model
 ↓
Tool Call
 ↓
Validate Arguments
 ↓
Execute Tool
 ↓
Tool Result
 ↓
Model
```

---

## Why Tool Schemas Matter

Without a schema, the model could produce:

```text
"Please get the weather for Mumbai in Celsius."
```

The application would need to extract the city and unit itself.

With a schema:

```json
{
  "city": "Mumbai",
  "unit": "C"
}
```

the application can directly validate and process the arguments.

---

# Function Schema vs Response Schema

These are related but different.

| Feature | Response Schema | Function/Tool Schema |
|---|---|---|
| Purpose | Defines final model output | Defines tool arguments |
| Example | `{score, passed}` | `{city, unit}` |
| Used for | Structured result | Tool invocation |
| Main consumer | Application | Tool/function |
| Validation | Before business logic | Before tool execution |

### Example

```text
User
 ↓
Model
 ├── Structured final response
 │       ↓
 │   Application
 │
 └── Tool call
         ↓
      Validate
         ↓
      Execute tool
```

---

# Schema Evolution

## Definition

**Schema evolution** means changing a schema over time while keeping the system reliable.

Suppose version 1 is:

```json
{
  "name": "John",
  "age": 30
}
```

Later, you add:

```json
{
  "name": "John",
  "age": 30,
  "city": "Mumbai"
}
```

Now your schema has evolved.

---

## Why Schema Evolution Is Difficult

AI systems often have multiple moving parts:

```text
Prompt
 ↓
Model
 ↓
Schema
 ↓
Backend
 ↓
Database
 ↓
Frontend
```

Changing one field may affect several components.

For example:

```text
schema:
score → number

database:
score → numeric

frontend:
score.toFixed(2)
```

If you change `score` to a string, multiple parts can break.

---

## Backward-Compatible Changes

Usually safer:

```text
v1:
{
  "name": string
}
```

Change to:

```text
v2:
{
  "name": string,
  "city": string (optional)
}
```

Older consumers can often continue working because they can ignore the new optional field.

### Riskier change

```text
v1:
age → integer
```

becomes:

```text
v2:
age → string
```

Existing consumers may break.

---

## Safe Schema Evolution

```text
Current Schema
      ↓
Design New Version
      ↓
Check Consumers
      ↓
Compatibility Test
      ↓
Deploy
      ↓
Monitor
      ↓
Deprecate Old Version
```

### Good practices

- Prefer additive changes where possible.
- Make newly added fields optional initially when appropriate.
- Version breaking changes.
- Test old and new consumers.
- Keep migration plans for stored data.
- Do not change field semantics silently.

# 1.1.2 Output Handling

## Structured Output APIs

Many modern AI APIs provide features specifically designed to constrain model responses to a defined structure.

Conceptually:

```text
Prompt
 +
Output Schema
       ↓
Structured Output API
       ↓
Model
       ↓
Schema-Conforming Output
```

This is preferable to simply saying:

> "Please return valid JSON."

because a natural-language instruction alone does not necessarily guarantee schema compliance.

### Important distinction

```text
"Return JSON"
       ↓
Formatting instruction

Schema-constrained output
       ↓
Structural contract
```

A production system should use provider-supported structured-output mechanisms when available and still validate the returned data at the application boundary.

---

# Parse Validation

## Definition

**Parsing** and **validation** are separate operations.

### Parsing

Converts raw model output into a data structure.

Example:

```text
Raw text
  ↓
JSON parser
  ↓
Python/JavaScript object
```

### Validation

Checks whether that parsed object satisfies the expected contract.

```text
Parsed object
      ↓
Schema validator
      ↓
Valid / Invalid
```

---

## Example

Model returns:

```json
{
  "score": 90,
  "passed": true
}
```

### Step 1 — Parse

```text
JSON string
   ↓
Object
```

### Step 2 — Validate

Check:

```text
score → number?
passed → boolean?
required fields present?
score within allowed range?
```

### Step 3 — Accept

```text
Valid
 ↓
Business Logic
```

---

# Parsing Failure vs Validation Failure

These are different problems.

### Parsing failure

The output isn't valid JSON at all:

```text
{
  "name": "John"
```

Missing closing `}`.

```text
Parse
 ↓
FAIL
```

### Validation failure

The JSON is valid, but doesn't satisfy the schema:

```json
{
  "name": "John",
  "age": "unknown"
}
```

The JSON parses correctly, but `age` violates an integer requirement.

```text
Parse
 ↓
Success
 ↓
Schema Validation
 ↓
FAIL
```

### Memory trick

```text
Parsing    = "Can I read it?"
Validation = "Does it follow the rules?"
```

# Repair Loops

## Definition

A **repair loop** attempts to fix an invalid AI response instead of immediately abandoning the operation.

### Basic flow

```text
Model
 ↓
Output
 ↓
Parse + Validate
 ↓
Valid?
 ├── Yes → Continue
 └── No
      ↓
   Repair
      ↓
   Validate again
      ↓
   Valid?
```

---

## Example

Expected:

```json
{
  "score": 0-100,
  "passed": true/false
}
```

AI returns:

```json
{
  "score": "85",
  "passed": "yes"
}
```

A repair process could send the validation error back to the model:

```text
Your previous output failed validation.

Problems:
- score must be a number.
- passed must be a boolean.

Return the corrected object only.
```

The model may then produce:

```json
{
  "score": 85,
  "passed": true
}
```

---

## Repair Loop Architecture

```text
                    ┌──────────────┐
                    │   AI Model   │
                    └──────┬───────┘
                           ↓
                       Raw Output
                           ↓
                    Parse + Validate
                           ↓
                      ┌────┴────┐
                      │ Valid?  │
                      └────┬────┘
                       Yes │ No
                           │
                  ┌────────┘
                  ↓
             Repair Prompt
                  ↓
              AI Model
                  ↓
             Validate Again
```

---

## When Repair Makes Sense

Repair is useful when:

- The underlying answer is mostly correct.
- Only formatting is wrong.
- A small number of fields violate constraints.
- The model can reasonably correct the problem.

### Example

```text
Correct information
+
Wrong formatting
→ Repair is reasonable
```

But:

```text
Completely wrong reasoning
+
Wrong facts
→ Simple repair may not be enough
```

The system may need a fresh generation or a different strategy.

# Retry Strategies

## Definition

A **retry strategy** determines what the application does when an AI request fails.

Not every failure should be handled in the same way.

---

## Retry Decision

```text
Request
  ↓
Failure
  ↓
What type?
 ┌──────────────┼───────────────┐
 ↓              ↓               ↓
Transient      Validation      Permanent
 ↓              ↓               ↓
Retry          Repair/Retry    Fail gracefully
```

---

## Transient Failures

Examples:

- Temporary provider outage
- Network timeout
- Temporary overload
- Rate limiting

These may justify retries.

### Exponential backoff

```text
Attempt 1 → wait 1 sec
Attempt 2 → wait 2 sec
Attempt 3 → wait 4 sec
Attempt 4 → stop
```

Add jitter when appropriate.

---

## Validation Failures

Suppose:

```text
API request succeeded
      ↓
Response received
      ↓
Schema validation failed
```

A suitable strategy might be:

```text
Invalid Output
     ↓
Repair
     ↓
Validate
     ↓
Still Invalid?
     ↓
Fresh Generation / Retry
```

---

## Permanent Failures

For errors such as an invalid API key or invalid request:

```text
Retry
Retry
Retry
```

does not solve the root cause.

Instead:

```text
Detect
 ↓
Log
 ↓
Correct Configuration / Request
```

---

# Bounded Retries

Never create:

```text
while(response_invalid) {
    retry();
}
```

That can create an infinite loop.

Instead:

```text
Maximum attempts = 3
```

Example:

```text
Attempt 1
   ↓
Invalid
   ↓
Repair
   ↓
Attempt 2
   ↓
Invalid
   ↓
Retry
   ↓
Attempt 3
   ↓
Invalid
   ↓
Return controlled error
```

---

# Repair vs Retry

These are not exactly the same.

| Repair | Retry |
|---|---|
| Attempts to correct the existing output | Generates another response/request |
| Often uses validation errors | Often responds to transient failures |
| Useful for formatting/schema problems | Useful for temporary API/network issues |
| Usually preserves the original task | May generate a fresh result |

### Combined strategy

```text
Request
  ↓
Generate
  ↓
Validate
 ┌┴──────────────┐
Valid            Invalid
 ↓                  ↓
Use             Repair
                   ↓
                Validate
                ┌──┴───┐
               Valid  Invalid
                 ↓       ↓
                Use    Retry/Fresh
```

# Real-World Example: AI Assessment Generator

Suppose an AI model generates an assessment question.

Your application expects:

```json
{
  "question": "What is HTTP?",
  "type": "mcq_single",
  "options": [
    "A protocol",
    "A database",
    "A programming language",
    "An operating system"
  ],
  "correct_option": 0,
  "difficulty": "easy"
}
```

You could define a schema:

```text
question        → string
type            → allowed enum
options         → array of strings
correct_option  → integer
difficulty      → allowed enum
```

### Pipeline

```text
AI
 ↓
Generate Question
 ↓
Parse JSON
 ↓
Validate Schema
 ↓
Validate Business Rules
 ↓
Save to Database
```

Notice there are potentially **two levels of validation**.

### Schema validation

Checks:

```text
correct_option → integer
```

### Business validation

Checks:

```text
correct_option < number of options
```

The second condition may not be captured by a simple field type alone.

---

# Schema Validation vs Business Validation

This distinction is extremely important.

### Schema validation

Checks the **shape and basic constraints**.

```text
score → number
name  → string
```

### Business validation

Checks whether the data makes sense for your application.

```text
score must be between 0 and 100

correct_option must refer to an existing option

start_date must be before end_date
```

### Architecture

```text
AI Response
    ↓
Parse
    ↓
Schema Validation
    ↓
Business Validation
    ↓
Database / Application
```

A valid schema does **not automatically mean valid business data**.

---

# Common Mistakes

### 1. Trusting AI output without validation

```text
AI → Database
```

is risky.

Prefer:

```text
AI
 ↓
Parse
 ↓
Schema Validation
 ↓
Business Validation
 ↓
Database
```

### 2. Using "return JSON" as the only control

It is an instruction, not necessarily a complete validation mechanism.

### 3. Confusing parsing and validation

```text
Parse = understand structure
Validate = check correctness against contract
```

### 4. Infinite repair loops

Always use a maximum number of attempts.

### 5. Retrying permanent errors

An invalid API key will not become valid because you retry five times.

### 6. Changing schemas without considering consumers

Schema changes can affect:

```text
AI
 ↓
Backend
 ↓
Database
 ↓
Frontend
```

### 7. Assuming schema validation guarantees correct information

A response can be perfectly valid JSON and still contain incorrect facts.

```json
{
  "age": 35
}
```

may satisfy the schema even if the person's actual age is 29.

Schema validation guarantees **structure**, not general factual truth.

---

# Key Takeaways

- A **response contract** defines the structure and rules expected from AI output.
- **Structured outputs** make AI responses easier and safer for software to consume.
- **JSON Schema** provides a standard way to describe JSON structure and constraints.
- **Pydantic** provides Python data modeling and validation and works especially well with Python/FastAPI applications.
- **Function/tool schemas** define the arguments the model can provide when invoking application tools.
- **Schema evolution** is the controlled modification of contracts over time.
- **Parsing** asks: "Can I convert this output into data?"
- **Validation** asks: "Does the data satisfy the contract?"
- **Repair loops** attempt to correct outputs that are close to valid.
- **Retries** are appropriate for retryable failures such as transient network/provider problems.
- Use **bounded retries** to prevent loops and uncontrolled API costs.
- Schema validation checks structure; **business validation checks application-specific correctness**.

### High-value interview questions

**Q1. Why is structured output preferable to asking an LLM to "return JSON"?**  
Because structured-output mechanisms can enforce a defined response structure more reliably, while a natural-language request alone does not guarantee compliance. Application-side validation should still be performed.

**Q2. What is the difference between parsing and validation?**  
Parsing converts raw output into a data structure; validation checks whether that structure satisfies the expected schema and constraints.

**Q3. What is a repair loop?**  
A repair loop feeds validation errors back into the model or transformation process so an invalid response can be corrected and validated again.

**Q4. What is the difference between schema validation and business validation?**  
Schema validation checks structural rules such as types and required fields. Business validation checks domain rules such as valid score ranges or whether a referenced option actually exists.

**Q5. Why is schema evolution important?**  
Because changing a response contract can break downstream consumers such as APIs, databases and frontends. Changes should therefore be designed and tested for compatibility.

**Q6. Should every invalid AI response trigger a retry?**  
No. First determine whether the problem is repairable, retryable, or permanent. Use bounded retries and appropriate backoff rather than repeatedly making the same request.
