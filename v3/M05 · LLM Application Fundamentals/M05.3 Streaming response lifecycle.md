# 1. M05.3 Streaming Response Lifecycle

## Simple Definition

**Streaming** means sending data to the client **incrementally as it becomes available**, rather than waiting for the complete result and sending everything at once.

### Non-streaming

```text
User Request
     ↓
Server processes everything
     ↓
Complete response
     ↓
Client receives response
```

The user may wait several seconds before seeing anything.

### Streaming

```text
User Request
     ↓
Server starts processing
     ↓
Chunk 1 ──→ Client
Chunk 2 ──→ Client
Chunk 3 ──→ Client
Chunk 4 ──→ Client
...
Final event ──→ Client
```

For AI applications, streaming is especially useful because the model can begin returning text before the entire answer has been generated.

---

## Why Streaming Matters

Streaming improves the **perceived responsiveness** of an application.

Without streaming:

```text
Request ─────────────────────────→ Complete Response
            user sees nothing
```

With streaming:

```text
Request ──→ "Hello"
          ──→ "Hello, here"
          ──→ "Hello, here is"
          ──→ "Hello, here is your answer..."
```

The total generation time may not change much, but the user gets feedback immediately.

### Common uses

- AI chat
- Live transcription
- Progress updates
- Long-running jobs
- Real-time dashboards
- Notifications
- Collaborative applications
- Streaming logs

# 1.1.1 SSE — Server-Sent Events

## Definition

**SSE (Server-Sent Events)** is a mechanism where a server maintains an HTTP connection and continuously sends events to a client.

The important direction is:

```text
Server ─────────→ Client
```

It is primarily **one-way communication**.

### Basic Flow

```text
Client
  │
  │ HTTP request
  ↓
Server
  │
  ├── event 1 ──→ Client
  ├── event 2 ──→ Client
  ├── event 3 ──→ Client
  └── event 4 ──→ Client
```

The client generally starts the connection, but the server continuously sends updates over it.

---

## SSE Message Structure

An SSE stream is composed of events. Conceptually:

```text
event: message
data: Hello

event: message
data: World
```

A blank line separates events.

Possible fields include:

- `event`
- `data`
- `id`
- `retry`

### Example

```text
event: token
data: Hello

event: token
data: world

event: done
data: {}
```

The application can interpret these events differently.

---

## SSE Characteristics

| Property | SSE |
|---|---|
| Direction | Server → Client |
| Underlying mechanism | HTTP |
| Best for | Server updates / streams |
| Browser support | Strong for standard SSE clients |
| Automatic reconnection support | Built into common SSE client behavior |
| Client-to-server messaging | Separate HTTP request normally required |

### Good use cases

SSE works well when the client primarily needs to **listen**:

```text
AI token stream
Job progress
Live notifications
Server logs
Status updates
```

---

# 1.1.2 WebSockets

## Definition

**WebSockets** provide a persistent, two-way communication channel between client and server.

Unlike SSE:

```text
Client ←────────→ Server
```

Both sides can send messages whenever needed.

### Connection Flow

```text
Client
   ↓
Connection request
   ↓
WebSocket connection
   ↕
Messages in both directions
   ↕
Connection remains open
```

---

## Example

Imagine a collaborative application:

```text
User A
   ↕
Server
   ↕
User B
```

Both clients can send updates and receive updates over persistent connections.

---

## WebSocket Characteristics

| Property | WebSocket |
|---|---|
| Direction | Bidirectional |
| Connection | Persistent |
| Common transport model | Full-duplex communication |
| Good for | Real-time interactive systems |
| Client → Server | Native |
| Server → Client | Native |

### Good use cases

- Chat applications
- Multiplayer games
- Collaborative editing
- Trading/market interfaces
- Real-time control systems
- Bidirectional AI applications
- Presence indicators

---

# SSE vs WebSockets

This is an important comparison.

| Feature | SSE | WebSockets |
|---|---|---|
| Communication | Server → Client | Client ↔ Server |
| Transport style | HTTP streaming | Persistent WebSocket connection |
| Simplicity | Simpler for server streams | More complex |
| Client-to-server messages | Usually separate HTTP calls | Built in |
| Ideal for | AI token streams, notifications | Interactive real-time systems |
| Automatic reconnection | Commonly supported | Must usually be implemented by application |
| Event-oriented streaming | Natural fit | Possible |

### Easy memory trick

```text
SSE        → Server Sends Events
WebSocket  → Web = two-way conversation
```

# 1.1.3 Streaming Text

## Definition

**Streaming text** means sending generated text incrementally instead of waiting for the complete text.

For an AI chatbot:

```text
Model generates:
"React is a JavaScript library..."
```

The application might receive:

```text
"React"
"React is"
"React is a"
"React is a JavaScript"
"React is a JavaScript library..."
```

The exact chunk boundaries depend on the API and transport.

---

## Streaming Text Flow

```text
User
 ↓
AI Request
 ↓
Model generation starts
 ↓
Text chunk 1
 ↓
Text chunk 2
 ↓
Text chunk 3
 ↓
...
Final chunk
 ↓
Completion event
```

The frontend usually maintains an accumulator:

```text
currentText = ""

chunk 1 → currentText += chunk 1
chunk 2 → currentText += chunk 2
chunk 3 → currentText += chunk 3
```

Result:

```text
Complete response
```

---

## Why Not Just Wait for the Final Answer?

Because the user experience is different.

### Non-streaming

```text
[Loading....................]
[Complete answer appears]
```

### Streaming

```text
[Generating...]
Hello
Hello, here
Hello, here is your
Hello, here is your answer
```

The second approach feels much more responsive.

---

## Important Streaming Text Considerations

A client must correctly handle:

- Chunk ordering
- Partial words
- UTF-8 boundaries
- Completion events
- Errors
- Cancellation

You should not assume that every chunk is a complete word or sentence.

# 1.1.4 Streaming Structured Events

Streaming is not limited to text.

An application can stream **typed events**.

For example:

```json
{"type":"start"}
```

```json
{"type":"text","delta":"Hello"}
```

```json
{"type":"text","delta":" world"}
```

```json
{"type":"tool_start","tool":"search"}
```

```json
{"type":"tool_result","status":"success"}
```

```json
{"type":"done"}
```

Now the client is receiving an **event stream**, not simply a stream of text.

---

## Why Structured Events Are Better for Complex Systems

Consider an AI agent.

It might perform:

```text
Think
 ↓
Call search tool
 ↓
Receive results
 ↓
Generate answer
```

If you stream only raw text, the UI cannot easily distinguish these phases.

Structured events allow:

```text
Event: thinking
Event: tool_start
Event: tool_result
Event: text
Event: progress
Event: done
```

The frontend can then render different UI states.

---

## Example Event Model

```text
┌─────────────────────────────┐
│ type: "text"                │
│ delta: "Hello"              │
└─────────────────────────────┘

┌─────────────────────────────┐
│ type: "progress"            │
│ percent: 50                 │
└─────────────────────────────┘

┌─────────────────────────────┐
│ type: "tool_start"          │
│ tool: "weather"             │
└─────────────────────────────┘

┌─────────────────────────────┐
│ type: "done"                │
└─────────────────────────────┘
```

# 1.1.5 Progress Events

## Definition

A **progress event** tells the client how far a long-running operation has progressed.

For example:

```json
{
  "type": "progress",
  "percent": 40,
  "message": "Processing documents"
}
```

---

## Typical Progress Flow

```text
Start
 ↓
10% → Loading
 ↓
30% → Parsing
 ↓
50% → Processing
 ↓
80% → Generating
 ↓
100% → Complete
```

### Important distinction

**Streaming output** and **progress events** are not the same thing.

### Streaming output

Tells you:

> "Here is some of the result."

### Progress event

Tells you:

> "Here is the current state of the operation."

---

## Why Progress Events Matter

For long operations they provide:

- User feedback
- Perceived responsiveness
- Visibility into current state
- Better debugging
- Better cancellation experience

For example:

```text
Analyzing 500 documents...

[██████████░░░░░░░░░░] 50%
```

# 1.1.6 Backpressure

## Definition

**Backpressure** occurs when the producer generates data faster than the consumer can process it.

This is a fundamental streaming concept.

### Example

Suppose:

```text
Server produces → 1,000 events/sec
Client processes → 100 events/sec
```

The client cannot keep up.

```text
Producer
   ↓
████████████████  Fast
        ↓
     Consumer
        ↓
      Slow
```

The unprocessed data may accumulate in buffers or queues.

---

## Why Backpressure Matters

Without proper handling, excessive buffering can cause:

- Memory growth
- Increased latency
- Slow UI
- Resource exhaustion
- Dropped messages

---

## Backpressure Strategies

Possible strategies include:

### 1. Slow the producer

```text
Producer detects congestion
        ↓
Reduce sending rate
```

### 2. Buffer

```text
Producer
   ↓
Queue
   ↓
Consumer
```

Useful when temporary bursts are expected.

### 3. Drop non-critical data

For some systems, old progress updates may no longer matter.

For example:

```text
10%
20%
30%
40%
```

If the client is behind, showing only the latest progress might be sufficient.

### 4. Batch messages

Instead of:

```text
event 1
event 2
event 3
event 4
```

send:

```text
[ event 1, event 2, event 3, event 4 ]
```

when appropriate.

---

## AI-Specific Example

Suppose a model produces tokens quickly while the browser is rendering slowly.

```text
AI Provider
    ↓
token token token token token
    ↓
Backend buffer
    ↓
Browser
```

The backend and frontend need mechanisms that prevent uncontrolled queue growth.

---

# 1.1.7 Disconnect Handling

## Definition

A **disconnect** occurs when the streaming connection is unexpectedly closed.

Possible reasons:

- User closes the browser
- Network disappears
- Laptop changes networks
- Mobile connection changes
- Server crashes
- Proxy/load balancer closes connection
- Idle timeout
- Application intentionally cancels the request

---

## Disconnect Lifecycle

```text
Streaming
   ↓
Connection lost
   ↓
Detect disconnect
   ↓
Determine state
   ↓
Cancel / Resume / Retry
```

The correct action depends on the type of stream.

---

## Important Question

When a client disconnects, should the server keep working?

### Example A — Interactive AI chat

Usually, continuing expensive generation after the user leaves may be wasteful.

```text
Client disconnects
       ↓
Cancel model generation
```

### Example B — Background report generation

The work may need to continue.

```text
Client disconnects
       ↓
Background job continues
       ↓
Result stored
       ↓
Client can retrieve it later
```

So disconnect handling depends on whether the operation is:

```text
Request-bound
or
Job-oriented
```

---

## Connection State

A robust stream can maintain states such as:

```text
CONNECTING
    ↓
OPEN
    ↓
STREAMING
    ↓
COMPLETED
```

or:

```text
STREAMING
    ↓
DISCONNECTED
    ↓
RECONNECTING
```

or:

```text
STREAMING
    ↓
FAILED
```

Explicit states make lifecycle management easier.

---

# 1.1.8 Reconnect Strategy

## Definition

A **reconnect strategy** determines what the client does after a connection is lost.

A naive approach is:

```text
Disconnect
 ↓
Immediately reconnect
 ↓
Immediately reconnect
 ↓
Immediately reconnect
```

This can create a **reconnection storm**.

---

## Exponential Backoff

A better strategy is:

```text
Disconnect
   ↓
Wait 1s
   ↓
Retry
   ↓
Wait 2s
   ↓
Retry
   ↓
Wait 4s
   ↓
Retry
```

Usually add **jitter** so many clients do not retry simultaneously.

---

## Reconnect Flow

```text
Connection
   ↓
Disconnected
   ↓
Attempt reconnect
   ↓
Success?
 ┌────┴────┐
Yes        No
 ↓          ↓
Resume    Backoff
             ↓
          Retry
```

---

## Resuming vs Restarting

A reconnecting client has two possible approaches.

### Restart

Start the operation from the beginning.

```text
Disconnect
 ↓
New request
 ↓
Generate again
```

Simple, but may cause:

- Duplicate work
- Duplicate cost
- Repeated output

### Resume

Continue from where the client stopped.

```text
Disconnect
 ↓
Reconnect
 ↓
Send last received event ID / sequence
 ↓
Server resumes from that point
```

This is more complex but useful for long-lived streams.

---

# Event IDs and Ordering

For reliable streaming, events can carry identifiers:

```text
event_id = 101
event_id = 102
event_id = 103
```

The client knows:

```text
Last received = 102
```

If it reconnects, it can potentially request:

```text
"Send events after 102."
```

This helps avoid missing events.

---

## Ordering

Suppose:

```text
Event 1
Event 2
Event 3
```

arrive as:

```text
Event 1
Event 3
Event 2
```

If order matters, the application needs:

- Sequence numbers
- Event IDs
- Ordering logic
- Buffering until missing events arrive

### Important principle

> **Streaming transport does not automatically solve application-level ordering and recovery requirements.**

# SSE vs WebSocket vs Streaming Events

| Concept | Meaning |
|---|---|
| **SSE** | HTTP-based server-to-client event stream |
| **WebSocket** | Persistent bidirectional communication |
| **Streaming text** | Text delivered incrementally |
| **Structured events** | Typed messages delivered incrementally |
| **Progress events** | Messages describing operation state/progress |

These are not necessarily competing concepts.

For example:

```text
SSE
 ↓
Structured Events
 ↓
Text Events + Progress Events + Tool Events
```

SSE is a **transport mechanism**, while "streaming text" and "progress events" describe **what is being streamed**.

# Common Mistakes

### 1. Treating SSE and WebSockets as the same thing

```text
SSE → primarily server → client
WebSocket → client ↔ server
```

### 2. Assuming every chunk is complete

A streamed chunk may contain only part of a word or message.

### 3. Treating streamed text as structured data

Raw text cannot automatically communicate events like:

```text
progress
tool_start
tool_result
done
```

Use structured events when the application needs multiple event types.

### 4. Ignoring backpressure

A producer may overwhelm a slow consumer.

### 5. Reconnecting immediately in a tight loop

This can overload your own backend and the provider.

Use bounded exponential backoff with jitter.

### 6. Not defining disconnect behavior

Decide whether disconnected clients should cause:

```text
Cancellation
or
Background continuation
```

### 7. Losing event position

For resumable streams, use sequence numbers/event IDs where appropriate.

### 8. No completion signal

The client should know when the stream has actually finished.

For example:

```text
type = "done"
```

### 9. Retrying a non-resumable operation blindly

Restarting an AI generation can duplicate work and increase cost.

# Key Takeaways

- **Streaming** delivers data incrementally instead of waiting for the complete result.
- **SSE** is primarily a server-to-client streaming mechanism over HTTP.
- **WebSockets** provide persistent bidirectional communication.
- **Streaming text** delivers generated text in chunks.
- **Structured events** allow different event types such as text, progress, tool calls and completion.
- **Progress events** communicate state or percentage rather than result content.
- **Backpressure** occurs when the producer is faster than the consumer.
- **Disconnect handling** defines what happens when the connection disappears.
- **Reconnect strategy** determines how the client recovers from connection loss.
- Use **exponential backoff and jitter** to avoid aggressive reconnect loops.
- Resumable streams may use **event IDs or sequence numbers**.
- A good streaming system explicitly handles **start, data, progress, completion, error, disconnect and reconnect states**.

## High-value interview questions

**Q1. What is the main difference between SSE and WebSockets?**  
SSE is primarily a server-to-client event stream over HTTP, while WebSockets provide persistent bidirectional communication.

**Q2. Why is streaming useful for AI applications?**  
It allows users to see generated content as it arrives, reducing perceived latency and making long responses feel interactive.

**Q3. What is backpressure?**  
Backpressure occurs when the producer generates data faster than the consumer can process it, potentially causing queues, memory growth and increased latency.

**Q4. Why use structured streaming events instead of only streaming text?**  
Structured events let the application distinguish between different states and actions, such as text generation, progress, tool execution, errors and completion.

**Q5. What should happen when an AI client disconnects?**  
The system should decide whether to cancel the operation or allow it to continue as a background job, depending on the application's semantics.

**Q6. How should reconnects be implemented?**  
Use bounded retries with exponential backoff and jitter; for resumable streams, use event IDs or sequence numbers to recover missed events.

**Q7. What is the difference between restarting and resuming a stream?**  
Restarting begins the operation again, while resuming continues from a known point, typically using an event ID or sequence position.
