# 1. Streaming Response Lifecycle

## 1.1 What Is Streaming?

**Streaming** means sending data to a client incrementally as it becomes available, instead of waiting for the complete result before returning it.

For example, when an AI model generates an answer, the application can display each incoming text chunk while the model continues generating the remaining answer.

### Non-streaming response

```text
User sends request
        |
        v
Server processes the entire request
        |
        v
Complete response becomes available
        |
        v
Client receives the response
```

The user may see a loading indicator for several seconds before receiving any content.

### Streaming response

```text
User sends request
        |
        v
Server starts processing
        |
        +----> Chunk 1 ----> Client
        +----> Chunk 2 ----> Client
        +----> Chunk 3 ----> Client
        +----> Chunk 4 ----> Client
        |
        v
   Final event
```

The client receives and displays partial results before generation finishes.

## 1.2 Why Streaming Matters

The primary benefit of streaming is **improved perceived responsiveness**.

Perceived responsiveness is how quickly an application appears to respond to a user, rather than the total time required to finish the operation.

Consider an AI response:

```text
Non-streaming:
[Loading........................]
[Complete answer appears]

Streaming:
[Generating...]
React
React is
React is a JavaScript
React is a JavaScript library...
```

Streaming does not necessarily reduce the total processing time. Instead, it allows users to see progress and partial output sooner.

### Common applications

- AI chat and text generation
- Live transcription
- Long-running jobs
- Progress indicators
- Real-time dashboards
- Notifications
- Collaborative applications
- Streaming server logs

## 1.3 Components of a Streaming System

A typical streaming system contains the following components:

```text
Client
  |
  v
Connection
  |
  v
Server / AI Provider
  |
  v
Incremental Events
  |
  v
Client Event Handler
  |
  v
UI / Application State
```

Each component has a responsibility.

| Component | Responsibility |
|---|---|
| Client | Initiates or maintains the connection |
| Connection | Carries data between the server and the client |
| Server or AI provider | Produces data and events |
| Event handler | Receives and interprets events |
| Application state | Tracks the current response and operation status |
| UI | Displays text, progress, tool activity, errors, and completion |

A production streaming system also needs to handle backpressure, disconnects, reconnections, event ordering, errors, cancellation, and completion.

### Important mental model

Streaming is not simply sending pieces of text. It is a **lifecycle** involving connection management, incremental events, state updates, and recovery from failures.

# 2. Streaming Communication Mechanisms

Two important mechanisms for streaming data are Server-Sent Events (SSE) and WebSockets.

They differ mainly in their communication direction and connection model.

## 2.1 Server-Sent Events (SSE)

### Definition

**Server-Sent Events (SSE)** is a mechanism for sending events from a server to a client over an HTTP connection that remains open while events are being delivered.

The primary direction is:

```text
Server --------------------> Client
```

The client initiates the connection, and the server uses it to send updates. Communication from the client to the server generally uses a separate HTTP request.

### SSE communication flow

```text
Client
  |
  | HTTP request
  v
Server
  |
  +---- Event 1 -----------> Client
  +---- Event 2 -----------> Client
  +---- Event 3 -----------> Client
  +---- Event 4 -----------> Client
```

The server can send multiple events over the same streaming response.

### SSE message structure

An SSE stream contains messages separated by a blank line.

```text
event: message
data: Hello

event: message
data: World

```

Important SSE fields include:

| Field | Purpose |
|---|---|
| `event` | Names the event type |
| `data` | Contains the event payload |
| `id` | Associates an identifier with an event |
| `retry` | Specifies a reconnection delay in milliseconds for compatible SSE clients |

Example:

```text
event: token
data: Hello

event: token
data: world

event: done
data: {}

```

The client can use event types to determine how to handle each message.

For example, `token` can represent a text chunk, while `done` can represent the end of generation.

### SSE characteristics

| Property | SSE |
|---|---|
| Communication direction | Primarily server to client |
| Underlying mechanism | HTTP streaming |
| Best suited for | Server updates and event streams |
| Client-to-server messages | Usually separate HTTP requests |
| Reconnection | Supported by standard browser SSE clients |
| Event-oriented data | Natural fit |

Automatic reconnection does not, by itself, guarantee that missed events will be replayed. Reliable recovery requires suitable event identifiers and server-side support.

### Common use cases

- AI-generated text
- Job progress updates
- Live notifications
- Server logs
- Status updates

**Memory trick:** SSE = **Server Sends Events**.

## 2.2 WebSockets

### Definition

**WebSockets** provide a persistent, bidirectional communication channel between a client and a server.

Both sides can send messages over the established connection.

```text
Client <-------------------> Server
```

This is called **full-duplex communication**.

### WebSocket connection flow

```text
Client
  |
  v
Connection request
  |
  v
WebSocket connection established
  |
  +<---- Messages in both directions ---->+
  |
  v
Connection remains open
```

Once established, the connection can carry messages initiated by either side.

### Example: Collaborative application

Imagine two users editing the same document.

```text
User A <------> Server <------> User B
```

When User A makes an edit, the server can distribute the update to User B. User B can also send updates through the same type of persistent connection.

### WebSocket characteristics

| Property | WebSocket |
|---|---|
| Communication direction | Bidirectional |
| Connection | Persistent |
| Communication model | Full-duplex |
| Client-to-server messages | Built in |
| Server-to-client messages | Built in |
| Reconnection | Usually managed by application logic |

### Common use cases

- Interactive chat applications
- Multiplayer games
- Collaborative editing
- Real-time trading interfaces
- Real-time control systems
- Bidirectional AI applications
- Presence indicators

**Memory trick:** WebSocket = a persistent **two-way conversation**.

## 2.3 SSE vs. WebSockets

| Feature | SSE | WebSockets |
|---|---|---|
| Direction | Server → Client | Client ↔ Server |
| Communication mechanism | HTTP streaming | WebSocket connection |
| Communication model | Primarily one-way | Bidirectional |
| Complexity | Often simpler for server-to-client streams | Requires managing a bidirectional connection |
| Client-to-server communication | Usually separate HTTP requests | Supported on the same connection |
| Reconnection | Commonly supported by standard SSE clients | Usually application-managed |
| Event-oriented streaming | Natural fit | Also supported |
| Suitable examples | AI token streams, notifications, progress | Collaborative editing, interactive real-time systems |

### How to choose

Use SSE when the client mainly needs to receive updates from the server.

Use WebSockets when both the client and server need to exchange messages interactively over a persistent connection.

For example, an AI chat interface that streams generated text may use SSE, while an application that needs continuous real-time communication in both directions may use WebSockets.

**Remember:**

```text
SSE        = Server → Client
WebSocket  = Client ↔ Server
```

# 3. Streaming Data and Events

SSE and WebSockets describe communication mechanisms. Streaming text, structured events, and progress events describe the data being delivered.

## 3.1 Streaming Text

### Definition

**Streaming text** means delivering generated text incrementally instead of waiting for the complete response.

Suppose the model generates:

```text
React is a JavaScript library.
```

The application might receive chunks such as:

```text
Chunk 1: "React"
Chunk 2: " is"
Chunk 3: " a JavaScript"
Chunk 4: " library."
```

The exact chunk boundaries depend on the provider and transport.

A chunk does not have to correspond to a complete word, sentence, or paragraph.

### Streaming text lifecycle

```text
User request
     |
     v
AI model begins generation
     |
     v
Receive text chunk 1
     |
     v
Receive text chunk 2
     |
     v
Receive text chunk 3
     |
     v
Receive final chunk
     |
     v
Completion event
```

### Accumulating the response

The client generally maintains an accumulator for the chunks it receives.

Conceptually:

```text
currentText = ""

chunk 1:
currentText = currentText + chunk 1

chunk 2:
currentText = currentText + chunk 2

chunk 3:
currentText = currentText + chunk 3
```

After all chunks have been processed, `currentText` contains the assembled response.

For example:

```text
Chunk 1: "React"
Chunk 2: " is"
Chunk 3: " useful."

Final text: "React is useful."
```

### Important implementation concerns

A streaming text client must account for:

- **Chunk ordering:** Text must be assembled in the intended order.
- **Partial words:** A word can be split across several chunks.
- **Text encoding:** Network and decoding layers must handle UTF-8 correctly.
- **Completion:** The client must know when generation has finished.
- **Errors:** The stream may fail before producing the full response.
- **Cancellation:** The user or application may stop generation early.

### Common misconception

Never assume that every chunk represents a complete word or sentence.

```text
Chunk 1: "Javas"
Chunk 2: "cript"
```

The correct assembled text is:

```text
JavaScript
```

The client should append chunks in order rather than interpreting each chunk as a standalone sentence.

## 3.2 Streaming Structured Events

### Definition

**Structured events** are typed messages delivered incrementally through a stream.

A stream can carry more than plain text. It can communicate generation status, tool activity, progress, results, errors, and completion.

Example events:

```json
{"type": "start"}
```

```json
{"type": "text", "delta": "Hello"}
```

```json
{"type": "text", "delta": " world"}
```

```json
{"type": "tool_start", "tool": "search"}
```

```json
{"type": "tool_result", "status": "success"}
```

```json
{"type": "done"}
```

The client interprets each event according to its type.

### Why structured events matter

Consider an AI agent that performs multiple steps:

```text
Begin processing
      |
      v
Call search tool
      |
      v
Receive search results
      |
      v
Generate answer
      |
      v
Complete
```

If the application sends only raw text, the frontend may struggle to distinguish between tool activity, progress information, and user-facing output.

Structured events make each phase explicit.

### Example event types

| Event type | Purpose | Possible UI behavior |
|---|---|---|
| `start` | Operation begins | Show the active generation state |
| `text` | Text content is available | Append text to the response |
| `progress` | Progress information is available | Update a progress indicator |
| `tool_start` | A tool operation begins | Display which tool is running |
| `tool_result` | A tool has returned a result | Update the tool status |
| `error` | An operation encounters an error | Display an error state |
| `done` | The operation has completed | Stop the loading indicator |

These event types are an example event model; an actual application must define its own event contract.

### Important distinction

A structured event stream may contain text events, progress events, and tool events in the same connection.

This allows the frontend to render different parts of the workflow correctly without guessing what each message means.

## 3.3 Progress Events

### Definition

A **progress event** communicates the current state or progress of an operation.

Example:

```json
{
  "type": "progress",
  "percent": 40,
  "message": "Processing documents"
}
```

The event tells the client that the operation is processing documents and reports progress at 40%.

### Example progress lifecycle

```text
Start
  |
  v
10%  - Loading
  |
  v
30%  - Parsing
  |
  v
50%  - Processing
  |
  v
80%  - Generating
  |
  v
100% - Complete
```

The percentages and stages above are illustrative.

### Streaming output vs. progress events

These concepts are related but different.

| Streaming output | Progress event |
|---|---|
| Communicates part of the result | Communicates the operation's state |
| Example: `"React is"` | Example: `{"type":"progress","percent":50}` |
| Adds content to the response | Updates progress or status UI |

Think of the distinction as:

- **Streaming output:** “Here is some of the result.”
- **Progress event:** “Here is the current state of the operation.”

### Why progress events matter

Progress events are particularly useful for long-running jobs because they provide:

- Feedback to the user
- Better perceived responsiveness
- Visibility into the current processing stage
- Useful information for debugging
- Better opportunities to communicate status when an operation is cancelled or fails

# 4. Backpressure Management

## 4.1 What Is Backpressure?

**Backpressure** occurs when a producer generates data faster than a consumer can process it.

The producer creates or sends data. The consumer receives, processes, or renders it.

Example:

```text
Producer: 1,000 events per second
Consumer:   100 events per second
```

The consumer cannot keep up with the producer.

```text
Fast producer
      |
      v
Events accumulate
      |
      v
Slow consumer
```

In an AI streaming application, the model or backend may produce events faster than the browser can process or render them.

## 4.2 Why Backpressure Matters

If a system does not manage backpressure, unprocessed data may accumulate.

Possible consequences include:

- Memory growth
- Increased latency
- Slow UI rendering
- Resource exhaustion
- Dropped messages

Backpressure management helps a system remain stable when the producer and consumer operate at different speeds.

## 4.3 Backpressure Handling Strategies

### Strategy 1: Slow the producer

If the system can control the production rate, it may slow or pause production when downstream processing is congested.

```text
Producer detects congestion
            |
            v
Reduce sending rate
            |
            v
Consumer catches up
```

This approach is useful when the producer and communication pipeline support flow control.

### Strategy 2: Buffer data

A buffer temporarily stores events before they are consumed.

```text
Producer
   |
   v
 Buffer / Queue
   |
   v
Consumer
```

Buffering can help when bursts are temporary.

However, a buffer is not an unlimited solution. If data continues arriving faster than it is processed, the buffer can grow indefinitely unless limits and handling rules are defined.

### Strategy 3: Drop non-critical data

Some data becomes less useful when a newer update is available.

For example, a progress display receives:

```text
10%
20%
30%
40%
```

If the client is behind and the only requirement is to display the latest progress, it may be sufficient to show 40% rather than render every intermediate value.

This strategy is appropriate for replaceable state updates, such as progress percentages. It is not appropriate for events where every item matters, such as required workflow steps or non-repeatable records.

### Strategy 4: Batch messages

Batching groups multiple events together.

Instead of processing each event separately:

```text
Event 1
Event 2
Event 3
Event 4
```

The system can process a batch:

```text
[Event 1, Event 2, Event 3, Event 4]
```

Batching can reduce per-event processing overhead, but it may introduce additional latency while the system waits to form a batch.

## 4.4 AI-Specific Backpressure Example

Suppose an AI provider produces text chunks faster than a browser can render them.

```text
AI provider
     |
     v
Text chunks
     |
     v
Backend buffer
     |
     v
Browser
     |
     v
UI rendering
```

The backend and client need a way to prevent uncontrolled buffer growth and keep the UI responsive.

### Core rule

**Never assume that the producer and consumer operate at the same speed.**

The correct strategy depends on the type of data, the ability to control production, the importance of each event, and the application's latency requirements.

# 5. Disconnect Handling and Recovery

## 5.1 What Is a Disconnect?

A **disconnect** occurs when the streaming connection closes unexpectedly or is terminated intentionally.

Possible causes include:

- The user closes the browser.
- The network connection disappears.
- A laptop changes networks.
- A mobile device switches networks.
- The server crashes.
- A proxy or load balancer closes the connection.
- An idle timeout is reached.
- The application intentionally cancels the request.

A robust streaming application must define what happens when a disconnect occurs.

## 5.2 Disconnect Lifecycle

```text
Stream is active
      |
      v
Connection is lost
      |
      v
Detect disconnect
      |
      v
Determine operation state
      |
      v
Choose recovery action
   /       |        \
Cancel   Resume    Retry
```

The correct recovery action depends on the purpose of the operation.

## 5.3 Should the Server Continue Working?

This is an important architectural decision.

### Case A: Interactive AI chat

Suppose a user submits a prompt and then closes the browser.

If the operation is tied to the active request, the backend may cancel the generation to avoid wasting compute resources and model-provider cost.

```text
Client disconnects
        |
        v
Backend detects disconnect
        |
        v
Cancel model generation
```

This design requires the backend to propagate cancellation to the model provider where supported.

### Case B: Background report generation

Suppose the user starts a report that takes several minutes.

The report may need to continue even after the user disconnects.

```text
Client disconnects
        |
        v
Background job continues
        |
        v
Result is stored
        |
        v
Client reconnects later
        |
        v
Client retrieves result
```

### Request-bound operations vs. job-oriented operations

| Request-bound operation | Job-oriented operation |
|---|---|
| Usually tied to a live request | Has an independent job lifecycle |
| May be cancelled when the client disconnects | Can continue after disconnection |
| Example: disposable interactive generation | Example: long-running report generation |
| Result may not be retained | Result can be persisted for later retrieval |

The application should make this decision explicitly rather than treating every disconnect the same way.

## 5.4 Connection States

Explicit connection states make streaming behavior easier to manage.

### Normal lifecycle

```text
CONNECTING
    |
    v
OPEN
    |
    v
STREAMING
    |
    v
COMPLETED
```

### Reconnection lifecycle

```text
STREAMING
    |
    v
DISCONNECTED
    |
    v
RECONNECTING
    |
    v
STREAMING / RESUMING
```

### Failure lifecycle

```text
STREAMING
    |
    v
FAILED
```

These states should be distinguished carefully:

- **COMPLETED:** The operation finished successfully.
- **FAILED:** The operation encountered a failure.
- **DISCONNECTED:** The client and server no longer have an active connection.
- **CANCELLED:** The operation was intentionally stopped.
- **RECONNECTING:** The client is attempting to re-establish communication.

A connection can be disconnected while its underlying job continues running. Connection state and job state should therefore not automatically be treated as identical.

## 5.5 Reconnect Strategies

### Why immediate reconnection is dangerous

Consider this strategy:

```text
Disconnect
    |
    v
Reconnect immediately
    |
    v
Fail
    |
    v
Reconnect immediately
    |
    v
Fail
    |
    v
Repeat indefinitely
```

Repeated aggressive reconnection can overload a server or create a **reconnection storm**, particularly when many clients lose connectivity at the same time.

### Exponential backoff

**Exponential backoff** increases the waiting period between unsuccessful retries.

Example:

```text
First retry:   wait 1 second
Second retry:  wait 2 seconds
Third retry:   wait 4 seconds
Fourth retry:  wait 8 seconds
```

A common model is:

\[
\text{delay}_n = \min(\text{baseDelay}\times 2^n,\ \text{maxDelay})
\]

Here, the delay grows exponentially until it reaches a configured maximum.

This is an illustrative retry model. The retry index and initial delay depend on the implementation.

### Jitter

**Jitter** adds random variation to retry delays.

Without jitter, thousands of clients might reconnect at exactly the same time. Jitter spreads attempts across time and can reduce synchronized load spikes.

### Recommended reconnect principles

- Use bounded retries when indefinite retries are not appropriate.
- Increase delays after repeated failures.
- Add jitter to reduce synchronized reconnects.
- Distinguish temporary connection failures from permanent application errors.
- Resume from a known position when the protocol and server support it.
- Stop retrying when the operation has completed or been cancelled.

### Reconnect flow

```text
Connection lost
      |
      v
Attempt reconnect
      |
      v
Did reconnect succeed?
     / \
   Yes  No
    |    |
    v    v
 Resume  Backoff
    |      |
    |      v
    |    Retry
    |      |
    +------+
```

## 5.6 Restart vs. Resume

Restart and resume are two different recovery strategies.

### Restart

Restart means beginning the operation again from the beginning.

```text
Disconnect
    |
    v
Create a new request
    |
    v
Run operation from the start
```

Potential problems:

- Duplicate work
- Duplicate model-provider cost
- Repeated output

Restarting is reasonable when the operation is inexpensive, cannot be resumed, or is designed to run again safely.

### Resume

Resume means continuing from a previously known position.

```text
Disconnect
    |
    v
Reconnect
    |
    v
Identify last received event
    |
    v
Request or replay missed events
    |
    v
Continue stream
```

Resume generally requires event-position tracking and server-side support for replaying or retrieving events.

### Comparison

| Feature | Restart | Resume |
|---|---|---|
| Starting point | Beginning | Known position |
| Implementation | Usually simpler | More complex |
| May repeat prior work | Yes | Usually avoids repeating acknowledged work |
| Event-position tracking | Not required | Required |
| Suitable for long-lived streams | Sometimes | Often preferable when supported |

Resume does not automatically guarantee exactly-once processing. A client might receive an event again if the acknowledgement or processing status was not recorded. Applications that require reliable processing should account for duplicates.

# 6. Event Ordering and Resumability

## 6.1 Why Event IDs Matter

Reliable streaming applications may assign identifiers to events.

For example:

```text
Event ID: 101
Event ID: 102
Event ID: 103
Event ID: 104
```

Suppose the client has successfully received events through ID 102.

```text
Last received event ID: 102
```

After reconnecting, the client can potentially request events after 102:

```text
Send or replay events after ID 102
```

This allows the server to provide missed events, provided it retains them and implements replay or resume behavior.

### Event IDs in SSE

SSE supports an `id` field:

```text
id: 101
event: message
data: First event

id: 102
event: message
data: Second event

```

A compatible `EventSource` client can track the last event ID and communicate that position during reconnection. The server must still implement the necessary behavior to replay events based on that identifier.

An ID alone does not make a stream resumable.

## 6.2 Sequence Numbers and Ordering

Events may have sequence numbers representing their intended order.

```text
Sequence 1
Sequence 2
Sequence 3
```

For some applications, observing events out of order can produce an incorrect result.

Imagine the intended event order is:

```text
Event 1
Event 2
Event 3
```

But the application processes them as:

```text
Event 1
Event 3
Event 2
```

If each event updates independent data, that may be acceptable. If each event depends on the previous event, this order may corrupt application state.

### Techniques for managing event ordering

- **Sequence numbers:** Indicate the expected event order.
- **Event IDs:** Identify events and help track the stream position.
- **Ordering logic:** Processes events according to application rules.
- **Buffering:** Temporarily holds events until missing earlier events arrive.

Sequence numbers and event IDs can serve related but distinct purposes. A sequence number often explicitly represents ordering, whereas an event ID identifies a particular event.

## 6.3 Important Reliability Principle

**A streaming transport does not automatically guarantee application-level recovery, correct event ordering, or exactly-once processing.**

The application must define:

1. How an event is identified.
2. How the client tracks its last successfully processed event.
3. Whether the server retains events for replay.
4. How duplicate events are detected or handled.
5. What happens if an expected event is missing.
6. When the stream is considered complete.

These details become particularly important for long-lived streams and workflows that execute tools, update persistent records, or generate expensive results.

# 7. Production Architecture and Common Mistakes

## 7.1 Complete Streaming Lifecycle

The entire lifecycle brings together connections, events, client processing, and failure recovery.

```text
Request
   |
   v
Open stream
   |
   v
Send start event
   |
   v
Receive events
   |
   +----> Progress events
   |
   +----> Text / structured events
                 |
                 v
          Client processes event
                 |
                 v
          Update application state
                 |
                 v
          Update the UI
                 |
                 v
          More events available?
              /        \
            Yes         No
             |           |
             v           v
        Continue       Complete

If the connection is lost:
             |
             v
       Detect disconnect
             |
             v
       Determine job state
             |
             v
    Cancel / Resume / Reconnect
```

The central idea is that streaming involves more than receiving chunks. A production design must manage the complete connection and event lifecycle.

## 7.2 Real-World Example: AI Chat Application

Consider an AI chatbot built with a frontend, backend, and AI provider.

### Step 1: The user submits a prompt

```text
User
  |
  v
Frontend submits prompt
  |
  v
Backend
  |
  v
AI provider
```

### Step 2: The model generates text incrementally

The provider may produce chunks such as:

```text
"React"
" is"
" a JavaScript"
" library."
```

### Step 3: The backend forwards events

```text
AI provider
     |
     v
Backend
     |
     v
SSE or WebSocket
     |
     v
Browser
```

The backend may forward text events as they become available. If the application also needs to show tool execution, progress, or status, it can define additional structured events.

### Step 4: The browser updates the UI

```text
Chunk 1 arrives ---> Append text
Chunk 2 arrives ---> Append text
Chunk 3 arrives ---> Append text
Chunk 4 arrives ---> Append text
```

The frontend maintains the current response and updates the UI as events arrive.

### Step 5: The backend signals completion

For an application using a JSON-based event contract, the final event might be:

```json
{
  "type": "done"
}
```

The frontend can then stop showing the generation indicator.

The event contract must define whether `done` represents successful completion and how error or cancellation events are communicated.

### Step 6: The user disconnects

For request-bound interactive generation:

```text
Browser disconnects
        |
        v
Backend detects disconnect
        |
        v
Cancel generation if appropriate
```

For a background job:

```text
Browser disconnects
        |
        v
Background job continues
        |
        v
Result is stored
        |
        v
User reconnects
        |
        v
User retrieves result
```

The correct behavior depends on the application's business requirements.

## 7.3 Production Architecture

A production AI streaming backend might look like this:

```text
                   User
                    |
                    v
                 Frontend
                    |
                    v
               Streaming Client
                    |
                    v
              SSE / WebSocket
                    |
                    v
```

- Backpressure
- Disconnect detection

- Cancellation
- Error handling

The exact mechanisms vary based on the transport, server framework, AI provider, and business requirements.

## 7.4 Common Mistakes

### Mistake 1: Treating SSE and WebSockets as identical

Remember:

```text
SSE       = Server → Client
WebSocket = Client ↔ Server
```

Choose the communication mechanism according to whether one-way streaming or bidirectional communication is required.

### Mistake 2: Assuming every chunk is complete

A chunk may contain only part of a word.

```text
Chunk 1: "Javas"
Chunk 2: "cript"
```

The client must assemble the text in the correct order.

### Mistake 3: Streaming only raw text in a complex agent

A multi-step agent may perform operations such as:

```text
thinking
tool_start
tool_result
text
progress
done
```

Explicit structured events make it easier for the frontend to display each phase correctly.

### Mistake 4: Ignoring backpressure

A producer can overwhelm a slower client. Uncontrolled buffering may increase memory usage and latency.

### Mistake 5: Reconnecting in a tight loop

Repeated immediate retries can overload infrastructure.

Use appropriate retry limits, exponential backoff, and jitter.

### Mistake 6: Failing to define disconnect behavior

Decide whether a disconnected client should cause the operation to be cancelled or allow the job to continue in the background.

### Mistake 7: Losing the stream position

A resumable stream needs a way to track which events have been received or processed. Event IDs and sequence numbers can help.

### Mistake 8: Omitting an explicit completion signal

The client needs to distinguish successful completion from an interrupted connection.

A JSON-based application event might be:

```json
{
  "type": "done"
}
```

Other stream protocols may communicate normal completion differently. The important point is that the application should define and recognize its completion semantics.

### Mistake 9: Blindly restarting expensive operations

Restarting an AI generation can repeat work, output, and cost.

For operations that need continuity, consider event replay, resumability, or storing the completed result for later retrieval.

## 7.5 Key Takeaways

- Streaming delivers data incrementally.
- Its main user-experience benefit is improved perceived responsiveness.
- SSE primarily provides server-to-client event streaming over HTTP.
- WebSockets provide persistent bidirectional communication.
- Streaming text delivers generated text in chunks.
- Structured events represent typed messages such as text, progress, tool activity, and completion.
- Progress events describe operation state rather than result content.
- Backpressure occurs when the producer is faster than the consumer.
- Buffers, throttling, dropping replaceable updates, and batching can help manage backpressure.
- Disconnect handling determines whether a running operation should be cancelled or continue.
- Exponential backoff and jitter can help prevent aggressive reconnect loops.
- Restart begins an operation again; resume continues from a known position.
- Event IDs and sequence numbers help support recovery and ordering.
- Reliable recovery may also require event retention, replay logic, and duplicate handling.
- A production streaming design must define the handling of data, progress, errors, cancellation, completion, and disconnects.

## 8.4 Question-and-Answer Recall

**Q1. What is streaming?**

**Answer:** Streaming is delivering data incrementally as it becomes available instead of waiting for the complete result.

**Q2. What is the primary user-experience benefit of streaming?**

**Answer:** Improved perceived responsiveness because users can see partial output or progress earlier.

**Q3. What is SSE?**

**Answer:** Server-Sent Events is an HTTP-based mechanism for sending events from a server to a client over a streaming connection.

**Q4. Is SSE primarily one-way or bidirectional?**

**Answer:** One-way, from the server to the client. Client-to-server communication generally uses separate HTTP requests.

**Q5. What are WebSockets?**

**Answer:** WebSockets provide a persistent, bidirectional communication channel that allows both client and server to send messages.

**Q6. What is the key difference between SSE and WebSockets?**

**Answer:** SSE primarily sends events from server to client, whereas WebSockets support communication in both directions over the established connection.

**Q7. What is streaming text?**

**Answer:** Streaming text is delivering generated text incrementally in chunks.

**Q8. Why should a client not assume that every chunk contains a complete word?**

**Answer:** Chunk boundaries depend on the provider and transport. A word can be split across multiple chunks, so the client must assemble chunks correctly.

**Q9. What are structured events?**

**Answer:** Structured events are typed messages that can represent text, progress, tool execution, errors, and completion.

**Q10. Why are structured events useful for AI agents?**

**Answer:** They allow the frontend to distinguish different stages of processing, such as starting a tool, receiving a result, generating text, and completing the operation.

**Q11. What is a progress event?**

**Answer:** A progress event communicates the current state or progress of an operation, such as 40% completion.

**Q12. How are progress events different from text chunks?**

**Answer:** Text chunks provide part of the result. Progress events describe the operation's current state.

**Q13. What is backpressure?**

**Answer:** Backpressure occurs when data is produced faster than it can be consumed or processed.

**Q14. What problems can backpressure cause?**

**Answer:** It can cause buffer growth, memory pressure, increased latency, slow rendering, resource exhaustion, and dropped messages.

**Q15. Name four backpressure management strategies.**

**Answer:** Slow the producer, buffer data, drop non-critical or replaceable updates, and batch messages.

**Q16. When is dropping events appropriate?**

**Answer:** When the omitted events are non-critical and can be replaced by newer information, such as intermediate progress percentages. It is inappropriate when every event must be processed.

**Q17. What can cause a streaming disconnect?**

**Answer:** Network failure, a closed browser, network switching, server crashes, proxy timeouts, idle timeouts, or intentional cancellation.

**Q18. Should the server always cancel an operation when the client disconnects?**

**Answer:** No. Request-bound operations may be cancelled, but job-oriented operations may need to continue in the background and store their results.

**Q19. What is exponential backoff?**

**Answer:** A retry strategy that increases the delay between unsuccessful attempts exponentially, usually subject to a maximum delay.

**Q20. Why add jitter to reconnection delays?**

**Answer:** To prevent many clients from retrying at the same time and creating a reconnection storm.

**Q21. What is the difference between restart and resume?**

**Answer:** Restart starts the operation from the beginning. Resume continues from a previously known position when the required recovery support is available.

**Q22. Why can restarting an AI stream be expensive?**

**Answer:** It may repeat the generation work, output, and model-provider cost.

**Q23. Why are event IDs useful?**

**Answer:** They help identify events and track the client's position in a stream. With server-side replay support, they can help the client retrieve missed events.

**Q24. What is a sequence number?**

**Answer:** A sequence number indicates the intended order of events and can help an application detect missing or out-of-order messages.

**Q25. Does using SSE or WebSockets guarantee event replay and exactly-once processing?**

**Answer:** No. Reliable recovery requires application-level mechanisms such as event IDs, event retention, replay logic, ordering, and duplicate handling where needed.

## 8.6 Scenario-Based Interview Questions

### Scenario 1: Designing an AI chatbot

**Question:** You are developing an AI chatbot. Users should see generated text immediately. The browser mostly receives updates from the backend. Which streaming mechanism would you consider first, and why?

**Answer:** SSE is a reasonable choice because the main requirement is server-to-client streaming over HTTP. The backend can forward incremental text events, while the frontend appends the arriving chunks. WebSockets become more relevant if the application needs persistent bidirectional communication.

### Scenario 2: A slow frontend

**Question:** Your AI provider generates events quickly, but the frontend renders them slowly. Memory usage rises during long responses. What would you investigate?

**Answer:** Investigate backpressure and buffering across the provider, backend, transport, client event handler, and rendering pipeline. Consider bounded buffering, controlled production where supported, batching, or dropping superseded updates where safe. Do not discard events that are essential to the final result.

### Scenario 3: Mobile users frequently disconnect

**Question:** Users on mobile networks repeatedly lose connectivity. Your application reconnects immediately and creates high server load. How would you improve it?

**Answer:** Use exponential backoff with jitter, apply appropriate retry limits, and identify whether each operation can resume. Avoid treating every connection failure as a reason to restart an expensive operation.

### Scenario 4: Long-running AI report

**Question:** A user starts a report that takes several minutes and closes their browser. The report must still finish. What should the backend do?

**Answer:** Run the report as a job whose lifecycle is independent of the browser connection. Persist the result and let the user retrieve it later. The streaming connection should communicate progress when available, but it should not define whether the job continues.

### Scenario 5: Missing stream events

**Question:** A client receives events 201 and 203, but event 202 is missing. The client cannot safely apply 203 before 202. How should it respond?

**Answer:** Track sequence numbers, detect the gap, and temporarily buffer event 203. Request or await event 202 if recovery is supported. Once the gap is resolved, process events in the required order. If the missing event cannot be recovered, apply a defined error or resynchronization strategy.

### Scenario 6: Duplicate events after reconnecting

**Question:** A client reconnects and receives an event that it may already have processed. Processing the event twice would create duplicate records. What should you design?

**Answer:** Track successfully processed event identifiers and use suitable deduplication or idempotency rules. Distinguish between receiving an event and successfully applying its business effects. A resumable stream alone does not guarantee exactly-once processing.

### Scenario 7: Complex AI agent workflow

**Question:** An agent searches for information, receives tool results, generates text, and completes the task. Why is streaming raw text alone a poor fit?

**Answer:** Raw text does not clearly identify workflow transitions. A structured event contract can distinguish `tool_start`, `tool_result`, `text`, `progress`, `error`, and `done`, allowing the frontend to render each phase appropriately.

### Scenario 8: Determining when a stream has finished

**Question:** The frontend displays generated text, but the user sees the loading indicator even after the answer appears. What might be missing from the design?

**Answer:** The frontend may lack a clearly defined completion signal or may not be handling it correctly. Define completion semantics and ensure the client transitions out of the streaming state when the operation successfully finishes.

## 8.7 Final Interview Summary

Before implementing a streaming feature, answer these questions:

1. **Transport:** Is SSE sufficient, or is bidirectional WebSocket communication required?
2. **Payload:** Will the client receive plain text, structured events, or both?
3. **State:** How will the client track partial output and operation status?
4. **Backpressure:** What happens when the producer is faster than the consumer?
5. **Disconnect:** Should the job stop or continue independently?
6. **Reconnection:** Will retries use backoff and jitter?
7. **Recovery:** Can the operation restart, or must it resume?
8. **Ordering:** How will missed or out-of-order events be detected?
9. **Duplicates:** Can processing an event twice cause unintended side effects?
10. **Completion:** How does the client distinguish success from failure or disconnection?

### The 7 things to remember

```text
1. Streaming      -> Send data incrementally
2. SSE            -> Server-to-client events
3. WebSocket      -> Bidirectional communication
4. Backpressure   -> Producer faster than consumer
5. Disconnect    -> Decide cancel vs. continue
6. Reconnect      -> Backoff + jitter
7. Resume         -> Event IDs + replay support
```

**Final takeaway:** A reliable streaming application needs more than incremental output. It must define its transport, event contract, state transitions, backpressure handling, cancellation policy, reconnection behavior, event ordering, and completion rules.
