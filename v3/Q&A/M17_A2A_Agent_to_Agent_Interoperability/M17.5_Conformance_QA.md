## M17.5.1 — Actual protocol implementation

**Q1. [Interview] What should an engineer understand about Actual protocol implementation (M17.5.1)?**

**Answer:** test cross-agent authorization and compatibility.


**Q2. [Scenario] Why could overlooking Actual protocol implementation create problems in a federated agent network?**

**Answer:** In a federated research, coding and audit agent network, this changes the decision criteria or the allowed workflow. Record who owns the rule, when it applies and how to verify compliance.

## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q3. [Interview] Explain conformance to an interviewer.**

**Answer:** Follow-up 1 — What would you test first? A negative case involving failure recovery and a normal task with a verified outcome.


**Q4. [Interview] How would you design Actual protocol implementation from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Treat this as an interface contract with explicit inputs, outputs, versions, errors and authorization. A working transport does not imply that an operation is semantically safe or interoperable. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q5. [Interview] How do State and evidence and Validation interact?**

**Answer:** Interview answer: First define their separate responsibilities. Identify who owns this information, where it lives, and when it changes. Keep transient model context distinct from durable application state and enforce scope on every read and write. Checking input and output data against schemas, required fields and domain constraints before further action. I would connect them only through a typed handoff with provenance and an explicit postcondition, rather than allowing hidden state coupling.


**Q6. [Interview] What would you do if Failure recovery fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure successful delegated task rate with cancellation propagation.


**Q7. [Interview] When would you avoid a framework or model for conformance?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q8. [Interview] How would you demonstrate L3 production readiness for M17.5?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the delegation trace and signed or hashed artifact inventory, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
