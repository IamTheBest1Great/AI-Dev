## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q27. [Interview] Explain lineage and lifecycle to an interviewer.**

**Answer:** Follow-up 1 — What would you test first? A negative case involving data deletion propagation and a normal task with a verified outcome.


**Q28. [Interview] How would you design Source → transformation → index/model lineage from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Make lifecycle and version information explicit. Record what changed, when it changed, and which cached or downstream copies need updating; compare against the current source of truth. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q29. [Interview] How do Data retention and Data deletion propagation interact?**

**Answer:** Interview answer: First define their separate responsibilities. In this part of a document ingestion and intelligence pipeline, Data retention is an explicit design concern. Define its inputs, owner, observable result and failure handling before implementing it. Its purpose must be linked to the overall goal: transform messy source data into trusted, lineage-rich AI inputs. Make lifecycle and version information explicit.


**Q30. [Interview] What would you do if Reprocessing/rebuild strategy fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure field extraction accuracy and rejected-bad-data rate.


**Q31. [Interview] When would you avoid a framework or model for lineage and lifecycle?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q32. [Interview] How would you demonstrate L3 production readiness for M34.4?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the document pipeline manifest with extraction quality and lineage, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
