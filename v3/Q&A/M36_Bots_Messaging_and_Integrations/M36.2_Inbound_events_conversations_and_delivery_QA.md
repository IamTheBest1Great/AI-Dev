**Q43. [Interview] Explain inbound events, conversations and delivery to an interviewer.**

**Answer:** Interview answer: Inbound events, conversations and delivery addresses the need to convert inbound messages into secure, idempotent tasks. I would begin with a bounded design for a multi-channel support bot with webhooks and handoff, then specify contracts for Webhooks and Signature validation. I would measure successful delivery and duplicate-trigger suppression, verify the actual outcome and demonstrate handling of the primary failure:.


**Q44. [Interview] How would you design Webhooks from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. HTTP callbacks sent by an event source; verify provider signature, event ID and freshness before mutating application state. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q45. [Interview] How do Signature validation and Replay prevention interact?**

**Answer:** Interview answer: First define their separate responsibilities. Define an expected outcome on representative fixtures. Compare observed behavior against a predeclared criterion; separate deterministic correctness from probabilistic model quality. Define expected behavior before, during and after failure. Use bounded retries, transaction/receipt checks and explicit unknown-outcome states instead of assuming every retry is safe.


**Q46. [Interview] What would you do if Conversation state fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure successful delivery and duplicate-trigger suppression.


**Q47. [Interview] When would you avoid a framework or model for inbound events, conversations and delivery?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q48. [Interview] How would you demonstrate L3 production readiness for M36.2?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the webhook event ledger and human-handoff transcript, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
