## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q27. [Interview] Explain task verification and robustness to an interviewer.**

**Answer:** Interview answer: Task verification and robustness addresses the need to ground screenshot actions in verified application state. I would begin with a bounded design for a sandboxed desktop computer-use assistant, then specify contracts for Environment-state verification and Goal completion. I would measure verified GUI goal completion under environmental changes, verify the actual outcome and demonstrate handling of the primary failure:.


**Q28. [Interview] How would you design Environment-state verification from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Define an expected outcome on representative fixtures. Compare observed behavior against a predeclared criterion; separate deterministic correctness from probabilistic model quality. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q29. [Interview] How do Goal completion and Recovery interact?**

**Answer:** Interview answer: First define their separate responsibilities. In this part of a sandboxed desktop computer-use assistant, Goal completion is an explicit design concern. Define its inputs, owner, observable result and failure handling before implementing it. Its purpose must be linked to the overall goal: ground screenshot actions in verified application state. Define expected behavior before, during and after failure.


**Q30. [Interview] What would you do if Navigation robustness fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure verified GUI goal completion under environmental changes.


**Q31. [Interview] When would you avoid a framework or model for task verification and robustness?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q32. [Interview] How would you demonstrate L3 production readiness for M21.3?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the GUI action trace with before/after screenshots and human takeover log, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
