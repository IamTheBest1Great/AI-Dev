## M21.4.1 — GUI execution

**Q1. [Interview] What should an engineer understand about GUI execution (M21.4.1)?**

**Answer:** stop or recover.


**Q2. [Scenario] Why could overlooking GUI execution create problems in a computer-use agent?**

**Answer:** In a sandboxed desktop computer-use assistant, this changes the decision criteria or the allowed workflow. Record who owns the rule, when it applies and how to verify compliance.

## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q3. [Interview] Explain perception-action loop to an interviewer.**

**Answer:** Interview answer: Perception-action loop addresses the need to ground screenshot actions in verified application state. I would begin with a bounded design for a sandboxed desktop computer-use assistant, then specify contracts for GUI execution and State and evidence. I would measure verified GUI goal completion under environmental changes, verify the actual outcome and demonstrate handling of the primary failure: screen scaling changes and the agent clicks outside the intended control.


**Q4. [Interview] How would you design GUI execution from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Ground the operation in the current observable source and define how to verify it. Treat recognized or generated content as uncertain until checked against concrete evidence. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q5. [Interview] How do State and evidence and Validation interact?**

**Answer:** Interview answer: First define their separate responsibilities. Identify who owns this information, where it lives, and when it changes. Keep transient model context distinct from durable application state and enforce scope on every read and write. Checking input and output data against schemas, required fields and domain constraints before further action. I would connect them only through a typed handoff with provenance and an explicit postcondition, rather than allowing hidden state coupling.


**Q6. [Interview] What would you do if Failure recovery fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure verified GUI goal completion under environmental changes.


**Q7. [Interview] When would you avoid a framework or model for perception-action loop?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q8. [Interview] How would you demonstrate L3 production readiness for M21.4?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the GUI action trace with before/after screenshots and human takeover log, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
