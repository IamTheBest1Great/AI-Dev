## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q73. [Interview] Explain fault handling and containment to an interviewer.**

**Answer:** Interview answer: Fault handling and containment addresses the need to meet reliability objectives despite partial outages. I would begin with a bounded design for a production AI API with model, database and queue dependencies, then specify contracts for Timeouts and Retries. I would measure task-success SLO and recovery time under injected faults, verify the actual outcome and demonstrate handling of the primary failure: provider outage causes a retry storm and duplicate tool writes.


**Q74. [Interview] How would you design Timeouts from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Define expected behavior before, during and after failure. Use bounded retries, transaction/receipt checks and explicit unknown-outcome states instead of assuming every retry is safe. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q75. [Interview] How do Retries and Exponential backoff interact?**

**Answer:** Interview answer: First define their separate responsibilities. In this part of a production AI API with model, database and queue dependencies, Retries is an explicit design concern. Define its inputs, owner, observable result and failure handling before implementing it. Its purpose must be linked to the overall goal: meet reliability objectives despite partial outages. Increase delay after repeated transient failures to reduce contention and overload.


**Q76. [Interview] What would you do if Jitter fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure task-success SLO and recovery time under injected faults.


**Q77. [Interview] When would you avoid a framework or model for fault handling and containment?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q78. [Interview] How would you demonstrate L3 production readiness for M28.1?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the failure-injection report with runbooks and SLO results, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
