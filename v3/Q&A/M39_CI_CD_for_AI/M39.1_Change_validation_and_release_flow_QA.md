<a id="lint"></a>
#### Lint

**Q1. [Conceptual] What is lint, and why does it matter in Delivery Pipeline?**

**Answer:** Static code-style and likely-error checks that catch simple issues before tests or deployment.


**Q2. [Interview] Where would you apply lint when designing a CI/CD pipeline for AI services, and how would you explain your decision?**

**Answer:** Use lint in the validate code and contracts stage. Define the relevant input, output, or decision; specify a measurable acceptance check instead of trusting a generated description alone.


**Q3. [Scenario] Your CI/CD pipeline for AI services encounters this problem: a prompt revision compiles but silently degrades retrieval answers. How would you handle it specifically for lint?**

**Answer:** To address it, prepare or implement versioned prompts/datasets, acceptance gates and canary verification. Static code-style and likely-error checks that catch simple issues before tests or deployment. Confirm the change with a reproducible negative test and an observed result.

Where applicable, add a negative test that proves the boundary still holds under retries, stale data or unauthorized access.

## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q53. [Interview] Explain change validation and release flow to an interviewer.**

**Answer:** Interview answer: Change validation and release flow addresses the need to gate deployments on code, security, and AI behavior. I would begin with a bounded design for a CI/CD pipeline for prompt- and model-dependent services, then specify contracts for Lint and Type check. I would measure change failure rate and behavior-regression escape rate, verify the actual outcome and demonstrate handling of the primary failure: a prompt revision compiles but silently degrades retrieval answers.


**Q54. [Interview] How would you design Lint from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Static code-style and likely-error checks that catch simple issues before tests or deployment. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q55. [Interview] How do Type check and Unit tests interact?**

**Answer:** Interview answer: First define their separate responsibilities. Verify static data and function contracts, especially tool results and workflow state transitions. Deterministic checks of small pure functions, validators and policy decisions in isolation. I would connect them only through a typed handoff with provenance and an explicit postcondition, rather than allowing hidden state coupling.


**Q56. [Interview] What would you do if Integration tests fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure change failure rate and behavior-regression escape rate.


**Q57. [Interview] When would you avoid a framework or model for change validation and release flow?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q58. [Interview] How would you demonstrate L3 production readiness for M39.1?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the release evidence bundle with evaluation and security thresholds, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
