## 1. Approval Validity Fundamentals

**Q1. [Conceptual] Explain Approval Validity Fundamentals in simple, interview-ready language.**

**Answer:** Approval validity means that a recorded approval still applies to the action about to execute. The action must have the approved meaning, target, parameters and relevant version, and the approving authority must still be acceptable under the current policy.


**Q2. [Interview] Why does Approval Validity Fundamentals matter, and what is one important design implication?**

**Answer:** These are distinct situations. An approval record should help the system distinguish them instead of collapsing them into a single Boolean such as approved=true.

<a id="2-permission-intent-and-approval"></a>
## 2. Permission, Intent and Approval

**Q7. [Conceptual] Explain Permission, Intent and Approval in simple, interview-ready language.**

**Answer:** Authentication can succeed while authorization fails. Authorization can succeed while the requested action is outside the user's instruction. The user can intend an action while a policy requires an additional approval. An approval can exist while the current permissions no longer allow execution.


**Q8. [Interview] Why does Permission, Intent and Approval matter, and what is one important design implication?**

**Answer:** For example, an assistant helping someone review task workloads should not infer that it may reassign every overdue task. Technical access to the reassignment tool does not establish that broader intent.


<a id="3-bind-approval-to-the-action"></a>
## 3. Bind Approval to the Action

**Q9. [Conceptual] Explain Bind Approval to the Action in simple, interview-ready language.**

**Answer:** An approval is bound when the executor can reliably determine whether the proposed operation is the same operation that was approved. A free-text comment saying “looks good” is insufficient unless the application associates it with an immutable proposal.


**Q10. [Interview] Why does Bind Approval to the Action matter, and what is one important design implication?**

**Answer:** An approval for creating a private draft should not be reused for publishing it publicly. An approval for assigning one task should not become approval for assigning every task returned by a new search.


<a id="4-normalize-parameters-before-review"></a>
## 4. Normalize Parameters Before Review

**Q11. [Conceptual] Explain Normalize Parameters Before Review in simple, interview-ready language.**

**Answer:** Normalization converts equivalent accepted inputs into the application’s explicit execution representation. For approval, normalization should happen before the user reviews the proposal.


**Q12. [Interview] Why does Normalize Parameters Before Review matter, and what is one important design implication?**

**Answer:** Materialize significant defaults into the approved proposal. The execution adapter should use that explicit value rather than recomputing a default later.


<a id="5-bind-approval-to-target-versions"></a>
## 5. Bind Approval to Target Versions

**Q13. [Conceptual] Explain Bind Approval to Target Versions in simple, interview-ready language.**

**Answer:** A target version identifies the state of the resource that was reviewed. The version can be a revision number, an ETag, a content digest, a quote identifier or another server-defined concurrency token.


**Q14. [Interview] Why does Bind Approval to Target Versions matter, and what is one important design implication?**

**Answer:** An application can require the target's current version to equal the approved expected version when the update is committed.


<a id="6-expire-stale-approvals"></a>
## 6. Expire Stale Approvals

**Q15. [Conceptual] Explain Expire Stale Approvals in simple, interview-ready language.**

**Answer:** There is no universal five-minute or one-hour lifetime for every action. Select a lifetime based on the action's risk, the rate of relevant state changes, the expected human workflow and any underlying quote or reservation expiry.


**Q16. [Interview] Why does Expire Stale Approvals matter, and what is one important design implication?**

**Answer:** Persist timestamps in an unambiguous format such as UTC instants. Evaluate validity with trusted server time. A user's browser clock or a model-supplied timestamp should not extend an approval.


<a id="7-recheck-current-permissions"></a>
## 7. Recheck Current Permissions

**Q17. [Conceptual] Explain Recheck Current Permissions in simple, interview-ready language.**

**Answer:** The execution gate should derive the actor and tenant from authenticated context and check current operation-level and object-level access. A stored approval is evidence of a past confirmation; it is not a replacement for the current access decision.


**Q18. [Interview] Why does Recheck Current Permissions matter, and what is one important design implication?**

**Answer:** The service must determine whether Alice still has the relevant request authority, Bob's approval remains valid, and the worker has the narrowly scoped execution capability. Do not reduce this chain to “the worker token can call the API.”.

## 8. Detect Changed External State

**Q23. [Conceptual] Explain Detect Changed External State in simple, interview-ready language.**

**Answer:** These are design examples, not universal rules. The service's documented action semantics decide which changes are significant.


**Q24. [Interview] Why does Detect Changed External State matter, and what is one important design implication?**

### Revalidate a plan, not merely a message

**Q25. [Conceptual] Explain Revalidate a plan, not merely a message in simple, interview-ready language.**

**Answer:** A multi-step plan can expand after approval because an earlier tool returns new results. If the user approved reassignment of tasks T1 and T2, a later search returning T3 does not place T3 inside the approval automatically.

### Tool changes are external state too

**Q29. [Conceptual] Explain Tool changes are external state too in simple, interview-ready language.**

<a id="9-close-the-check-to-execution-gap"></a>
## 9. Close the Check-to-Execution Gap

**Q33. [Conceptual] Explain Close the Check-to-Execution Gap in simple, interview-ready language.**

**Answer:** Checking a target version and then sending an unconditional update leaves such a gap. Checking whether an approval is unused and then marking it used in a separate uncoordinated operation can let two workers consume it.


**Q34. [Interview] Why does Close the Check-to-Execution Gap matter, and what is one important design implication?**

**Answer:** The local reservation prevents another local worker from using the approval for a different action. The provider's idempotency prevents duplicate effects within its documented scope. The provider's conditional-write support protects the target version. Each control has a separate job.


<a id="10-approval-lifecycle-and-timeout-recovery"></a>
## 10. Approval Lifecycle and Timeout Recovery

**Q35. [Conceptual] Explain Approval Lifecycle and Timeout Recovery in simple, interview-ready language.**

**Answer:** Consuming an approval once should mean binding it to one logical action, not forbidding all safe recovery calls for that action. A same-action receipt lookup or contract-safe idempotent retry is different from authorizing a second independent effect.


**Q36. [Interview] Why does Approval Lifecycle and Timeout Recovery matter, and what is one important design implication?**

**Answer:** These states describe a possible application model. They should not be confused with a vendor's actual response enums.


<a id="approval-consumption-is-not-proof-of-completion"></a>
### Approval consumption is not proof of completion

**Q37. [Conceptual] Explain Approval consumption is not proof of completion in simple, interview-ready language.**

**Answer:** The approval may be reserved before the request is sent. A worker can then crash. Conversely, the provider may commit a write before the client records the successful response.


**Q38. [Interview] Why does Approval consumption is not proof of completion matter, and what is one important design implication?**

**Answer:** Therefore, do not infer the outcome solely from approval.used = true. Associate the approval with an action record whose execution state and receipt can be reconciled.

## 12. Approval Screens, Receipts and Audit Evidence

**Q43. [Conceptual] Explain Approval Screens, Receipts and Audit Evidence in simple, interview-ready language.**

**Answer:** An approval receipt proves that the approval workflow recorded a confirmation. An action receipt identifies what the executor accepted or completed. A verification record describes the resulting environment state.


**Q44. [Interview] Why does Approval Screens, Receipts and Audit Evidence matter, and what is one important design implication?**

**Answer:** A useful approval screen identifies the operation, target, important before-and-after values, affected scope, additional side effects and relevant expiry. It should be generated from the stored proposal that execution will use.

<a id="13-failure-patterns-and-design-decisions"></a>
## 13. Failure Patterns and Design Decisions

**Q49. [Conceptual] Explain Failure Patterns and Design Decisions in simple, interview-ready language.**

**Answer:** For a single-resource update in a service you control, an immutable proposal, current access check, approval claim and conditional write in one transaction can be straightforward.


**Q50. [Interview] Why does Failure Patterns and Design Decisions matter, and what is one important design implication?**

**Answer:** For a remote operation, preserve a durable execution intent and use the provider's documented idempotency, concurrency and receipt mechanisms. Explicitly describe any guarantee that remains unavailable.


<a id="17-l3-project-and-completion-evidence"></a>
## 17. L3 Project and Completion Evidence

**Q51. [Conceptual] Explain L3 Project and Completion Evidence in simple, interview-ready language.**

**Answer:** Retain the schema, action and approval records, expected state transitions, sanitized trace, test inputs, actual results and a brief explanation of the transaction boundary. State whether the effect is local or remote and what the provider guarantees.


**Q52. [Interview] Why does L3 Project and Completion Evidence matter, and what is one important design implication?**

**Answer:** L2 is demonstrated by explaining why each check exists. L3 requires running these cases and showing that the environment satisfies the intended invariants.
