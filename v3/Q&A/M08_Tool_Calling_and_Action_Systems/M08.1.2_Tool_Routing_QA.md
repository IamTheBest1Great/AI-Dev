## 1. Routing Fundamentals

**Q1. [Conceptual] Explain Routing Fundamentals in simple, interview-ready language.**

**Answer:** Tool routing is the process of identifying which available capability, if any, can satisfy the current task and selecting an appropriate operation for the next step.


**Q2. [Interview] Why does Routing Fundamentals matter, and what is one important design implication?**

**Answer:** Combining these into one model judgment makes failures difficult to diagnose. A missing tool, an irrelevant tool and a denied tool require different responses.


<a id="routing-can-select-no-tool"></a>
### Routing can select no tool

**Q3. [Conceptual] Explain Routing can select no tool in simple, interview-ready language.**

**Answer:** A user asking “What is a tool namespace?” may need a direct explanation. A user asking for the current state of a task needs an authoritative lookup if the answer is not already available.


**Q4. [Interview] Why does Routing can select no tool matter, and what is one important design implication?**

**Answer:** A router should not maximize the number of calls. It should advance the requested outcome with appropriate evidence and effects.


**Q5. [Scenario] A developer misunderstands Routing can select no tool while building a production tool-calling assistant. How would you correct the design?**

**Answer:** Clarify the actual behavior: A router should not maximize the number of calls. It should advance the requested outcome with appropriate evidence and effects. Demonstrate the difference with a concrete input and expected result before changing the system.


**Q6. [Project / Real-world] How would you demonstrate Routing can select no tool in a real production tool-calling assistant?**

**Answer:** Use the source’s practical detail: A router should not maximize the number of calls. It should advance the requested outcome with appropriate evidence and effects. Show a trace, baseline comparison, or test result that demonstrates the behavior.


<a id="routing-is-contextual"></a>
### Routing is contextual

**Q7. [Conceptual] Explain Routing is contextual in simple, interview-ready language.**

**Answer:** The same sentence can require different next steps depending on workflow state. “Check whether it finished” means something different after a long-running export than after a failed local calculation.


**Q8. [Interview] Why does Routing is contextual matter, and what is one important design implication?**

**Answer:** Preserve the identity of the ongoing operation. Do not interpret every user message as an entirely new action.

<a id="2-namespaces-and-tool-identity"></a>
## 2. Namespaces and Tool Identity

**Q11. [Conceptual] Explain Namespaces and Tool Identity in simple, interview-ready language.**

**Answer:** A namespace organizes names within a defined scope. It helps distinguish tools that otherwise have identical or similar names.


**Q12. [Interview] Why does Namespaces and Tool Identity matter, and what is one important design implication?**

**Answer:** Two services may both expose a tool called search. One searches approved manuals; the other searches task records. Even if both return text, they have different sources, permissions and purposes.


<a id="3-grouping-related-tools"></a>
## 3. Grouping Related Tools

**Q13. [Conceptual] Explain Grouping Related Tools in simple, interview-ready language.**

**Answer:** A flat catalog is simple when only a few tools exist. With many similarly named tools, a hierarchy can reduce ambiguity: domain first, operation second, precise tool last.


**Q14. [Interview] Why does Grouping Related Tools matter, and what is one important design implication?**

**Answer:** Grouping places tools into useful categories so that discovery and selection can narrow the search space.


<a id="4-designing-a-tool-catalog"></a>
## 4. Designing a Tool Catalog

**Q15. [Conceptual] Explain Designing a Tool Catalog in simple, interview-ready language.**

**Answer:** A tool catalog is an inventory of capabilities and the information needed to discover, understand and reference them.


**Q16. [Interview] Why does Designing a Tool Catalog matter, and what is one important design implication?**

**Answer:** A catalog may be static configuration, a database, a remote discovery response, or a combination. The important distinction is which fields come from trusted application control and which are external descriptive data.


<a id="5-selecting-the-appropriate-tool"></a>
## 5. Selecting the Appropriate Tool

**Q17. [Conceptual] Explain Selecting the Appropriate Tool in simple, interview-ready language.**

**Answer:** The task description is a planning aid. The model’s interpretation of it does not manufacture permission or consent.


**Q18. [Interview] Why does Selecting the Appropriate Tool matter, and what is one important design implication?**

**Answer:** Cost can distinguish otherwise suitable tools. It should not justify switching to an unauthorized source or weakening verification.


<a id="deterministic-rules-versus-model-selection"></a>
### Deterministic rules versus model selection

**Q19. [Conceptual] Explain Deterministic rules versus model selection in simple, interview-ready language.**

**Answer:** A deterministic router uses explicit conditions. It is easy to audit for a narrow domain but can require maintenance as tasks vary.


**Q20. [Interview] Why does Deterministic rules versus model selection matter, and what is one important design implication?**

**Answer:** A model router handles varied wording and complex descriptions, but can misinterpret intent or overvalue persuasive metadata.


**Q21. [Scenario] You must choose between the options in Deterministic rules versus model selection for a production tool-calling assistant. What would you compare?**

**Answer:** Use the distinction stated in the notes: A model router handles varied wording and complex descriptions, but can misinterpret intent or overvalue persuasive metadata. Compare correctness, operating constraints and the actual workload before choosing.

**Answer:** Use the source’s practical detail: A model router handles varied wording and complex descriptions, but can misinterpret intent or overvalue persuasive metadata. Show a trace, baseline comparison, or test result that demonstrates the behavior.


<a id="6-relevance-filtering"></a>
## 6. Relevance Filtering

**Q23. [Conceptual] Explain Relevance Filtering in simple, interview-ready language.**

**Answer:** It is a candidate-generation stage. It should preserve the right tools while removing obvious distractions.


**Q24. [Interview] Why does Relevance Filtering matter, and what is one important design implication?**

**Answer:** Define a routing evaluation query with an acceptable set of next tools. Candidate Recall@K asks whether that set is represented among the first K candidates. If several different tools are acceptable, specify how the metric handles alternatives.

### Description quality

**Q29. [Conceptual] Explain Description quality in simple, interview-ready language.**

<a id="7-discovery-and-catalog-freshness"></a>
## 7. Discovery and Catalog Freshness

**Q33. [Conceptual] Explain Discovery and Catalog Freshness in simple, interview-ready language.**

**Answer:** Discovery is different from choosing a tool for a specific request. It establishes or refreshes the inventory from which selection operates.


**Q34. [Interview] Why does Discovery and Catalog Freshness matter, and what is one important design implication?**

**Answer:** In MCP, initialization negotiates protocol compatibility and capabilities before normal operation. Only negotiated capabilities should be used. Source: MCP lifecycle specification, 2025-11-25.


<a id="8-dynamic-loading"></a>
## 8. Dynamic Loading

**Q35. [Conceptual] Explain Dynamic Loading in simple, interview-ready language.**

**Answer:** Dynamic loading, in this context, means bringing relevant tool definitions or approved adapters into the active workflow when needed.


**Q36. [Interview] Why does Dynamic Loading matter, and what is one important design implication?**

**Answer:** This design can reduce context size, but introduces additional steps and cache decisions. Measure its total latency rather than assuming fewer prompt tokens always mean a faster workflow.

<a id="cache-boundaries"></a>
### Cache boundaries

**Q41. [Conceptual] Explain Cache boundaries in simple, interview-ready language.**

**Answer:** A schema cache hit says that a definition is available. It does not say that the current user can execute it.


**Q42. [Interview] Why does Cache boundaries matter, and what is one important design implication?**

**Answer:** Cache schemas by origin and revision. Cache permitted views with appropriate scope. Invalidate or refresh entries when the relevant lifecycle or access state changes.

## 9. Binding a Selection to Execution

**Q45. [Conceptual] Explain Binding a Selection to Execution in simple, interview-ready language.**

**Answer:** MCP’s HTTP authorization specification describes access at the transport level. Access to a server must still be combined with the application’s rules for individual business operations and resources. Source: MCP authorization specification, 2025-11-25.


**Q46. [Interview] Why does Binding a Selection to Execution matter, and what is one important design implication?**

**Answer:** After a write attempt, status and read-back should refer to the original connection, target and logical operation.

<a id="12-runnable-routing-example"></a>
## 12. Runnable Routing Example

**Q55. [Conceptual] Explain Runnable Routing Example in simple, interview-ready language.**

**Answer:** The catalog’s route identity, domain, effect and revision are trusted fixture configuration. Only descriptions represent imported text. In a real system, a provider’s descriptive hints must not automatically become the trusted effect policy.


**Q56. [Interview] Why does Runnable Routing Example matter, and what is one important design implication?**

**Answer:** The expected revision in the successful call is application-held state representing the contract selected earlier. It should not be accepted as an authoritative value supplied by the model.

## 17. L3 Project Exercise and Acceptance Evidence

**Q63. [Conceptual] Explain L3 Project Exercise and Acceptance Evidence in simple, interview-ready language.**

**Answer:** Build a fictional tool catalog and router for manuals, assets and tasks. Include at least two connections with overlapping short names, one read tool, one write tool and an operation-status capability.
