## 1. Tool Fundamentals

**Q1. [Conceptual] Explain Tool Fundamentals in simple, interview-ready language.**

**Answer:** A tool is a callable capability through which an AI application obtains information, performs a computation, or requests an action in another system. Examples include searching manuals, reading a task, calculating a value and creating a maintenance record.


**Q2. [Interview] Why does Tool Fundamentals matter, and what is one important design implication?**

**Answer:** The model usually proposes a tool name and arguments. The application decides whether that proposal is valid and permitted, executes through an approved implementation, and interprets the result.


<a id="a-tool-call-is-not-ordinary-prose"></a>
### A tool call is not ordinary prose

**Q3. [Conceptual] Explain A tool call is not ordinary prose in simple, interview-ready language.**

**Answer:** Writing “I created task T-104” does not create a task. Producing a correctly shaped tool-call object also does not prove that execution happened.


**Q4. [Interview] Why does A tool call is not ordinary prose matter, and what is one important design implication?**

**Answer:** A failure between events matters. If the network disconnects after a write commits, the model may see a timeout even though the task now exists.


**Q5. [Scenario] A developer misunderstands A tool call is not ordinary prose while building a production tool-calling assistant. How would you correct the design?**

## 2. Anatomy of a Tool Contract

**Q11. [Conceptual] Explain Anatomy of a Tool Contract in simple, interview-ready language.**

**Answer:** Prefer operations with a clear business meaning. A tool named “manageeverything” with dozens of optional arguments is difficult to select, validate and audit.


**Q12. [Interview] Why does Anatomy of a Tool Contract matter, and what is one important design implication?**

**Answer:** A tool contract specifies the operation’s identity, inputs, outputs, meaning, constraints and observable outcomes. It should let a caller distinguish a successful result from a rejected request, an incomplete operation and an unknown outcome.


<a id="tool-call-versus-logical-operation"></a>
### Tool call versus logical operation

**Q13. [Conceptual] Explain Tool call versus logical operation in simple, interview-ready language.**

**Answer:** One user intention can involve several technical calls: resolve the asset, validate the request, create a task, and check its status. These calls belong to one logical operation.


**Q14. [Interview] Why does Tool call versus logical operation matter, and what is one important design implication?**

**Answer:** Keep the identity of that logical operation stable through retries and status checks. Otherwise, a recovered network call can accidentally become a second business action.


**Q15. [Scenario] You must choose between the options in Tool call versus logical operation for a production tool-calling assistant. What would you compare?**

## 3. Schema Design

**Q17. [Conceptual] Explain Schema Design in simple, interview-ready language.**

**Answer:** A schema defines the allowed structure of data. For tool calls, it tells the application which fields can appear, what types and values they accept, and which combinations are valid.


**Q18. [Interview] Why does Schema Design matter, and what is one important design implication?**

**Answer:** JSON Schema has versions, called dialects. Tools and providers may support different subsets or impose additional requirements. An input accepted by a general-purpose JSON Schema validator is not automatically accepted by every model-facing tool interface.


<a id="json-schema-fundamentals"></a>
### JSON Schema fundamentals

**Q19. [Conceptual] Explain JSON Schema fundamentals in simple, interview-ready language.**

**Answer:** JSON Schema uses keywords such as type, properties, required and additionalProperties to describe objects. Declaring a property does not automatically make it required, and undeclared properties are not automatically rejected. These behaviors must be specified deliberately. ### Schema size and clarity

**Q23. [Conceptual] Explain Schema size and clarity in simple, interview-ready language.**

**Answer:** Do not simplify by hiding important distinctions. “amount” without currency and units is shorter than “amountminor” plus “currency,” but it is ambiguous.


**Q24. [Interview] Why does Schema size and clarity matter, and what is one important design implication?**

**Answer:** A very large schema can overwhelm selection and argument generation. Remove unused fields, use meaningful names and split unrelated operations.

## 4. Required and Optional Inputs

**Q27. [Conceptual] Explain Required and Optional Inputs in simple, interview-ready language.**

**Answer:** A required field must appear in the input object. That does not automatically mean its value is nonempty, non-null or meaningful.


**Q28. [Interview] Why does Required and Optional Inputs matter, and what is one important design implication?**

**Answer:** Avoid one optional field having different meanings in different code paths. A missing priority must not mean “normal” in one adapter and “highest urgency” in another.

## 5. Typed Inputs and Outputs

**Q29. [Conceptual] Explain Typed Inputs and Outputs in simple, interview-ready language.**

**Answer:** Types prevent ambiguous representations from crossing system boundaries. The string “false” is not the Boolean false, and the string “10” is not the number 10.


**Q30. [Interview] Why does Typed Inputs and Outputs matter, and what is one important design implication?**

**Answer:** If the user says “tomorrow afternoon,” resolving an exact timestamp may require a timezone and a defined scheduling convention. The tool schema should not encourage the model to invent missing details that materially affect the action.

## 9. Trusted Execution Context

**Q49. [Conceptual] Explain Trusted Execution Context in simple, interview-ready language.**

**Answer:** Having account permission to create tasks does not mean every user message authorizes creation. “Show me the open tasks” is a read request.


**Q50. [Interview] Why does Trusted Execution Context matter, and what is one important design implication?**

## 10. Result Normalization

**Q51. [Conceptual] Explain Result Normalization in simple, interview-ready language.**

**Answer:** Result normalization converts different backend response forms into a consistent application-level contract while preserving their meaning, evidence and uncertainty.


**Q52. [Interview] Why does Result Normalization matter, and what is one important design implication?**

**Answer:** One service may return a record directly, another may return a job ID, and another may use an error envelope. The model should receive a clear account of the outcome instead of guessing from inconsistent transport details.

## 11. Worked Task-Creation Workflow

**Q65. [Conceptual] Explain Worked Task-Creation Workflow in simple, interview-ready language.**

**Answer:** An authorized lookup returns ASSET-0007 and its relevant attributes. The assistant uses that exact identifier. A similarly named asset in tenant B is outside the allowed scope.


**Q66. [Interview] Why does Worked Task-Creation Workflow matter, and what is one important design implication?**

**Answer:** Before dispatch, the executor records one logical operation with the normalized business payload and its deduplication identity. A retry of the same intended action uses that identity; a materially different action requires a separate operation.

## 13. Schema Evolution and Testing

**Q71. [Conceptual] Explain Schema Evolution and Testing in simple, interview-ready language.**

**Answer:** Record schema versions and adapter versions. Test old and new producers and consumers according to the compatibility policy rather than assuming additive changes are always safe.


**Q72. [Interview] Why does Schema Evolution and Testing matter, and what is one important design implication?**

**Answer:** Documentation examples should validate under the stated schema. Negative examples should fail for the intended reason.

## 17. L3 Project Exercise and Acceptance Evidence

**Q73. [Conceptual] Explain L3 Project Exercise and Acceptance Evidence in simple, interview-ready language.**

**Answer:** Build a small controlled task tool with a documented schema, trusted execution context, normalized outcomes and a simulated backend capable of committing a write before losing its response.


**Q74. [Interview] Why does L3 Project Exercise and Acceptance Evidence matter, and what is one important design implication?**
