## 1. Tool-Permission Fundamentals

**Q1. [Conceptual] Explain Tool-Permission Fundamentals in simple, interview-ready language.**

**Answer:** A tool permission specifies whether an identity may invoke a particular operation on particular resources under stated conditions. It is enforced by trusted software, not created by the language model's desire to finish a task.


**Q2. [Interview] Why does Tool-Permission Fundamentals matter, and what is one important design implication?**

**Answer:** A service credential might technically allow deletion of every task. The assistant's authority for the current request may extend only to reading one project. Broad backend capability must therefore be constrained by application policy and the authenticated user's scope.


<a id="2-a-practical-action-classification"></a>
## 2. A Practical Action Classification

**Q3. [Conceptual] Explain A Practical Action Classification in simple, interview-ready language.**

**Answer:** The examples are risk reasoning exercises, not universal classifications. An application's policy must account for its actual business rules.


**Q4. [Interview] Why does A Practical Action Classification matter, and what is one important design implication?**

**Answer:** A useful action classification distinguishes read-only operations, low-risk writes, high-risk writes, and actions involving irreversible effects, money, or sensitive information.


<a id="context-changes-risk"></a>
### Context changes risk

**Q5. [Conceptual] Explain Context changes risk in simple, interview-ready language.**

**Answer:** The tool name is identical, but the effects differ. Classify the operation, fields, target scope, audience, automation, reversibility, and sensitivity together.


**Q6. [Interview] Why does Context changes risk matter, and what is one important design implication?**

**Answer:** Changing a personal color preference affects only one user's display. Changing the due date of a shared task may alter reminders and schedules. Changing visibility to public may disclose the entire task history.

<a id="3-read-only-tools"></a>
## 3. Read-Only Tools

**Q9. [Conceptual] Explain Read-Only Tools in simple, interview-ready language.**

**Answer:** Authorize the specific object and the returned fields. If Lina has access to P-17, that does not imply access to P-29 in the same tenant. Matching a tenant alone is insufficient for finer project permissions.


**Q10. [Interview] Why does Read-Only Tools matter, and what is one important design implication?**

**Answer:** Permission to read a record does not automatically permit sending it to every tool. A local summary tool and an external analysis service may have different approved processing scopes.


<a id="4-low-risk-writes"></a>
## 4. Low-Risk Writes

**Q11. [Conceptual] Explain Low-Risk Writes in simple, interview-ready language.**

**Answer:** A low-risk write makes a bounded change whose consequences are limited, understood, recoverable, and verifiable in the current context.


**Q12. [Interview] Why does Low-Risk Writes matter, and what is one important design implication?**

**Answer:** Recoverability should be established, not assumed. An “undo” button may reverse one field while leaving notifications, audit events, or downstream actions intact.


<a id="5-high-risk-writes"></a>
## 5. High-Risk Writes

**Q13. [Conceptual] Explain High-Risk Writes in simple, interview-ready language.**

**Answer:** Blast radius describes the scope of possible consequences. Reassigning T-104 affects one task. Reassigning every overdue task may affect hundreds of owners and notification recipients.


**Q14. [Interview] Why does High-Risk Writes matter, and what is one important design implication?**

**Answer:** A high-risk write can substantially affect other people, many records, important workflows, access rights, availability, or external systems.


<a id="6-irreversible-financial-and-sensitive-actions"></a>
## 6. Irreversible, Financial, and Sensitive Actions

**Q15. [Conceptual] Explain Irreversible, Financial, and Sensitive Actions in simple, interview-ready language.**

**Answer:** An irreversible action cannot reliably restore the prior situation. Permanent deletion is an obvious example, but disclosure is another: once a private export reaches an external party, deleting the original file does not recall the copy.


**Q16. [Interview] Why does Irreversible, Financial, and Sensitive Actions matter, and what is one important design implication?**

**Answer:** Do not treat any human response as equivalent to the designated review. The important issue is valid authority over the concrete action, not merely the presence of a confirmation message.


<a id="7-server-side-permission-enforcement"></a>
## 7. Server-Side Permission Enforcement

**Q17. [Conceptual] Explain Server-Side Permission Enforcement in simple, interview-ready language.**

**Answer:** Every protected access or state change should pass through the appropriate enforcement point. The model's decision to call a tool is not that enforcement point.


**Q18. [Interview] Why does Server-Side Permission Enforcement matter, and what is one important design implication?**

**Answer:** Resolve tenant, user, groups, and relevant attributes from authenticated server state. Do not accept isadmin: true, a different tenant ID, or a list of permitted projects from ordinary model arguments.

<a id="least-privilege-for-tools-and-credentials"></a>
### Least privilege for tools and credentials

**Q23. [Conceptual] Explain Least privilege for tools and credentials in simple, interview-ready language.**

**Answer:** Expose only the operations needed for the workflow. Use service credentials with a bounded scope, and keep secrets out of the model's context.


**Q24. [Interview] Why does Least privilege for tools and credentials matter, and what is one important design implication?**

**Answer:** Where a connector acts through a service account, enforce the requesting user's rights in addition to the account's technical capability. Otherwise the assistant can become a confused deputy: a broadly privileged component misused on behalf of a less privileged requester.


**Q25. [Scenario] A developer misunderstands Least privilege for tools and credentials while building a production tool-calling assistant. How would you correct the design?**

**Answer:** Clarify the actual behavior: OWASP's Excessive Agency guidance identifies excessive functionality, permissions, and autonomy as related sources of risk. Reducing unnecessary capabilities limits the consequences of mistakes and malicious instructions. Demonstrate the difference with a concrete input and expected result before changing the system.

<a id="8-explicit-authorization-and-risk-based-approvals"></a>
## 8. Explicit Authorization and Risk-Based Approvals

**Q27. [Conceptual] Explain Explicit Authorization and Risk-Based Approvals in simple, interview-ready language.**

**Answer:** Explicitness does not require a special phrase. “Archive these three completed tasks” is a clear action request if the three tasks are identified and the policy permits it.


**Q28. [Interview] Why does Explicit Authorization and Risk-Based Approvals matter, and what is one important design implication?**

**Answer:** For a consequential action, the intended operation, targets, material parameters, and expected effects should be clear. “Please review my tasks” does not by itself authorize deleting them.

<a id="10-a-permission-decision-workflow"></a>
## 10. A Permission Decision Workflow

**Q33. [Conceptual] Explain A Permission Decision Workflow in simple, interview-ready language.**

**Answer:** Confirm that the proposed effect is within the user's request and the principal's permitted operations. Both must be satisfied.


**Q34. [Interview] Why does A Permission Decision Workflow matter, and what is one important design implication?**

**Answer:** The adapter revalidates current permission, inputs, and preconditions and applies the operation using the appropriate idempotency and verification contract. The planner should not bypass this adapter.

## 11. Runnable Policy-Gate Example

**Q35. [Conceptual] Explain Runnable Policy-Gate Example in simple, interview-ready language.**

**Answer:** validapproval represents a decision already verified by trusted approval code. It must never be accepted as a client-supplied Boolean.


**Q36. [Interview] Why does Runnable Policy-Gate Example matter, and what is one important design implication?**

**Answer:** This Python standard-library fixture demonstrates the ordering of a few permission decisions. It does not implement authentication, durable approval storage, a network tool, or action execution.


<a id="deliberate-limitations"></a>
### Deliberate limitations

**Q37. [Conceptual] Explain Deliberate limitations in simple, interview-ready language.**

**Answer:** The fixture's intent set binds only target and operation. A real action intent and approval must also bind material parameters, such as the new assignee, external destination, and relevant resource version. Its risk table is simplified; production classification must inspect actual fields and side effects.

**Answer:** The example checks permission in memory at one instant. Real execution needs a defined current-policy and concurrency contract. A PERMIT result is not a permanent capability to execute later after state changes.

## 12. Worked Scenarios and Common Mistakes

**Q41. [Conceptual] Explain Worked Scenarios and Common Mistakes in simple, interview-ready language.**

**Answer:** Lina asks to add “Reviewed” to T-104 in P-17. The server verifies her project-edit permission and confirms that the label has no workflow trigger. The intended field and value are clear.


**Q42. [Interview] Why does Worked Scenarios and Common Mistakes matter, and what is one important design implication?**

**Answer:** The reassignment request times out after dispatch. The assistant should not ask “May I try again?” as if approval resolves the execution uncertainty.


<a id="16-l3-project-and-acceptance-evidence"></a>
## 16. L3 Project and Acceptance Evidence

**Q43. [Conceptual] Explain L3 Project and Acceptance Evidence in simple, interview-ready language.**

**Answer:** A matrix mapping users, operations, projects, objects, and allowed fields. Server-side rejection of cross-tenant and same-tenant unauthorized IDs. Rejection of an extra unauthorized field in an otherwise valid payload. A permitted routine write executed without redundant approval. A high-impact action blocked until its required concrete approval is valid. Proof that an approval cannot override a denied permission. A sensitive read or dry run checked for data and destination access.


**Q44. [Interview] Why does L3 Project and Acceptance Evidence matter, and what is one important design implication?**

**Answer:** Build a fictional task API with two tenants, two projects within one tenant, three users, and separate read, label, reassignment, and deletion operations.


**Q45. [Scenario] A developer misunderstands L3 Project and Acceptance Evidence while building a production tool-calling assistant. How would you correct the design?**

**Answer:** Clarify the actual behavior: Implement a trusted permission gate and a risk policy that considers at least data sensitivity, target count, and notification effects. Integrate approval decisions using the contract from M08.5.1, and execution verification using M08.4.1. Demonstrate the difference with a concrete input and expected result before changing the system.


**Q46. [Project / Real-world] How would you demonstrate L3 Project and Acceptance Evidence in a real production tool-calling assistant?**

**Answer:** Use the source’s practical detail: Acceptance criterion: Every effect must be attributable to a permitted operation inside the user's valid task scope. A model's statement that an action is safe, approved, or complete is not completion evidence. Show a trace, baseline comparison, or test result that demonstrates the behavior.
