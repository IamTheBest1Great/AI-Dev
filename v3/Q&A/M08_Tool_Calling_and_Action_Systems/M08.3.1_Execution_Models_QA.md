## 1. Execution Model Fundamentals

**Q1. [Conceptual] Explain Execution Model Fundamentals in simple, interview-ready language.**

**Answer:** An execution model determines when tool calls run, which calls depend on earlier results, how concurrent results are combined, and what happens when only some work succeeds.


**Q2. [Interview] Why does Execution Model Fundamentals matter, and what is one important design implication?**

**Answer:** Consider a request to create a maintenance task for an authorized resource. The application may need to load the resource, verify current policy, check a required field, create the task, and verify the resulting record. Those steps have different responsibilities and failure consequences.


<a id="execution-is-about-state-transitions"></a>
### Execution is about state transitions

**Q3. [Conceptual] Explain Execution is about state transitions in simple, interview-ready language.**

**Answer:** For a remote write, “the client stopped waiting” is a statement about the client. It is not a statement about whether the server created the record.


**Q4. [Interview] Why does Execution is about state transitions matter, and what is one important design implication?**

**Answer:** Represent calls with explicit states rather than one done Boolean. Useful distinctions include planned, blocked, authorized, dispatched, acknowledged, succeeded, failed, unknown, and awaiting reconciliation.


**Q5. [Scenario] A developer misunderstands Execution is about state transitions while building a production tool-calling assistant. How would you correct the design?**

### Tool capability versus task permission

**Q7. [Conceptual] Explain Tool capability versus task permission in simple, interview-ready language.**

**Answer:** Use allowlisted tools, validated arguments, server-derived tenant/resource scope, and appropriate credentials. Never treat a model-generated tenantid, document instruction, or earlier successful call as proof that a later write is permitted.


**Q8. [Interview] Why does Tool capability versus task permission matter, and what is one important design implication?**

**Answer:** A tool may technically support deleting any task in a database. The current request may authorize only creating a draft task for ship A. The executor should apply the narrower task and identity scope.

## 2. Single Calls

**Q11. [Conceptual] Explain Single Calls in simple, interview-ready language.**

**Answer:** Before dispatch, validate the tool name, argument types, resource identity, permissions, and preconditions. After dispatch, validate the response and determine whether the intended result is established.


**Q12. [Interview] Why does Single Calls matter, and what is one important design implication?**

**Answer:** The application now has one dispatched call and an unknown outcome. It must reconcile or retry under the same established idempotency contract. Creating a new operation ID solely because the response was lost can create a second task.

## 3. Sequential Calls

**Q21. [Conceptual] Explain Sequential Calls in simple, interview-ready language.**

**Answer:** Two independent reads can be run sequentially for simplicity or rate-limit control. Their ordering is a scheduling choice, not a data dependency.


**Q22. [Interview] Why does Sequential Calls matter, and what is one important design implication?**

**Answer:** Sequential order can be necessary because data flows between calls, because a business rule imposes order, or because shared-resource contention makes concurrency unsuitable.


<a id="what-counts-as-completion-of-a-step"></a>
### What counts as completion of a step?

**Q23. [Conceptual] What counts as completion of a step?**

**Answer:** An API may return an acknowledgment that processing has started. That is different from the business operation being completed.


**Q24. [Interview] How would you justify the answer to “What counts as completion of a step?” in an interview?**

**Answer:** Define dependency conditions precisely: “request accepted,” “record committed,” “record visible,” and “business process complete” are different milestones.


**Q25. [Scenario] In a production tool-calling assistant, how would you test the behavior discussed in “What counts as completion of a step?”?**

**Answer:** Clarify the actual behavior: If step 2 requires a completed export, an accepted export job is not enough. The workflow needs to wait for or query the job’s terminal result before consuming its output. Demonstrate the difference with a concrete input and expected result before changing the system.

### Benefits and costs

**Q27. [Conceptual] Explain Benefits and costs in simple, interview-ready language.**

**Answer:** Sequential execution is easier to reason about and can reduce concurrent contention. It can also add avoidable waiting when many calls are independent.


**Q28. [Interview] Why does Benefits and costs matter, and what is one important design implication?**

## 4. Dependent Calls and Dependency Graphs

**Q31. [Conceptual] Explain Dependent Calls and Dependency Graphs in simple, interview-ready language.**

**Answer:** A dependent call requires data or a verified condition from another call. A dependency graph represents these relationships explicitly.


**Q32. [Interview] Why does Dependent Calls and Dependency Graphs matter, and what is one important design implication?**

**Answer:** For a bounded workflow without intentional loops, a directed acyclic graph, or DAG, is a useful representation. An edge from A to B means B cannot run until A satisfies its dependency condition.


<a id="scheduling-ready-work"></a>
### Scheduling ready work

**Q33. [Conceptual] Explain Scheduling ready work in simple, interview-ready language.**

**Answer:** A node is ready when its required predecessors have succeeded and its own authorization, deadline, and resource constraints permit execution.


**Q34. [Interview] Why does Scheduling ready work matter, and what is one important design implication?**

**Answer:** A failed predecessor can mark dependents as blocked. An unknown predecessor should retain that uncertainty rather than being silently converted to failure.

<a id="5-parallel-calls"></a>
## 5. Parallel Calls

**Q37. [Conceptual] Explain Parallel Calls in simple, interview-ready language.**

**Answer:** Parallel execution allows several operations to be in progress at the same time. It can reduce waiting when operations are independent and the system has available capacity.


**Q38. [Interview] Why does Parallel Calls matter, and what is one important design implication?**

**Answer:** Concurrency is not a guarantee of simultaneous CPU execution. Threads, asynchronous I/O, processes, and remote workers have different behavior. Choose the mechanism according to the workload and runtime.


<a id="6-fan-out-and-fan-in"></a>
## 6. Fan-Out and Fan-In

**Q39. [Conceptual] Explain Fan-Out and Fan-In in simple, interview-ready language.**

**Answer:** The plan should specify why each branch exists, whether it is required, its deadline, and how its result contributes to the final task.


**Q40. [Interview] Why does Fan-Out and Fan-In matter, and what is one important design implication?**

**Answer:** For a draft task, optional background notes may be omitted. Current authorization and required business fields are not optional merely because their services are slow.

### Early completion and remaining work

**Q41. [Conceptual] Explain Early completion and remaining work in simple, interview-ready language.**

**Answer:** For writes, do not abandon tracking simply because another branch failed. A late receipt may be essential to establish whether compensation or further verification is needed.

<a id="7-partial-failure"></a>
## 7. Partial Failure

**Q45. [Conceptual] Explain Partial Failure in simple, interview-ready language.**

**Answer:** Distributed calls do not share the simple failure boundary of one local function. A client process can fail after a remote service commits a write, and one branch can be healthy while another is unavailable.


**Q46. [Interview] Why does Partial Failure matter, and what is one important design implication?**

**Answer:** A local argument-validation error before any dispatch differs from a connection loss after a write request was sent. Treating both as “try again” ignores the most important distinction.


<a id="8-timeout-cancellation-and-unknown-outcomes"></a>
## 8. Timeout, Cancellation, and Unknown Outcomes

**Q47. [Conceptual] Explain Timeout, Cancellation, and Unknown Outcomes in simple, interview-ready language.**

**Answer:** A timeout means the caller’s waiting policy expired. It does not establish that the service never received the request or that the service rolled it back.


**Q48. [Interview] Why does Timeout, Cancellation, and Unknown Outcomes matter, and what is one important design implication?**

**Answer:** An open circuit breaker prevents or limits new calls. It does not undo earlier calls or prove that outstanding writes failed.


<a id="9-compensation"></a>
## 9. Compensation

**Q49. [Conceptual] Explain Compensation in simple, interview-ready language.**

**Answer:** A compensating action is a new business operation intended to counteract some effect of an earlier completed operation.


**Q50. [Interview] Why does Compensation matter, and what is one important design implication?**

**Answer:** It is not a magical rollback of time. It can have different semantics, permissions, costs, and failure modes from the original action.


<a id="10-worked-verified-action-workflow"></a>
## 10. Worked Verified-Action Workflow

**Q51. [Conceptual] Explain Worked Verified-Action Workflow in simple, interview-ready language.**

**Answer:** If optional descriptive notes are unavailable, the workflow may continue only if those notes were explicitly optional and their absence does not change the requested task semantics.


**Q52. [Interview] Why does Worked Verified-Action Workflow matter, and what is one important design implication?**

**Answer:** A useful unknown-status message is: “The task creation request was submitted, but its result has not yet been confirmed. The workflow is checking the original operation before attempting another write.”.

<a id="12-testing-and-l3-project-exercise"></a>
## 12. Testing and L3 Project Exercise

**Q59. [Conceptual] Explain Testing and L3 Project Exercise in simple, interview-ready language.**

**Answer:** Unauthorized scope is blocked before dispatch. A required read failure blocks the write. An optional read failure preserves a clearly labeled partial preview. Independent reads can overlap without mismatched results. A dependent call receives only a verified predecessor ID. A write commits but its response is lost. Recovery resolves the original operation without a second effect. A compensation succeeds, fails, or remains unknown with accurate state. A process restart resumes from durable progress.


**Q60. [Interview] Why does Testing and L3 Project Exercise matter, and what is one important design implication?**

**Answer:** Keep operation IDs, payload fingerprints, authorized resource scope, state transitions, service receipts, attempt counts, and verified effect counts. Protect these artifacts because they can contain sensitive identifiers.
