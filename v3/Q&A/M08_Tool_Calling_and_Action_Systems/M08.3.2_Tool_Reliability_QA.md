## 1. Tool Reliability Fundamentals

**Q1. [Conceptual] Explain Tool Reliability Fundamentals in simple, interview-ready language.**

**Answer:** Tool reliability is the ability to perform the intended authorized operation, recognize its actual outcome, and recover from failures without introducing unacceptable additional effects.


**Q2. [Interview] Why does Tool Reliability Fundamentals matter, and what is one important design implication?**

**Answer:** It includes more than uptime. A tool that responds quickly with the wrong tenant’s record is not reliable. A retry loop that eventually returns success after creating three tasks is not reliable. A timeout handler that declares failure after the server committed the write is not reliable either.


<a id="2-side-effect-classification"></a>
## 2. Side-Effect Classification

**Q3. [Conceptual] Explain Side-Effect Classification in simple, interview-ready language.**

**Answer:** RFC 9110 distinguishes safe methods from idempotent methods. Safe methods have read-oriented intended semantics. Idempotent methods are defined so repeating the same request has the same intended effect as making it once.


**Q4. [Interview] Why does Side-Effect Classification matter, and what is one important design implication?**

**Answer:** Classification should describe the actual endpoint behavior. Do not infer it only from a tool name or HTTP verb.

## 4. Timeouts, Deadlines, and Cancellation

**Q31. [Conceptual] Explain Timeouts, Deadlines, and Cancellation in simple, interview-ready language.**

**Answer:** A deadline is the latest time by which the complete operation should finish or transition to an explicit unresolved state.


**Q32. [Interview] Why does Timeouts, Deadlines, and Cancellation matter, and what is one important design implication?**

**Answer:** A timeout that is too short creates unnecessary retries and unknown outcomes. A timeout that is too long consumes resources and delays useful recovery.

## 5. Retries and Retry Budgets

**Q37. [Conceptual] Explain Retries and Retry Budgets in simple, interview-ready language.**

**Answer:** A retry repeats an attempt to complete the same logical operation after a failure. It is not a new business request.


**Q38. [Interview] Why does Retries and Retry Budgets matter, and what is one important design implication?**

**Answer:** Status codes provide clues, not a complete business-outcome model. A server error can occur after a commit, and a conflict can mean several different things.

## 7. Circuit Breakers

**Q45. [Conceptual] Explain Circuit Breakers in simple, interview-ready language.**

**Answer:** Azure’s Circuit Breaker pattern describes closed, open, and half-open states and distinguishes circuit breaking from retry logic.


**Q46. [Interview] Why does Circuit Breakers matter, and what is one important design implication?**

**Answer:** A circuit breaker temporarily limits calls to a dependency that appears unhealthy. It aims to reduce repeated failures and allow recovery.


<a id="8-fallbacks"></a>
## 8. Fallbacks

**Q47. [Conceptual] Explain Fallbacks in simple, interview-ready language.**

**Answer:** A fallback uses an alternative path when the preferred path is unavailable or unsuitable. It is valid only if it preserves the guarantees required by the task.


**Q48. [Interview] Why does Fallbacks matter, and what is one important design implication?**

**Answer:** A different write service may not share the original service’s deduplication scope. Switching services after an ambiguous create can produce one record in each system.


<a id="queuing-as-fallback"></a>
### Queuing as fallback

**Q49. [Conceptual] Explain Queuing as fallback in simple, interview-ready language.**

**Answer:** A queued request is accepted for later processing, not completed. It needs durable identity, expiry, authorization policy for delayed execution, deduplication, and a way to report eventual status.


**Q50. [Interview] Why does Queuing as fallback matter, and what is one important design implication?**

**Answer:** Do not silently queue an action when the user expected it to happen now if the delay changes its meaning materially. The user-facing state should reflect what the system actually accepted.

## 9. Idempotency

**Q57. [Conceptual] Explain Idempotency in simple, interview-ready language.**

**Answer:** Idempotency means that repeating the same intended operation does not create additional intended effects under a defined contract.


**Q58. [Interview] Why does Idempotency matter, and what is one important design implication?**

**Answer:** Use a stable logical operation key to express intent. Use a payload fingerprint to detect accidental reuse of that key with different arguments.

**Q69. [Conceptual] Explain Worked Failure and Recovery Timeline in simple, interview-ready language.**

## 13. Testing and L3 Project Exercise

**Q73. [Conceptual] Explain Testing and L3 Project Exercise in simple, interview-ready language.**

**Answer:** Count committed tasks, reservations, messages, or other relevant outcomes at the authoritative system. A client’s attempt count is not an effect count, and one returned response does not prove one committed effect.


**Q74. [Interview] Why does Testing and L3 Project Exercise matter, and what is one important design implication?**

**Answer:** Test failures before dispatch, before commit, after commit but before response, during verification, and during recovery. These locations produce different knowledge about the effect.
