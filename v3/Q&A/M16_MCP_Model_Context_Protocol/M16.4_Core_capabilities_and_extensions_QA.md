## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q33. [Interview] Explain core capabilities and extensions to an interviewer.**

**Answer:** Follow-up 1 — What would you test first? A negative case involving stateless protocol core and a normal task with a verified outcome.


**Q34. [Interview] How would you design Stateless protocol core from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Identify who owns this information, where it lives, and when it changes. Keep transient model context distinct from durable application state and enforce scope on every read and write. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q35. [Interview] How do Multi-round-trip request patterns and Header-based routing interact?**

**Answer:** Interview answer: First define their separate responsibilities. In this part of a remote MCP gateway for internal enterprise tools, Multi-round-trip request patterns is an explicit design concern. Define its inputs, owner, observable result and failure handling before implementing it. Its purpose must be linked to the overall goal: expose typed capabilities with authenticated, per-call authorization.


**Q36. [Interview] What would you do if Cacheable list results fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure unauthorized calls rejected and supported operations interoperable.


**Q37. [Interview] When would you avoid a framework or model for core capabilities and extensions?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q38. [Interview] How would you demonstrate L3 production readiness for M16.4?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the version-pinned MCP integration and conformance test report, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
