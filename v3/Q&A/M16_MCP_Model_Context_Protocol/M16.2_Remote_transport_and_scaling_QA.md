## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q33. [Interview] Explain remote transport and scaling to an interviewer.**

**Answer:** Follow-up 1 — What would you test first? A negative case involving http-native architecture and a normal task with a verified outcome.


**Q34. [Interview] How would you design HTTP-native architecture from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Use HTTP transport and ordinary networking infrastructure for remote MCP connections, following the negotiated specification version. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q35. [Interview] How do Stateless design and Horizontal scaling interact?**

**Answer:** Interview answer: First define their separate responsibilities. Each request contains enough identity and metadata to be processed independently; persistent agent workflows belong above the transport. Add equivalent server instances behind a balancer, avoiding hidden in-process session assumptions and preserving auth and rate limits. I would connect them only through a typed handoff with provenance and an explicit postcondition, rather than allowing hidden state coupling.


**Q36. [Interview] What would you do if Load balancers fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure unauthorized calls rejected and supported operations interoperable.


**Q37. [Interview] When would you avoid a framework or model for remote transport and scaling?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q38. [Interview] How would you demonstrate L3 production readiness for M16.2?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the version-pinned MCP integration and conformance test report, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
