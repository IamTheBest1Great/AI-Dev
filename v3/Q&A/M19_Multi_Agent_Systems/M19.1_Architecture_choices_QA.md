## M19.1.2 — When not to use multi-agent

**Q33. [Interview] What should an engineer understand about When not to use multi-agent (M19.1.2)?**

**Answer:** Use a single structured workflow when it is simpler, more reliable, cheaper, and easier to test.


**Q34. [Scenario] Why could overlooking When not to use multi-agent create problems in a multi-agent research workflow?**

**Answer:** In a research organization with specialist agents, this changes the decision criteria or the allowed workflow. Record who owns the rule, when it applies and how to verify compliance.

## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q63. [Interview] Explain architecture choices to an interviewer.**

**Answer:** Interview answer: Architecture choices addresses the need to compare multi-agent coordination against a strong single-workflow baseline. I would begin with a bounded design for a research organization with specialist agents, then specify contracts for Supervisor and Orchestrator-worker. I would measure task quality per cost and coordination-failure rate, verify the actual outcome and demonstrate handling of the primary failure:.


**Q64. [Interview] How would you design Supervisor from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. A central decision-maker assigns work to specialist agents, checks their results and decides whether to retry, ask a human or finish. Use explicit budget and authority limits. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q65. [Interview] How do Orchestrator-worker and Hierarchical interact?**

**Answer:** Interview answer: First define their separate responsibilities. The orchestrator defines subtasks and coordinates completion; workers execute well-scoped units. Workers should not invent new privileged responsibilities. Agents are arranged into levels of coordination, allowing local supervision but adding delegation latency and possible information loss at each boundary.


**Q66. [Interview] What would you do if Peer-to-peer fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure task quality per cost and coordination-failure rate.


**Q67. [Interview] When would you avoid a framework or model for architecture choices?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q68. [Interview] How would you demonstrate L3 production readiness for M19.1?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the single-agent versus multi-agent benchmark and coordination trace, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
