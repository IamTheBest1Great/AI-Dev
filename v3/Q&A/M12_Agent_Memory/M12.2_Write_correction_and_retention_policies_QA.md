### M12.2.1.1 — Write decisions and evidence

<a id="what-to-write"></a>
#### What to write

**Q1. [Conceptual] What is what to write, and why does it matter in Write decisions and evidence?**

**Answer:** Write memory only when it has durable utility, sufficient evidence, permitted purpose and a correction path; avoid storing every conversation statement as a fact.


**Q2. [Interview] Where would you apply what to write when designing a long-running assistant with user memory, and how would you explain your decision?**

**Answer:** Use what to write in the detect candidate memory stage. Define the relevant input, output, or decision; specify a measurable acceptance check instead of trusting a generated description alone.


**Q3. [Scenario] Your long-running assistant with user memory encounters this problem: old user preferences reappear after the user corrected them. How would you handle it specifically for what to write?**

**Answer:** To address it, prepare or implement versioned memories, read-time freshness checks and deletion reconciliation. Write memory only when it has durable utility, sufficient evidence, permitted purpose and a correction path; avoid storing every conversation statement as a fact. Confirm the change with a reproducible negative test and an observed result.

## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q41. [Interview] Explain write, correction and retention policies to an interviewer.**

**Answer:** Interview answer: Write, correction and retention policies addresses the need to store useful experience while respecting correction, deletion and tenancy. I would begin with a bounded design for a persistent training assistant for seafarers, then specify contracts for What to write and What not to write. I would measure stale-recall rate and correction propagation success, verify the actual outcome and demonstrate handling of the primary failure:.


**Q42. [Interview] How would you design What to write from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Write memory only when it has durable utility, sufficient evidence, permitted purpose and a correction path; avoid storing every conversation statement as a fact. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q43. [Interview] How do What not to write and Confidence interact?**

**Answer:** Interview answer: First define their separate responsibilities. Do not persist secrets, unsupported inferences, transient content or unnecessary sensitive details. User control and legal policy determine other exclusions. Evidence-based degree of support for a stored claim; distinguish model extraction confidence from source reliability and never treat scores as truth probabilities without calibration.


**Q44. [Interview] What would you do if Source attribution fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure stale-recall rate and correction propagation success.


**Q45. [Interview] When would you avoid a framework or model for write, correction and retention policies?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q46. [Interview] How would you demonstrate L3 production readiness for M12.2?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the memory ledger with provenance, TTL and deletion receipts, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
