## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q5. [Interview] Explain memory lifecycle to an interviewer.**

**Answer:** Interview answer: Memory lifecycle addresses the need to store useful experience while respecting correction, deletion and tenancy. I would begin with a bounded design for a persistent training assistant for seafarers, then specify contracts for Write and correction and Read and maintenance. I would measure stale-recall rate and correction propagation success, verify the actual outcome and demonstrate handling of the primary failure: old user preferences reappear after the user corrected them.


**Q6. [Interview] How would you design Write and correction from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. In this part of a persistent training assistant for seafarers, Write and correction is an explicit design concern. Define its inputs, owner, observable result and failure handling before implementing it. Its purpose must be linked to the overall goal: store useful experience while respecting correction, deletion and tenancy.


**Q7. [Interview] How do Read and maintenance and State and evidence interact?**

**Answer:** Interview answer: First define their separate responsibilities. In this part of a persistent training assistant for seafarers, Read and maintenance is an explicit design concern. Define its inputs, owner, observable result and failure handling before implementing it. Its purpose must be linked to the overall goal: store useful experience while respecting correction, deletion and tenancy. Identify who owns this information, where it lives, and when it changes.


**Q8. [Interview] What would you do if Validation fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure stale-recall rate and correction propagation success.


**Q9. [Interview] When would you avoid a framework or model for memory lifecycle?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q10. [Interview] How would you demonstrate L3 production readiness for M12.5?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the memory ledger with provenance, TTL and deletion receipts, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
