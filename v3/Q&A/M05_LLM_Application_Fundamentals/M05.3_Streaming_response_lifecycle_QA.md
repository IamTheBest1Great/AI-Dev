**Answer:** Streaming means sending data to a client incrementally as it becomes available, instead of waiting for the complete result before returning it.

## 2.1 Server-Sent Events (SSE)

**Q19. [Conceptual] Explain Server-Sent Events (SSE) in simple, interview-ready language.**

**Answer:** Server-Sent Events (SSE) is a mechanism for sending events from a server to a client over an HTTP connection that remains open while events are being delivered.


**Q20. [Interview] Why does Server-Sent Events (SSE) matter, and what is one important design implication?**

**Answer:** The client initiates the connection, and the server uses it to send updates. Communication from the client to the server generally uses a separate HTTP request.

## 5.4 Connection States

**Q73. [Conceptual] Explain Connection States in simple, interview-ready language.**

**Answer:** COMPLETED: The operation finished successfully. FAILED: The operation encountered a failure. DISCONNECTED: The client and server no longer have an active connection. CANCELLED: The operation was intentionally stopped. RECONNECTING: The client is attempting to re-establish communication.


**Q74. [Interview] Why does Connection States matter, and what is one important design implication?**

**Answer:** A connection can be disconnected while its underlying job continues running. Connection state and job state should therefore not automatically be treated as identical.

<a id="5-6-restart-vs-resume"></a>
## 5.6 Restart vs. Resume

**Q77. [Conceptual] Explain Restart vs. Resume in simple, interview-ready language.**

**Answer:** Restart and resume are two different recovery strategies.


**Q78. [Interview] Why does Restart vs. Resume matter, and what is one important design implication?**

**Answer:** Resume does not automatically guarantee exactly-once processing. A client might receive an event again if the acknowledgement or processing status was not recorded. Applications that require reliable processing should account for duplicates.
