## 1. Provider Integration Fundamentals

**Q1. [Conceptual] Explain Provider Integration Fundamentals in simple, interview-ready language.**

**Answer:** An AI provider is a company or platform that gives an application access to AI models through an API or SDK.


**Q2. [Interview] Why does Provider Integration Fundamentals matter, and what is one important design implication?**

**Answer:** Instead of running a large AI model on your own infrastructure, your application can send requests to the provider, which runs the model and returns the response.


<a id="2-ai-provider-options"></a>
## 2. AI Provider Options

**Q3. [Conceptual] Explain AI Provider Options in simple, interview-ready language.**

**Answer:** Different providers offer different models, APIs, capabilities and deployment options. There is no permanently best provider for every workload.


**Q4. [Interview] Why does AI Provider Options matter, and what is one important design implication?**

**Answer:** The important architectural principle is that the Anthropic API does not have to use the same request and response format as another provider.

## 5. Idempotency and Safe Retries

**Q17. [Conceptual] Explain Idempotency and Safe Retries in simple, interview-ready language.**

**Answer:** Idempotency is the property that repeating an operation with the same intended request does not create additional unintended effects.


**Q18. [Interview] Why does Idempotency and Safe Retries matter, and what is one important design implication?**

**Answer:** This matters because a request may fail or time out even when the underlying operation has already succeeded.

## 6. Provider Capabilities and Abstraction

**Q23. [Conceptual] Explain Provider Capabilities and Abstraction in simple, interview-ready language.**

**Answer:** A capability available from multiple providers does not mean that their APIs, request formats or behavior are the same.


**Q24. [Interview] Why does Provider Capabilities and Abstraction matter, and what is one important design implication?**

**Answer:** An overly restrictive abstraction can hide capabilities that are important to the application.

## 8. Provider Fallback and Failure Handling

**Q35. [Conceptual] Explain Provider Fallback and Failure Handling in simple, interview-ready language.**

**Answer:** Provider fallback means using an alternative provider or model when the primary choice cannot successfully handle a request.


**Q36. [Interview] Why does Provider Fallback and Failure Handling matter, and what is one important design implication?**

**Answer:** Fallback should not automatically be triggered for every error. For example, invalid input or incorrect application permissions may remain invalid regardless of which provider receives the request.


<a id="why-use-fallback"></a>
### Why use fallback?

**Q37. [Conceptual] Why use fallback?**

**Answer:** Fallback can help improve availability when the primary provider is temporarily unavailable or experiencing a relevant failure.


**Q38. [Interview] How would you justify the answer to “Why use fallback?” in an interview?**

**Answer:** It can also help a system continue operating when a particular provider does not support a required task, provided an alternative supports it.


**Q39. [Scenario] In a production LLM API, how would you test the behavior discussed in “Why use fallback?”?**
