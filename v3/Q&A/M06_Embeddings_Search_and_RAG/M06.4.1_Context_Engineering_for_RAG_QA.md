## 1. Context Engineering Fundamentals

**Q1. [Conceptual] Explain Context Engineering Fundamentals in simple, interview-ready language.**

**Answer:** Context engineering for RAG is the process of selecting, organizing, labeling, and budgeting the evidence supplied to a language model for a particular question.


**Q2. [Interview] Why does Context Engineering Fundamentals matter, and what is one important design implication?**

**Answer:** Retrieval asks, “Which pieces might be useful?” Context assembly asks, “Which of those pieces should the model actually receive, in what form, and with which source information?”.


<a id="context-is-more-than-retrieved-text"></a>
### Context is more than retrieved text

**Q3. [Conceptual] Explain Context is more than retrieved text in simple, interview-ready language.**

**Answer:** The complete model input can contain system instructions, the current question, conversation history, tool schemas, tool outputs, retrieved evidence, and formatting requirements. The available space is shared among them.


**Q4. [Interview] Why does Context is more than retrieved text matter, and what is one important design implication?**

**Answer:** Anthropic’s context engineering discussion treats context as a finite resource that must be curated over time. In a RAG application, that means controlling the evidence package rather than simply appending every retrieved result.

## 2. M06.4.1.1 — Context Selection

**Q11. [Conceptual] Explain M06.4.1.1 — Context Selection in simple, interview-ready language.**

**Answer:** The input to selection is usually a candidate pool from lexical, dense, or hybrid retrieval followed by a reranker. Selection should consider the question’s evidence needs, not only the ranking score.


**Q12. [Interview] Why does M06.4.1.1 — Context Selection matter, and what is one important design implication?**

**Answer:** Selection should balance relevance, coverage, source quality, freshness, and token cost. Security and deletion checks are mandatory eligibility rules, not optional scoring bonuses.


<a id="preserve-context-needed-for-interpretation"></a>
### Preserve context needed for interpretation

**Q13. [Conceptual] Explain Preserve context needed for interpretation in simple, interview-ready language.**

**Answer:** A passage saying “This does not apply to configuration Z” is meaningless if the preceding rule is absent. A table cell needs its row label, column header, units, and applicable footnote.


**Q14. [Interview] Why does Preserve context needed for interpretation matter, and what is one important design implication?**

**Answer:** Context selection should preserve these dependencies. Expanding a child chunk to a parent section can help, but every added sentence must remain within the user’s authorized scope and token budget.

<a id="3-context-ordering-and-prioritization"></a>
## 3. Context Ordering and Prioritization

**Q17. [Conceptual] Explain Context Ordering and Prioritization in simple, interview-ready language.**

**Answer:** There is no universal order that is best for all models and tasks. Test the arrangement that matches your application.


**Q18. [Interview] Why does Context Ordering and Prioritization matter, and what is one important design implication?**

**Answer:** Ordering determines the sequence in which selected evidence appears. Useful arrangements include grouping by answer component, source version, chronology, or authority.


<a id="4-token-budgeting"></a>
## 4. Token Budgeting

**Q19. [Conceptual] Explain Token Budgeting in simple, interview-ready language.**

**Answer:** Use the actual model’s tokenizer or supported token-counting mechanism when implementing the budget. Character counts and words-per-token rules are rough estimates and can be poor for code, tables, identifiers, or multilingual text.


**Q20. [Interview] Why does Token Budgeting matter, and what is one important design implication?**

**Answer:** The first four cost 2,250 tokens. Adding background gives 3,350, leaving 1,050 of the 4,400 budget. There is no need to include the duplicate just because space remains.

## 5. Deduplication and Repeated Evidence

**Q21. [Conceptual] Explain Deduplication and Repeated Evidence in simple, interview-ready language.**

**Answer:** Do not merge v3 and v4 merely because their text is similar. The small difference may be the entire reason the user asked a comparison question.


**Q22. [Interview] Why does Deduplication and Repeated Evidence matter, and what is one important design implication?**

**Answer:** Overlap can produce passages that differ slightly while repeating most information. Near-duplicate handling should consider source spans, version identity, and semantic contribution.


<a id="deduplication-should-preserve-context"></a>
### Deduplication should preserve context

**Q23. [Conceptual] Explain Deduplication should preserve context in simple, interview-ready language.**

**Answer:** Two overlapping passages may each contain unique useful information. A careful merge can create one coherent source span. A careless merge can reorder sentences, omit an exception, or combine text from incompatible versions.


**Q24. [Interview] Why does Deduplication should preserve context matter, and what is one important design implication?**

**Answer:** Keep source offsets and document version in the merge record. If the system cannot confidently merge without changing meaning, choose one complete span or retain the necessary separate pieces.

### Position-sensitivity test

**Q33. [Conceptual] Explain Position-sensitivity test in simple, interview-ready language.**

**Answer:** Construct a question with known supporting evidence. Place the same evidence at the beginning, middle, and end among controlled distractors. Keep total length and source content constant.


**Q34. [Interview] Why does Position-sensitivity test matter, and what is one important design implication?**

**Answer:** Measure correctness, qualifier retention, and citation support across placements. Repeat with multiple examples; one successful case does not establish robust long-context behavior.

<a id="8-contradictory-context"></a>
## 8. Contradictory Context

**Q37. [Conceptual] Explain Contradictory Context in simple, interview-ready language.**

**Answer:** Not every apparent conflict is a real contradiction. Two manuals may apply to different configurations. A v3 statement and a v4 statement may represent a deliberate revision. Two numeric values may use different units or reporting periods.


**Q38. [Interview] Why does Contradictory Context matter, and what is one important design implication?**

**Answer:** A useful response can identify the disagreeing sources, describe the specific disputed point, and say that the available evidence does not establish which governs.

**Q39. [Conceptual] Explain Context Compression in simple, interview-ready language.**

## 10. Abstaining When Evidence Is Insufficient

**Q49. [Conceptual] Explain Abstaining When Evidence Is Insufficient in simple, interview-ready language.**

**Answer:** Abstention means declining to make an unsupported claim, or limiting the answer to what the available evidence can establish.


**Q50. [Interview] Why does Abstaining When Evidence Is Insufficient matter, and what is one important design implication?**

**Answer:** A model’s self-reported certainty should not override missing support. A fluent answer about the right topic can still be unsupported.
