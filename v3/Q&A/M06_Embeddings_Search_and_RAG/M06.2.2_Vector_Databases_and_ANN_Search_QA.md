## Branch 1 — Foundation & Mechanics

**Q1. [Conceptual] Explain Branch 1 — Foundation & Mechanics in simple, interview-ready language.**

**Answer:** Vector database: stores vector representations plus associated records and supports similarity search. ### 2.1 HNSW (Hierarchical Navigable Small World)

**Q17. [Conceptual] Explain HNSW (Hierarchical Navigable Small World) in simple, interview-ready language.**

**Answer:** Lifecycle connection: Primary index-construction choice when low latency is required. Original paper: Malkov & Yashunin (arXiv:1603.09320).


**Q18. [Interview] Why does HNSW (Hierarchical Navigable Small World) matter, and what is one important design implication?**

**Answer:** Organizes vectors into a multi-level graph. Search starts in sparse upper layers to leap toward the right region, then descends to dense lower layers to examine nearby candidates closely.

<a id="2-2-ivf-and-ivfflat"></a>
### 2.2 IVF and IVFFlat

**Q27. [Conceptual] Explain IVF and IVFFlat in simple, interview-ready language.**

**Answer:** IVF (inverted file): partition vector space into regions with representative centroids. At query time, compare the query to centroids, pick the nearest lists, and search only those. IVFFlat: vectors inside the lists remain uncompressed ("Flat"). Approximation arises because only some lists are visited; "Flat" does not mean all lists are scanned. Read index names carefully: IVFFlat vs IVFPQ have different compression behaviour.


**Q28. [Interview] Why does IVF and IVFFlat matter, and what is one important design implication?**

**Answer:** Lifecycle connection: Alternative index construction, heavily dependent on the shape and clustering of your dataset.

#### Product Quantization (PQ)

**Q51. [Conceptual] Explain Product Quantization (PQ) in simple, interview-ready language.**

**Answer:** Split the vector into subvectors; replace each with the ID of the nearest learned codebook entry.


**Q52. [Interview] Why does Product Quantization (PQ) matter, and what is one important design implication?**

**Answer:** 768 dims → 96 subvectors × 8 dims; each subvector stored as 1 byte (256 centroids). Code size = 96 bytes vs 3,072 bytes float32 (~32x), before overhead. Toy arithmetic, not a guarantee of accuracy or a full memory estimate.

### 4.3 Updates, Deletes, Tombstones, and Compaction

**Q75. [Conceptual] Explain Updates, Deletes, Tombstones, and Compaction in simple, interview-ready language.**

**Answer:** A tombstone is a logical marker (gravestone) that a record is inactive; serving stops immediately while physical cleanup is deferred. Physical deletion from graph indexes is slow and heavy.


**Q76. [Interview] Why does Updates, Deletes, Tombstones, and Compaction matter, and what is one important design implication?**

**Answer:** Lifecycle connection: Cleanup and maintenance; critical for legal compliance (e.g., GDPR) and system health.

### 5.3 Holistic Architecture Notes

**Q85. [Conceptual] Explain Holistic Architecture Notes in simple, interview-ready language.**

**Answer:** Do vector DBs replace relational DBs? No. Vector DBs do similarity search over unstructured data; relational DBs give ACID transactions and structured lookups. Extensions like pgvector let PostgreSQL do both, which also simplifies joins with ACL tables.


**Q86. [Interview] Why does Holistic Architecture Notes matter, and what is one important design implication?**

**Answer:** Heterogeneous data (code, Slack, PDFs) for an agentic system: don't dump everything into one unpartitioned index. Options: (1) route queries to domain-specific collections with specialized embeddings (e.g., a code model for code, a text model for chat); or (2) use a strong multimodal/general embedding with strict metadata pre-filtering by datasource so code questions don't pull chatter.
