## 2. M06.6.1.1 — Change Detection and Content Hashing

**Q1. [Conceptual] Explain M06.6.1.1 — Change Detection and Content Hashing in simple, interview-ready language.**

**Answer:** A webhook means “something may have changed.” It does not necessarily contain the final authoritative content. Fetch the source under approved credentials and compare it with known state.


**Q2. [Interview] Why does M06.6.1.1 — Change Detection and Content Hashing matter, and what is one important design implication?**

**Answer:** Possible signals include connector webhooks, database change streams, file modification metadata, source revision IDs, delta APIs, and scheduled inventory comparisons. Each signal has different delivery and consistency behavior.

## 4. M06.6.1.1 — Version Tracking and Publication

**Q3. [Conceptual] Explain M06.6.1.1 — Version Tracking and Publication in simple, interview-ready language.**

**Answer:** Write new artifacts into a non-serving generation. Verify that the required dense, lexical, metadata, and citation representations are ready. Then update the authoritative serving pointer to the new revision.


**Q4. [Interview] Why does M06.6.1.1 — Version Tracking and Publication matter, and what is one important design implication?**

**Answer:** If the dense index is ready but the lexical index failed, publishing only the dense part can produce inconsistent hybrid results. The publication condition should reflect the system's required branches or explicitly activate a tested degraded mode.

<a id="5-m06-6-1-1-freshness-policies"></a>
## 5. M06.6.1.1 — Freshness Policies

**Q9. [Conceptual] Explain M06.6.1.1 — Freshness Policies in simple, interview-ready language.**

**Answer:** If the current revision is unavailable, choose a deliberate response: mark available information as older, ask the user whether historical information is acceptable, use a live approved source, or abstain. Do not silently answer a current-state question from obsolete evidence.


**Q10. [Interview] Why does M06.6.1.1 — Freshness Policies matter, and what is one important design implication?**

**Answer:** A freshness policy states how current knowledge must be for a task and what to do when that requirement cannot be met.


<a id="6-m06-6-1-1-deletion-handling"></a>
## 6. M06.6.1.1 — Deletion Handling

**Q11. [Conceptual] Explain M06.6.1.1 — Deletion Handling in simple, interview-ready language.**

**Answer:** A temporary connector outage, incomplete page of results, or permission error is not proof of deletion. A reliable deletion signal comes from an authoritative event or a completed inventory comparison under known semantics.


**Q12. [Interview] Why does M06.6.1.1 — Deletion Handling matter, and what is one important design implication?**

**Answer:** Deleting a source should make it ineligible and initiate removal of its derived artifacts. It must not be represented only as “the next crawl probably will not find the file.”.


<a id="8-m06-6-1-2-idempotent-updates-and-failed-recovery"></a>
## 8. M06.6.1.2 — Idempotent Updates and Failed Recovery

**Q13. [Conceptual] Explain M06.6.1.2 — Idempotent Updates and Failed Recovery in simple, interview-ready language.**

**Answer:** An operation is idempotent when repeating it has the same intended effect on state as applying it once.


**Q14. [Interview] Why does M06.6.1.2 — Idempotent Updates and Failed Recovery matter, and what is one important design implication?**

**Answer:** A useful key can combine tenant, document ID, source revision, transformation version, and stage. Store completion status and the associated payload fingerprint. Reusing an event ID with a different payload should be treated as an error, not silently accepted.


<a id="9-m06-6-1-2-reconciliation-and-freshness-monitoring"></a>
## 9. M06.6.1.2 — Reconciliation and Freshness Monitoring

**Q15. [Conceptual] Explain M06.6.1.2 — Reconciliation and Freshness Monitoring in simple, interview-ready language.**

**Answer:** Compare identities, active revisions, content hashes, transformation versions, permissions, lifecycle states, and required artifacts. A count-only check is weak: 1,000 source documents and 1,000 index records can still contain different IDs.


**Q16. [Interview] Why does M06.6.1.2 — Reconciliation and Freshness Monitoring matter, and what is one important design implication?**

**Answer:** Useful discrepancy classes include missing source representation, orphaned derived artifact, wrong active revision, stale ACL, incomplete store publication, duplicate chunk identity, and pending deletion beyond its objective.

## 10. Worked Revision and Deletion Example

**Q17. [Conceptual] Explain Worked Revision and Deletion Example in simple, interview-ready language.**

**Answer:** M-104 v3 is published at lifecycle generation 41. Both dense and lexical indexes reference manifest 41. A response cache entry depends on M-104 v3.


**Q18. [Interview] Why does Worked Revision and Deletion Example matter, and what is one important design implication?**

**Answer:** Generation 43 deletes M-104 while an old generation-42 worker is still running. The authoritative gate records the tombstone before acknowledging the deletion contract. The worker later tries to publish 42 and is rejected because 42 is older than 43.
