## 1. The Scenario and Learning Objectives

**Q1. [Conceptual] Explain The Scenario and Learning Objectives in simple, interview-ready language.**

**Answer:** A fictional organization maintains workshop manuals for two vessels, Ship A and Ship B, inside tenant A. A separate organization is tenant B.


**Q2. [Interview] Why does The Scenario and Learning Objectives matter, and what is one important design implication?**

**Answer:** For an authorized Ship A user, the answer should cite revision 4 and identify the maintenance supervisor. A Ship B user without permission should not obtain the paragraph, its private metadata or a cached answer based on it.


<a id="2-source-version-and-permission-model"></a>
## 2. Source, Version and Permission Model

**Q3. [Conceptual] Explain Source, Version and Permission Model in simple, interview-ready language.**

**Answer:** Tenant A and tenant B may both have a document named M-104. The display name alone is not a globally unique key.


**Q4. [Interview] Why does Source, Version and Permission Model matter, and what is one important design implication?**

**Answer:** A storage URL can change without changing the document's logical identity. Store the source locator separately.


<a id="3-ingest-the-revised-manual"></a>
## 3. Ingest the Revised Manual

**Q5. [Conceptual] Explain Ingest the Revised Manual in simple, interview-ready language.**

**Answer:** Accept the revision through an authorized source-management route. Check type and content, file size, parser limits and source identity. Confirm that the event represents an approved revision rather than an arbitrary attachment.


**Q6. [Interview] Why does Ingest the Revised Manual matter, and what is one important design implication?**

**Answer:** A cleaner that removes “supervisor” because it looks like a repeated header would destroy the very fact the answer needs.


<a id="4-publish-consistent-retrieval-data"></a>
## 4. Publish Consistent Retrieval Data

**Q7. [Conceptual] Explain Publish Consistent Retrieval Data in simple, interview-ready language.**

**Answer:** Stage v4's text, lexical entries and vectors without making a partial revision visible as current. Once the required components are ready, update the serving manifest to v4.


**Q8. [Interview] Why does Publish Consistent Retrieval Data matter, and what is one important design implication?**

**Answer:** The application should be able to say which revision a request used. Mixing v3 lexical results with v4 vector results can produce contradictory context.


<a id="5-retrieve-only-authorized-evidence"></a>
## 5. Retrieve Only Authorized Evidence

**Q9. [Conceptual] Explain Retrieve Only Authorized Evidence in simple, interview-ready language.**

**Answer:** Authorization is relevant to both phases. Permission metadata must be preserved offline, and current access decisions must be enforced online.


**Q10. [Interview] Why does Retrieve Only Authorized Evidence matter, and what is one important design implication?**

**Answer:** Source restrictions should be applied during retrieval where supported. An authoritative check should also guard materialization because index metadata may lag behind current source or policy state.

### Filtered ANN and candidate quality

**Q11. [Conceptual] Explain Filtered ANN and candidate quality in simple, interview-ready language.**

**Answer:** A filter can leave few eligible neighbors among approximate search results. Applying a correct access check does not guarantee adequate retrieval recall.


**Q12. [Interview] Why does Filtered ANN and candidate quality matter, and what is one important design implication?**

**Answer:** Evaluate filtered ANN against exact search on the same eligible corpus. Depending on the engine and workload, increase the candidate budget, adjust search settings or use an authorized exact-search fallback.

### Distinguish user filters from security filters

**Q15. [Conceptual] Explain Distinguish user filters from security filters in simple, interview-ready language.**

**Answer:** A generated query rewrite can modify convenience terms under defined rules. It must not remove the security scope.

<a id="deliberate-limits-of-the-executable-model"></a>
### Deliberate limits of the executable model

**Q33. [Conceptual] Explain Deliberate limits of the executable model in simple, interview-ready language.**

**Answer:** Production code must implement the required concurrency guarantee. A successful check and a later network write are separate events unless the serving design binds them through an appropriate transaction, lease or invalidation mechanism. Recheck before emission and define how revocation races are handled.


**Q34. [Interview] Why does Deliberate limits of the executable model matter, and what is one important design implication?**

**Answer:** The program runs sequentially in one process. It does not implement durable storage, distributed locking, event delivery, network streaming, model calls, physical storage compaction or backup retention.


**Q35. [Scenario] A developer misunderstands Deliberate limits of the executable model while building a multi-tenant RAG assistant over versioned training manuals. How would you correct the design?**

**Answer:** Clarify the actual behavior: The program runs sequentially in one process. Demonstrate the difference with a concrete input and expected result before changing the system.


**Q36. [Project / Real-world] How would you demonstrate Deliberate limits of the executable model in a real multi-tenant RAG assistant over versioned training manuals?**

## 9. Permission Changes and In-Flight Requests

**Q37. [Conceptual] Explain Permission Changes and In-Flight Requests in simple, interview-ready language.**

**Answer:** A cache key containing only tenant ID and query text is insufficient when two people in the same tenant have different access.


**Q38. [Interview] Why does Permission Changes and In-Flight Requests matter, and what is one important design implication?**

**Answer:** A final access check should prevent releasing an answer derived from the revoked source. If the service streams answers, it must define how revocation is coordinated with already-started streams.

## 10. Delete the Source and Verify Removal

**Q43. [Conceptual] Explain Delete the Source and Verify Removal in simple, interview-ready language.**

**Answer:** A complete deletion design identifies every derived artifact and determines how it stops serving and when it is physically removed.


**Q44. [Interview] Why does Delete the Source and Verify Removal matter, and what is one important design implication?**

**Answer:** Requests should stop receiving evidence from that source even while background cleanup is unfinished. The runnable program demonstrates this by retaining chunk objects temporarily while denying access.


<a id="11-failure-recovery-and-audit-evidence"></a>
## 11. Failure Recovery and Audit Evidence

**Q45. [Conceptual] Explain Failure Recovery and Audit Evidence in simple, interview-ready language.**

**Answer:** If vector updates succeed but lexical updates fail, retain staged data until the required publication conditions are met. A reconciliation job should find and repair differences between the registry and indexes.


**Q46. [Interview] Why does Failure Recovery and Audit Evidence matter, and what is one important design implication?**

**Answer:** A repeated ingestion event should not create duplicate chunks. Use stable operation identities and idempotent writes, or detect a completed operation and return its previous result.
