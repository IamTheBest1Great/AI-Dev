## 1. Failure-Mode Fundamentals

**Q1. [Conceptual] Explain Failure-Mode Fundamentals in simple, interview-ready language.**

**Answer:** A RAG failure mode is a repeatable way in which a retrieval-augmented generation system produces an incomplete, incorrect, unsupported, unauthorized, stale, or unusable result.


**Q2. [Interview] Why does Failure-Mode Fundamentals matter, and what is one important design implication?**

**Answer:** Changing the prompt addresses only some of these causes. Diagnosis should locate the earliest stage that violated its contract.


<a id="2-m06-5-1-1-retrieval-failures"></a>
## 2. M06.5.1.1 — Retrieval Failures

**Q3. [Conceptual] Explain M06.5.1.1 — Retrieval Failures in simple, interview-ready language.**

**Answer:** A retrieval miss occurs when an eligible, relevant item exists in the searchable collection but is not returned within the candidate set used by the next stage.


**Q4. [Interview] Why does M06.5.1.1 — Retrieval Failures matter, and what is one important design implication?**

**Answer:** Check whether the relevant chunk is actually indexed, whether the query and document vectors use compatible embedding configurations, and whether a lexical baseline can retrieve it. An exact-term question is a useful reason to compare BM25 or other lexical retrieval with dense retrieval.

<a id="3-m06-5-1-2-knowledge-failures"></a>
## 3. M06.5.1.2 — Knowledge Failures

**Q9. [Conceptual] Explain M06.5.1.2 — Knowledge Failures in simple, interview-ready language.**

**Answer:** Two passages may state different values because they concern different versions, scopes, or conditions. Apparent contradiction is not automatically source unreliability.


**Q10. [Interview] Why does M06.5.1.2 — Knowledge Failures matter, and what is one important design implication?**

**Answer:** Track at least source change time, connector observation time, index publication time, and effective validity. These answer different questions. A current ingestion timestamp proves recent processing, not current knowledge.


<a id="4-m06-5-1-3-generation-failures"></a>
## 4. M06.5.1.3 — Generation Failures

**Q11. [Conceptual] Explain M06.5.1.3 — Generation Failures in simple, interview-ready language.**

**Answer:** Break the answer into atomic claims and map each factual claim to evidence. A claim can be topically consistent yet unsupported. Treat “sounds reasonable” and “is stated or justified by the source” as different standards.


**Q12. [Interview] Why does M06.5.1.3 — Generation Failures matter, and what is one important design implication?**

**Answer:** Useful controls include constrained answer scope, explicit evidence references, extractive intermediate facts, and post-generation validation. None of these independently guarantees factual correctness.


<a id="context-overflow"></a>
### Context overflow

**Q13. [Conceptual] Explain Context overflow in simple, interview-ready language.**

**Answer:** Context overflow occurs when assembled input exceeds a limit or when automatic truncation removes necessary material. There are several budgets: embedding input, reranker input, model input, model output, and application-specific message limits.


**Q14. [Interview] Why does Context overflow matter, and what is one important design implication?**

**Answer:** Reserve space for instructions, conversation, tool outputs, and the answer. Truncation should follow an explicit priority policy. Do not silently chop the tail of a procedure if that tail contains exceptions.


**Q15. [Scenario] A developer misunderstands Context overflow while building a multi-tenant RAG assistant over versioned training manuals. How would you correct the design?**

**Answer:** Clarify the actual behavior: Even context that fits can be ineffective if it is repetitive or irrelevant. “Within the token limit” is a capacity check, not a quality check. Demonstrate the difference with a concrete input and expected result before changing the system.

<a id="5-stage-by-stage-diagnosis"></a>
## 5. Stage-by-Stage Diagnosis

**Q17. [Conceptual] Explain Stage-by-Stage Diagnosis in simple, interview-ready language.**

**Answer:** OpenTelemetry traces provide a general model of related spans across a request. Applying that model to RAG stages is an architectural choice; the retrieval-specific fields must be defined by the application.


**Q18. [Interview] Why does Stage-by-Stage Diagnosis matter, and what is one important design implication?**

**Answer:** Useful diagnostic substitutions include exact vector search instead of ANN, gold evidence instead of retrieved evidence, no rewriting instead of rewriting, and a current-source-only fixture instead of a mixed-version collection. These are evaluation experiments on authorized data, not permission bypasses.

## 6. Metrics That Identify the Problem

**Q19. [Conceptual] Explain Metrics That Identify the Problem in simple, interview-ready language.**

**Answer:** Citation correctness asks whether cited evidence supports its claim. Citation completeness asks whether claims requiring evidence are cited. An answer with one correct citation and five uncited factual claims can perform well on the first measure and poorly on the second.


**Q20. [Interview] Why does Metrics That Identify the Problem matter, and what is one important design implication?**

**Answer:** Unanswerable queries need a separate policy because their relevant set can be empty. Do not divide by zero or silently score abstention as failure. Measure correct abstention, unsupported-answer rate, and inappropriate abstention on answerable queries.


**Q21. [Scenario] A developer misunderstands Metrics That Identify the Problem while building a multi-tenant RAG assistant over versioned training manuals. How would you correct the design?**

**Answer:** Clarify the actual behavior: The candidate stage missed B, and refinement lost C. Fixing only generation cannot recover either absent fact. Demonstrate the difference with a concrete input and expected result before changing the system.


**Q22. [Project / Real-world] How would you demonstrate Metrics That Identify the Problem in a real multi-tenant RAG assistant over versioned training manuals?**

**Answer:** Use the source’s practical detail: Suppose one invented query requires eligible gold chunks {A, B, C}. Candidate generation returns {A, C, D, E, F}. Reranking and context assembly retain {A, D}. Show a trace, baseline comparison, or test result that demonstrates the behavior.

## 7. Worked Incident: The Wrong Maintenance Interval

**Q23. [Conceptual] Explain Worked Incident: The Wrong Maintenance Interval in simple, interview-ready language.**

**Answer:** The authoritative current fixture is v4, which says “14 days.” Revision v3 says “30 days.” Neither value is an operational recommendation outside this exercise.


**Q24. [Interview] Why does Worked Incident: The Wrong Maintenance Interval matter, and what is one important design implication?**

**Answer:** Confirm the user is allowed to access M-104 v4. Verify the source manifest marks v4 as published and v3 as superseded. Inspect extraction: both values and their headings are correct. Inspect candidates: v3 and v4 both appear because the active-version filter was omitted. Inspect reranking: v3 ranks first because its chunk repeats the query terms. Inspect context: the budget retains v3 and removes v4. Inspect citations: the display URL resolves to the latest source, creating a v3-text/v4-link mismatch.


<a id="corrective-work"></a>
### Corrective work

**Q25. [Conceptual] Explain Corrective work in simple, interview-ready language.**

**Answer:** Add a published-version constraint to all retrieval branches. Preserve version-specific source locators in evidence records. Rebuild any citation cache that stored only document IDs. Add a regression case in which an obsolete revision has stronger lexical overlap than the current one.


**Q26. [Interview] Why does Corrective work matter, and what is one important design implication?**

**Answer:** A reranker upgrade alone would be unreliable: even if v4 usually ranks higher, obsolete content would remain eligible.

## 13. L3 Project Exercise and Acceptance Evidence

**Q37. [Conceptual] Explain L3 Project Exercise and Acceptance Evidence in simple, interview-ready language.**

**Answer:** Build a small diagnostic collection with two tenants, two versions of M-104, a table containing a fictional interval, a deliberately missing appendix, an obsolete duplicate, and one allowed document containing an irrelevant instruction-like sentence.


**Q38. [Interview] Why does L3 Project Exercise and Acceptance Evidence matter, and what is one important design implication?**

**Answer:** Create at least twelve labeled questions covering exact terms, paraphrases, multi-fact answers, historical versions, unanswerable requests, restricted sources, and source deletion. Keep a development set separate from the final evaluation questions.
