## Cross-cutting production interview drill

These questions are adapted from the source study guide’s interview section and assess how the individual concepts work together.

**Q29. [Interview] Explain scaling and capacity to an interviewer.**

**Answer:** Interview answer: Scaling and capacity addresses the need to balance serving throughput, precision and output quality. I would begin with a bounded design for a low-latency local model inference service, then specify contracts for GPU scheduling and Autoscaling. I would measure time-to-first-token, output tokens/sec and quality regressions, verify the actual outcome and demonstrate handling of the primary failure: quantization reduces RAM but breaks numeric extraction accuracy.


**Q30. [Interview] How would you design GPU scheduling from scratch?**

**Answer:** Interview answer: I would identify the trusted input source, decide which component owns the operation, define typed fields, and specify success and failure states. Define the security and resource boundary in the infrastructure rather than only in agent instructions. Test its enforcement under unauthorized and exhausted-resource conditions. Then I would create at least a happy-path and an unauthorized/invalid-input test.


**Q31. [Interview] How do Autoscaling and Tensor parallelism concepts interact?**

**Answer:** Interview answer: First define their separate responsibilities. In this part of a low-latency local model inference service, Autoscaling is an explicit design concern. Define its inputs, owner, observable result and failure handling before implementing it. Its purpose must be linked to the overall goal: balance serving throughput, precision and output quality. In this part of a low-latency local model inference service, Tensor parallelism concepts is an explicit design concern.


**Q32. [Interview] What would you do if Pipeline/model parallelism concepts fails in production?**

**Answer:** Interview answer: I would contain the impact, check trace IDs, state and external receipts, then classify the failure as transient, permanent or unknown outcome. I would not blindly repeat a write. After fixing the cause, I would add the incident as a versioned regression case and measure time-to-first-token, output tokens/sec and quality regressions.


**Q33. [Interview] When would you avoid a framework or model for scaling and capacity?**

**Answer:** Interview answer: When the rules and data contracts are deterministic, a small application service or workflow is usually easier to test and operate. I add an agent or new framework only when variable inputs and evidence show a measurable improvement that offsets extra coordination, cost and risk.


**Q34. [Interview] How would you demonstrate L3 production readiness for M32.4?**

**Answer:** Interview answer: I would present a working repository, a state and permission diagram, the serving benchmark with precision and capacity comparisons, known limitations, representative evaluation fixtures, failure-injection results and tracing. I would also show restart behavior and an operator takeover path where needed.
