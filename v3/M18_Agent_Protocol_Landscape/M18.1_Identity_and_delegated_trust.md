# Part 2 — Architecture, Boundaries and Decision Model

## 2.1 What is this section really solving?

**Problem:** In an agent commerce assistant with delegated authorization, it is not enough to say that a model or framework supports **identity and delegated trust**. Engineers must show which data it consumes, which state it changes, which actor authorizes it, how failure is represented and which result counts as success.

**Intended outcome:** Separate protocol interoperability from identity, consent and financial execution. The required deliverable is a **protocol boundary diagram and test-transaction audit trail**. Its quality is measured with **unauthorized charge attempts prevented and reconciled transactions**, not just a fluent model answer.

**Example:** An assistant prepares a low-value purchase but waits for explicit payment authorization. To solve this properly, first identify the trustworthy source of the task, then establish the constraint on user identity vs agent identity vs client identity, and finally verify agent identity vs workload/service identity at a concrete output boundary.

A useful mental model has five independent layers: (1) intent and constraints, (2) trusted and untrusted inputs, (3) application-owned state, (4) actions or computations, and (5) verified evidence. A language model may participate in some layers but should not silently become the owner of identity, payments, tenancy, or other privileged controls.

## 2.2 Reference Architecture and Lifecycle

```mermaid
flowchart TD
  S0["Identify agent and user"]
  S1["Establish delegated scope"]
  S2["Discover eligible offer"]
  S3["Request transaction approval"]
  S4["Execute, reconcile and audit"]
  S0 --> S1
  S1 --> S2
  S2 --> S3
  S3 --> S4
  S4 --> OK(("Verified outcome"))
  S2 -.-> FAIL["Detected failure / unknown outcome"]
  FAIL --> REVIEW["Reconcile / seek approval / stop"]
```

**How to read the diagram:** Every arrow represents a deliberate state transition. A failed node does not automatically return to the previous node: decide whether the outcome is known, whether the operation can be repeated safely, and whether a human decision is required. The terminal "verified outcome" means the application checked the intended postcondition; generating the answer or sending a request alone is insufficient.

## 2.3 Input, State, Control and Evidence

| Layer | Example in this section | Engineering rule |
|---|---|---|
| Input | User identity vs agent identity vs client identity and the current request | Validate its format, scope, age and source |
| Application state | Task ID, tenant, stage, version, previous receipts | Persist what is needed to continue correctly |
| Computation / tools | Agent identity vs workload/service identity in a bounded execution path | Use typed contracts and explicit error handling |
| Authority | User permissions, policy checks, approval status | Enforce independently of retrieved text or model output |
| Result | protocol boundary diagram and test-transaction audit trail | Verify the resulting state before reporting completion |
| Measurement | unauthorized charge attempts prevented and reconciled transactions | Define a repeatable denominator and test dataset |

For **identity and delegated trust**, avoid conflating data that the model reads with state that the service must remember. If a source, agent or API changes its mind, the application should reconcile the conflict explicitly. The safest design makes state transitions observable and reproducible.

## 2.4 Architecture Choices and Tradeoffs

| Approach | When appropriate | Benefits | Limitations |
|---|---|---|---|
| Deterministic code | Rules for user identity vs agent identity vs client identity are stable and testable | Cheap, inspectable, fast | Cannot resolve poorly structured ambiguity alone |
| Typed workflow | Several steps with clear dependencies and failure paths | Explicit transitions and checkpoints | Adds orchestration and state management |
| Single agent with tools | Inputs vary and tool choice needs model interpretation | Flexible reasoning under limits | More evaluation, cost and authorization risk |
| Multiple agents / external services | Independent specialties show measured benefit | Parallel expertise and independent scaling | Handoffs, duplicated work, trust and coordination overhead |

**Recommended default:** Start with deterministic checks and a typed workflow. Introduce a model for the genuinely ambiguous parts only after establishing a baseline. This principle applies even when the roadmap discusses specialized agent frameworks, multimodal interfaces or new protocols.

## 2.5 Explicit Decision Contract

Before choosing an implementation, write the following decisions down:

1. **Task boundary:** What does "done" mean for identity and delegated trust? Which operations are explicitly excluded?
2. **Inputs and provenance:** Which fields support User identity vs agent identity vs client identity and Agent identity vs workload/service identity? Who supplied them and when?
3. **Authority:** Who is permitted to start, approve, inspect, cancel or replay the operation?
4. **State ownership:** Which fields must survive a restart? Which data should expire?
5. **Limits:** What are the maximum time, attempts, spend, token count or other resource ceilings?
6. **Verification:** Which independent test proves the output or side effect occurred?
7. **Recovery:** What happens if the process fails after the external operation completes?

# Part 3 — End-to-End Worked Example

## 3.1 Scenario, assumptions and scope

**Scenario:** An assistant prepares a low-value purchase but waits for explicit payment authorization.

Assume a single authorized company, a fixed development test dataset and one operator who can review uncertain outcomes. Use fake or sandbox accounts for destructive or financial actions; do not assume screenshots, model scores or network acknowledgements are the same as final state.

**Inputs:** A task ID, authenticated tenant/user, a goal, relevant source references, resource budget, policy version and any human approvals. **Outputs:** A result artifact, a trace of meaningful decisions, a terminal status and a list of unresolved facts. **Failure state:** Errors and unknown external outcomes are stored explicitly instead of being hidden behind "success".

## 3.2 Lifecycle stages and handoffs

| Stage | Task-specific question | Evidence / postcondition |
|---|---|---|
| 1. Identify agent and user | How does **User identity vs agent identity vs client identity** affect this stage? | Log stage outcome, resource scope and protocol boundary diagram and test-transaction audit trail. |
| 2. Establish delegated scope | How does **Agent identity vs workload/service identity** affect this stage? | Log stage outcome, resource scope and protocol boundary diagram and test-transaction audit trail. |
| 3. Discover eligible offer | How does **Delegated authority** affect this stage? | Log stage outcome, resource scope and protocol boundary diagram and test-transaction audit trail. |
| 4. Request transaction approval | How does **Credential binding** affect this stage? | Log stage outcome, resource scope and protocol boundary diagram and test-transaction audit trail. |
| 5. Execute, reconcile and audit | How does **Agent provenance** affect this stage? | Log stage outcome, resource scope and protocol boundary diagram and test-transaction audit trail. |

The stage handoff should be a typed record rather than free-form prose alone. For example, a retrieval stage might emit source IDs, scores and ACL checks; an execution stage should return the operation ID, external receipt and confirmed status. This makes it possible to replay, resume, debug and inspect exactly which stage produced the bad result.

{

Store large artifacts in controlled object storage and keep stable references in the task record, rather than placing unlimited blobs in state or model context.

## 3.4 Expected outcomes and acceptance criteria

A credible demonstration for **M18.1** shows that **User identity vs agent identity vs client identity** and **Agent identity vs workload/service identity** are implemented with visible state boundaries. # Part 5 — Failure Modes and Troubleshooting

## 5.1 Failure taxonomy

**Primary risk for this module:** A payment is repeated after a timeout or exceeds the approved budget. A recommended baseline defense is to signed mandates where applicable, independent policy checks and idempotency. This is not the only possible failure: even a well-designed policy gate can fail when state, source versions, external receipts or tool permissions are inconsistent.

| Symptom | Likely cause | First diagnostic check | Safer response |
|---|---|---|---|
| User identity vs agent identity vs client identity gives inconsistent results | Stale input, weak contract or hidden default | Compare source and schema versions | Reject, refresh or reconcile before continuing |
| Agent identity vs workload/service identity fails after partial work | Timeout or unknown external commit | Inspect action ID and external receipt | Avoid blind retries; use idempotency/reconciliation |
| Delegated authority crosses an access boundary | Missing resource-level policy check | Trace actor, tenant, action and resource | Contain access, revoke credentials, add regression |
| Credential binding becomes too costly | Unbounded loops, fan-out or expensive model | Check per-task attempts, tokens and spend | Stop at budget and escalate or degrade |
| Agent provenance looks correct but is wrong | No independent postcondition verification | Review real state and source evidence | Mark uncertain, repair test and avoid false success |
| A new release breaks old tasks | Incompatible state or interface version | Compare manifests and release revisions | Roll back or migrate with compatibility tests |
| A monitoring dashboard says 'green' but users complain | Metric measures response, not outcome | Compare SLI to user-visible postcondition | Add outcome-based signal and failure slice |

## 5.2 Failure exercise A — Unknown outcome after timeout

An operation involved in **Agent identity vs workload/service identity** returns a timeout. The request may have reached the external provider. If the workflow immediately retries with a new identifier, it could create a duplicate write or charge. A safer sequence is: preserve the task/action ID, classify the outcome as unknown, query the external system for a receipt, replay only using a supported idempotency key, and request human review when reconciliation is impossible.

**Expected evidence:** two runs with the same business-action identifier produce at most one accepted business effect, and both runs have a clear recorded outcome. For read-only operations, demonstrate bounded retry and consistent source-version handling instead.

## 5.3 Failure exercise B — Stale or poisoned context

A retrieved source or old checkpoint contains an instruction contradicting the active rules. Test whether the application treats source text as untrusted and obtains policy decisions from the correct component. **Delegated authority** should be handled as data only where its source is not authorized to instruct the agent.

**Expected evidence:** the system retains current constraints, records the untrusted source ID and either answers from verified evidence or abstains. No tool permission should be inferred from the content of a document or message.

## 5.4 Failure exercise C — Unbounded resource use

A task repeatedly invokes **Credential binding** but makes no measurable progress. The runtime must count failed attempts and retries in its global budget. Separate transient errors from permanent invalid inputs; use exponential backoff only for safe retries, and stop with an actionable error when the limit is reached.

**Expected evidence:** bounded step count, cost and duration; recorded reason for termination; and no orphaned privileged workers after cancellation.

## 5.5 Failure exercise D — Misleading success report

The model writes "completed", but the application has not verified **Agent provenance** or the final artifact. Require the independent postcondition before setting a terminal success state. For human approvals, verify that approval applies to the same resource version and action payload that will actually execute.

**Expected evidence:** a simulated false-success message remains `failed`, `pending`, or `unknown` until the relevant state check passes.

# Part 11 — Senior / Staff-Level Production Scenarios

## 11.1 Scenario — Stale decision during a policy change

**Situation:** A workflow dealing with **User identity vs agent identity vs client identity** began under an older policy. During execution the governing rule or permitted resource scope changes. The model still sees the previous description and proposes to continue.

**Expected diagnosis:** Inspect policy versions, who initiated the task, which evidence was cached and where authorization is actually checked. **Containment:** prevent privileged actions from proceeding on a stale approval. **Recovery:** re-evaluate current policy, invalidate stale context or state references, obtain new approval where necessary and record the decision. **Regression:** repeat the test with the policy updated between planning and execution.

**Interview takeaway:** Approvals and permissions must be bound to the exact actor, target, action payload and version; prompt summaries do not supersede active policy.

## 11.2 Scenario — Crash immediately after a side effect

**Situation:** An action related to **Agent identity vs workload/service identity** commits in a downstream system. The worker crashes before recording a success checkpoint. On restart, the workflow appears unfinished.

**Expected diagnosis:** Look for a business action ID, idempotency key and provider receipt. **Containment:** do not send a second non-idempotent action. **Recovery:** query external state, persist the confirmed receipt or unknown status and resume from a safe boundary. **Regression:** kill the worker between action and checkpoint, rerun the same task ID and assert one business effect.

**Interview takeaway:** Checkpointing and exactly-once effects are separate contracts. Recovery must reconcile the external world, not only replay local steps.

## 11.3 Scenario — A new version passes tests but degrades one tenant

**Situation:** After an upgrade, aggregate success remains stable, but a subset of users sees failures involving **Delegated authority** and **Credential binding**. The new implementation uses a different cache key, contract or evaluation distribution.

**Expected diagnosis:** Compare request traces across versions and tenants; inspect data scope, schema changes, cache invalidation and per-slice metrics. **Containment:** revert or disable the affected route. **Recovery:** update migration and compatibility tests and recalibrate any thresholds on a fixed dataset. **Regression:** preserve affected tenant-safe fixtures without exporting private data.

**Interview takeaway:** A single global score hides critical slices. Track versions and accepted outcomes, not only latency and error-free transport.

## 11.4 Scenario — Leadership asks for full automation tomorrow

**Situation:** Stakeholders want the feature in **identity and delegated trust** to operate without human review. They have only a successful demo and no evidence for authorization, failure recovery or spend control.

**Recommended response:** Identify which actions are read-only and which affect external state. Propose graduated autonomy: deterministic validation first, supervised tool actions next, and narrowly scoped autonomy only after measured success. Define an approval matrix, a kill switch, an operations owner, and a controlled rollout with a rollback path. Show a test report covering unauthorized charge attempts prevented and reconciled transactions and the top risks before increasing privileges.

**Interview takeaway:** Autonomy is an engineering decision supported by testable boundaries and business evidence, not a default requirement of an agent project.
