Definition

Information retrieval, or IR, finds items that are useful for an information need. The user expresses that need through a query, and the system selects and often ranks documents, passages, records or other evidence.

A retrieval system has at least four important objects:

Object Meaning
Corpus The collection being searched
Query The representation of the user’s information need
Index A structure that makes search practical
Relevance judgment A decision about whether an item helps answer the need

Matching is not the same as relevance

A document containing every query word can still be the wrong source. It might discuss a different equipment model, an obsolete revision or a condition the user did not ask about.

Conversely, a useful passage may not contain the user’s wording. “Preventive maintenance” may answer a question about “avoiding unexpected breakdowns.” Different retrieval methods recognize different forms of matching.

Retrieval and generation

Retrieval selects evidence. Generation turns evidence and instructions into an answer. A fluent answer cannot establish that retrieval succeeded, and a relevant retrieved passage does not guarantee that the generator uses it correctly.

This is why evaluation separates candidate coverage, ranking quality, context assembly, answer quality and citations. Fix the stage that failed instead of treating every incorrect answer as a prompting problem.

Candidate generation versus reranking

First-stage retrieval searches a large corpus relatively efficiently and produces a candidate set. A reranker then applies a more detailed relevance assessment to that smaller set.

Basic reranking belongs in the main practical pipeline. It should not be postponed until every advanced RAG technique has been explored. However, it cannot recover a necessary passage that was absent from the candidate set.

Key takeaway

Retrieval should find the right eligible evidence, not merely similar text. Eligibility includes authorization, current source state and task-specific constraints.

Vector-search execution: index, database, exact search and ANN

How vector search fits into retrieval. A vector index is a fast lookup structure; a vector database is the surrounding storage and application service. The database may add metadata, filtering, durability, replication and lifecycle controls, but the exact feature set depends on the product. A standalone ANN library should not be mistaken for a complete production database.

What the vector record needs to preserve

A candidate should remain traceable to its source and current eligibility. Alongside the vector, preserve identifiers and control metadata such as chunk_id, document_id, document_version, tenant_id, resource scope, source locator, ACL version, content hash, embedding configuration, index generation and active/deleted status. The original source text remains the evidence of record; the vector is an index representation.

Exact search and approximate nearest-neighbour (ANN) search

Exact search evaluates all eligible vectors under the selected metric. It is useful for small corpora, highly selective filters and as a reference implementation for evaluating ANN. ANN explores only part of the search space or uses compressed representations to reduce work. It may miss a true nearest neighbour, so speed must be assessed alongside recovery quality.

Keep two recall concepts separate. ANN recall compares ANN results with exact top results generated from the same vectors, metric and eligible set. Relevance recall compares retrieved passages with human-labelled, authorized and current gold evidence. ANN can reproduce exact neighbours very well while the underlying embedding representation still retrieves poor evidence.

Baseline rule: Compare exact and ANN using the same corpus snapshot, embeddings, metric, eligibility predicate and tie policy. If exact relevance is already poor, tuning ANN is unlikely to solve the main problem.

Keep candidate counts distinct

Do not call every stage “top-k”. Record the dense candidate limit, lexical candidate limit, fused unique candidate count, reranker input count and final evidence/context count separately. This reveals where a relevant passage disappeared.

2. Inverted Indexes and Posting Lists

Syllabus coverage: M06.2.1.1 — Classical search concepts.

Inverted index

An inverted index maps each indexed term to the documents or passages containing it. Instead of scanning every document for a word, the system looks up that word’s entries.

The Stanford IR textbook describes the dictionary-and-postings structure and its construction from tokenized, normalized documents. The conceptual change is from “document to words” to “word to documents.” Source: Introduction to Information Retrieval, inverted index construction

Posting lists

A posting list contains the document IDs associated with a term. A posting may also store term frequency, positions, field information or other data used in scoring and matching.

Fictional corpus:

ID Text
D1 unit-a indicator inspection
D2 unit-b inspection schedule
D3 invoice payment schedule

Selected posting lists:

Term Documents
inspection D1, D2
schedule D2, D3
indicator D1
invoice D3

For inspection AND schedule, the system intersects two lists and returns D2. For indicator OR invoice, it unions the relevant lists and returns D1 and D3.

Why document granularity matters

In a RAG corpus, an indexed “document” may actually be a chunk. Its length and term statistics therefore reflect the chunking design. Re-chunking can change lexical rankings even when the original source wording is unchanged.

Keep stable source identity alongside index-local document IDs. Search-engine IDs help the engine find records; source IDs and versions help the application verify authority, permissions and citations.

Key takeaway

Posting lists make exact-term search efficient, and their stored information determines which matching operations are possible.

3. Tokenization and Linguistic Processing

Tokenization

Tokenization divides text into units for indexing and querying. The analyzer may also normalize case, punctuation and word forms. Query processing must be compatible with index processing.

The Stanford text explains that tokenization choices affect which queries can match, especially for punctuation, hyphenation, identifiers and language-specific conventions. This makes tokenization a retrieval design decision, not merely text cleanup. Source: Stanford IR textbook, tokenization

Domain examples

A manual search may need to distinguish M-104, M-140 and M104. A software corpus may need to preserve C++, C# and method names. Removing punctuation indiscriminately can collapse meaningful distinctions.

A practical design can store multiple fields: a full-text field with linguistic analysis and an exact keyword field for identifiers. The query can use each according to its purpose.

Stop-word handling awareness

Stop words are common terms that some systems remove or treat specially. Examples in English include articles and prepositions. Removing them can reduce index noise, but it can also damage phrases or meaning.

Words such as “not,” “without,” “before” and “after” may be critical in procedures. A generic stop-word list should not be applied blindly to every domain. Modern systems can retain common terms when they are useful; stop-word removal is a choice, not an unavoidable IR stage.

Stemming awareness

Stemming uses rules or algorithms to reduce related word forms to a shared stem. The result need not be a valid dictionary word. It can improve recall when “inspect,” “inspection” and “inspecting” should match, but aggressive conflation can also merge distinct terms.

Lemmatization awareness

Lemmatization aims to reduce words to their dictionary base form, often using linguistic information. It can be more sensitive to grammatical context and language than simple stemming.

The Stanford textbook distinguishes these approaches and explains their role in grouping morphological variants. Their usefulness remains task-dependent; neither should be assumed to improve every query. Source: Stanford IR textbook, stemming and lemmatization

Practical analyzer tests

Build a small test table containing exact codes, plurals, hyphenated names, abbreviations, negation, mixed case and relevant languages. Record expected indexed terms and matching behavior.

If a user searches Unit-A and receives only Unit-B, inspect analyzer output and field selection before blaming the ranking formula.

4. Boolean, Phrase and Fuzzy Search

Boolean retrieval

Boolean retrieval combines conditions using operators such as AND, OR and NOT. It asks whether a record satisfies a logical expression, not necessarily how strongly it should rank.

Examples:

inspection AND indicator
maintenance OR servicing
inspection AND NOT archived

In an application, archived status should usually be a trusted metadata field rather than just a word excluded from body text. A document can contain the sentence “This procedure is not archived” while its lifecycle state says otherwise.

Phrase search

Phrase search looks for a sequence of terms in the specified order, with behavior governed by the analyzer and any permitted positional gap or slop.

A positional index records where terms occur so the engine can test phrase and proximity conditions. This is different from merely checking that all words appear somewhere in the same document. Source: Stanford IR textbook, positional indexes

For example, “return to service” should differ from a document containing “return the invoice” and “service schedule” in separate sections. Exact source quotations and specialized multi-word terms can benefit from phrase search.

Fuzzy and typo-tolerant matching awareness

Fuzzy matching allows small spelling differences, often measured using edit distance. It can help when a user types “inspeciton” instead of “inspection.”

Elasticsearch’s fuzzy-query documentation describes term matching through edit-distance expansions and exposes controls that bound those expansions. Its implementation details are product-specific, but the general tradeoff is broader matching versus additional work and possible false positives. Source: Elasticsearch fuzzy query

Why identifiers need care

M-104 and M-140 may be different manuals, not typos. Automatically correcting one to the other can return a plausible but wrong procedure.

Use exact matching for identifiers when the query clearly specifies one. If no result exists, a controlled suggestion can ask whether the user meant another identifier. Do not silently replace a critical code simply because it is one edit away.

5. TF-IDF and BM25

Term frequency

Term frequency, or TF, measures how often a term occurs in a document. Repetition can indicate relevance, but its benefit should not grow without limit. A long document repeating “inspection” 100 times is not necessarily more useful than a precise paragraph using it twice.

Inverse document frequency

Document frequency, (df(t)), is the number of indexed documents containing term (t). Inverse document frequency, or IDF, gives greater weight to terms that occur in fewer documents.

A simple unsmoothed form is:

[ \operatorname{IDF}(t)=\log\frac{N}{df(t)}, ]

where (N) is the number of indexed documents. Implementations use different smoothing conventions. The key intuition is that a term appearing everywhere carries less discriminating information. Source: Stanford IR textbook, inverse document frequency

TF-IDF

TF-IDF combines within-document frequency with across-corpus rarity. A simple formulation is:

[ w(t,d)=\operatorname{TF}(t,d)\operatorname{IDF}(t). ]

The exact TF transform, normalization and query scoring method vary. Treat TF-IDF as a family of weighting schemes rather than one universal implementation.

BM25

BM25 is a lexical ranking function that combines term rarity, saturating term frequency and document-length normalization. A common form is:

[ \operatorname{BM25}(q,d)= \sum_{t\in q}\operatorname{IDF}(t) \frac{f(t,d)(k_1+1)}{ f(t,d)+k_1\left(1-b+b\frac{|d|}{\operatorname{avgdl}}\right)}. ]

Here:

  • (f(t,d)) is the term frequency in the document.
  • (|d|) is document length under the index’s analysis.
  • (\operatorname{avgdl}) is average indexed-document length.
  • (k_1) controls the saturation behavior of term frequency.
  • (b) controls the amount of length normalization.

The Stanford textbook develops BM25 from probabilistic retrieval, including frequency and length effects. Lucene documents a positive IDF variant of (\log(1+(N-df+0.5)/(df+0.5))). Exact scoring details differ by implementation, so reproduce the deployed engine’s behavior when precision matters. Sources: Stanford IR textbook, BM25, Lucene BM25Similarity

Worked BM25 calculation

For an invented one-term query, let (N=100), (df=5), (k_1=1.2), (b=0.75), and document length equal average length.

Using the positive IDF form:

[ \operatorname{IDF}=\log\left(1+\frac{95.5}{5.5}\right)\approx2.9104. ]

If the term occurs once, the frequency factor is 1, so its contribution is approximately 2.9104.

If it occurs three times, the factor is:

[ \frac{3\times2.2}{3+1.2}=1.5714. ]

The contribution is approximately 4.5734. Tripling the occurrences does not triple the score, illustrating saturation. These parameter values are illustrative, not an instruction to use one setting for every corpus.

Practical limitations

BM25 does not directly understand whether a passage answers the question, contains a contradiction, has been superseded or belongs to the user’s tenant. It also depends on analyzer behavior and collection statistics.

Nevertheless, it is a valuable baseline, especially for precise terminology, names, codes and rare phrases. A dense retriever should demonstrate improvement over a properly configured lexical baseline rather than over a deliberately weak keyword search.

6. Field Boosting, Facets and Filters

Field boosting

Field boosting gives different relevance weight to matches in different fields. A match in a document title or equipment-code field may deserve more influence than a match in a long body or repeated footer.

For an invented manual search, a scoring design might prioritize exact equipment-code matches, then title matches, then section headings, then body terms. The weights must be evaluated; an overly strong title boost can suppress the only body passage containing an answer.

A boost changes ranking. It is not a hard eligibility rule. A sufficiently strong match elsewhere may still outrank a boosted result depending on the scoring design.

Faceted search

Facets summarize a result set by structured attributes such as document type, equipment family, language or revision status. Users can use them to narrow the search interactively.

Facet counts can reveal information. If an unauthorized document contributes to a count or category label, the interface may expose its existence even when its text is hidden. Compute facets over the authorized result universe.

Metadata filters

Filters enforce conditions such as tenant, permission scope, approved status, effective date or equipment model. Elasticsearch explicitly distinguishes scored query context from binary filter context, a useful conceptual separation for search design. Source: Elasticsearch query and filter context

Filter correctness and recall

A filter can reduce recall if metadata is wrong or the constraint is overly restrictive. “After 2024” is not the same as “effective during 2024.” Source-created time, publication time and effective time must not be confused.

When no results appear, inspect the eligible corpus and filter interpretation before expanding the query or relaxing important controls. Security constraints must not be dropped to make the result list look fuller.

7. First-Stage Retrieval and Top-k

Syllabus coverage: M06.2.1.2 — First-stage retrieval.

Top-k

Top-k retrieval returns up to (k) highest-ranked eligible candidates. The parameter controls candidate count; it is not a guarantee of quality or sufficient evidence.

Distinguish several counts:

  • Candidates requested from each retrieval branch.
  • Candidates retained after fusion and deduplication.
  • Candidates sent to the reranker.
  • Evidence units selected for the answer.

For example, retrieving 50 lexical and 50 dense candidates does not mean sending 100 passages to the answering model. After union, authorization, deduplication and reranking, perhaps five evidence units fit the final task. The numbers are illustrative.

Recall and precision tradeoff

A larger candidate pool can increase the chance of including required evidence, but it also increases downstream work and may introduce more difficult distractors. A small pool can be efficient while missing the answer entirely.

Tune candidate count using retrieval coverage, reranker quality, latency and evidence-token cost. The right budget may vary by query type.

Filtering and approximate search

Some search systems can apply filters during candidate generation; others may filter a retrieved pool afterward. Post-filtering can leave too few authorized candidates if many high-scoring items were ineligible.

Whatever the engine’s mechanics, do not expose unauthorized content to external rerankers, models or users. If the eligible pool is too small, retrieve more within the allowed scope or use a safer fallback. Do not remove the authorization requirement.

Key takeaway

Candidate recall sets a ceiling on what reranking can achieve. The candidate budget should be measured, not guessed.

Mandatory filters, ANN selectivity and the post-filter trap

Filtering when the retrieval branch is approximate

Filtering and ANN exploration interact. A system may return only eligible rows while still exploring an area dominated by ineligible records. This is a retrieval-recall problem, not permission to weaken the filter.

Distinguish predicate correctness (“every returned row satisfies the filter”) from eligible-neighbour recall (“the search explored enough of the eligible space to find the best rows”). Both need tests.

8. Dense, Sparse and Hybrid Search

Dense search

Dense search compares compatible query and document embeddings using a similarity or distance function. It can retrieve related wording without exact term overlap.

Dense Passage Retrieval provides a primary research example of learned dual-encoder passage retrieval. Its results demonstrate the possibility of effective dense candidate generation under the evaluated conditions, not the universal superiority of dense search for every source collection. Source: Dense Passage Retrieval

Dense search can struggle with exact identifiers, numerical distinctions, domain shift and contradictory statements. It still needs metadata filters and source validation.

Sparse search

Sparse search uses representations with relatively few active dimensions. Traditional term-based methods such as TF-IDF and BM25 are central examples; learned sparse encoders are another family.

Do not use “sparse” as a synonym for “simple.” A learned sparse system can use neural models to generate term weights or expansions. The important distinction concerns representation and retrieval behavior.

Hybrid search

Hybrid search combines complementary retrieval signals, commonly lexical and dense retrieval. One branch may find a rare equipment code while the other finds a relevant paraphrase.

Hybrid retrieval can improve coverage when its branches make different errors. It can also add latency, duplicate candidates and noise. If both branches consistently retrieve the same wrong material, combining them does not fix the underlying problem.

10. Reciprocal Rank Fusion

Syllabus coverage: M06.2.1.3 — Fusion and query improvement.

Definition

Reciprocal Rank Fusion, or RRF, combines ranked lists using positions instead of requiring raw score calibration.

A common form is:

[ \operatorname{RRF}(d)=\sum_{j}\frac{1}{c+r_j(d)}, ]

where (r_j(d)) is the one-based rank of candidate (d) in list (j), and (c) is a positive rank constant. A candidate absent from a list contributes zero for that list.

Elasticsearch documents this method for combining result sets with different relevance indicators. The rank constant and the window of results retained from each branch affect the merged output. Source: Elasticsearch reciprocal rank fusion

Worked example

Use an illustrative rank constant of 60:

Candidate Lexical rank Dense rank RRF score
A 1 3 0.032266
B 2 1 0.032522
C 3 Absent 0.015873
D Absent 2 0.016129

The fused order is B, A, D, C. B benefits from ranking near the top of both branches.

Runnable RRF example

from collections import defaultdict


def rrf(ranked_lists, rank_constant=60):
    if rank_constant <= 0:
        raise ValueError("rank_constant must be positive")
    scores = defaultdict(float)
    for ranked_ids in ranked_lists:
        seen = set()
        unique_ids = []
        for item_id in ranked_ids:
            if item_id not in seen:
                seen.add(item_id)
                unique_ids.append(item_id)
        for rank, item_id in enumerate(unique_ids, start=1):
            scores[item_id] += 1.0 / (rank_constant + rank)
    return sorted(scores.items(), key=lambda item: (-item[1], item[0]))


print(rrf([["A", "B", "C"], ["B", "D", "A"]]))

This standard-library example assumes the lists already contain eligible candidates from a consistent source snapshot. Production code must enforce those assumptions.

RRF versus score addition

A BM25 score of 12 and a cosine score of 0.8 are not on a shared scale. Adding them directly gives the larger numeric scale undue influence. RRF avoids this particular problem by using ranks.

RRF also discards score-gap information. A branch’s first result barely beating its second is treated through ranks, just like a much larger gap. Weighted or score-calibrated fusion may be useful, but should be tested against a simple rank-fusion baseline.

Two different k-like parameters

The retrieval candidate count and RRF rank constant are different concepts. Calling both k in code can create confusion. Prefer names such as candidate_limit and rank_constant.

ANN candidate-generation internals and vector-index engineering

ANN algorithms are candidate-generation strategies. They sit underneath the dense retrieval branch. They do not replace lexical retrieval, relevance evaluation, authorization or source-version checks.

HNSW: graph-based ANN

Hierarchical Navigable Small World (HNSW) organizes vectors in a multi-layer graph. Search makes broad moves through sparse upper layers, then descends to denser lower layers to explore nearby candidates. Think of moving from a city-wide map to a neighbourhood street network.

ParameterControlsEngineering effect
MGraph connectivity / links per nodeInfluences graph memory and navigability.

Tuning sequence: hold the build configuration fixed and vary ef_search first. If no affordable query setting meets the target, test higher build effort or connectivity in a new index generation. Raising query exploration cannot always compensate economically for a weak graph.

Static benchmarks are insufficient. Frequent inserts, updates, tombstones and deletes can increase traversal work or degrade graph navigability. Include realistic data churn in evaluation and rebuild or compact only when measured behavior justifies it.

IVF and IVFFlat: centroid/list-based ANN

Inverted File (IVF) partitions the vector space into regions represented by centroids. At query time, the system selects nearby centroids and probes only the corresponding lists. IVFFlat stores uncompressed vectors within those lists; it is still approximate because unprobed lists are skipped. Do not confuse IVFFlat with IVFPQ, which adds product quantization.

More probes usually inspect more vectors and may improve recall at additional cost. If the corpus changes substantially—for example, a multilingual technical collection is added after centroids were trained on English policy documents—measure list imbalance and retrieval quality by data slice, then retrain/rebuild when evidence shows the partitioning no longer represents the corpus.

Vector compression: scalar and product quantization

Scalar quantization (SQ) reduces precision independently for each coordinate. Product quantization (PQ) splits a vector into subvectors and represents each with a learned codebook identifier. PQ can reduce memory much more aggressively, but approximation can swap the order of close candidates.

A common recovery pattern is: retrieve a larger shortlist from the compressed index → fetch original vectors for that shortlist → rescore with the original metric (or use a text reranker) → pass the better-ranked results onward. Rescoring can correct ordering among retrieved candidates; it cannot recover a relevant passage that never entered the shortlist.

Record the embedding model and revision, query/document encoding convention, dimensions and numeric type, metric and normalization, chunking/extraction versions, metadata schema and authorization fields, index family/build parameters, and corpus/index generation. Equal vector dimensions do not make two embedding models compatible.

Change one variable per experiment. Compare exact/original vectors, ANN/original vectors, ANN/compressed vectors, and compressed retrieval plus rescoring on the same queries and filters. Report ANN recall, relevance recall, slice-level quality, p95/p99 latency and measured memory. Do not attribute a gain to HNSW if the embedding model, chunking and reranker all changed together.

Engine-specific examples: pgvector exposes HNSW and IVFFlat indexes; FAISS exposes HNSW and IVF/PQ index families. Parameter names and filter behavior vary by version. Treat example settings as starting points, not universal recommendations.

11. Query Expansion, Rewriting and Multi-Query Retrieval

Query expansion

Expansion adds related terms or controlled aliases to improve recall. For example, a domain dictionary might map “PMS” to “planned maintenance system” when that meaning is appropriate to the collection.

Uncontrolled expansion can create query drift. “Port inspection” might be expanded toward computer networking even when the user means a harbor. Preserve the original query and record the expansion source.

Query rewriting

Rewriting reformulates a query into a more useful search form while preserving the information need. It may resolve conversational references, remove irrelevant phrasing or make an implicit subject explicit.

Conversation:

User: Open the Unit A inspection manual.
User: What changed in the latest revision?

A rewrite might make the second question searchable as “Changes in the latest approved revision of the Unit A inspection manual.” It must not invent a revision number or convert “latest approved” into “latest uploaded.”

Multi-query retrieval

Multi-query retrieval searches several formulations and merges their candidate sets. One query might emphasize the equipment name, another the procedural wording and another a controlled synonym.

Possible benefit: improved coverage when one wording fails. Costs include additional retrieval calls, duplicate evidence and more opportunities for drift.

Set a query budget, preserve the original query as a branch when useful, and deduplicate candidates by stable identity. A model generating ten almost identical rewrites has increased cost without necessarily adding useful evidence.

Original intent as a constraint

For exact identifiers, dates, negation and comparison scope, validate that rewrites preserve important constraints. “Before storage” and “after storage” are different information needs.

Query text from the user or an external source must not be allowed to remove the server’s authorization filters. An expanded query changes relevance search, not who the user is allowed to access.

Key takeaway

Query improvement should broaden useful matching while preserving intent and control boundaries.

12. Self-Querying and Controlled Filters

Definition

Self-querying uses a model or parser to translate a natural-language request into a semantic search query plus structured metadata constraints.

Example user request:

Find approved English manuals for Unit A published after January 2025.

A conceptual parsed result could be:

{
  "search_text": "Unit A manuals",
  "filters": {
    "language": "en",
    "status": "approved",
    "publication_date_after": "2025-01-31"
  }
}

The date interpretation must be defined by the application; ambiguous requests may need clarification. This example illustrates why a parser output is a proposal that requires validation.

Separate user constraints from security constraints

The model can propose fields such as document type or date range. It must not determine the authenticated tenant or grant itself access to another collection.

A trusted server combines allowed user filters with mandatory controls:

effective_filter = authorized_scope AND validated_user_constraints

This is conceptual logic, not a SQL string to concatenate. Use typed query construction and parameterized operations where relevant.

Validation rules

Allow only known fields and operators. Validate types, ranges and enumerated values. Reject unsupported fields rather than silently ignoring them. Set limits on expensive queries and record how the natural-language request became a structured query.

If the parsed constraints conflict, an empty result may be correct. The system should explain the issue or seek clarification without dropping mandatory restrictions.

Self-querying versus routing

Self-querying builds a search request. Routing chooses which source or retrieval method should handle it, such as SQL for a count or lexical search for an exact code. A complete system can use both, but each needs its own validation and evaluation.

A note on namespaces and trusted filter scope

Namespaces are not authorization by themselves

A namespace, collection name or partition label is only a routing/organization mechanism unless trusted server-side routing and access enforcement prevent cross-scope access. Never accept a client-provided tenant or namespace value as the authority for access. Derive the permitted scope from verified identity and policy, then combine it with validated user-requested filters.

IR5-E2Why is "self-querying" described as producing a proposal rather than a final search request? Recall+
Model answer / explanation

Because the component generating the structured filter (often a model) is treated as untrusted input — exactly like user input — so its output must pass through the same validation and authorization logic as anything else before it's allowed to actually execute against the index, rather than being trusted and run directly.

NEW — Interview

IR5-E3What's the one-sentence rule for where tenant/permission scope is allowed to come from in a self-querying system? Interview+
Model answer / explanation

Tenant and permission scope must come only from trusted, server-side authentication — never from the model's parsed output or the user's natural-language request — and the backend combines that mandatory scope with the model's proposed (validated) constraints using an AND, never an OR that could expand access.

IR5-E6Product wants self-querying to support a "search across all tenants I have ANY relationship with" feature for a small set of power users with elevated cross-tenant roles. A namespace can be only a logical label or routing hint. Production vector-search architecture and lifecycle controls

Production storage: index vs database

A vector index accelerates nearest-neighbour lookup. A production vector database or integrated storage layer may additionally provide metadata, filters, CRUD, replication, backups and operational controls. Verify the actual product capabilities. FAISS or another index library alone does not automatically supply authentication, tenant isolation, durable metadata, backup strategy or deletion workflows. A vector database also does not automatically replace a relational database: relational systems remain useful for transactions, structured records and policy joins; integrated extensions such as pgvector can combine relational data with vector search.

Sharding and replication solve different problems

MechanismPurposeRisk to plan for
ShardingSplits records/work across nodes for capacity and parallelism.Skewed tenant size or traffic creates hot shards; cross-shard fan-out adds cost.
ReplicationCopies data for availability and read capacity.Lagging replicas may serve stale versions or resurrect a deleted record.

For global top-k, gather enough candidates from each shard and merge at a coordinated layer using compatible scores or rank-based fusion. “Top-2 per shard” is not generally sufficient to guarantee the global top-10. Do not directly compare scores from different branches or incompatible model/metric configurations.

Updates, tombstones and compaction

Distinguish content changes from control-metadata changes. If embedded text changes, re-embed. If only ACL changes, update authorization metadata and policy version; the vector can remain unchanged. Track content version and ACL/policy version separately so a “content unchanged” optimization cannot skip a permission revocation.

A tombstone marks a record inactive so it stops being served immediately, while physical index cleanup is deferred. Compaction later reorganizes storage and reclaims space. Compaction is operational maintenance, not a compliance guarantee; serving-time suppression must happen immediately.

Deletion must propagate to derived artifacts

A deleted source may survive in lexical indexes, extracted text, thumbnails, summaries, graph facts, query caches, answer caches, reranker stores, conversation-memory summaries, replicas and backups subject to retention policy. Track derived data by source ID and version; invalidate or purge it through a deletion workflow and verify every serving path. A zero-result vector search alone is not proof of deletion.

Versioned publication and atomic cutover

Build a new generation in staging, validate its vectors, metadata, source locators and all required indexes, reconcile updates/deletions that occurred during the build, then switch the authoritative manifest/generation atomically. Query encoder and index generation must move together. Keep the previous valid generation available for rollback; never serve new vectors with old citation locators or mix incompatible generations.

Production gates

  • Eligibility: no unauthorized records in adversarial security tests.
  • Approximation: ANN recall against a filtered exact reference meets the project gate.
  • Relevance: no material regressions on identifiers, rare classes, languages or other critical slices.
  • Performance: p95/p99 latency and timeout rate meet budget at target concurrency.
  • Lifecycle: updates, ACL changes, tombstones, replicas and caches obey the declared serving guarantee.
  • Recovery: failed builds preserve the previous valid generation and can be rolled back.

IR6-F1Why does the material insist on not deliberately weakening the BM25 baseline when comparing it to dense or hybrid retrieval? Recall+
Model answer / explanation

A deliberately under-tuned baseline makes any alternative look artificially superior, which can justify adopting a more complex (costlier, higher-latency) system based on a comparison that wouldn't hold up against a properly configured baseline — the whole point of a baseline is to represent the best reasonable version of the simpler approach, so the comparison reflects a genuine trade-off rather than a strawman.

IR6-F2What's the difference between what Hit@20 tells you and what nDCG@5 tells you, and why do you need both? Recall+
Model answer / explanation

Hit@20 answers "did the evidence make it into a reasonably large candidate pool at all" (coverage), while nDCG@5 answers "was the evidence placed usefully near the top once pool size is small" (ranking quality) — a system can have perfect coverage and terrible ranking (buries the answer at position 18) or vice versa, so either metric alone hides a different class of problem.

IR6-F3You're given an A/B test showing a new retrieval config improves the average relevance score by 8%. What's the first follow-up question you ask before approving the rollout? Interview+
Model answer / explanation

"Does the 8% average improvement hold up when broken out by query category, especially exact-identifier and permission-sensitive queries?" — an aggregate improvement can mask a regression in a smaller but critical query category, and that's exactly the failure mode this section repeatedly warns about.

IR6-F6You inherit a retrieval system with no historical evaluation data and a backlog of vague "search feels off" complaints. Walk through how you'd build an evaluation practice from zero, in priority order. Senior Situational+

IR6-V01Why should vector retrieval be measured with p95 and p99 latency, not only average latency?Theory · Mid+
Model answer / explanation

Average latency hides slow outliers. Tail latency affects users and service-level objectives, especially under concurrency and selective filters. Record percentiles and timeout rates, and break the path into query embedding, database search, reranking, source fetch and generation.

IR6-V02How are sharding and replication different?Theory · Junior+
Model answer / explanation

Sharding splits data across nodes to distribute storage and compute. Replication stores additional copies to improve availability and read capacity. Shards introduce routing and fan-out concerns; replicas introduce consistency and stale-read concerns.

IR6-V03What is a hot shard, and why can tenant-based sharding create one?Situational · Mid+
Model answer / explanation

A hot shard receives disproportionate data volume or traffic. Tenant sizes are often skewed, so one very large or active tenant can overload a shard while others remain underused. Monitor load as well as record count and isolate unusually large tenants when justified.

IR6-V04How should a system calculate a global top-k across multiple shards?Practical · Senior+
Model answer / explanation

Collect a sufficiently large candidate set from each shard, then merge at a coordinator using compatible scores or a deliberate fusion/reranking method. Taking only a tiny fixed number from each shard can omit a true global top result. Raw scores from incompatible metrics or retrieval branches should not be mixed directly.

IR6-V05A replica serves a document that was deleted on the primary a few seconds earlier. What determines whether that is acceptable?Situational · Mid+
Model answer / explanation

The declared deletion/consistency guarantee determines the answer. A lagging replica must not resurrect a source beyond the declared enforcement point.

IR6-V06What is a tombstone, and how is it different from compaction?Theory · Junior+
Model answer / explanation

A tombstone is a logical deletion marker that makes a record ineligible for serving immediately. Compaction is a later background process that reorganizes storage and reclaims physical space. Compaction is not a substitute for immediate serving-time suppression or a compliance guarantee.

IR6-V07Vector search returns no result for a deleted source, but the assistant later summarizes the same source. Where else should deletion be checked?Situational · Senior+
Model answer / explanation

IR6-V08Why should content version and ACL/policy version be stored separately?Theory · Mid+
