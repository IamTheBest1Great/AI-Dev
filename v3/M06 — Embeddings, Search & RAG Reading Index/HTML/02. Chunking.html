Orientation

Start with the three units

① Source unit

Preserves original document structure and authoritative lineage. Typical examples: a complete section, table or code function/class.

② Retrieval unit

What vector or lexical search scores: a focused paragraph, sentence or table row.

③ Answer-context unit

What the answering LLM reads: the retrieved fragment deliberately expanded with heading, scope, conditions and exceptions.

The core design question: What unit makes the required evidence easy to find without losing the conditions needed to interpret it? The guide rejects a universal "500 tokens + 20% overlap" rule.

THE CORE DESIGN QUESTION

Chunk for meaning, not a magic number.

A large source is divided into retrievable pieces—but headings, equipment names, units, exceptions and lineage must travel with the evidence.

Additional explanation · source pages 3–4, 10

  • Topic overview: Chunking is the step that turns prepared source content (manuals, policies, tables, code, OCR output) into units that can be indexed, retrieved and handed to a language model as evidence.
  • It keeps three things attached to each unit: interpretable meaning, source lineage, and access-control information.
  • The core design question: "What unit makes the required evidence easy to find without losing the conditions needed to interpret it?" — not "How many tokens per piece?"
  • Three distinct units: Source unit (authoritative structure), Retrieval unit (what search scores), and Answer-context unit (what the LLM reads).
  • Two lifecycles meet at the index: Build time (Budget Planning → Boundary Selection → Enrichment) and Query time (Query-Time Retrieval → Verify & Maintain).
  • Why it matters: Prevents context loss, enforces security through boundaries, ensures correctness over time (purging updates), and provides trustworthy non-duplicated evidence.
  • Real-world applications: Technical manuals, legal clauses, product catalogs, code references, maintenance tables, multi-tenant document stores.
  • Study routine: Build the mental model → Learn one lifecycle stage at a time → Trace the whole system (Manual M-104) → Revise and test.
  • Completion test for every stage: Define the stage, explain its mechanism, identify inputs/outputs, diagnose one failure, and justify one engineering trade-off.

Study guide learning objectives

  • Define chunking and explain the source, retrieval and answer-context units.
  • Budget tokens separately for the embedder, reranker and answering LLM, and detect silent truncation.
  • Choose and combine fixed-size, recursive, sentence, semantic and structure-aware strategies.
  • Compute stride, window count and duplication.
  • Design chunk metadata (embedding text versus control fields).
  • Run the query pipeline: filter first, search small, diagnose, expand, and assemble within budget.
  • Deduplicate and evaluate by source span.
  • Diagnose production failures and justify engineering trade-offs.
Clarified conceptDoubt 8. Why do embedding, reranking, and answer generation need separate token budgets?
  • Embedder: Chunk + Heading Prefix + Formatting (e.g., ≤512 tokens).
  • Reranker: User Query + Candidate Passage + Formatting evaluated jointly.
  • Answering LLM: System Prompt + History + Query + All Expanded Chunks + Reserved Output Tokens.
  • Each stage processes a different composite input with a different model ceiling.

3.1 Budget Planning Card

Purpose: Know the exact token size ceilings across every downstream model before cutting a single word.
Key Decisions: Which model-specific tokenizer to use, what overhead counts against each stage's budget, and how many tokens to reserve for output.
  • Core Techniques: Model-specific subword tokenization, explicit prefix/heading accounting, and separate budget enforcement.
  • Failure Mode 1: Counting words/characters instead of tokens.
  • Failure Mode 2 (Silent truncation): If chunk+prefix exceeds embedder limits, the API silently truncates the tail, breaking retrieval matching.
  • Failure Mode 3 (Reranker overflow): A chunk fits the embedder but overflows the reranker when processed jointly with a long query.
  • Failure Mode 4 (LLM overflow): Chunks individually fit, but collectively overflow the LLM's context window.

3.2 Balancing the Three Consumer Budgets

ConsumerWhat Counts Against Its BudgetConstraint
1. Embedding ModelChunk body text + Injected Heading/Prefix + formatting tokens.Often has a strict hard ceiling (e.g., 512 tokens). Exceeding it causes hard errors or silent tail truncation.
2. Reranker ModelUser Query + Candidate Passage + Cross-encoder formatting tokens.Processes query and chunk jointly. Candidate chunks must leave room for long user queries.
3. Answering LLMSystem Instructions + History + Query + All Assembled Evidence + Reserved Output.Must leave enough headroom for reasoning and generated response, avoiding context bloat.

3.3 Worked Embedding Budget Calculation

  • Example A (Maximum Body Budget): Embedding limit 512 tokens. 30-token heading + 10-token formatting. Maximum Body Budget = 512 − 30 − 10 = 472 tokens.
  • Example B (Checking Chunk Fit): 30 + 470 + 20 = 520 tokens > 512, exceeds limit by 8 tokens. Must split or trim — never silently truncate.
Question / model answerQ18. Why is token-aware chunking important instead of using only word or character counts?
  • Language models operate within token-based input limits rather than word or character limits.
  • A word does not necessarily correspond to one token; punctuation, numbers, and special characters may split into multiple tokens.
  • Two chunks with the same word count can have different token counts.
  • Use the tokenizer associated with the target model to estimate chunk size accurately.
Question / model answerQ19. Why must we consider separate token budgets for embedding, reranking, and answer generation?
  • Embedding model: Chunk + prefixes/metadata must fit the embedder's input limit.
  • Reranking model: Query and candidate passage are processed together, so their combined token count must fit.
  • Answer-generation model: System prompt, history, query, retrieved context, and reserved output must fit the context window.
  • A chunk that fits the embedding model may still be too large for reranking, and valid chunks may collectively exceed the answer-generation budget.
Question / model answerQ20. A chunk contains 30 tokens of heading, 470 tokens of content, and 20 tokens of formatting. The embedding limit is 512 tokens. Does the chunk fit?
  • Total = 30 + 470 + 20 = 520 tokens. Limit = 512.
  • Exceeds limit by 520 − 512 = 8 tokens. The chunk does not fit.
  • Must reduce the chunk or adjust its content while preserving important context.
Question / model answerQ39. Your chunks exceed the target size even after recursive splitting. What could be happening?
  • Wrong length function unit: splitter measures characters/words, not model tokens.
  • Missing separator fallback: run-on OCR/log line lacks expected separators; no token-level fallback configured.
  • Unaccounted metadata injection: headings/prefixes prepended after splitting, pushing a 490-token body over 512.
Engineering scenarioScenario 5: The chunk fits the embedding model but fails during reranking
  • Problem: A 450-token chunk fits the embedder limit but fails in the reranker because the combined query+passage limit is exceeded.
  • Solution: Treat embedding and reranking stages as separate constraints. Calculate the combined token count, leaving headroom for the query.
  • Reduce or prepare the candidate passage appropriately before reranking, ensuring reduction does not remove critical relevance signals.
  • Reserve enough capacity for the query and any model-specific formatting.
Clarified conceptDoubt 7. Why can't we rely on word count?
  • Because words and tokens are not equivalent.
  • A tokenizer may split one word into multiple tokens; punctuation and formatting also contribute to token count.
  • The same number of words can produce different token counts.
  • Use the tokenizer associated with the target model when enforcing token limits.
BOUNDARY SELECTION & SLICING · SOURCE PAGES 26–39

SemanticMeaning shifts between adjacent units

Recommended combination: permission boundary → section / record → semantic unit → recursive size fallback → exact tokenizer check.

4.1 Boundary Selection Card

Purpose: Decide where to draw the cutting lines so each retrieval unit preserves coherent meaning and structure.
  • Failure Modes: Heading separated from body.
  • Condition/exception separated from instruction.
  • Table header separated from row (e.g., '150' isolated without a unit or column label).
  • Code signature separated from function body.
  • Semantic splitter severing a rule from its differently worded exception.
  • False sentence splits on abbreviations (Rev. 4, 3.5 bar). Unlogged hard splits.

4.2 Comparison of the 5 Core Chunking Strategies

StrategyMechanismStrength / best fitMain risk / limitation
Fixed-sizeCut by fixed character, word or token windows; stride = size − overlap.Simple, predictable and reproducible.Can split a sentence, heading, procedure step or table row; measurement unit must be explicit.
RecursiveTry larger separators first (section → paragraph → sentence → word / hard limit).Preserves natural boundaries while respecting a maximum size.Needs separator order and fallback rules; long unbroken spans can still exceed the cap.
Sentence-basedDetect sentences and group one or more into a chunk.Preserves grammatical boundaries and enables sentence-window retrieval.Grammar is not meaning; a sentence can depend on its heading or neighboring scope.
SemanticEmbed adjacent provisional units and split where similarity drops.Adapts to topic changes in unstructured prose without headings.Embedding cost, model dependency and risk of separating rules from exceptions with different vocabulary.
Structure-awareParse headings, tables, code, FAQs, slides and other explicit formats.Strong baseline for manuals: heading + body, row + headers, signature + code body, question + answer.Requires format-specific parsers and recursive fallback for oversized structural blocks.

4.3 Deep-Dive Worked Examples (A–F)

  • A. Fixed-Size Half-Open Intervals: 24 tokens, size=10, overlap=2 → windows [0,10), [8,18), [16,24).
  • B. Recursive Worked Budget: Paragraphs 180 + 170 = 350 ≤ 400 tokens (Chunk 1). Paragraph 3 (420 tokens) exceeds 400; falls back to sentence boundaries. Oversized sentence → explicit logged hard split.
  • C. Sentence-Based Scope Trap: "This procedure applies only to Unit A." / "Inspect the indicator every 30 days." / "For Unit B, use the separate schedule in section 5." Isolating Sentence 2 makes it look universal.
  • D. Semantic Boundary Decision: Succeeds detecting a sharp drop between inspection exceptions and invoice terms. Fails when a procedure and its differently-worded exception have low cosine similarity — structural rules must constrain semantic signals.
  • E. Structure-Aware Rules: Procedures keep prerequisites + steps + warnings together; tables retain title/headers/units/footnotes on every row; code uses AST; FAQs keep question+answer together; PDFs stitch across pages.
  • F. Recommended 5-Step Order: Separate sources/permissions → group by structure → preserve semantic units → split oversized groups recursively → measure final representation with exact tokenizer.

4.4 Overlap Math, Token Bloat & Boundary Quality

  • Stride (S): Chunk size (C) minus Overlap (O). S = C − O.
  • Window count n: 0 if N=0; 1 if 0<N≤C; 1 + ⌈(N−C)/(C−O)⌉ if N>C.
  • Asymptotic Duplication: Approximated by C / (C − O).
  • Worked Example: N=10,000, C=500, O=100 → S=400, n=25, total stored = 12,400 tokens (2,400 duplicated).
  • Why Overlap is a Weak Band-Aid: Cannot fix distant structural dependencies (a header 2,000 tokens away). Creates "false independent evidence." Artificially inflates chunk-level Recall@K.
Question / model answerSQ3. What does recursive chunking mean?

It tries preferred larger natural boundaries first (e.g., sections, paragraphs) and uses finer boundaries (sentences, words, hard limit) when content exceeds the chosen size limit. It requires explicit separators and fallback rules.

Question / model answerSQ4. How does semantic chunking differ from sentence splitting?

Sentence splitting identifies grammatical boundaries. Semantic chunking estimates changes in topic or meaning, often using vector representations of neighboring text units.

Question / model answerSQ8. What problem does overlap address?

It makes some boundary-adjacent content available in neighboring chunks. It does not automatically preserve long conditions or prevent permission errors.

Question / model answerQ2. What can go wrong when we split a document without considering meaning?
  • Mechanical splitting can separate dependent information.
  • Example: Equipment: Emergency Generator / Instruction: Inspect every 30 days / Exception: during maintenance shutdowns — a mechanical split could separate the instruction from the equipment name or its exception.
  • This creates context loss and can lead to incorrect or unsupported answers.
Question / model answerQ6. How should tables and safety exceptions be handled during chunking?
  • Tables: retain table title, column headers, row labels, units, and relevant footnotes. Repeat headers if split.
  • Safety conditions/exceptions: remain connected to the rules they modify.
  • Avoid putting an entire large table or manual into one chunk — reduces retrieval precision.
Question / model answerQ10. How would you chunk a maintenance table safely?
  • Row-oriented strategy preserving table structure.
  • Each chunk retains table title, relevant column headers, row labels, units, and applicable footnotes.
  • If split across chunks, repeat necessary headers so each chunk is independently interpretable.
  • Safety conditions and exceptions retained with the rows they modify.
Question / model answerQ13. What is the difference between fixed-size chunking and recursive chunking?
  • Fixed-size divides text according to a predetermined character, word, or token limit; may use overlap.
  • Recursive attempts to split using a hierarchy of natural separators (section → paragraph → sentence).
  • Fixed-size relies on predetermined boundaries; recursive attempts to preserve natural document structure.
Question / model answerQ14. What does implementation complexity mean in recursive chunking?
  • Configuring the separator hierarchy, defining the length measurement, handling paragraphs/sentences that exceed the limit.
  • Preserving document structure and retaining metadata such as headings, source offsets, and document hierarchy.
  • Designing and configuring the splitting procedure correctly.
Question / model answerQ15. What is the difference between sentence-based chunking and semantic chunking?
  • Sentence-based uses grammatical and punctuation boundaries.
  • Semantic chunking attempts to identify changes in meaning or topic, using embeddings of neighboring sentences/windows.
  • Sentence-based focuses on linguistic structure; semantic focuses on meaning.
Question / model answerQ16. What is one major limitation of semantic chunking?
  • Semantic boundaries are not always straightforward.
  • A safety exception may use different terminology from the instruction it modifies; semantic chunking can accidentally separate them.
  • Also requires embedding computations and threshold configuration.
  • Do not rely on semantic similarity alone — consider document hierarchy and structural relationships.
Question / model answerQ22. What is the difference between a chunk size and an overlap size?
  • Chunk size determines the maximum amount of content in an individual chunk (e.g., 500 tokens).
  • Overlap determines how much content is repeated between neighboring chunks (e.g., 50 tokens).
  • Excessive overlap creates duplicate content and increases storage and retrieval costs.
Question / model answerQ23. How would you decide the appropriate overlap percentage?
  • Do not select an overlap percentage without evaluating document structure and retrieval behavior.
  • For documents where important info crosses boundaries, small overlap may help.
  • For well-structured documents, less overlap may be sufficient.
  • Test different overlap values against representative queries; measure relevance, duplication, context completeness, token usage.
Question / model answerQ24. Why is preserving document hierarchy important during chunking?
  • Document hierarchy provides context about relationships between pieces of information.
  • A heading may identify the equipment, procedure, or department to which paragraphs apply.
  • If separated, the resulting chunk may become ambiguous.
  • Preserve relationships such as document, chapter, section, subsection, paragraph; include parent heading in child chunk's metadata or text.
Question / model answerQ27. What should happen when a paragraph is larger than the configured chunk size?
  • First attempt to split using smaller natural boundaries, such as sentences.
  • If a sentence is still too large, use a lower-level fallback strategy while preserving meaning.
  • Avoid blindly cutting at an arbitrary character position.
  • Retain the parent heading and relevant metadata so smaller pieces remain understandable.
Question / model answerQ28. Can the same document require different chunking strategies for different sections?
  • Yes. A document can contain different content structures.
  • Paragraphs → recursive chunking; tables → row-aware chunking; procedures → step sequences; headings → connected to content; code → logical blocks.
  • Identify the content type and apply an appropriate chunking method to each section.
Question / model answerQ37. Your semantic chunking strategy performs worse than recursive chunking. Why might that happen?
  • Semantic chunking is not automatically better.
  • Semantic similarity may incorrectly separate sentences that are logically connected but use different terminology (especially instructions, conditions, exceptions).
  • It introduces embedding computations and configuration decisions that may not improve retrieval for every document type.
  • For structured technical documents, recursive or structure-aware chunking may perform better.
Question / model answerQ40. How would you decide whether to split a document at a paragraph boundary or a sentence boundary?
  • Consider whether the paragraph expresses one complete idea or multiple independent topics.
  • If coherent and fits token limit → preserve as one unit.
  • If too large or contains multiple distinct ideas → consider splitting at sentence boundaries.
  • Check whether sentences depend on each other; conditions, exceptions, definitions should remain connected.
  • Preserve meaning rather than producing equal-sized chunks.

Clarified conceptDoubt 4. Does recursive chunking always create the largest possible chunks?
  • No. It follows a separator hierarchy and attempts to preserve natural boundaries while respecting a configured size limit.
  • If a section is 336 tokens and the max is 400, it stays one chunk.
  • If the max is 100, it splits at paragraph/sentence boundaries — producing natural-sized pieces, not mechanical cuts.

  • Mainly implementation and configuration decisions.
  • Selecting the separator hierarchy; defining the length measurement; handling content that exceeds the limit.
  • Preserving heading and section relationships; retaining metadata and source offsets.
  • Does not necessarily mean computationally expensive.

5.1 Enrichment Card

Purpose: Stamp every generated chunk with deterministic identity, strict access-control/version metadata, exact original source coordinates, and structural node relationships.
  • Failure Mode 1: Putting "TOP SECRET" or "Restricted to Ship A" inside the embedded text and expecting vector search to enforce permissions.
  • Failure Mode 2: Using purely position-based chunk IDs (chunk_01) which shift meaning when a paragraph is inserted at the top. Use content-hash or stable IDs.
  • Failure Mode 3: Unversioned parent links causing a v4 child to expand into a stale v3 parent.
  • Failure Mode 4: Relying on a stale local worker's current:true flag instead of authoritative source state.

5.3 Semantic vs. Control Metadata — "Security Guard Outside the Building"

  • KEY IDEA: Embeddings only understand linguistic similarity and grammar — they do not enforce security or permissions.
  • Writing "TOP SECRET" or "Restricted to Tenant A" inside the chunk text will not prevent semantic search from returning it to an unauthorized employee.
  • Include in embedding text: Document title, section/subsection headings, equipment family/unit identifier, key content labels/table headers, document language.
  • Keep as control fields: tenant_id, acl_ref/acl_version/user-group lists, version_id/chunking_config, lifecycle flags (current/deleted), internal system IDs (chunk_id, parent_id, source_blocks).
  • Sensitive control metadata should never be casually dumped into LLM prompts or application logs.

5.4 Deterministic Identities, Source Spans & Re-Chunking

  • Position-based vs. content-hash IDs: A position-based ID (chunk_05) shifts meaning on insert. A content-hash ID stays stable for unchanged text if the hash includes sufficient lineage context.
  • Source Span vs. Chunk ID: A chunk_id is an ephemeral artifact of a specific chunking configuration. A source span points to the immutable physical location. It survives re-chunking and serves as the single source of truth for dedup, citation verification, and cross-strategy evaluation.

5.5 Building Parent-Child & Hierarchical Graphs at Build Time

  • Child Nodes (Embedded & Indexed for Search): Small, granular retrieval units (e.g., C31: Inspection interval paragraph; C32: Indicator check paragraph; C33: Exception paragraph).
  • Parent Node (Stored in Document Store for Expansion): Larger surrounding section P3 (Section 3.2 — Unit A inspection, containing scope, steps, and all exceptions). Every child stores parent_id.
  • Full Hierarchical Representation: Represents a document at multiple connected granularities: Document → Chapter → Section → Paragraph → Sentence.
  • Why a hierarchy is NOT automatically a summary tree: LLM-generated summaries must be labelled as derived representations and tracked by source-span dependencies. Never interchangeable with original source evidence.

6.1 The Six Query-Time Steps (formerly D1–D6)

  • Step 1 — Hard Pre-Filter: Filter index by tenant_id, acl, version_id (current=True), and deleted=False before vector/lexical scoring. "Station the security guard outside the building."
  • Step 2 — Search Small Units: Run hybrid (vector + lexical/BM25) search over granular child chunks or focus sentences.
  • Step 3 — Diagnose Context Need: Check if missing context is structural (same document/section) or cross-referenced (another section/document).
  • Step 4 — Structural Expansion: Fetch parent section, sentence window, table headers, or code class signature. Must re-verify ACL and version on every expanded span.
  • Step 5 — Secondary Search: If a chunk says "Follow Policy B" or "See Section 8", trigger a fresh authorized query for that target.
  • Step 6 — Budgeted Assembly: Assemble expanded units within the LLM context budget; insert a shared parent only once even if five of its children matched.

6.2 Small-to-Big Retrieval Patterns

  • Parent-Child Expansion: Search hits a child sentence, expands to parent section adding scope and prerequisites. Shared parent deduplication: insert P3 once even if C31, C32, C33 all match.
  • Sentence-Window Retrieval (radius w): Index each sentence; expand to s_(i−w)…s_(i+w). Window ≤ 2w+1 sentences. Clip at section, revision, and permission boundaries. Store central focus sentence ID separately.
  • Table Small-to-Big: Expand a row to include table title, column headers, units, footnotes.
  • Code Small-to-Big: Expand specific function match to include signature, docstring, type definitions, and containing class/module context.

6.3 Structural Expansion vs. Secondary Search

  • Structural Expansion ("Zoom out"): Traverses deterministic, pre-computed links (parent_id, prev/next, table schema) created at Build Time. Use when missing context is immediately adjacent or structurally enclosing.
  • Secondary Search ("Look up another file"): Executes a new query against the search index using extracted entity/section references. Use when text contains an explicit cross-reference to another section/document.
  • Why the other fails: A second search is unnecessary overhead when the parent ID is known; zooming out to the parent of Section 2 never fetches Section 8.

6.4 "Lost in the Middle" — Why More Context Is Not Always Better

  • Research by Liu et al. demonstrated LLMs exhibit a strong U-shaped performance curve over long contexts: they attend well to information at the very beginning (primacy) and very end (recency), but performance drops sharply for facts buried in the middle.
  • Practical rule: Never blindly expand to an entire 4,000-token chapter when your budget is 2,000. Expand to the smallest sufficient structural level. Order the highest-confidence evidence near the prompt boundaries.

6.6 Reference Python Implementation: Query-Time Context Assembly

def assemble(query, user, index, budget_tokens):
    """Query-time assembly:
    1. Hard Pre-Filter + Search Small Units: filter first, then search.
    2. Structural Expansion: expand parent once per parent_id, verify ACL/version.
    3. Source-Span Deduplication: dedup by stable source_span.
    4. Budgeted Assembly: enforce LLM token budget."""
    hits = index.search(query, filters={
        "tenant_id": user.tenant_id,
        "acl": user.groups,
        "current": True,
        "deleted": False,
    })  # Hard Pre-Filter + Search Small Units

    seen_spans, parents, context, used = set(), set(), [], 0
    for h in hits:
        unit = h.parent if h.parent_id and h.parent_id not in parents else h
        if h.parent_id:
            parents.add(h.parent_id)  # Insert each shared parent at most once
        if not user.can_read(unit) or unit.version_id != h.version_id:
            continue  # Authorize and version-check expanded unit
        if unit.source_span in seen_spans:
            continue  # Source-Span Deduplication (not chunk_id)
        if used + unit.tokens > budget_tokens:
            break  # Budgeted Assembly: enforce LLM answer-context budget
        seen_spans.add(unit.source_span)
        context.append(unit)
        used += unit.tokens
    return context

  • Why stable source spans: Different chunking methods generate different chunk boundaries and IDs. A method with 10× larger chunks may show higher chunk-level Recall@10 simply because each chunk swallows a chapter.

7.4 Deletion, Re-Chunking & "Unlearning"

  • Chunks as "Frozen Slices of Time": Once sliced and embedded, chunks sit in vector memory as frozen snapshots. A vector DB will keep serving obsolete chunks forever unless explicitly purged.
  • What Must Be Purged on Update/Delete: (1) Child chunks and vector/BM25 entries; (2) Parent section nodes; (3) Pre-computed sentence windows; (4) Derived LLM summaries; (5) Query and expansion caches.
  • Why Partial Deletion Fails: If a restricted/deleted child is removed but its cached Parent Node (P3) remains, another child (C31) can trigger parent expansion to P3 and re-expose the deleted/restricted content.
  • Serving-Time Recheck: Verify every expanded span is currently authorized and belongs to the active source version, and recheck before emitting the final answer/citation.

Clarified conceptDoubt 1. Four often-confused failure concepts: context loss vs. stale data vs. duplicate evidence vs. retrieval failure
  • Context Loss: A valid current fact is separated from surrounding information needed to interpret it. Root cause: Boundary Selection (poor boundaries) or Structural Expansion (missing expansion). Fix: structure-aware chunking, prepended headings, parent-child/sentence-window expansion.
  • Stale Data: Indexed information is outdated because the source document was updated/deleted but old chunks remain active. Root cause: Unlearning & Purge (missing purge/version filter). Fix: version metadata, hard pre-filters, purge all derived chunks/parents/vectors on update.

  • Retrieval Failure: Well-formed, current chunks exist but the search engine fails to surface them. Root cause: Search Small Units (embedding mismatch, vocabulary gap, bad filters). Fix: hybrid search (Vector + BM25), query expansion, reranking, tuning child granularity.

9.1 Gap 1: Hybrid Indexing — BM25 + Vector

  • Why vector search alone fails: Dense embeddings struggle with exact alphanumeric part numbers, error codes, or manual IDs (M-104, C32, Rev. 4, 3.5 bar).
  • How chunk design serves both: Prepending the Section Path and Equipment Identifier boosts semantic context (embeddings) and exact term matching (BM25).
  • Keeping child chunks focused (100–300 tokens) prevents BM25 length-normalization penalties.
  • Both indexes must share the same chunk_id and control metadata so hard pre-filters apply identically before RRF or reranking.

9.2 Gap 2: Parent Size vs. Answer Budget (Scenario 6 Rule)

  • Formula: Max Safe Parent Size (P_max) ≤ Total LLM Evidence Budget (B_evidence) / k_distinct
  • B_evidence is the budget reserved for retrieved evidence (after system prompt, history, query, output reserve).
  • k_distinct is the minimum number of distinct sections/documents needed (typically 2–4).
  • Rule of thumb: Child Retrieval Unit 100–300 tokens; Parent Expansion Unit 400–1,000 tokens; never an entire 4,000-token chapter.
  • Fallback: 3-tier hierarchy (Chapter 4000 → Subsection 800 → Child 200); expand only to Subsection, or dynamically fall back to a Sentence Window (R=2 or 3).

9.3 Gap 3: Multimodal, OCR, and Multi-Page PDFs

  • Page breaks are layout artifacts, not semantic boundaries: Strip running headers/footers/page numbers, stitch continuous text across pages, chunk by logical structure, store "pages": [20, 21] in source_span metadata.
  • OCR noise & table serialization: Convert tables to structured Markdown or explicit Key: Value row serializations. Keep a link to the cropped page bbox.

9.4 Gap 4: Contextual Retrieval & Late Chunking

  • Contextual Retrieval (Anthropic pattern — Enrichment): At build time, an LLM or structural parser generates a 20–50 token situational prefix prepended to the chunk before embedding and BM25. Trade-off: increases ingestion compute. Deterministic header prepending gets ~80% of the benefit for free.
  • Late Chunking (Jina AI pattern — between Boundary Selection and Enrichment): Pass a long document window through a long-context transformer's token-level layers first so tokens attend to surrounding pronouns/headings; pool token embeddings by chunk boundaries afterward. Caveat: never let late-chunking windows cross permission/ACL boundaries.

9.5 Gap 5: Zero-Downtime Index Migration Playbook

  • Never mix chunking configurations in active serving: Mixing v1 and v2 chunks in the same unfiltered query inflates duplicate evidence and corrupts citations.
  • Shadow build: Ingest and chunk into a new index namespace (or stamp chunking_config on all new records while keeping them dark).
  • Parity & regression gate: Run automated boundary, source-span coverage, ACL-leak, and deletion tests against the shadow index.
  • Atomic pointer flip: Switch the serving router atomically in a single transaction.
  • Garbage collection & cache purge: Purge all old v1 child chunks, parent nodes, vectors, and query caches once verified.

10.1 Official Syllabus Glossary (14 Core Terms)

  • Chunk: A retrievable unit derived from source content.
  • Fixed-size: Splitting by a chosen character, word, or token count.
  • Recursive: Falling back from larger natural boundaries to smaller ones when a unit exceeds the limit.
  • Sentence-based: Using grammatical sentence boundaries to form units.
  • Semantic chunking: Estimating boundaries from changes in topic or meaning.
  • Token-aware: Measuring length with the relevant model's tokenizer and enforcing a token budget.
  • Structure-aware: Respecting headings, records, tables, code blocks, or other explicit structure.
  • Parent-child: Searching a small child unit and resolving its larger parent for context.
  • Hierarchical: Representing content at several related levels of granularity.
  • Sentence window: Indexing a central focus sentence plus a symmetric window of nearby sentence context.
  • Small-to-big: Expanding deliberately from a precise retrieval unit to broader evidence.
  • Overlap: Repeated content across neighboring chunks to reduce boundary misses (S = C − O).
  • Boundary quality: How well chunk splits preserve self-contained, interpretable evidence without severing conditions.
  • Source span: A stable, locatable region in the original source representation (survives re-chunking).

10.2 The 8 High-Value Revision Rules

  • 1. Specify the chunk-size unit explicitly (characters, words, or model-specific tokens).
  • 2. Measure the final representation, including headings and prefixes, against the consuming model's limit to prevent silent truncation.
  • 3. Preserve conditions, units, identifiers, and source locations — never isolate a number or interval from its equipment name, table header, or safety exception.
  • 4. Keep retrieval units and answer-context units conceptually separate.
  • 5. Expand only within authorized, version-consistent boundaries (enforce ACLs and verify parent.version_id == child.version_id).
  • 6. Count repeated source text as repeated text, not independent evidence.
  • 7. Use stable source facts/spans to compare different chunking schemes.
  • 8. Treat chunking changes as index migrations with deletion consequences — never serve mixed revisions.

11.2 Rapid-Fire Interview Challenge (15 Questions)

#Question30-Second Crisp Answer
1Is smaller chunk size always better?No. Smaller chunks improve vector match specificity, but isolating a fragment like "Inspect every 30 days" strips equipment name, scope, exceptions. Decouple retrieval size from context size using Small-to-Big expansion.
2Why can overlap hurt retrieval?Excessive overlap bloats the index, wastes LLM tokens, makes 1 repeated sentence look like 3 independent proofs, inflates chunk-level Recall@K.
3Why is a heading important in a chunk?Headings often hold the only mention of the subject, equipment variant, or operating scope governing all paragraphs beneath them.
4When would you prefer recursive chunking?As the default general-text baseline when documents have natural paragraph/sentence structure and must obey a strict token cap via top-down fallback.
5When would you prefer semantic chunking?Only on unstructured prose lacking explicit headings where topic shifts are subtle — and only after benchmarking proves its accuracy gain justifies the extra complexity.
6Why should table headers be repeated?A raw table row like "Generator B | 15 days" loses column meaning and units once split. Repeat table title, headers, units on every row chunk.
7How do you handle a long paragraph?Split recursively at sentence boundaries (and clause/word fallback with logged hard-split flag) while prepending inherited section heading and metadata to every piece.
8What does parent-child retrieval solve?The specificity-vs-completeness trade-off: small child chunks provide razor-sharp search matching, expanding to parent section recovers heading, scope, exceptions.
9Why should chunk metadata include a version?To filter out obsolete policies, prevent a v4 child from expanding to a stale v3 parent, reproduce exact citations, cleanly purge outdated derivatives.
10Why is source traceability necessary?Recording document_id + version_id + source_span allows verifiable citations, accurate deduplication, fair cross-strategy evaluation, targeted deletion.
11Why are token limits different across models?Embedders (Chunk + Prefix), Rerankers (Query + Passage), Answering LLMs (System + History + Query + All Chunks + Output) use different models and process different inputs.
12What if relevant information is in another section?Parent-child expansion only zooms out within the current section hierarchy. If Section 2 says "See Section 8", trigger a Secondary Authorized Search for that target.
13How do you prevent duplicate evidence?Deduplicate retrieved and expanded passages by canonical source_span, not chunk_id, and insert shared parent sections at most once.
14How do you investigate incorrect RAG answers?Check stage by stage: Does the chunk preserve context without silent truncation? Did retrieval surface it? Did expansion introduce conflicts or blow the budget?
15How do you know a chunking strategy is better?Hold queries, corpus, embeddings, retrieval constant; change one variable at a time; evaluate on stable source spans/facts; inspect failure traces manually.

Appendix B · alphabetical glossary

Alphabetical glossary of all terms and acronyms

  • ACL (Access Control List): Permission information deciding who may read a document or chunk; stored as control metadata and enforced by the hard pre-filter, never by embeddings.
  • Answer-context unit: What the answering LLM reads: the retrieval unit deliberately expanded with heading, scope or exceptions.
  • AST (Abstract Syntax Tree): Parsed structure of source code, used to split code so signatures, docstrings and class context stay with function bodies.
  • BM25: Lexical ranking used alongside vectors; strong on exact identifiers.
  • Boundary quality: How well chunk splits preserve self-contained, interpretable evidence.
  • Child chunk: A small, indexed retrieval unit (e.g., C32) that stores a parent_id for expansion.
  • Chunk: A retrievable unit derived from source content.
  • chunk_id: Identifier under one specific chunking configuration; ephemeral.
  • Chunking configuration: Reproducible settings that produced the chunks; stamped on every chunk.
  • Context loss: A valid current fact separated from heading, scope, unit or exception needed to interpret it.
  • Contextual retrieval: Prepending a short situational prefix to each chunk before embedding and BM25 indexing.
  • Control metadata: Fields such as tenant, ACL, version and lifecycle flags kept outside the embedded text.
  • Cross-encoder / reranker: A model that scores query and candidate passage jointly.
  • Deduplication: Removing repeated evidence by comparing source_span, not chunk_id.
  • Duplicate evidence: The same source statement appearing several times, making one fact look like several proofs.
  • Embedder / embedding model: Model that converts a chunk into a vector; has a hard input ceiling.
  • Fixed-size chunking: Splitting by a stated count of characters, words or tokens using half-open intervals.
  • Half-open interval: Range [start, end) that includes start and excludes end.
  • Hierarchical chunking: Representing content at several linked granularities.
  • Hybrid search: Combining lexical (BM25) and vector retrieval, then fusing or reranking results.
  • Late chunking: Embedding a long window first so tokens see surrounding context, then pooling by chunk boundaries.
  • Lost in the Middle: LLMs use information at start/end of long prompt better than middle.
  • OCR: Optical Character Recognition; extracts text from images/scans.
  • Overlap (O): Content repeated across neighbouring chunks to reduce boundary misses.
  • Parent node: Larger enclosing section stored for expansion; inserted once even if several children match.
  • Parent-child retrieval: Search a small child for precision, resolve its parent for interpretation context.
  • RAG (Retrieval-Augmented Generation): Pipeline in which retrieved evidence is supplied to an LLM.
  • Recall@K: Whether required evidence appears in the top K retrieved results.
  • Recursive chunking: Trying larger natural separators first and falling back to smaller ones when a unit exceeds the cap.
  • Retrieval unit: The small, focused unit the search engine scores.
  • RRF (Reciprocal Rank Fusion): Rank-based method for merging result lists.
  • Semantic chunking: Cutting where embedding similarity between adjacent units drops.
  • Sentence window: A focus sentence plus a symmetric window of radius w (at most 2w + 1 sentences).
  • Sentence-based chunking: Grouping grammatical sentences under a token budget.
  • Silent truncation: A provider cutting off input beyond its limit without error.
  • Small-to-big: Locate evidence with a small unit, deliberately supply a larger unit for interpretation.
  • Source span: A stable, locatable region of the original source that survives re-chunking.
  • Source unit: The original structural unit (section, table, function) preserving authoritative lineage.
  • Stale data: Indexed content no longer matching the current source due to unpropagated updates.
  • Stride (S): Distance between window starts: S = C − O.
  • Structure-aware chunking: Aligning boundaries with headings, records, tables, code blocks and FAQ pairs.
  • Subword tokenization (BPE, WordPiece, Unigram): Splitting text into variable-length pieces.
  • Token-aware chunking: Measuring length with the consuming model's tokenizer and enforcing a token budget.
  • Unlearning: Purging every derived chunk, parent, window, summary, vector and cache when a source changes.
  • Version ID / current flag: Revision stamp and lifecycle flag used to exclude obsolete content.
