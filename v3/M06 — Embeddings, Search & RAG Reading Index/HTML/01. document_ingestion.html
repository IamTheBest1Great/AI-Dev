01Acquisition & Layered Validation (`State: RECEIVED`)Receive and validate⌄

How it connects: Uploading a file only transfers bytes. Before any parser touches those bytes, the system must lock down who owns the file, protect server resources, and verify what the file actually is.

  1. Authenticated Upload Record & OWASP Controls

  • An upload creates an asynchronous ingestion job (state: "RECEIVED") rather than making the file immediately searchable.

  • Server-Derived Context: The backend must derive tenant_id and submitted_by from the authenticated session—never from an editable client request field.

  • Path Sanitization: Store original_filename for display only; generate safe internal storage names and controlled locations so malicious filenames cannot overwrite server filesystem paths (OWASP File Upload guidelines).

  1. Resource Quotas & Archive Unpacking
  • Enforce strict bounds on uploaded bytes, decompressed bytes (preventing zip bombs), page counts, image dimensions, parser runtime, and output size.
  • If an archive (.zip) is uploaded, track every extracted child document individually with its own source relationship and access policy—never let unpacked children become public by default.
  1. Multi-Signal MIME Detection (Detection $\neq$ Parsing)
  • Detection estimates the media format (application/pdf, text/html); Parsing interprets that format to extract content.
  • Because extensions and client-declared types can be spoofed, combine five signals (e.g., via Apache Tika):

  1. Filename extension (quick hint).

  2. Declared content type (untrusted sender hint).

  3. Byte signature / Magic numbers (characteristic leading bytes).

  4. Container inspection (vital because .docx, .xlsx, and .jar all use ZIP containers).

  5. Parser validation (confirming the format is readable and supported).

  • If a format isn't supported, halt with an explicit status (UNSUPPORTED_FORMAT) rather than returning an empty string and logging "Success."
02Format-Aware Routing & Faithful Extraction (`State: PROCESSING`)Route and extract⌄

How it connects: Once the format is verified, the job moves to PROCESSING. Instead of flattening everything into plain text—which destroys conditions and relationships—the router sends the file to specialized extractors that preserve structure and coordinates.

1. PDF Processing (Appearance vs. Reading Order)

  • Page-by-Page Classification: A 100-page PDF might have 90 native text pages and 10 scanned appendices. Evaluate every page/region individually: use native extraction where embedded text is complete, and trigger OCR only on image regions or unusable text layers.

  • Preserving Location Metadata: Extract into structured blocks (e.g., using PyMuPDF) that record:

  • page_index (0-based physical position, e.g., 11) AND page_label (printed page number, e.g., "8", accounting for Roman numeral covers).

  • section_path (e.g., ["Maintenance", "Inspection"]), block_id, and bbox (bounding-box coordinates with a documented coordinate origin).

  • Resolving PDF Hazards:

  • Columns: Use layout-aware sorting so left and right columns don't interleave into false sentences.

  • Headers/Footers: Strip verified repeating boilerplate from searchable text while keeping the source intact.

  • Hyphenation: Rejoin line-wrapped words ("main-tenance") only when verified; never destroy hyphens in equipment codes (M-104).

  • Footnotes & Annotations: Keep qualifying footnotes ("except during testing") attached to their statements, and decide via policy whether reviewer comments/annotations count as official instructions.

2. HTML, Markdown, and Office Documents

  • HTML: Extract the main content landmark while stripping navigation menus, cookie banners, and sidebars (otherwise, a nav bar with "Installation | Maintenance | Troubleshooting" makes every webpage match all three topics). Capture dynamic content safely without executing arbitrary scripts, and log retrieval time alongside the URL since web pages change.

  • Markdown: Keep heading hierarchies (# Deprecated behavior) linked to the paragraphs beneath them so obsolete rules aren't mistaken for current ones. Keep code fences (delete_all()), ordered lists, blockquotes, and links intact so code examples are treated as text to describe, not commands to execute.

  • Office Documents:

  • Word: Explicitly define whether accepted changes, rejected changes, or all tracked changes are authoritative.

  • Presentations: Avoid arbitrary text-box reading order; define whether speaker notes are authoritative and share slide permissions.

  • Spreadsheets: Retain sheet names, cell ranges, headers, and units. Separate formulas (=B2*C2) from cached displayed values (which may be stale if the workbook wasn't recalculated).

3. Tables, Images, Scans, and OCR

  • Table Serialization: Flattening a table into "Unit A 30 days Unit B 14 days" breaks cell associations. Serialize each row with its full context (Table title, section, column headers, row headers, units, and qualifying notes) AND keep structured table data alongside search text for exact SQL/arithmetic queries.

  • Images & Vision Models: Distinguish decorative images from technical diagrams. If a vision model generates a caption ("damaged valve"), store it strictly as a derived artifact tagged with the model version and uncertainty markers—never as an unquestioned source fact.

  • Scans & OCR Workflow (Tesseract):

  1. Detect regions needing OCR $\rightarrow$ 2. Preprocess image (deskew, binarize, scale, denoise while keeping original) $\rightarrow$ 3. Set language/segmentation $\rightarrow$ 4. Extract text + coordinates + confidence $\rightarrow$ 5. Validate critical fields (M-104 vs M-1O4, 14 vs 74) $\rightarrow$ 6. Store with OCR config version.
  • Crucial Rule: OCR confidence $\neq$ Factual correctness. Never silently auto-correct unfamiliar equipment codes into common dictionary words.
03Normalization & Quality Gates (`State: VALIDATING`)Normalize and quality-check⌄

How it connects: Raw extracted blocks contain formatting artifacts. Stage 3 standardizes the text without altering its meaning (Normalization) and runs diagnostic checks (Quality Gates) before enrichment.

  1. Normalization (Cleaning Without Changing Meaning)

  • Safe Transformations: Unicode normalization (straight vs. curly quotes), line-ending standardization, collapsing prose whitespace, and removing verified page footers.

  • Unsafe Transformations: Expanding abbreviations without domain verification, collapsing spaces inside code/aligned tables, or using an LLM to rewrite/simplify instructions (which risks dropping negations like "not" or altering conditions).

  • Span Mapping: Retain raw extracted text alongside cleaned text, maintaining a map from cleaned spans back to original blocks for debugging and citations.

  1. Quality Gates (Diagnostic Signals)

  • A parser returning 200 OK does not mean extraction succeeded. Quality gates check for: missing pages, implausibly short text (e.g., 1 MB file yielding 10 KB text), repeated garbage characters, mismatched table row counts, broken section trees, and lost identifiers.

  • Failed checks route the job to EXTRACTION_REVIEW_REQUIRED or QUARANTINED (or trigger alternative processing, such as visual extraction for diagram-heavy pages).

04Enrichment, Provenance, Deduplication & VersioningEnrich identity and governance⌄

How it connects: While Normalization cleans the content inside the document, Enrichment attaches the external governance context—identity, lineage, version authority, and access control—that makes the content safe for enterprise use.

  1. The Three Metadata Categories

  • Source Metadata: Title, author, approved revision (v4), effective date, source URI.

  • Processing Metadata: Parser version (parser-config-7), extraction timestamp, OCR config, cleaning-rule version (cleaning-rules-3).

  • Control Metadata: tenant_id, optional ship_id, acl_ref + acl_version, publication_state, and deleted flag. (Note: Always pull control metadata from trusted repositories; ignore a PDF internal property claiming classification=public).

  1. Provenance (W3C PROV) & The Three Identifiers
  • Provenance records origin, transformation activities, and dependencies so any retrieved passage can answer: Which source/revision supplied this? What page/bbox? Which parser/chunker config created it? What downstream artifacts depend on it?

  1. Deduplication & Permission Isolation (The Multi-Tenant / Ship Rule)

  • Exact vs. Near-Duplicate: Exact byte/normalized hashes avoid redundant extraction; near-duplicate detection (e.g., same manual with a new cover page) helps group results but must never auto-delete a separate revision or governed source.

  • Never Merge Permissions: If Tenant A and Tenant B (or Ship A and Ship B) upload byte-identical manuals (same Content Hash), you may reuse compute/storage, but you must preserve separate Logical Document IDs and ACLs.

  • Granular Propagation: ACLs must propagate to every derivative (chunks, tables, vector embeddings, summaries, captions, facets, snippets, and caches). If a document has section-level restrictions, enforce chunk-level ACLs so parent-chunk expansion never leaks unauthorized sibling sections.

  1. Versioning: Source Revisions vs. Processing Changes
  • Distinguish when the source revision changes (v3 $\rightarrow$ v4) versus when processing changes (re-running OCR, updating cleaning rules, or changing chunk sizes/embedding models on v4).
  • Authority Policy: "Newest upload timestamp" $\neq$ "Current approved manual". If an old v3 file is uploaded today after v4 was approved yesterday, the authority policy must keep v4 active for current-procedure queries and relegate v3 to historical status.
05Deliberate Publication, Operations & Reverse-Lineage Deletion (`State: READY`)Publish, operate and delete⌄

How it connects: A validated, enriched document is still staged until all downstream indexes are synchronized. This final stage governs production rollout, safe retries, failure diagnosis, and complete data eradication upon deletion.

  1. Deliberate Publication & Idempotent Retries

  • Staging before Publication: v4 stays in APPROVED_STAGED until all downstream lexical indexes, vector databases, and permissions are ready. Only then is it flipped to PUBLISHED/READY while retiring v3 from current-manual retrieval.

  • Idempotency & Job States: Track jobs through RECEIVED → PROCESSING → VALIDATING → READY. Use deterministic IDs, uniqueness constraints, and controlled upsert operations so retrying a failed job halfway through never creates duplicate active documents, chunks, or index entries.

  1. Reverse-Lineage Deletion (Eradicating Derivatives)
  • Deleting the original PDF is never enough. When a source is deleted:

  1. The serving layer immediately marks the document_id unavailable.

  2. A deletion worker traverses the Reverse Lineage Map (tracked via provenance) to purge or invalidate every dependent chunk, lexical posting, vector embedding, vision caption, summary, and answer/snippet cache.

  3. Audit logs/backups remain locked outside ordinary search paths. Deletion is only complete when cached phrasings and direct citation lookups can no longer surface the deleted evidence.

1. Document Ingestion Fundamentals

Definition

Document ingestion is the controlled process of accepting a source, extracting its useful content and structure, attaching trustworthy metadata, and making an approved representation available to later processing stages.

Uploading a PDF is only the beginning. A retrieval system cannot use the visual appearance of the PDF as reliable text without a suitable extraction method. It also needs to know which document the text came from, which revision it represents, who may access it, and whether it has since been replaced or deleted.

A useful distinction is:

Stage Main question Typical result
Acquisition What source did we receive? Original bytes and source identifier
Validation Are we allowed and able to process it? Accepted, rejected or quarantined state
Extraction What content and structure exist? Text, blocks, tables, images and locations
Normalization How can we represent these consistently? Canonical document representation
Enrichment What context must travel with the content? Version, provenance, permissions and quality flags
Publication Is this representation ready for downstream use? Approved ingestion record

Chunking, embedding and indexing follow ingestion. Some implementations place all these jobs inside one service; the conceptual boundaries still matter because they let you diagnose failures.

Extraction quality is an upper limit on later usefulness

Suppose a manual says, “Do not operate the unit when indicator X is red.” If extraction drops the word “not,” a perfect retriever may return incorrect instructions with a valid-looking citation. The generator did not invent the error; the evidence was corrupted before retrieval.

Similarly, extracting a table as “A B 5 9” loses the relationship between each item and its value. Increasing the number of retrieved chunks cannot reconstruct the missing relationship reliably.

Source content and derived content

Keep the original source separate from its derivatives:

  • Original: the uploaded PDF, HTML snapshot or Office document.
  • Extracted: machine-readable blocks and their locations.
  • Normalized: cleaned text with a stable internal structure.
  • Derived: chunks, embeddings, summaries, captions and search records.

A derived summary is not the original source. It should carry a link to the source and a record of the transformation that produced it. This distinction becomes essential when investigating an incorrect answer or deleting a source.

Key takeaway

Ingestion should preserve meaning, identity, authority and access conditions together. A pipeline that extracts readable text but loses these properties is incomplete.

A typical ingestion process includes six conceptual stages:

Stage Purpose
Acquisition Receive and identify the source.
Validation Check whether the file is acceptable and processable.
Extraction Retrieve text, tables, images, and structure.
Normalization Standardize extracted content without changing its meaning.
Enrichment Attach metadata, provenance, version, and permissions.

04Why should the original document be stored separately from extracted text?Show answer

Answer:

The original document provides the reference against which extracted and processed content can be checked.

Keeping it separate allows the system to:

  • Verify whether extraction preserved the source meaning.
  • Investigate incorrect answers and citations.
  • Reprocess documents when the parser or extraction configuration changes.
  • Preserve the original evidence when cleaning rules change.
  • Maintain traceability between the source and its derived content.

For example, if a maintenance interval is extracted incorrectly, the original PDF helps establish whether the error originated in the source or during extraction.

Key takeaway: Never treat extracted or cleaned text as a perfect replacement for the original source.

2. File Uploads and MIME Detection

Syllabus coverage: M06.1.1.1 — File and content handling.

File uploads

An upload interface should create an ingestion job, not immediately mark a document as searchable. The application needs enough information to associate the file with the correct owner and source collection.

A conceptual upload record might contain:

{
  "upload_id": "upload-42",
  "tenant_id": "tenant-A",
  "source_system": "manuals-portal",
  "source_document_id": "M-104",
  "original_filename": "Maintenance_Manual_Rev4.pdf",
  "submitted_by": "user-17",
  "state": "RECEIVED"
}

The server derives the tenant and actor from authenticated context. It should not trust a freely editable request field that says the uploader belongs to another tenant. The original filename is useful display metadata, but it should not become an unrestricted filesystem path.

OWASP recommends layered upload validation, authorization, size limits, generated storage names, controlled storage locations and appropriate file-content checks. It specifically warns that a client-supplied content type is not a trustworthy security decision. These are upload controls; they do not themselves establish that extracted text is factually correct. Source: OWASP File Upload Cheat Sheet

MIME/type detection

A MIME type describes a media format, such as application/pdf or text/html. The filename extension is a hint, not proof. A file named manual.pdf can contain different bytes, and several document formats use common archive containers.

Detection can combine:

Signal What it contributes Why it is insufficient alone
Filename extension A quick format hint Files can be renamed
Declared content type Information from the sender The sender can be wrong or malicious
Byte signature Recognition of characteristic bytes A container signature may be ambiguous
Container inspection Identification of internal structure Requires more processing and limits
Parser validation Evidence that the expected format can be read Successful parsing does not imply safe content

Apache Tika documents detection based on byte patterns, resource names, supplied metadata and container-aware inspection. Its detector returns a best estimate of media type; identifying a ZIP-like container does not necessarily identify the document stored inside it. Source: Apache Tika content detection

Routing based on content

Once detection and validation succeed, route to an appropriate extractor. Text-based PDFs, scanned PDFs, spreadsheets and web pages require different handling. A single “convert everything to plain text” function can be a prototype, but it should not hide lost tables, unsupported embedded objects or empty pages.

Use an explicit outcome such as UNSUPPORTED_FORMAT or EXTRACTION_REVIEW_REQUIRED. Returning an empty string and recording success makes later retrieval failures look like model failures.

Resource limits

An ingestion service should define limits on uploaded bytes, decompressed bytes, page count, image dimensions, parser runtime and extracted output size. These limits protect availability and make operational behavior predictable.

If an archive contains documents, track its children individually. Each child needs a source relationship and access policy; it must not silently become a new public document merely because it was extracted from an accepted archive.

Key takeaway

Detect, validate and route before extraction. A MIME label selects processing behavior; it is not a certificate of safety, quality or authorization.

05What is the difference between MIME detection and parsing?Show answer

Answer:

MIME detection estimates the file's format, while parsing interprets that format to extract its content.

For example, detection may identify a file as a PDF. A PDF parser then attempts to extract its text and other supported content.

The file extension and client-declared content type are not sufficient proof of the actual format. Detection may use file signatures, metadata, and container inspection.

Even a successfully parsed file may contain missing text, incorrect reading order, or unsupported structures.

Key takeaway: Detection identifies the likely format; parsing extracts its content.

06How would you validate and process an uploaded document safely?Show answer

Answer:

I would validate the upload before processing it by checking:

  • File size and applicable processing limits.
  • The relationship between the declared format and actual file content.
  • Whether an appropriate parser supports the format.
  • Whether the uploader and source collection are authorized.
  • Resource limits such as page count, decompressed size, image dimensions, and processing time.

I would use controlled storage locations and avoid treating the supplied filename as a filesystem path.

Unsupported or questionable files should receive an explicit status, such as UNSUPPORTED_FORMAT or EXTRACTION_REVIEW_REQUIRED, rather than being marked successfully processed with empty content.

Key takeaway: Validate, detect, and route before extraction.

07A PDF contains both native-text pages and scanned pages. How would you process it?Show answer

Answer:

I would evaluate the document at the page or region level.

For pages with meaningful, correctly extracted embedded text, I would use native text extraction. For scanned pages or regions where the text layer is missing or unusable, I would use Optical Character Recognition (OCR).

I would also check whether important tables, diagrams, annotations, or text regions were missed.

For example, a 100-page manual may contain 90 text-based pages and 10 scanned appendix pages. OCR can be applied to the scanned pages instead of unnecessarily processing every page with OCR.

Key takeaway: Choose the extraction method according to the actual content and quality of each page or region.

3. PDF Processing

PDF extraction is a page- and region-level decision

The source notes' example uses 90 native-text pages and 10 scanned appendix pages. OCR confidence is not proof of factual correctness.

Why PDFs require special handling

A PDF describes how a page should appear. Its internal text order may differ from the order a person reads. A page may contain several columns, positioned text fragments, scanned images, invisible OCR text, vector diagrams and footnotes.

PyMuPDF’s extraction documentation explains that plain text may follow the order established by the document creator and provides block, word and layout-related extraction options. Sorting can help some layouts, but reading order is still something to inspect, especially in complex pages. Source: PyMuPDF text extraction

A page-level decision

Classify each page rather than assuming the whole file has one extraction mode:

  1. Does the page have meaningful embedded text?
  2. Is the embedded text plausibly complete and in the correct language?
  3. Are some regions images that contain additional text?
  4. Are important tables, diagrams or annotations missing from text extraction?
  5. Does extraction preserve the intended reading order?

A 100-page manual may contain 90 native-text pages and 10 scanned appendices. OCR for every page wastes effort and can introduce duplicate text. Never doing OCR misses the appendices.

Preserve location information

Useful source locations include page number, section heading, block identifier and bounding box. Store both the PDF page index and, if available, the printed page label. A PDF’s twelfth physical page may be labeled “8” because the cover and contents use different numbering.

A normalized block can be represented as:

{
  "document_id": "tenant-A:M-104",
  "version_id": "v4",
  "block_id": "p12-b6",
  "kind": "paragraph",
  "page_index": 11,
  "page_label": "8",
  "section_path": ["Maintenance", "Inspection"],
  "text": "Inspect indicator X before starting the unit.",
  "bbox": [72, 180, 510, 225],
  "extraction_method": "native_text"
}

The values are fictional. The bounding-box coordinate system must be documented by the implementation; do not assume different parsers use identical units or origins.

Common PDF problems

Headers and footers: A repeated title can dominate small chunks. Remove verified boilerplate from the searchable representation while retaining the source.

Columns: Interleaving left-column and right-column text can create false sentences. Use layout-aware extraction and inspect representative pages.

Hyphenation: A line break may split “maintenance” into two fragments. Join only when the evidence supports that transformation; product identifiers with hyphens must survive.

Ligatures and unusual encodings: Text that looks normal on the page may extract incorrectly. Compare source renderings with output when quality flags indicate trouble.

Footnotes: Keep the relationship between a statement and its qualifying footnote. A condition such as “except during testing” can change the meaning of a procedure.

Annotations: Decide whether comments and markup are official content. A reviewer’s suggestion should not automatically outrank approved instructions.

Key takeaway

The page image is evidence of appearance; the extracted representation is evidence for search. Validate the relationship between them.

5. Images, Tables, Scans and OCR

Preserve table relationships instead of flattening cells

The values are fictional training examples from the supplied notes. Structured table data supports exact filtering and arithmetic; serialized rows provide searchable context.

Images

An image may be decorative, a photograph, a screenshot, a technical diagram or a page scan. These roles need different representations.

OCR extracts visible text. A vision model can produce descriptions or identify relationships, but those descriptions are generated interpretations. Store them as derived content with the model/configuration version and original image reference.

A caption saying “damaged valve” should not become an unquestioned source fact if the source image is ambiguous. For high-consequence details, preserve the image for direct review and mark uncertainty in generated descriptions.

Tables

A table’s meaning is distributed across cells, headers, units, notes and sometimes previous pages. Converting each cell into a disconnected string loses the relationships that a reader relies on.

Fictional source table:

Equipment variant Inspection interval Condition
Unit A 30 days Normal service
Unit B 14 days Normal service

A useful searchable serialization is:

Table: Inspection intervals, manual M-104 v4, section 3.2.
Equipment variant: Unit A.
Inspection interval: 30 days.
Condition: Normal service.

This is a representation of one row, not an independently authored instruction. Its metadata should point to the original table and row. Include the table title and relevant notes when they qualify the values.

Keep structured table data alongside search text when exact filtering, arithmetic or comparison is needed. A vector search result can identify a relevant table; SQL or structured computation can answer an exact aggregation more reliably than asking a model to reconstruct many cells.

Scanned documents

A scan stores an image of text. There may be no usable text layer. Some files contain poor OCR left by an earlier system, so the presence of text does not prove its quality.

Important scan problems include rotation, skew, blur, uneven lighting, low contrast, handwriting and mixed languages. Store page-level quality flags instead of one blanket “OCR succeeded” indicator.

OCR

Optical character recognition converts visible text in an image into machine-readable characters. Recognition can be wrong even when the output looks plausible.

Tesseract’s guidance discusses image scaling, binarization, noise, skew, borders, page segmentation and language-related configuration. These settings influence recognition quality; tuning should be evaluated on representative source images rather than assumed to help every document. Source: Tesseract improving output quality

A practical OCR workflow is:

  1. Detect pages or regions that need OCR.
  2. Prepare images while preserving the originals.
  3. Choose the appropriate language and layout configuration.
  4. Extract text and available location/confidence information.
  5. Check critical fields and suspicious output.
  6. Store the OCR result with its configuration and source coordinates.

An OCR confidence value is not a calibrated probability that a business statement is correct. High confidence in the characters still does not establish that the correct row, unit or revision was selected.

Critical-character errors

For retrieval, errors in names and identifiers are especially damaging. M-104 misread as M-1O4 may break exact lookup. An interval of 14 misread as 74 may create a dangerous factual error. Use domain-specific validation where justified, while preserving the original recognized value and the correction history.

Do not silently “correct” all unfamiliar words to common words. An uncommon equipment code may be valid. Uncertainty should lead to a review state or qualified answer, not confident invention.

6. Cleaning Without Changing Meaning

Normalization: safe cleaning, strict boundaries, quality gates

The source's strict boundary: retain raw and cleaned spans with mappings; do not use an LLM to rewrite instructions.

Syllabus coverage: M06.1.1.2 — Data quality and traceability.

Definition

Cleaning removes processing noise while preserving source meaning. It is different from summarizing, rewriting or “improving” the author’s instructions.

Typical operations include Unicode normalization, line-ending normalization, removal of verified boilerplate, whitespace repair and deduplication of repeated extracted blocks. Each rule should be explicit and versioned.

Safe and unsafe transformations

Transformation Usually useful when verified Main risk
Normalize line endings Consistent storage and comparison Very low for ordinary prose
Collapse repeated spaces Repair extraction artifacts Can damage code or aligned tables
Remove repeated page footer Reduce irrelevant retrieval matches Could remove meaningful revision text
Repair line-wrap hyphenation Reconstruct split words Could corrupt identifiers
Expand abbreviations Improve interpretability Could select the wrong meaning
Rewrite instructions with a model Produce readable derivatives Can alter conditions, negation or facts

Keep raw extraction and cleaned text separately when feasible. A mapping from cleaned spans to original blocks makes citations and debugging stronger.

Quality gates

A useful ingestion gate checks content completeness, not just “the parser returned successfully.” Possible checks include missing pages, implausibly short text, repeated character sequences, table row-count changes, broken section hierarchy and lost required identifiers.

These checks are diagnostic signals. A document with very little text may legitimately contain diagrams, so a low character count should trigger inspection or alternative processing rather than automatic rejection in every case.

Key takeaway

Cleaning should reduce noise without manufacturing facts. Preserve enough evidence to explain every consequential transformation.

Metadata layers

Visual summary based on the supplied study notes.

Metadata extraction

Metadata describes content and its handling. Separate three categories:

  1. Source metadata: title, source author, approved revision, effective date and source location.
  2. Processing metadata: parser version, extraction time, OCR configuration and quality status.
  3. Control metadata: tenant, ACL reference, deletion state and publication status.

Some metadata is extracted from the document itself; other metadata comes from trusted application systems. A PDF field claiming classification=public should not override a restricted access policy from the source repository.

Provenance

Provenance explains where an item came from and how it was produced. The W3C PROV family models provenance using entities, activities and agents, giving a useful conceptual vocabulary for recording derivations and responsibility. A RAG implementation can adopt these ideas without requiring a full semantic-web stack. Source: W3C PROV overview

For a retrieved passage, provenance should answer:

  • Which original source and revision supplied this text?
  • Which extraction and cleaning operations produced it?
  • Which chunking and embedding configurations were used?
  • Which source location can a reviewer inspect?
  • Which later artifacts depend on it?

The last question is what makes source deletion operationally possible.

Document IDs

Use a stable logical document ID for the continuing source, and a separate version ID for an immutable revision.

Logical document: tenant-A:M-104
Source revision: v4
Extraction run: extract-2026-10-20-03
Chunk identity: tenant-A:M-104:v4:section-3.2:chunk-02

The exact scheme is a design choice. It should prevent collisions and make lineage resolvable. Do not rely on filename alone: users rename files and upload identical filenames to different tenants.

A content hash answers “Are these bytes equal?” It does not answer “Are these the same business document?” Two separate departments can own byte-identical documents with different permissions.

Minimal lineage record

{
  "document_id": "tenant-A:M-104",
  "version_id": "v4",
  "source_hash": "sha256-of-original-bytes",
  "source_uri": "manuals-portal/M-104",
  "parser_version": "parser-config-7",
  "normalization_version": "cleaning-rules-3",
  "acl_ref": "acl-M-104",
  "acl_version": 12,

}

This is a conceptual schema. The hash string illustrates the field’s purpose; a real record stores the computed digest.

8. Deduplication, Versioning and Permissions

Permission isolation across tenants and ships

Identical bytes do not prove shared ownership or permission. Every derivative must inherit the correct policy scope.

Reverse-lineage deletion

Visual summary based on the supplied study notes.

Deduplication

Exact deduplication identifies identical bytes or identical normalized text. Near-duplicate detection identifies substantially similar content, such as the same manual with an added cover page.

These decisions have different consequences. Exact byte equality can avoid repeating extraction. Near duplication may justify review, grouping or ranking diversity, but it should not automatically erase a newer revision or a separately governed source.

Use two hashes when useful: one for raw bytes and one for a clearly defined normalized representation. The normalization algorithm must be versioned; changing it changes what “same content” means.

A safe principle is to deduplicate processing without merging access rights. Shared physical storage may be possible, but each logical source still retains its own ownership, revision, retention and permission relationships.

Versioning

Versioning should distinguish source changes from processing changes:

Change Source revision changes? Derived artifacts may change?
Manual v3 replaced by v4 Yes Yes
OCR engine corrected the same scan No Yes
Chunk size changed No Yes
Embedding model changed No Yes
Permission membership changed No Authorization state changes

A current-source policy needs an explicit authority rule. “Newest upload timestamp” may not equal “latest approved manual.” An old revision uploaded today must not automatically replace an approved revision uploaded yesterday.

Permission metadata

Permissions must follow the content into every representation that can expose information: paragraphs, chunks, tables, captions, summaries, vectors, keyword records and caches.

For a source restricted to ship A, a ship B user must not receive its text, title, existence-revealing metadata or source URL through search results. An instruction telling the model “only use ship A documents” does not enforce this boundary.

Attach a stable policy reference and enough filterable metadata to narrow retrieval safely. Resolve authorization in trusted server code, apply it before evidence reaches an external reranker or generator, and recheck access before emitting the final answer or citation. Policy changes can occur while a request is running.

If a document contains sections with different permissions, whole-document inheritance is insufficient. Either create separately controlled source units or represent chunk-level policies accurately. Parent expansion must not include unauthorized sibling sections.

Deletion dependency

Deleting the original upload is not enough. The system needs a reverse lineage map from the source to all derived records. A deletion should stop serving the source promptly, then remove or invalidate searchable and cached derivatives according to the declared lifecycle.

Retained audit records and backups need their own controlled policy; they must not remain searchable simply because they are retained. The observable test is whether deleted evidence can still reach an answer, citation, snippet, table or cache response.

The publication gate should verify each required index, source/version state and ACL readiness, then switch the active version in a controlled way. The previously approved version should remain available according to policy until the new version is safely published.

Likely interviewer follow-upWhat should current queries see while v5 is staged?
What a strong answer demonstratesThe last valid approved version, subject to its current status and policy; staged content should not leak into ordinary retrieval.
I48An ingestion worker crashes after creating half the chunks. A retry starts the same job and creates duplicate active chunks. How would you prevent this?SCENARIO · MODEL ANSWER

Model answer: Make each processing operation idempotent. Use stable job, source-version and derivative identifiers; enforce uniqueness constraints; record processing state; and use controlled upserts rather than creating fresh active artifacts on every retry. The retry should reconcile existing outputs, resume or replace incomplete work, and ensure that only one valid set is eligible for publication. Test failures at different points in the pipeline, not just a clean first run.

Likely interviewer follow-upWhat invariant should hold after running the same ingestion job twice?
What a strong answer demonstratesThere should be one logically active result for each intended source/version/derivative identity, with no duplicated published content or conflicting index entries.
I49A user deletes a manual while a delayed worker is still processing it. The worker later finishes and republishes its chunks. How would you prevent this race?SCENARIO · MODEL ANSWER

Model answer: Deletion should immediately mark the logical source unavailable to serving paths and record a deletion state or tombstone that workers must check before publication. A delayed job must not publish derivatives for a deleted source. The deletion worker should follow reverse lineage to invalidate existing derivatives, while job orchestration cancels or rejects stale work and reconciles any artifacts created during the race. Completion should be verified through search, snippets and citation access.

Likely interviewer follow-upWhat is the most important safety rule for a late-arriving worker result?
What a strong answer demonstratesA result from an obsolete or deleted source state must never reactivate or republish that source.
I50Describe a safe publication state machine for a document that must be searchable only after all checks pass.LIKELY INTERVIEW · MODEL ANSWER

Model answer: Use explicit states such as RECEIVED, PROCESSING, VALIDATING, APPROVED_STAGED and PUBLISHED/READY, plus failure or review states. Each transition should have a defined precondition. Validation checks content quality, metadata and permissions; the staged state waits for lexical/vector indexes and ACL propagation to be verified; publication occurs only after those dependencies are ready. State changes and retries should be idempotent, and a failed update must not leave partially published content.

Likely interviewer follow-upWhich state should represent a file whose extraction succeeded but whose ACL propagation has not completed?
What a strong answer demonstratesA staged or pending-publication state, not READY or PUBLISHED.
I51How would you design the deletion workflow so that derived content cannot continue to surface?LIKELY INTERVIEW · MODEL ANSWER

Model answer: Mark the source unavailable to serving immediately, then traverse reverse lineage to identify all dependent chunks, lexical postings, vector embeddings, captions, summaries, snippets and caches. Purge or invalidate each dependent artifact, while keeping required audit or backup records outside ordinary serving paths under their retention controls. Verify deletion by attempting retrieval, snippet access and direct citation lookup. The deletion job should be retryable and its completion state should reflect actual verification, not just successful removal of the original file.

Likely interviewer follow-upWhat observable test demonstrates that deletion is complete?
What a strong answer demonstratesThe deleted source and its derivatives no longer appear through ordinary retrieval, snippets, caches or direct citation access.

32What is the difference between ingestion and retrieval?Show answer

Answer:

Ingestion prepares source documents for downstream use. It validates, extracts, normalizes, enriches, and publishes approved content.

Retrieval finds relevant content when a user asks a question. It searches the available knowledge and applies authorization restrictions before returning evidence.

For example, extracting an approved maintenance procedure belongs to ingestion. Finding that procedure for a user's question belongs to retrieval.

Key takeaway: Ingestion prepares the knowledge; retrieval finds the relevant evidence.
