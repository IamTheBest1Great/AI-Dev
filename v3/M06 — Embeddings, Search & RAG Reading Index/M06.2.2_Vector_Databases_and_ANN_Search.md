# Branch 1 — Foundation & Mechanics

> *The base concepts of vector search: what a vector store actually is, what "correct" means, and the exact-vs-approximate tradeoff.*

## 1.1 Vector Storage Fundamentals

**Lifecycle connection:** The architectural foundation. Before inserting any data, decide whether you need a raw mathematical index or a secure, production-ready database.

### Definitions

- **Vector database:** stores vector representations plus associated records and supports similarity search. Depending on the system it may also offer filters, access control, durability, replication, text search, and operations tooling.
- **Vector index:** the data structure that accelerates vector lookup. It is *one component* of a retrieval system. A library containing an ANN index (e.g., FAISS) is **not** automatically a database with authentication, backups, transactional metadata, or a deletion policy.

> **Analogy:** The index is the card catalog. The database is the whole library, with a librarian checking permissions.

### What is actually stored?

```json
{
  "chunk_id": "tenant-A:M-104:v4:section-7:chunk-2",
  "document_id": "M-104",
  "document_version": "v4",
  "tenant_id": "tenant-A",
  "resource_id": "ship-A",
  "source_locator": "section 7, paragraph 2",
  "acl_version": 18,
  "content_hash": "example-hash",
  "embedding_model": "example-model-revision",
  "index_generation": "g12",
  "status": "active"
}
```

The embedding is an additional numeric field (or separate object). Original text may be co-stored or fetched by `chunk_id`.

- **Vector** answers: *"Which items are close in this representation?"*
- **Metadata** answers: *"Who owns this? Which version is valid? Where did it come from?"*
- Neither replaces the other.

### Three tiers of correctness

| Tier | Question | Example failure |
|---|---|---|
| 1. Numerical search correctness | Did search find the nearest **eligible** vectors? | ANN skipped a close vector |
| 2. Retrieval relevance | Do the passages actually answer the question? | Closest passage is about a different machine |
| 3. Application correctness | May this evidence be used **now**? | Passage is deleted, superseded, or unauthorized |

A perfect exact search can still fail tiers 2 and 3. **Similarity is not permission.**

### Why candidate generation matters

Vector search produces a **candidate pool**. A reranker refines it; evidence assembly picks what fits the context budget.

Example: dense retrieval returns 40, hybrid union has 70 unique, reranker keeps 8. These are three different counts. Name them explicitly:

- `dense_candidate_k` = 40
- `fused_candidate_count` = 70
- `final_context_k` = 8

Log the stage where a relevant passage disappeared; this makes debugging tractable.

**Key takeaway:** An index accelerates similarity lookup. The complete application remains responsible for relevance, provenance, permissions, and lifecycle.

## 1.2 Exact Search, ANN, and Candidate Generation

**Lifecycle connection:** Dictates the retrieval execution strategy: how candidates are gathered before they reach a reranker or LLM.

### Exact search

Evaluates similarity/distance against **every eligible vector**, returns the best under the metric (subject to numerical precision and a defined tie policy).

- Work ∝ **N × d** (N vectors, d dimensions). A conceptual model, not a wall-clock prediction; hardware, batching, memory layout, and filters matter.
- Use when: the corpus is small, **filters leave few rows**, or you need a **reference/gold baseline** to test an ANN index.

### ANN (Approximate Nearest Neighbor)

Reduces work by exploring only selected parts of the vector space or using compressed representations. **May miss true neighbors.** "Approximate" is not "arbitrary": a good index recovers most useful neighbors efficiently.

pgvector's default is exact search; approximate indexes can change returned results, and behaviour is product-specific.

### ANN recall ≠ relevance recall

Let E_K(q) = exact top-K IDs and A_K(q) = approximate top-K IDs.

```
ANN Recall@K(q) = |A_K(q) ∩ E_K(q)| / K
```

(Assumes ≥K eligible records; otherwise use exact result count as denominator and document the convention.)

**Example:** exact = {A,B,C,D,E}, approx = {A,B,D,F,G} → overlap {A,B,D} → recall@5 = 3/5 = **0.60**.

If a human says only B and H truly answer the question, ANN recall says nothing about whether H is represented well. **Relevance recall** requires human-labeled, authorized, current gold evidence.

### Recall vs. latency (illustrative, invented)

| Configuration | ANN recall@10 | Relevance recall@10 | p95 latency |
|---|---:|---:|---:|
| Small exploration | 0.83 | 0.66 | 19 ms |
| Medium exploration | 0.94 | 0.73 | 31 ms |
| Large exploration | 0.98 | 0.74 | 62 ms |
| Exact reference | 1.00 | 0.75 | 105 ms |

Medium looks attractive; doubling exploration again buys ~1 point of relevance for 2x latency. Better embeddings or lexical retrieval may help more. But a rare missed passage can matter a lot to the business even if the average gap is small.

### Code: exact-search reference (stdlib only)

Eligibility is applied **before** scoring. In production, `allowed_ids` comes from trusted authorization logic, never a client claim.

```python
from math import sqrt

def cosine(a, b):
    if len(a) != len(b):
        raise ValueError("Embedding dimensions differ")
    na = sqrt(sum(x * x for x in a))
    nb = sqrt(sum(x * x for x in b))
    if na == 0 or nb == 0:
        raise ValueError("Cosine is undefined for a zero vector")
    return sum(x * y for x, y in zip(a, b)) / (na * nb)

def exact_search(rows, query, allowed_ids, k):
    eligible = [r for r in rows if r["id"] in allowed_ids]
    ranked = sorted(eligible, key=lambda r: (-cosine(query, r["vector"]), r["id"]))  # tie policy: id
    return [r["id"] for r in ranked[:k]]

rows = [
    {"id": "A", "vector": [1.0, 0.0]},
    {"id": "B", "vector": [0.8, 0.6]},
    {"id": "C", "vector": [0.0, 1.0]},
]
assert exact_search(rows, [1.0, 0.0], {"B", "C"}, 2) == ["B", "C"]
```

### Code: measuring ANN recall@K

```python
def ann_recall_at_k(exact_ids, approx_ids, k):
    e, a = set(exact_ids[:k]), set(approx_ids[:k])
    denom = min(k, len(e)) or 1          # documented convention for small eligible sets
    return len(e & a) / denom

print(ann_recall_at_k(list("ABCDE"), list("ABDFG"), 5))  # 0.6

def mean_recall(queries, exact_fn, ann_fn, k):
    return sum(ann_recall_at_k(exact_fn(q), ann_fn(q), k) for q in queries) / len(queries)
```

Use the **same** eligibility predicate, embedding version, metric, and tie policy for exact and ANN evaluation.

## Branch 1 Q&A

### A. Theoretical

**Q1 [Junior · Theory] What is the main difference between a vector index and a vector database?**
An index accelerates finding similar vectors. A database stores vectors alongside metadata, handles CRUD, and can enforce access permissions, durability, and replication. Verify which capabilities a given product actually provides.

**Q2 [Junior · Theory] Why not always use exact search if it guarantees the closest vectors?**
At scale, work ∝ N×d per query. With millions of vectors, it crushes CPU/latency budgets for real-time use. (Exception: small eligible sets.)

**Q3 [Mid · Theory] Retrieval returns a semantically relevant passage. Can you guarantee application correctness?**
No. Relevance (tier 2) ≠ application correctness (tier 3). The passage may be outdated, deleted, or unauthorized.

**Q4 [Mid · Theory] Does exact vector search guarantee the right answer?**
No. It finds the nearest eligible vectors under a metric. The embedding may rank irrelevant text highly, and generation can still misuse evidence.

**Q5 [Mid · Theory] How do you compute ANN Recall@K?**
Take exact top-K IDs, take ANN top-K IDs, divide overlap count by K (document the convention if fewer than K eligible).

**Q6 [Mid · Theory] Why is ANN recall different from relevance recall?**
ANN recall compares against the exact result *in the same representation*. Relevance recall compares against human-labeled gold evidence. If the embedding is poor, ANN recall can be ~1.0 while relevance is low.

**Q7 [Junior · Theory] Why do we retain an exact reference system?**
To isolate approximation loss from embedding/chunking/corpus problems, and to have a stable comparator while tuning.

**Q8 [Mid · Theory] Why label counts like `dense_candidate_k` and `final_context_k` separately?**
Because several different "top-k" numbers exist in a pipeline. Without labels you can't tell where a relevant passage was lost.

### B. Situational

**Q9 [Senior · Situational] Your multi-tenant RAG (FastAPI) returns highly relevant chunks, but QA reports occasional cross-tenant leaks. Where is the flaw?**
The system treats similarity as authorization. Tenant boundaries must be enforced by database-level metadata filters or isolated namespaces/partitions, driven by **server-derived identity** (from the auth token), not by vector proximity or a client-supplied `tenant_id`.

**Q10 [Senior · Situational] Exact search gets 60% relevance, ANN gets 59%. The PM wants two weeks of ANN tuning. Agree?**
No. A 1-point gap is negligible. The real issue is that even the exact pipeline is at 60%. Investigate embeddings, chunking, query handling, and document coverage.

**Q11 [Mid · Situational] Exact search finds the relevant chunk for 92% of authorized questions; ANN for 80%. What now?**
That 12-point gap points to approximation. Tune query exploration, then build parameters; compare against a **filtered** exact reference.

**Q12 [Mid · Situational] Why must the exact reference be *filtered*?**
An unfiltered reference may include prohibited or superseded passages that the application correctly excludes, which would make ANN look worse (or better) for the wrong reasons.

### C. Practical (code / hands-on)

**Q13 [Mid · Practical] Write a function to compute recall@K, then explain what the number means when K=10 and result is 0.8.**
See `ann_recall_at_k`. 0.8 means 8 of the 10 exact nearest neighbors were returned by ANN. It says nothing yet about whether those 8 answer the user's question.

**Q14 [Mid · Practical] Design a benchmark harness for exact vs ANN.**
Freeze corpus snapshot, embeddings, metric, and eligibility predicate. Run N representative queries through both; record ANN recall@K, relevance recall@K (gold labels), p50/p95/p99 latency, and memory. Slice by query type (identifiers, conceptual, rare topics, multilingual).

### D. Real-life

**Q15 [Senior · Real-life] A legal-tech product says "our vector DB is 99% recall." What follow-up questions do you ask?**
99% of *what*? ANN recall vs relevance recall? On which corpus, filters, and K? Which tenants/slices? At what p95 latency and memory? Were deleted/unauthorized docs excluded from the reference?

**Q16 [Mid · Real-life] A startup uses FAISS in a notebook and wants to ship it as "the database." What's missing?**
Auth, tenant isolation, metadata storage/filters, durability/backups, replication, update/delete workflow, monitoring, versioned publication.

# Branch 2 — Indexing Algorithms

> *The distinct mathematical models used for ANN.*

## 2.1 HNSW (Hierarchical Navigable Small World)

**Lifecycle connection:** Primary index-construction choice when low latency is required. Original paper: Malkov & Yashunin (arXiv:1603.09320).

### Concept

Organizes vectors into a **multi-level graph**. Search starts in sparse upper layers to leap toward the right region, then descends to dense lower layers to examine nearby candidates closely.

> **Analogy:** Navigating a map: district (upper layer) → street → exact building (dense bottom layer). Real levels are graph links between vectors, not literal districts.

```mermaid
flowchart TD
    Q["Query"] --> L2["Top layer: sparse, long jumps"]
    L2 --> L1["Middle layer: closer hops"]
    L1 --> L0["Bottom layer: dense, all vectors"]
    L0 --> R["Candidate neighbors"]
```

### The three controls

| Control | Influences | Practical question |
|---|---|---|
| `M` (connectivity) | Graph links per node → **memory/index size** | Is the graph connected enough? |
| `ef_construction` | Build-time exploration → **build time/graph quality** | Is a better graph worth longer builds? |
| `ef_search` | Query-time exploration → **latency & recall** | How much latency can retrieval spend? |

### Construction vs querying

- A weakly built graph limits recall; raising `ef_search` can't always fix it economically.
- Rebuilding is unnecessary if a modest `ef_search` increase hits the target.
- **Sensible experiment:** hold `M` and `ef_construction` fixed, vary `ef_search`. If no affordable `ef_search` meets the target, test a higher `ef_construction`/`M` in a **new index generation**.

### Lifecycle risk

A graph that excels on a static benchmark may degrade after months of updates/deletes (tombstones bloat traversal; navigability suffers). **Include update/delete operations in the workload test** and schedule rebuilds/compaction based on measured drift.

### Code: HNSW with FAISS

```python
import numpy as np, faiss

d, n = 128, 100_000
xb = np.random.random((n, d)).astype("float32")
xq = np.random.random((5, d)).astype("float32")

index = faiss.IndexHNSWFlat(d, 32)        # M = 32
index.hnsw.efConstruction = 200           # build-time effort
index.add(xb)

index.hnsw.efSearch = 64                  # query-time effort (tune this first)
D, I = index.search(xq, 10)
```

### Code: HNSW in pgvector (PostgreSQL)

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id bigserial PRIMARY KEY,
  tenant_id text NOT NULL,
  doc_version text NOT NULL,
  status text NOT NULL DEFAULT 'active',
  embedding vector(768)
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- query-time exploration
SET hnsw.ef_search = 100;

SELECT id FROM chunks
WHERE tenant_id = 'tenant-A' AND status = 'active'
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 10;
```

> With an approximate index, a `WHERE` filter may be applied *after* the index scan, which can return fewer than `LIMIT` rows. See [Branch 4](#41-filtering-and-production-storage).

**Memory aid:** HNSW = *navigate a graph, then explore nearby candidates.*

## 2.2 IVF and IVFFlat

**Lifecycle connection:** Alternative index construction, heavily dependent on the shape and clustering of your dataset.

### Concept

- **IVF (inverted file):** partition vector space into regions with representative **centroids**. At query time, compare the query to centroids, pick the nearest lists, and search only those.
- **IVFFlat:** vectors inside the lists remain **uncompressed ("Flat")**. Approximation arises because only some lists are visited; "Flat" does *not* mean all lists are scanned.
- Read index names carefully: **IVFFlat vs IVFPQ** have different compression behaviour.

### Worked example

120,000 vectors in 120 lists; query probes 6 lists. If balanced: ~6,000 vectors inspected instead of 120,000 (≈5%). But real lists are unbalanced, and a true nearest neighbor sitting just across a boundary in an unprobed list is **missed**. More probes → more recall, more work (gain depends on clustering quality and query distribution).

### Training and representative data

Centroids must reflect the data you will search. Training on English policy docs and later ingesting multilingual technical manuals gives poorly fitted clusters.

- Train on a sample covering document types, languages, tenants (where policy permits), and time periods.
- Keep evaluation set **separate** from tuning data.
- Rebuild on **evidence** (list imbalance growth, widening quality gap), not just on a calendar.

### Code: IVFFlat with FAISS

```python
import numpy as np, faiss

d, n, nlist = 128, 120_000, 120
xb = np.random.random((n, d)).astype("float32")

quantizer = faiss.IndexFlatL2(d)                 # holds the centroids
index = faiss.IndexIVFFlat(quantizer, d, nlist)  # nlist = number of lists
index.train(xb)                                  # learn centroids on representative data
index.add(xb)

index.nprobe = 6                                 # lists searched per query
D, I = index.search(xb[:3], 10)
```

### Code: IVFFlat in pgvector

```sql
-- Build AFTER data is loaded so centroids are representative
CREATE INDEX ON chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
SET ivfflat.probes = 10;
```

```mermaid
flowchart TD
    Q["Query"] --> CMP["Compare to centroids"]
    CMP --> P["Pick nprobe nearest lists"]
    P --> S["Scan vectors inside those lists only"]
    S --> R["Candidates (may miss neighbors in unprobed lists)"]
```

## 2.3 HNSW vs IVF Comparison

| Dimension | HNSW-style question | IVF-style question |
|---|---|---|
| Construction | How costly are graph connections? | Is the training sample representative? |
| Query control | How broad is graph exploration (`ef_search`)? | How many lists probed (`nprobe`/`probes`)? |
| Memory | Vectors + graph links | Vectors/codes + list structures |
| Distribution change | Does graph quality hold after updates? | Do centroids still represent the corpus? |
| Filtering | Can eligible neighbors be reached efficiently? | How selective are filters within probed lists? |

This is a **decision framework**, not a claim that one family always wins. Benchmark on **your** workload.

## Branch 2 Q&A

### A. Theoretical

**Q1 [Junior · Theory] How does HNSW skip irrelevant data?**
Sparse upper layers allow big leaps toward the target region; only the dense bottom layer is explored closely around the final neighborhood.

**Q2 [Junior · Theory] What is a centroid in IVF?**
The mathematical center of a cluster of vectors; a representative marker for that list/bucket.

**Q3 [Mid · Theory] Why is IVFFlat "approximate" if vectors aren't compressed?**
Because only a subset of lists is searched; a true neighbor may be in an unsearched list near a boundary.

**Q4 [Junior · Theory] Name the three HNSW controls and what each affects.**
`M` → memory/connectivity; `ef_construction` → build time/graph quality; `ef_search` → query latency/recall.

**Q5 [Mid · Theory] What are the IVF analogues of build vs query effort?**
Build: number of lists (`nlist`/`lists`) and training sample quality. Query: number of probes (`nprobe`/`probes`).

**Q6 [Mid · Theory] Does increasing `ef_search` always improve recall for every query?**
No. It usually helps on average at a latency cost, but it is not guaranteed per query and can plateau if another bottleneck exists.

### B. Situational

**Q7 [Mid · Situational] HNSW recall is too low. Rebuild immediately?**
No. Raise `ef_search` first. Only if no affordable value meets the target, rebuild with higher `ef_construction` or `M` as a new generation.

**Q8 [Senior · Situational] HNSW is perfect on a static benchmark; after 6 months of updates/deletes, latency spikes and recall drops. Why?**
Continuous updates and tombstones degrade graph navigability (bloated traversal, poorly connected regions). Schedule rebuilds/compaction and include churn in benchmarks.

**Q9 [Senior · Situational] IVF trained on English financial reports; a year later multilingual manuals arrive; latency fine, recall terrible. Diagnose.**
Data drift: centroids no longer represent the distribution, so new data sits in poorly fitted clusters. Retrain centroids on a representative sample of the new corpus and measure list imbalance.

**Q10 [Mid · Situational] Which index would you choose for an interactive chatbot with frequent small updates and a generous RAM budget?**
Likely HNSW-style (low latency, incremental inserts), but only after benchmarking update behaviour, memory (vectors + graph), and filtered recall against alternatives.

**Q11 [Mid · Situational] Which for a mostly-static corpus with tight memory?**
IVF-family with quantization (IVFPQ/IVFSQ) is a candidate; add rescoring. Measure.

### C. Practical

**Q12 [Mid · Practical] Write the experiment to tune HNSW `ef_search`.**
Fix corpus, embeddings, `M`, `ef_construction`. For `ef_search` in [16, 32, 64, 128, 256]: compute ANN recall@10 vs filtered exact, relevance recall@10, p95 latency under target concurrency. Choose the cheapest value meeting gates.

```python
for ef in [16, 32, 64, 128, 256]:
    index.hnsw.efSearch = ef
    # run queries -> record recall@10, p95 latency
```

**Q13 [Mid · Practical] Your pgvector IVFFlat index gives poor recall right after a big import. Likely cause and fix?**
The index was built when the table was nearly empty (poor centroids). Rebuild after loading representative data; tune `lists` and raise `probes`.

**Q14 [Mid · Practical] How do you compute IVF work saved?**
Approx fraction scanned ≈ `nprobe / nlist` if balanced (6/120 = 5%). Verify actual list size distribution since imbalance changes this.

### D. Real-life

**Q15 [Senior · Real-life] A product launches in new languages and search quality drops only for those languages. HNSW or IVF?**
Could be either; first check the embedding model's multilingual quality with exact search. If exact is fine but ANN isn't, inspect IVF centroids (drift) or HNSW exploration. Slice metrics by language.

**Q16 [Mid · Real-life] Team copies "M=64, ef=500" from a blog. Evaluate.**
Parameters are workload-dependent. Cost: memory (M) and build time (ef_construction). Validate against own exact reference, latency budget, and memory; don't import benchmark values as standards.

## 3.1 Product and Scalar Quantization

**Lifecycle connection:** The optimization phase, applied when infrastructure cost or memory limits threaten production scaling.

### The memory problem

```
raw vector bytes = N × d × b
```

For N = 1,000,000; d = 768; b = 4 (float32):

```
1,000,000 × 768 × 4 = 3,072,000,000 bytes ≈ 3.07 GB (decimal) ≈ 2.86 GiB
```

This **excludes** metadata, graph links, text, replicas, allocator overhead, and build-time temp space. Vector search runs in **RAM** for speed, which is expensive.

### Scalar Quantization (SQ)

Reduces precision of **each coordinate** (e.g., map [-1, 1] into 256 integer bins). Distinct values can collapse into the same bin. int8 ≈ 1/4 of float32 coordinate storage (plus scaling parameters/alignment overhead in real layouts).

### Product Quantization (PQ)

Split the vector into **subvectors**; replace each with the ID of the nearest **learned codebook** entry.

- 768 dims → 96 subvectors × 8 dims; each subvector stored as 1 byte (256 centroids).
- Code size = **96 bytes** vs 3,072 bytes float32 (~32x), before overhead.
- Toy arithmetic, **not** a guarantee of accuracy or a full memory estimate.

| | Scalar Quantization | Product Quantization |
|---|---|---|
| Unit approximated | Each coordinate | Group of coordinates (subvector) |
| Mechanism | Fewer value levels | Learned codebook IDs |
| Typical compression | ~4x (int8) | Often much larger (e.g., 32x) |
| Analogy | Rounding each number | Replacing a whole phrase with a dictionary ID |

### What compression changes

Rounding error can swap the order of closely scored candidates. **Rescoring pattern:**

1. Retrieve a larger pool (e.g., top-100) with compressed index.
2. Fetch raw/uncompressed vectors (or text) for only those 100.
3. Rescore exactly (or rerank with a text reranker).
4. Pass top results to the LLM.

Rescoring fixes **ordering**; it **cannot recover** a relevant item that never entered the pool.

```mermaid
flowchart TD
    A["Memory limits"] --> B["Quantization"]
    B --> C["Scalar quantization"]
    B --> D["Product quantization"]
    C --> C1["Reduce coordinate precision"]
    D --> D1["Split into subvectors"]
    D --> D2["Map to codebook IDs"]
    D --> D3["Massive RAM savings"]
    B --> E["Rank swapping / accuracy loss"]
    E --> F["Rescoring pattern"]

```

## 3.2 Index Construction and Tuning

**Lifecycle connection:** The deployment-gating phase: prove the index works before production.

### The Index Contract

Record before indexing:

- Embedding model **and revision**
- Query/document encoding conventions
- Dimension and numeric type
- Similarity metric and normalization policy
- Chunking and extraction versions
- Metadata schema and authorization fields
- Index family and build parameters
- Corpus snapshot / generation

Two vectors of equal dimension from different models are **incompatible**. A successful insert doesn't prove meaningful comparison.

### One experiment answers one question

- ❌ Weak: change embedding model + chunk size + HNSW settings + reranker + prompt → "score went up."
- ✅ Strong: hold corpus and representation fixed; vary only query exploration; measure neighbor recovery, relevance retrieval, p95 latency, memory.

### Workload realism

Test short identifiers, conceptual questions, rare topics, multilingual queries, high-selectivity and low-selectivity filters, warm and cold caches, and realistic concurrency. **Never use average latency alone**; use p95/p99 and timeout rate. Break latency into: query embedding, DB retrieval, reranking, source fetch, generation.

### Quality gates (fictional example thresholds, not standards)

| Gate | Example requirement |
|---|---|
| Eligibility | **Zero** unauthorized passages returned in the security suite |
| Approximation | ANN recall@20 ≥ 0.95 on the chosen benchmark |
| Relevance | No material regression on exact identifiers / rare document classes |
| Performance | Retrieval p95 within budget at target concurrency |
| Deletion | Deleted IDs cannot be served after the declared enforcement point |
| Recovery | A failed build leaves the previous valid generation usable |

Vector search is done in RAM for speed. RAM is expensive and raw vectors exhaust it quickly; disk doesn't fix the latency problem.

**Q2 [Mid · Theory] SQ vs PQ?**
SQ reduces precision of each coordinate independently. PQ splits the vector into chunks and replaces each chunk with a codebook ID learned from data.

## 4.1 Filtering and Production Storage

**Lifecycle connection:** Security and application logic. Ensure the right users see only the right data.

### Metadata filtering

A filter restricts eligibility (tenant, current version, language, product, date). Some are optional relevance preferences; others are **mandatory security constraints**. Database predicates (e.g., Qdrant payload filters, SQL `WHERE`) can express them, but security-critical values must be derived from **trusted identity and policy**.

> A user-provided `tenant_id` must **never** decide the security boundary. If an authenticated tenant-A user submits `tenant-B`, the server must not adopt it.

### Pre-, post-, and integrated filtering

| Mode | What it does | Risk |
|---|---|---|
| **Pre-filtering** | Removes ineligible records *before* similarity selection | May need filter-aware index or exact fallback for efficiency |
| **Post-filtering** | Removes ineligible records *after* initial top-K | **Starvation:** top-100 → 98 removed → 2 left |
| **Integrated filtering** | Eligibility checked during index traversal | Implementation-specific; verify behaviour |

A DB may guarantee returned rows satisfy a predicate while still exploring a region full of ineligible rows. **Security and retrieval recall are different properties.**

### The post-filter trap and the forbidden fix

Top-100 contains only 2 tenant-A rows → only 2 results even though tenant A has many useful passages. The tempting fix, *"disable the filter if fewer than 5 results,"* is a **security defect**.

**Valid fixes:**

- Increase bounded exploration (e.g., larger `ef_search`/candidate K, iterative scans where supported).
- Use a filter-aware index.
- Query an **authorized partition/namespace**.
- Run **exact search over the small eligible subset** (small tenant → small N → exact is cheap).

All unauthorized content must stay inside the trusted retrieval boundary: **never** send it to a reranker, embedding provider, LLM, user-facing log, or citation preview. Re-check authorization/deletion state before final emission if state can change mid-request.

### Collections and namespaces

Semantics vary (physical index, logical partition, routing label). Names help organization but become a **security control only when trusted server-side routing and access enforcement prevent unauthorized access**. A client-supplied namespace string is not isolation.

PostgreSQL Row-Level Security illustrates DB-enforced policies, but table owners/superusers/`BYPASSRLS` roles can bypass them. **Test the actual service role.**

## 4.2 Sharding, Replication, and Scaling

**Lifecycle connection:** Infrastructure scaling for enterprise growth and high availability.

### Sharding

Splits data across nodes/partitions to balance storage and compute. Example: shard 1 owns tenants A–F, shard 2 owns G–L; a tenant-A query routes to shard 1.

> **Analogy:** Splitting a book into chapters across desks.

Challenges: balancing *load* (not just record count), correct routing. One huge tenant → **hot shard** while others idle. Hash sharding may balance counts but not traffic.

### Merging results across shards

A global top-10 **cannot** be built from "top-2 per shard." Collect enough candidates from every shard (e.g., 5 shards × top-10 = 50), sort at a **fusion layer** by *compatible* scores, return the true top-10. Dense scores need compatible embeddings/metrics; lexical scores (e.g., BM25) depend on collection statistics. Prefer deliberate fusion/reranking (e.g., RRF) over mixing incomparable numbers.

```python
import heapq

def global_top_k(shard_results, k):
    # shard_results: list of lists of (score, id), higher is better, scores comparable across shards
    merged = (item for res in shard_results for item in res)
    return heapq.nlargest(k, merged, key=lambda x: x[0])
```

### Replication

Stores extra copies for availability and read capacity.

> **Analogy:** A full copy of the book on every desk.

Consistency risk: if a delete reaches the primary before a replica, a replica query must not resurrect the source. Need a current authorization/deletion registry, read-routing policy, or stronger consistency.

### Scaling tradeoffs

| Change | Benefit | Cost / risk |
|---|---|---|
| Add shards | More storage + parallelism | Fan-out cost, routing complexity |
| Add replicas | Read capacity + availability | Storage + update propagation, staleness |
| Compress vectors | Lower memory | Approximation loss, rescoring |
| Lower candidate count | Less retrieval/rerank work | Missed evidence |
| Isolate large tenants | Workload control | More operational units |
| Cache retrieval | Lower repeated latency | Permission, freshness, invalidation |

Infrastructure complexity is a cost even when average latency improves.

## 4.3 Updates, Deletes, Tombstones, and Compaction

**Lifecycle connection:** Cleanup and maintenance; critical for legal compliance (e.g., GDPR) and system health.

### Updates

A document change can alter text, metadata, permissions, or all three.

- Embedded content changed → **re-embed**.
- ACL-only change → update metadata/authorization; vector may stay.
- Record **content version** and **policy (ACL) version separately**, otherwise a "no content change" optimization can skip a permission revocation.

### Tombstones

A **tombstone** is a logical marker (gravestone) that a record is inactive; serving stops *immediately* while physical cleanup is deferred. Physical deletion from graph indexes is slow and heavy.

### Compaction

**Compaction** is an asynchronous background process that reorganizes storage and reclaims bytes from tombstoned vectors. It is **operational, not a compliance guarantee**; privacy and freshness must not depend on its schedule. Suppress tombstoned items at serving time *now*.

### Derived artifacts: the hidden leak

A deleted source may survive in: lexical indexes, extracted text, thumbnails, generated summaries, graph facts/summaries, **query caches, answer caches, long-term conversation memory summaries**, reranker stores, and backups (per retention policy). Track derived artifacts by **source ID + version** so deletion can propagate.

### Versioned publication

For manual M-104: build v4 in a **staging generation**; validate extraction, vectors, metadata, source locators; publish as active only when all required indexes are ready. If publication fails midway, never mix v4 text with a v3 citation locator. Use a **manifest/publication record** stating which generation is authoritative.

## 5.3 Holistic Architecture Notes

**Do vector DBs replace relational DBs?** No. Vector DBs do similarity search over unstructured data; relational DBs give ACID transactions and structured lookups. Extensions like **pgvector** let PostgreSQL do both, which also simplifies joins with ACL tables.

**Heterogeneous data (code, Slack, PDFs) for an agentic system:** don't dump everything into one unpartitioned index. Options: (1) route queries to domain-specific collections with specialized embeddings (e.g., a code model for code, a text model for chat); or (2) use a strong multimodal/general embedding with strict **metadata pre-filtering** by `data_source` so code questions don't pull chatter.

**Atomicity test:** during active batch insert of a new doc version, hammer reads; any hybrid of old metadata + new vector indicates a non-atomic update.

**End-to-end mental model:**

```
Identity (server-derived) -> Eligible set (tenant, ACL, version, status)
  -> Candidate generation (exact / ANN [+ lexical])
  -> Fusion -> Rerank -> Evidence assembly -> Authz/deletion recheck -> LLM
  Lifecycle registry (versions, ACLs, deletions) governs every stage.
```

Inspect each stage: does retrieval contain v4? Does context assembly include it? Does the answer cite it? Errors can occur at any stage; log stage-wise candidate IDs.

**Q4 [Mid · Theory] Why keep content version and ACL version separate?**
So ACL-only changes (permission revocations) are never skipped by "content unchanged" optimizations.

### B. Situational

**Q5 [Senior · Situational] Agentic assistant searches code repos, Slack, and PDFs. How do you design vector representation?**
Separate collections per domain with suited embeddings, or one strong embedding with mandatory `data_source` pre-filters; route queries by intent; evaluate per-source recall.

**Q6 [Senior · Situational] How do you test the atomicity of index updates?**
Concurrent read blast during batch update; flag any mixed old/new metadata/vector result; remediate with staged generation + manifest.

**Q7 [Senior · Situational] Retrieval finds v4 but the answer cites v3. Where's the bug?**
Likely source lookup or context assembly (e.g., resolving locator against the wrong version, cache keyed without version), not the ANN index.

**Q8 [Senior · Situational] User asks an ambiguous question ("what changed in section 7?") with multiple manuals. What does the system do?**
Detect ambiguity (multiple authorized candidates), ask a clarifying question or route via document/version metadata first; avoid guessing across tenants/versions.

### C. Practical

**Q9 [Senior · Practical] Prove tenant isolation for vector retrieval.**
Derive identity server-side; enforce tenant/resource policy before evidence leaves the retrieval boundary; adversarial tests (forged tenant IDs, document IDs, direct lookups, cache probes); inspect reranker and LLM inputs and logs; test revocation mid-request; confirm DB role lacks bypass.

**Q10 [Mid · Practical] Which five artifacts would you deliver to show an index is production-ready?**
Index contract, exact-vs-ANN report, latency percentiles at target concurrency, filter-selectivity matrix, and update/deletion/permission negative-test results.

**Q11 [Mid · Practical] Design logging so you can debug stage-level loss without leaking data.**
Log IDs, versions, scores, and stage names (not raw unauthorized text); store per-stage candidate lists under access control; scrub on deletion.

### D. Real-life

**Q12 [Senior · Real-life] Customers complain the bot quotes a deleted contract clause. Incident response?**
Contain: disable caches for that source, mark deletion in registry, purge derived artifacts. Investigate propagation gap (caches/summaries/memory). Add deletion test to CI; post-mortem; confirm enforcement point and notify per policy.

**Q13 [Senior · Real-life] You must choose between one big shared index with filters vs per-tenant indexes. Decide.**
Depends on tenant count/size, isolation policy, lifecycle (per-tenant delete/export), and cost. Shared+filters is cheaper but needs rigorous filter enforcement and handling of selectivity; per-tenant gives stronger isolation and simple deletion but more operational units. Hybrid: isolate large/high-sensitivity tenants.

**Q14 [Mid · Real-life] Leadership asks which vector DB to pick. How do you answer?**
Define requirements (scale, filters, updates, latency p95, compliance, ops skills); shortlist; run the project harness on your own data; compare exact-referenced recall, latency, memory, operational complexity, cost. Don't rely on popularity.

## Glossary

| Term | Meaning |
|---|---|
| Vector database | Storage + query system supporting vector representations (plus metadata/ops features) |
| Vector index | Structure used to accelerate vector lookup |
| Exact search | Best results under selected metric over the eligible set |
| ANN | Search that may sacrifice neighbor recovery to reduce work |
| ANN recall@K | Overlap of approximate top-K with exact top-K, divided by K |
| Relevance recall | Fraction of human-labeled gold evidence retrieved |
| HNSW | Hierarchical graph-based ANN approach |
| `M` / `ef_construction` / `ef_search` | HNSW connectivity / build effort / query effort |
| IVF / IVFFlat | Partitioned search using inverted lists / with uncompressed vectors in lists |
| Centroid | Representative center of a cluster/list |
| `nlist` / `nprobe` | Number of lists / lists searched per query |
| Scalar quantization | Lower-precision approximation of individual coordinates |
| Product quantization | Codebook approximation of vector subvectors |
| Rescoring | Re-computing exact scores on a shortlist from a compressed search |
| Candidate pool | Items retrieved and available for later refinement |
| Pre-/post-filtering | Eligibility applied before / after similarity selection |
| Filter selectivity | Fraction of records satisfying a predicate |
| Shard / Replica | Partition of the data / additional copy of data |
| Hot shard | Shard overloaded by skewed data or traffic |
| Tombstone | Logical deletion marker |
| Compaction | Background storage reorganization and space reclamation |
| Derived artifact | Cache, summary, graph fact, or memory derived from a source |
| Index generation | Identified version of a built index |
| Index contract | Recorded configuration of embedding, chunking, metric, schema, index params |

## Final Revision Checklist

- [ ] Separate nearest-neighbor recovery (ANN recall) from evidence relevance (relevance recall).
- [ ] Benchmark with identical vectors, metric, permissions, and corpus version; use a **filtered** exact reference.
- [ ] Treat HNSW `M`, `ef_construction`, `ef_search` as different controls; tune `ef_search` first.
- [ ] Treat IVF list count and probes as different controls; train on representative data.
- [ ] Measure compression loss separately from ANN traversal loss; use rescoring for ordering.
- [ ] Include metadata, graph, replicas, and temp build space in memory estimates.
- [ ] Keep security predicates **mandatory**, even when they reduce candidates; never "relax" them to fill results.
- [ ] Derive tenant/identity server-side; test the actual DB role.
- [ ] Merge shard results at a fusion layer using comparable scores.
- [ ] Test updates, deletions, caches, and replicas, not just inserts.
- [ ] Propagate deletes to all derived artifacts; don't rely on compaction for compliance.
- [ ] Preserve source IDs and versions through every derived artifact; publish via manifest/generation.
- [ ] Choose an index based on **measured workload** behaviour, with p95/p99 and slice metrics.

## Multiple-Choice Question Bank

**Easy**

**1. Suitable baseline for measuring ANN approximation loss?**
A. A different embedding model B. Exact search over the same eligible vectors C. Unfiltered web search D. Longer prompt
**Answer: B.** Hold representation, metric, corpus, and eligibility constant.

**2. Which statement about replicas is correct?**
A. They contain different shards B. They eliminate stale reads C. They are copies whose consistency behaviour must be understood D. They remove the need for deletion tests
**Answer: C.**

**Medium**

**3. ANN overlaps 8 of exact top-10. Recall@10?**
A. 0.08 B. 0.20 C. 0.80 D. 1.25
**Answer: C.** 8/10.

**4. Which change specifically tests compression loss?**
A. Replace embeddings and prompts B. Compare original vs compressed representations controlling the rest C. Increase answer length D. Remove metadata filters
**Answer: B.**

**5. Why might exact search be reasonable on a large database?**
A. Large DBs are small in memory B. A mandatory filter may leave a small eligible subset C. Exact always has constant cost D. It needs no metric
**Answer: B.** Database size ≠ per-query eligible set size.

**Hard**

**6. Tenant filtering leaves only 2 of 100 candidates. Best response?**
A. Remove the filter B. Ask the model to ignore unauthorized passages C. Bounded deeper search or authorized partition/exact search D. Include prohibited candidates without citations
**Answer: C.** A model instruction can't repair a disclosure that already occurred.

**7. After deletion, vector search is empty but a cached answer includes the source. What failed?**
A. Cosine similarity B. Deletion propagation across derived artifacts C. Exact search definition D. Need for a reranker
**Answer: B.**

**8. Exact relevance recall is 0.60, ANN is 0.59. Best next step?**
A. Rebuild HNSW B. Inspect representation, query handling, chunking, source coverage C. Remove the eval set D. Claim 99% accuracy
**Answer: B.**

**9. PQ saves memory but the top document fell to rank 15. Best mitigation?**
A. Drop the filter B. Retrieve a larger pool and rescore with raw vectors/reranker C. Lower `ef_search` D. Increase chunk size blindly
**Answer: B.**

**10. A dev changed embedding model, chunking, and index type simultaneously and saw +10%. Verdict?**
A. Merge B. Reject; confounded, require independent tests C. Merge if latency is fine D. Only test the index
**Answer: B.**
