# Part 2 — Architecture, Boundaries and Decision Model

## 2.1 What is this section really solving?

**Problem:** In an AI gateway routing between hosted and local models, it is not enough to say that a model or framework supports **gateway responsibilities**. Engineers must show which data it consumes, which state it changes, which actor authorizes it, how failure is represented and which result counts as success.

**Intended outcome:** Normalize provider integration without hiding semantic differences. The required deliverable is a **gateway route decision log and compatibility matrix**. Its quality is measured with **SLO attainment by route with quality and total cost**, not just a fluent model answer.

**Example:** A model gateway routes a simple extraction to a low-cost model but complex reasoning to a stronger one. To solve this properly, first identify the trustworthy source of the task, then establish the constraint on provider abstraction, and finally verify model routing at a concrete output boundary.

A useful mental model has five independent layers: (1) intent and constraints, (2) trusted and untrusted inputs, (3) application-owned state, (4) actions or computations, and (5) verified evidence. A language model may participate in some layers but should not silently become the owner of identity, payments, tenancy, or other privileged controls.

## 2.2 Reference Architecture and Lifecycle

```mermaid
flowchart TD
  S0["Inspect task and policies"]
  S1["Pick compliant provider"]
  S2["Translate request schema"]
  S3["Execute with metering"]
  S4["Validate response or fallback"]
  S0 --> S1
  S1 --> S2
  S2 --> S3
  S3 --> S4
  S4 --> OK(("Verified outcome"))
  S2 -.-> FAIL["Detected failure / unknown outcome"]
  FAIL --> REVIEW["Reconcile / seek approval / stop"]
```

**How to read the diagram:** Every arrow represents a deliberate state transition. A failed node does not automatically return to the previous node: decide whether the outcome is known, whether the operation can be repeated safely, and whether a human decision is required. The terminal "verified outcome" means the application checked the intended postcondition; generating the answer or sending a request alone is insufficient.

## 2.3 Input, State, Control and Evidence

| Layer | Example in this section | Engineering rule |
|---|---|---|
| Input | Provider abstraction and the current request | Validate its format, scope, age and source |
| Application state | Task ID, tenant, stage, version, previous receipts | Persist what is needed to continue correctly |
| Computation / tools | Model routing in a bounded execution path | Use typed contracts and explicit error handling |
| Authority | User permissions, policy checks, approval status | Enforce independently of retrieved text or model output |
| Result | gateway route decision log and compatibility matrix | Verify the resulting state before reporting completion |
| Measurement | SLO attainment by route with quality and total cost | Define a repeatable denominator and test dataset |

For **gateway responsibilities**, avoid conflating data that the model reads with state that the service must remember. If a source, agent or API changes its mind, the application should reconcile the conflict explicitly. The safest design makes state transitions observable and reproducible.

## 2.4 Architecture Choices and Tradeoffs

| Approach | When appropriate | Benefits | Limitations |
|---|---|---|---|
| Deterministic code | Rules for provider abstraction are stable and testable | Cheap, inspectable, fast | Cannot resolve poorly structured ambiguity alone |
| Typed workflow | Several steps with clear dependencies and failure paths | Explicit transitions and checkpoints | Adds orchestration and state management |
| Single agent with tools | Inputs vary and tool choice needs model interpretation | Flexible reasoning under limits | More evaluation, cost and authorization risk |
| Multiple agents / external services | Independent specialties show measured benefit | Parallel expertise and independent scaling | Handoffs, duplicated work, trust and coordination overhead |

**Recommended default:** Start with deterministic checks and a typed workflow. Introduce a model for the genuinely ambiguous parts only after establishing a baseline. This principle applies even when the roadmap discusses specialized agent frameworks, multimodal interfaces or new protocols.

## 2.5 Explicit Decision Contract

Before choosing an implementation, write the following decisions down:

1. **Task boundary:** What does "done" mean for gateway responsibilities? Which operations are explicitly excluded?
2. **Inputs and provenance:** Which fields support Provider abstraction and Model routing? Who supplied them and when?
3. **Authority:** Who is permitted to start, approve, inspect, cancel or replay the operation?
4. **State ownership:** Which fields must survive a restart? Which data should expire?
5. **Limits:** What are the maximum time, attempts, spend, token count or other resource ceilings?
6. **Verification:** Which independent test proves the output or side effect occurred?
7. **Recovery:** What happens if the process fails after the external operation completes?

# Part 3 — End-to-End Worked Example

## 3.1 Scenario, assumptions and scope

**Scenario:** A model gateway routes a simple extraction to a low-cost model but complex reasoning to a stronger one.

Assume a single authorized company, a fixed development test dataset and one operator who can review uncertain outcomes. Use fake or sandbox accounts for destructive or financial actions; do not assume screenshots, model scores or network acknowledgements are the same as final state.

**Inputs:** A task ID, authenticated tenant/user, a goal, relevant source references, resource budget, policy version and any human approvals. **Outputs:** A result artifact, a trace of meaningful decisions, a terminal status and a list of unresolved facts. **Failure state:** Errors and unknown external outcomes are stored explicitly instead of being hidden behind "success".

## 3.2 Lifecycle stages and handoffs

| Stage | Task-specific question | Evidence / postcondition |
|---|---|---|
| 1. Inspect task and policies | How does **Provider abstraction** affect this stage? | Log stage outcome, resource scope and gateway route decision log and compatibility matrix. |
| 2. Pick compliant provider | How does **Model routing** affect this stage? | Log stage outcome, resource scope and gateway route decision log and compatibility matrix. |
| 3. Translate request schema | How does **Fallback** affect this stage? | Log stage outcome, resource scope and gateway route decision log and compatibility matrix. |
| 4. Execute with metering | How does **Prompt transformation** affect this stage? | Log stage outcome, resource scope and gateway route decision log and compatibility matrix. |
| 5. Validate response or fallback | How does **Response normalization** affect this stage? | Log stage outcome, resource scope and gateway route decision log and compatibility matrix. |

The stage handoff should be a typed record rather than free-form prose alone. For example, a retrieval stage might emit source IDs, scores and ACL checks; an execution stage should return the operation ID, external receipt and confirmed status. This makes it possible to replay, resume, debug and inspect exactly which stage produced the bad result.

## 3.3 Minimal domain-neutral state record

```json
{
  "task_id": "demo-task-001",
  "tenant_id": "demo-tenant",
  "section": "M30.1",
  "status": "running",
  "policy_version": "policy-v1",
  "state_version": 1,
  "attempt_count": 1,
  "source_ids": ["source-example-1"],
  "approval_status": "not_required",
  "external_action_id": null,
  "verified": false
}
```

The example deliberately omits passwords, API keys, private records and full prompt content. Your real schema should include only necessary fields. Store large artifacts in controlled object storage and keep stable references in the task record, rather than placing unlimited blobs in state or model context.

## 3.4 Expected outcomes and acceptance criteria

A credible demonstration for **M30.1** shows that **Provider abstraction** and **Model routing** are implemented with visible state boundaries. The successful path creates gateway route decision log and compatibility matrix. The negative path rejects unauthorized, malformed or stale input. The recovery path stops or resumes without duplicating a business operation.

**Measurable success:** Slo attainment by route with quality and total cost. Capture the baseline first, then compare the improved design using the same fixtures and denominators. When results depend on model sampling, repeat cases and inspect important slices rather than reporting a single average.

# Part 4 — Engineering Implementation and Code

## 4.1 Implementation sketch

The following example illustrates one boundary from the wider **M30** module. It is not a turnkey production implementation of every concept in **M30.1**; adapt its types, tests and runtime to the selected task.

```python
from dataclasses import dataclass
@dataclass(frozen=True)
class RequestPolicy:
    privacy: str
    max_cost_usd: float
    requires_tools: bool

def choose_route(p: RequestPolicy, routes: list[dict]):
    eligible = [r for r in routes if r["privacy"] == p.privacy
                and r["estimated_cost"] <= p.max_cost_usd
                and (not p.requires_tools or r["tool_support"])]
    if not eligible: raise RuntimeError("No authorized route")
    return min(eligible, key=lambda r: r["estimated_latency_ms"])

# Quality and schema compatibility must also be evaluated per route.
```

## 4.2 Apply the sketch to this section

For **M30.1**, extend the sketch to cover these concrete capabilities:

- **Provider abstraction:** Specify valid/invalid inputs and which component owns the decision. Add a negative test that intentionally violates the rule.
- **Model routing:** Record a receipt, source reference or measurable state transition, depending on whether the feature is data processing or an external action.
- **Fallback:** Apply a permission boundary and add a test that tries to cross it.
- **Prompt transformation:** Handle cancellation, retry and timeout without hiding partial completion.
- **Response normalization:** Produce a trace that links this stage's result to the overall task and schema version.

The minimal implementation should remain easy to inspect. A file that only calls an LLM API without validating inputs, recording state or checking the result is an API demo—not completion evidence for a production engineering module.

## 4.3 Component contracts and ownership

| Component | Responsibility | Must not assume |
|---|---|---|
| Request adapter | Authenticate, parse and bind tenant | Caller-provided tenant IDs are trustworthy |
| Coordinator | Own workflow state and status | A model response equals task completion |
| Tool/data adapter | Enforce resource permissions and typed schema | The model may authorize itself |
| Policy/approval service | Allow, deny or request approval with reason | Natural-language permission is sufficient |
| Artifact store | Save versioned output and provenance | Temporary files are durable |
| Evaluation harness | Test outputs and final external state | A single successful run proves reliability |

## 4.4 Production checklist for the implementation

**Before deployment:** Define threat boundaries, pin external dependencies, keep credentials out of model context, select an owner, establish retention, and create a known-good rollback. For gateway responsibilities, specifically verify the interactions between **Provider abstraction**, **Fallback** and **Response normalization**. Also define the response when a downstream service reports an unknown commit.

**During execution:** Record correlation IDs, bounded counts and reasons for tool selection or branching. Enforce timeouts and keep independent verification for important actions. **After execution:** Persist approved output, clean up temporary workspaces, and measure SLO attainment by route with quality and total cost.

# Part 5 — Failure Modes and Troubleshooting

## 5.1 Failure taxonomy

**Primary risk for this module:** Fallback provider accepts request but changes tool-call behavior. A recommended baseline defense is to behavioral contract tests, typed adapters and quality-sensitive fallback. This is not the only possible failure: even a well-designed policy gate can fail when state, source versions, external receipts or tool permissions are inconsistent.

| Symptom | Likely cause | First diagnostic check | Safer response |
|---|---|---|---|
| Provider abstraction gives inconsistent results | Stale input, weak contract or hidden default | Compare source and schema versions | Reject, refresh or reconcile before continuing |
| Model routing fails after partial work | Timeout or unknown external commit | Inspect action ID and external receipt | Avoid blind retries; use idempotency/reconciliation |
| Fallback crosses an access boundary | Missing resource-level policy check | Trace actor, tenant, action and resource | Contain access, revoke credentials, add regression |
| Prompt transformation becomes too costly | Unbounded loops, fan-out or expensive model | Check per-task attempts, tokens and spend | Stop at budget and escalate or degrade |
| Response normalization looks correct but is wrong | No independent postcondition verification | Review real state and source evidence | Mark uncertain, repair test and avoid false success |
| A new release breaks old tasks | Incompatible state or interface version | Compare manifests and release revisions | Roll back or migrate with compatibility tests |
| A monitoring dashboard says 'green' but users complain | Metric measures response, not outcome | Compare SLI to user-visible postcondition | Add outcome-based signal and failure slice |

## 5.2 Failure exercise A — Unknown outcome after timeout

An operation involved in **Model routing** returns a timeout. The request may have reached the external provider. If the workflow immediately retries with a new identifier, it could create a duplicate write or charge. A safer sequence is: preserve the task/action ID, classify the outcome as unknown, query the external system for a receipt, replay only using a supported idempotency key, and request human review when reconciliation is impossible.

**Expected evidence:** two runs with the same business-action identifier produce at most one accepted business effect, and both runs have a clear recorded outcome. For read-only operations, demonstrate bounded retry and consistent source-version handling instead.

## 5.3 Failure exercise B — Stale or poisoned context

A retrieved source or old checkpoint contains an instruction contradicting the active rules. Test whether the application treats source text as untrusted and obtains policy decisions from the correct component. **Fallback** should be handled as data only where its source is not authorized to instruct the agent.

**Expected evidence:** the system retains current constraints, records the untrusted source ID and either answers from verified evidence or abstains. No tool permission should be inferred from the content of a document or message.

## 5.4 Failure exercise C — Unbounded resource use

A task repeatedly invokes **Prompt transformation** but makes no measurable progress. The runtime must count failed attempts and retries in its global budget. Separate transient errors from permanent invalid inputs; use exponential backoff only for safe retries, and stop with an actionable error when the limit is reached.

**Expected evidence:** bounded step count, cost and duration; recorded reason for termination; and no orphaned privileged workers after cancellation.

## 5.5 Failure exercise D — Misleading success report

The model writes "completed", but the application has not verified **Response normalization** or the final artifact. Require the independent postcondition before setting a terminal success state. For human approvals, verify that approval applies to the same resource version and action payload that will actually execute.

**Expected evidence:** a simulated false-success message remains `failed`, `pending`, or `unknown` until the relevant state check passes.

## 7.2 Glossary: foundational terms


1. **Provider abstraction:** Adapter interface that reduces superficial API differences without assuming providers behave identically.

2. **Model routing:** Selection of model/provider using task complexity, privacy, latency, cost and measured quality constraints.

3. **Fallback:** Switch to an alternate authorized provider, tool or workflow after defined failure.

4. **Prompt transformation:** Convert internal request structure into provider-specific input conventions while preserving instruction hierarchy and content semantics.

5. **Response normalization:** Map provider responses into a stable application schema while surfacing unsupported features, refusals and errors.

6. **Rate limiting:** Limit requests or work performed by principal, tenant, tool or destination to protect reliability and fairness.

7. **Quotas:** Consumption limits over a time period or resource group.

8. **Cost attribution:** Assign model and tool usage to a specific task, user/tenant and feature with consistent retry accounting.

10. **Logging:** Emit structured, correlated evidence of behavior and outcomes.

11. **Policy enforcement:** Evaluate authorization, data handling and spending constraints before routing or executing a request.

12. **Responsibilities:** In this part of an AI gateway routing between hosted and local models, **Responsibilities** is an explicit design concern.

# Part 11 — Senior / Staff-Level Production Scenarios

## 11.1 Scenario — Stale decision during a policy change

**Situation:** A workflow dealing with **Provider abstraction** began under an older policy. During execution the governing rule or permitted resource scope changes. The model still sees the previous description and proposes to continue.

**Expected diagnosis:** Inspect policy versions, who initiated the task, which evidence was cached and where authorization is actually checked. **Containment:** prevent privileged actions from proceeding on a stale approval. **Recovery:** re-evaluate current policy, invalidate stale context or state references, obtain new approval where necessary and record the decision. **Regression:** repeat the test with the policy updated between planning and execution.

**Interview takeaway:** Approvals and permissions must be bound to the exact actor, target, action payload and version; prompt summaries do not supersede active policy.

## 11.2 Scenario — Crash immediately after a side effect

**Situation:** An action related to **Model routing** commits in a downstream system. The worker crashes before recording a success checkpoint. On restart, the workflow appears unfinished.

**Expected diagnosis:** Look for a business action ID, idempotency key and provider receipt. **Containment:** do not send a second non-idempotent action. **Recovery:** query external state, persist the confirmed receipt or unknown status and resume from a safe boundary. **Regression:** kill the worker between action and checkpoint, rerun the same task ID and assert one business effect.

**Interview takeaway:** Checkpointing and exactly-once effects are separate contracts. Recovery must reconcile the external world, not only replay local steps.

## 11.3 Scenario — A new version passes tests but degrades one tenant

**Situation:** After an upgrade, aggregate success remains stable, but a subset of users sees failures involving **Fallback** and **Prompt transformation**. The new implementation uses a different cache key, contract or evaluation distribution.

**Expected diagnosis:** Compare request traces across versions and tenants; inspect data scope, schema changes, cache invalidation and per-slice metrics. **Containment:** revert or disable the affected route. **Recovery:** update migration and compatibility tests and recalibrate any thresholds on a fixed dataset. **Regression:** preserve affected tenant-safe fixtures without exporting private data.

**Interview takeaway:** A single global score hides critical slices. Track versions and accepted outcomes, not only latency and error-free transport.

## 11.4 Scenario — Leadership asks for full automation tomorrow

**Situation:** Stakeholders want the feature in **gateway responsibilities** to operate without human review. They have only a successful demo and no evidence for authorization, failure recovery or spend control.

**Recommended response:** Identify which actions are read-only and which affect external state. Propose graduated autonomy: deterministic validation first, supervised tool actions next, and narrowly scoped autonomy only after measured success. Define an approval matrix, a kill switch, an operations owner, and a controlled rollout with a rollback path. Show a test report covering SLO attainment by route with quality and total cost and the top risks before increasing privileges.

**Interview takeaway:** Autonomy is an engineering decision supported by testable boundaries and business evidence, not a default requirement of an agent project.
