```text

calculate_emi(principal, rate, tenure)

calculate_simple_interest(principal, rate, time)
```

**Initially: No.**

```text

+
```

# Example

User says:

> "If my salary is ₹50,000 and I get a 15% raise, then pay 10% tax, what will I receive?"

The **agent** does this:

### 1. Understand the task

```text
Salary = 50,000
Raise = 15%
Tax = 10%
```

### 2. Create a plan

```text
Step 1 → Calculate salary after raise
Step 2 → Calculate tax
Step 3 → Subtract tax
```

### 3. Call calculator tools

```text
calculate(50000 * 1.15)
→ 57500

calculate(57500 * 0.10)
→ 5750

calculate(57500 - 5750)
→ 51750
```

### 4. Return an understandable answer

```text
Original salary: ₹50,000

After 15% raise: ₹57,500

10% tax: ₹5,750

Final amount: ₹51,750
```

# The key difference: Normal Calculator vs Calculator Agent

| Normal Calculator        | Calculator Agent             |
| ------------------------ | ---------------------------- |
| User enters formula      | User speaks naturally        |
| `50000 * 1.15`           | "Increase my salary by 15%"  |
| One calculation          | Can perform multiple steps   |
| No reasoning about task  | Plans the calculation        |
| Fixed UI                 | Conversational               |
| Limited workflow         | Can use multiple tools       |
| Doesn't remember context | Can maintain session context |

## Core flow

```text
User Message
     ↓
LLM
     ↓
Does it need calculation?
     ↓
   YES
     ↓
Select appropriate tool
     ↓
Execute deterministic calculation
     ↓
Validate result
     ↓
LLM explains result
     ↓
User
```

The important principle is:

> **The LLM should understand and orchestrate the problem, but the actual mathematical calculation should usually be performed by a deterministic tool.**

So a calculator agent is essentially:

```text
LLM
+
Tool Calling
+
Calculator Engine
+
Planning
+
Validation
+
Conversation Memory
```
